# zoe-py

The Python extension module `zoe._zoe`, built by maturin into the `zoedb` wheel. Specification: "In-process mode".

## Layout

- `src/storage.rs`: `zoe._zoe.Storage`, a frozen pyclass that Python can subclass. It implements the `IStorage` methods that ZODB's `MVCCAdapter` calls.
- `src/errors.rs`: the mapping of core errors to the exceptions of ZODB and to `zoe.WrongThread`, and of the errors that stop a pack.
- `src/publish.rs`: the publication of commits, in commit order.
- `src/sequence.rs`: `zoe._zoe.Sequence`, which `Storage.sequence(name)` returns.
- `src/client.rs`: `zoe._zoe.Client`, the native client of `zoe.zeo.ClientStorage`, on `zoe-client`, and the tokio runtime of the native clients. ADR 0035 records the decision.
- `src/signals.rs`: the handlers of SIGTERM and SIGHUP, the watcher thread that closes the open storages of the process at a signal, and the at-fork hook. ADR 0031 records the design.
- `python/zoedb/src/zoe/component.xml` and `python/zoedb/src/zoe/config.py`: the `<zoe>`, `<zoeclient>` and `<zoe-server>` sections of ZConfig and the `zoe://` URI of zodburi.
- `python/zoedb/src/zoe/zeo.py`: `zoe.zeo.ClientStorage`, the client of a ZOE server, in Python, and `_NativeClientStorage`, the same class with the native client inside.
- `python/zoedb/src/zoe/serve.py`: `python -m zoe.serve`, which runs the `zoe` binary with the `<zoe-server>` section.
- `src/cli.rs`: `zoe._zoe.main`, the `zoe` command of the console script.
- `python/zoedb/src/zoe/__main__.py`: `zoe.__main__.main`, the entry point of the console script `zoe` and of `python -m zoe`.
- `python/zoedb/src/zoe/storage.py`: `zoe.storage.Storage` subclasses `zoe._zoe.Storage` and ZODB's `ConflictResolvingStorage`, declares `IStorage`, `IBlobStorage`, `IStorageIteration`, `IStorageCurrentRecordIteration`, `IStorageRestoreable`, `IBlobStorageRestoreable` and `IExternalGC`, and adds `tpc_vote` with the conflict resolution, `openCommittedBlobFile`, `history`, `iterator`, `copyTransactionsFrom`, `pack`, `registerDB` and `supportsUndo`. It defines `WrongThread`.

## Invariants

- The module declares that it does not use the GIL, so that the GIL stays off when CPython 3.14t loads it.
- `import zoe` does not import ZODB. `zoe.Storage` and `zoe.WrongThread` load `zoe.storage` at first use. The extension imports an exception class of ZODB only when it raises it.
- Every call into the core runs inside `py.detach`: it releases the GIL, and on a free-threaded build it holds nothing.
- No mutex of the core or of this module is held while Python code runs. A lookup under a mutex binds its result to a local before it builds an exception, because building an exception runs Python code. A mutex that can wait, such as the mutex of a transaction entry during a vote, is taken only inside `py.detach`. A Python reference is dropped outside every mutex. The per-OID locks of a vote are not mutexes: they stay held while `_p_resolveConflict` runs.
- The last reference to the store drops without the GIL, so the database closes without it: each call moves its reference into the detached closure, `close` drops the store there, a storage that Python frees without `close` closes its store detached too, and the watcher of the signals, which never attaches, drops it in its thread.
- `zoe.Storage` is thread-safe and all Connections of a process share it.
- A table keyed by the address of the ZODB transaction object holds one core transaction (`Txn<StoreRef>`, which shares the store) per `tpc_begin`. The entry keeps the object alive, so no other object gets its address while the entry exists.
- A second `tpc_begin` of a transaction, or a call with a transaction that the storage did not begin, raises `StorageTransactionError`. `tpc_abort` of an unknown transaction does nothing.
- The thread that calls `tpc_begin` drives the transaction. `store`, `deleteObject`, `restore`, `storeBlob`, `restoreBlob`, `checkCurrentSerialInTransaction` and `tpc_vote` from another thread raise `zoe.WrongThread`, a subclass of `StorageTransactionError`. The core checks the thread, so a refused call changes nothing. `tpc_finish` and `tpc_abort` work from any thread.
- `temporaryDirectory()` is `tmp` in the blob directory, the `blobs/tmp/` of the core. The call creates the blob store when it does not exist.
- `storeBlob` takes a file of `temporaryDirectory()`, or of one of its subdirectories, by rename, never by copy: it calls `store_blob_at` of the core, which keeps the crash rules of the core. A Connection writes its new blobs there, and a savepoint moves them into a subdirectory there. The directory of the file and the temporary directory compare by their real paths. A file from elsewhere is copied into a new blob file of the core, then removed once the copy is staged. A file of the store directory or of the blob directory outside `tmp`, such as `zoe.redb` or a committed blob file, is refused with `StorageTransactionError`, so a wrong path never removes a file of the store.
- A refused `storeBlob` leaves the file in its place: the core checks the transaction before it takes the file. A file that the transaction took belongs to it: `tpc_abort`, `close` and an error after the take remove it.
- `loadBlob` returns the path of a read-only file in the blob directory, from the blob record. A serial that wrote no blob for the oid raises `POSKeyError`, and so does a blob record whose file is missing, as in ZODB's blob storages. `openCommittedBlobFile` opens that path, as ZODB's blob storages do: it checks no hash.
- The store opens with the absolute form of `path`, so the blob paths do not depend on the current directory.
- `blob_dir` goes to the core as `Options::blob_dir`; `None` is `<path>/blobs`. The core keeps the blob files, their temporary directory and every rename there, and every sync goes through its `Vfs`. The store does not record its blob directory, so each open must give the same one: a store with blob records refuses a blob directory without a layout file with `MissingBlobDir`, which is `StorageError`. Two open storages never share a blob directory: the core locks it, and the second open raises `StorageError`. The core checks `blob_dir` before it creates anything, so a refused `blob_dir` leaves no store directory, no `zoe.redb` and no lock file. A read-only storage refuses a `blob_dir` whose parent directory is missing with `FileNotFoundError`, as it refuses a missing store directory.
- `tpc_begin(transaction, tid, status)` with a `tid` begins a restore transaction, which commits under `tid`, as ZODB's copy functions call it. `tid` must be after the last tid of the store, else `tpc_begin` raises `StorageTransactionError`. `restoreBlob` stages a copy of a version with its blob there: it calls `restore_blob_at` or `restore_blob` of the core and takes the file as `storeBlob` does. The previous serial is the current serial of the store, so `serial` and `prev_txn` are not used. A change of the oid before the vote raises `ConflictError`, and the vote never resolves it. `status` takes `" "` and `"p"`, as text or bytes, and any other status raises `StorageTransactionError`. The store keeps no transaction status, so the `"p"` of a transaction that a pack changed is not kept: a copy back to another storage gives `" "`.
- `restore` stages a copy of a version in a restore transaction: it calls `Txn::restore` of the core. `data` of `None` copies a deletion. As for `restoreBlob`, the previous serial is the current serial of the store, so `serial` and `prev_txn` are not used, and a version raises `Unsupported`. Outside a restore transaction, `restore` raises `StorageTransactionError`.
- `deleteObject(oid, oldserial, transaction)` is the `deleteObject` of ZODB's `IExternalGC`. It calls `Txn::delete` of the core, which stages a record with an empty pickle. `oldserial` takes what the serial of `store` takes. The vote checks it as for `store`: a stale serial raises `ConflictError`, and the vote never resolves it. A call after the vote raises `StorageTransactionError`. The class declares `IExternalGC`, and `get_info` of `zoe serve` lists the interfaces of `zoe.Storage`, so a stock `ClientStorage` provides it too. It never declares `IStorageUndoable`.
- `iterator(start, stop)` gives the transactions from `start` to `stop`, both included, up to the last tid of the core at the time of the call. The extension method `_iterator` calls `Store::iterator`, which reads the oids of each transaction from the transaction index: it holds one transaction and a slice of tids at a time, whatever the length of the range. `zoe.storage.Storage.iterator` makes ZODB's `TransactionRecord` with the status `" "` and the extension as bytes, and `DataRecord` with `data_txn` `None`. A deletion has `data` `None`. The iterator holds only a weak reference to the store: after `close`, its next call raises `StorageError`.
- `record_iternext(next)` gives the current record of the first oid at or after `next` that has one, and the next such oid or `None`. It skips a deleted object. When no oid at or after `next` has a current record, it raises `ValueError`, as FileStorage does.
- `copyTransactionsFrom(other)` copies each transaction of `other.iterator()` in a restore transaction under its tid, with its status, `restore` for a record and `restoreBlob` for a blob record whose file `other` has. It copies the blob file into `temporaryDirectory()`, so `restoreBlob` takes the copy by rename and the file of `other` stays. An error aborts the transaction, removes a copy that `restoreBlob` did not take and closes the iterator of `other`. `zodbconvert` calls it on the destination. ZODB's own `copyTransactionsFrom` of FileStorage reads this storage through `iterator` and `loadBlob`.
- A read-only storage refuses `restore`, `deleteObject`, `storeBlob`, `restoreBlob` and `temporaryDirectory` with `ReadOnlyError`. `loadBlob` and `openCommittedBlobFile` work.
- `zoe.Storage` resolves conflicts in this process, as ZODB's `ConflictResolvingStorage` does. `tpc_vote` calls `_vote_resolving`: the core takes the locks and, when each stale written oid can be resolved, keeps them and returns each oid with its committed serial and pickle. For each oid, `tryToResolveConflict` runs the `_p_resolveConflict` method of the class, and `tpc_vote` stores the result over the committed serial. Then it calls `tpc_vote` of the extension, which checks the serials again with the same locks. `tpc_vote` returns the resolved oids, or an empty list.
- A conflict that does not resolve raises the `ConflictError` of `tryToResolveConflict`, with `oid`, `class_name` and `serials`. If ZODB cannot read the class name from the pickle, the error comes without it. A read-current conflict is never resolved: it raises `ReadConflictError`.
- A staged pickle that the core cannot read back from its spill file fails `_vote_resolving` with `StorageError`, whose cause is the error of the core. `_vote_resolving` aborts the transaction first, so the locks are free when the error leaves `tpc_vote`. The error is not a `ConflictError`, so ZODB does not retry the transaction.
- Any error between the first vote and the end of the second vote, an asynchronous one included, makes `tpc_vote` call `tpc_abort` before it raises. So the locks are free when the error leaves `tpc_vote`, and the transaction is never left voted. The later `tpc_abort` of ZODB does nothing.
- While `_p_resolveConflict` runs, `tpc_abort` from another thread and `close` take the transaction, because no call holds its mutex. They release the locks at once. The resolving `tpc_vote` then raises `StorageTransactionError`.
- `registerDB` hands the database to `ConflictResolvingStorage`, so the resolution uses the record transforms of the database.
- `tpc_finish` runs its callback after the commit is durable. A commit is published when its callback has run. Callbacks run in commit order: a commit waits until the commit before it is published. A failed or panicking callback still publishes its commit.
- A callback cannot commit in its own storage: that `tpc_finish` raises `StorageTransactionError` before it commits, because its commit would wait for the callback that runs it. A thread-local list of the storages whose callbacks run tells this.
- A `ConflictError` on a stored object gets the stored pickle as `data`, so ZODB fills its class name. If ZODB cannot read the pickle, the error comes without `data`. `_vote_resolving` first applies the `_crs_untransform_record_data` of the database to the pickle, so the class name comes from the pickle and not from the transformed record. A record that does not untransform gives no `data`.
- `lastTransaction` gives only a published tid. It waits until the last tid of the core is published. A callback that calls it does not wait and gets the tid before its own commit.
- A read-only storage refuses `tpc_begin`, `new_oid`, `store` and `pack` with `ReadOnlyError`. It does not create a missing directory. It does not use the read-only open of the core: it opens the store for writes and takes the exclusive lock.
- `close` marks the table closed and aborts the open transactions. A `tpc_begin` that read the store before the close finds the mark when it inserts its entry, aborts its transaction and raises `StorageError`. So no transaction keeps the store open after `close`, and the directory lock is free when no call is in progress. A second `close` does nothing. A call on a closed storage raises `StorageError`, the blob calls too.
- `close` aborts the transactions that no call uses first. Their locks go, so a vote that waits for one of them ends at once, and `close` does not wait for a lock timeout.
- `Storage.sequence(name)` returns a `zoe._zoe.Sequence` for the sequence `name` of the store. Its `next()` returns an `int`. It is not part of a ZODB transaction: it takes no transaction entry and no per-OID lock, and an abort does not give the value back. The `Sequence` holds the storage, not the store, so `next` reads the store as the other calls do: after `close`, `sequence` and `next` raise `StorageError`. `next` runs inside `py.detach`. A read-only storage refuses `next` with `ReadOnlyError`. `Sequence.__traverse__` reports the storage to the garbage collector, so a cycle such as `storage.x = storage.sequence(name)` is collectable. `Sequence` has no `__clear__`, because it is frozen: the collector breaks the cycle at the attributes of the storage.
- `__len__` returns `Store::object_count` of the core: the oids that have a record, a deletion included, as the `len()` of FileStorage. A closed storage gives 0, so the truth value of a storage never raises. The storage opens the store for writes in the core, also when it is read-only, so the open upgrades a store of `ZOE format 1` and the count exists. `getSize` is the size of the files in the store directory. `getName` and `sortKey` are the canonical path of the directory.
- `pack(t, referencesf)` turns `t` into a tid as ZODB's own storages do: `TimeStamp(*time.gmtime(t)[:5] + (t % 60,))`. Then `_pack` runs `Store::pack` at that tid. The pack keeps every record after the tid and, for each object that a reader at the tid or later can reach, the newest record at or before it. `pack` never calls `referencesf`: the core reads the references in the pickles.
- `Storage(path, pack_gc=False)` gives `Options::pack_gc` false to the core: a pack then keeps the newest record at or before the tid of each object, also when no reader can reach the object, and reads no reference. An object whose newest record at or before the tid is a deletion goes. `pack_gc` is true by default. The store does not record it, so each open gives it.
- `_pack` runs the whole pack inside one `py.detach`, so the GIL is free from start to end. The pack takes no per-OID lock and does not wait for a publication. Other threads read and commit while it runs: a commit waits for at most one batch of the pack. A second pack waits for the first. A pack can run from any thread, also while a transaction of that thread is open.
- A pack at a time before the last pack does nothing. A pack at a time after the last tid packs at the last tid.
- A closed storage refuses `pack` with `StorageError`. A pack in progress keeps the store open after `close` until it ends, as any call in progress does.
- `supportsUndo()` is false.
- The wheel never imports Plone. Only `zoe.plone`, through the `plone` extra, does.
- The version of the wheel equals the version of the crates.
- The wheel has one console script, `zoe`, on `zoe.__main__:main`. It runs `zoe._zoe.main(sys.argv)`, which runs `zoe_server::cli::main`, the code of the `zoe` binary, inside `py.detach`. The console script has no parser of its own. ADR 0028 records this.
- The extension depends on `zoe-server` without the feature `serve`, so it never links the server or rmcp. `cargo tree -p zoe-py -e normal` must not list rmcp. It lists tokio, which comes through `zoe-client` and the native client (ADR 0035).
- `zoe.__main__.main` restores the default SIGINT handler before it calls the extension. The command runs without the GIL, and Python handles a signal only when it runs Python code. So Ctrl-C stops the console script at once, as it stops the binary.
- The command writes its report and its messages to the file descriptors 1 and 2 of the process, not to `sys.stdout` and `sys.stderr`.
- A change to a public Python API is a stop-and-ask.
- `_lock_table_is_empty()` tells if no transaction of the core holds or waits for a lock. It is a private hook for the tests, not a public API.

## The close at SIGTERM and SIGHUP

- When `zoe.Storage` opens a store, read-only too, the extension installs a handler of SIGTERM and one of SIGHUP, each only when `signal.getsignal` gives `signal.SIG_DFL` for that signal. A return of `None`, a handler that Python did not install, is not the default: the extension then installs nothing for that signal. zoe-py has no `unsafe` code and no `libc` for this check. An ignored signal and a handler of the application keep their action.
- The extension installs each handler at most once per process. Each later open checks again a signal that has no handler of the extension yet.
- The handler of signal-hook only writes to a pipe. The first install registers the at-fork hook, then starts one watcher thread per process, `zoe-signals`, which reads the pipe.
- The watcher never attaches to the interpreter: it runs no Python code, takes no GIL and drops no Python reference.
- The store and the table of a storage live in `Shared`, which the storage holds in an `Arc`. The process keeps a list of `Weak<Shared>`, one for each storage that opened. The store is a `StoreRef`: a share of the store. The drop of the last share sets the flag `database_closed` of `Shared` after the store drops.
- The watcher does not wait for a read through a weak handle of the core: a read of the iterator of `_iterator` or of a blob file. Such a read holds the redb database, not a share of the store. When the store drops during such a read, the watcher raises the signal at once, and the store stays unclean. The repair on open (ZOE-128) covers it. A full fix needs an API of the core.
- At a signal, the watcher closes each open storage of the process. It marks the table closed, moves the entries of the open transactions into `Table::closing` and takes the store. So, as after `close`, `tpc_begin` and each call on the store raise `StorageError`, and a call with a transaction of before the signal raises `StorageTransactionError`. The entries hold Python references, so they stay in `closing`. The watcher aborts each transaction there that no call uses: it takes the transaction of the core out of the entry. When no call holds the store (`Arc::try_unwrap`), it drops the store in its thread, so the database closes cleanly. A `tpc_finish` takes its entry out of the table before its commit, so a commit that started before the signal ends and is durable before the database closes.
- The store closes once: in `close`, in the drop or in the watcher, whichever takes it first. When `close` or the drop took it first, the watcher waits for the flag `database_closed`.
- The wait lasts at most 5 seconds from the signal, for all the storages together. A store that a call still holds at the bound stays open, and the others close. After the bound, the watcher starts no close and drops no share of a store.
- After the close, or at the bound, the watcher calls `emulate_default_handler`: it restores the default action of the signal and raises it, so the process ends with the status of the signal. This holds also when no storage is open, when a close fails and when a close panics. A second signal during the close changes nothing.
- `close` and the drop of a storage remove the entries of the table, `closing` too. The drop removes them, so that their Python references drop there, never in the watcher, which can hold the last `Arc<Shared>`.
- A handler that the application sets later with `signal.signal` replaces the handler of the extension. The extension never puts its handler back.
- The at-fork hook gives the child of `os.fork()` the default action of each signal of the extension whose action Python still sees as `SIG_DFL`. The child has no watcher, and the pipe of the handler is the pipe of the parent. A handler of the application stays in the child. The child does not install the handlers again.
- No option and no ZConfig key turns the handlers off or sets the bound.
- `signal-hook` is the only crate that the close adds.

## The `<zoe>` stanza and the `zoe://` URI

- `%import zoe` loads `component.xml`. It declares the `<zoe>` section, which implements `ZODB.storage`, so `<zodb>` and `<zodb_db>` take it. `zoe.config.ZoeStorage.open` opens a `zoe.Storage`.
- The keys are `path`, `blob-dir`, `backend`, `lock-timeout`, `early-locks` and `read-only`, in kebab-case. `zoe.config.KEYS` gives the converter of each key. `component.xml` declares every key as a string, and a unit test checks it. `ZoeStorage.open` converts the text of the section with `KEYS`, as the twins and the URI do. So the three take the same syntax.
- Every key has an environment twin: `ZOE_` and the key in upper case, with `_` for `-`. The twin gives the value only when the section does not set the key. An empty value of any key counts as not set: the key takes its twin, then its default. No key has a default in `component.xml`, else a twin could never apply; a missing key takes the default of `zoe.Storage`.
- `open_storage` expands a leading `~` in `path` and `blob-dir`, from the section, a twin or the URI.
- Only the section reads the twins. The URI and `zoe.Storage` do not.
- `zoe:///absolute/path?key=value` resolves through the `zoe` entry point of `zodburi.resolvers`, `zoe.config.resolve_uri`. The path of the URI is `path`. The query takes the other keys of the section, with the same names and values, each at most once: a repeated key raises `ValueError`. The other query keys go to zodburi as database keywords, and zodburi refuses an unknown key with `KeyError`. A host, a fragment or a relative path raises `ValueError`.
- zodburi comes with the `uri` extra, `zoedb[uri]`, because it needs ZEO. A plain install of zoedb keeps the entry point, which only zodburi reads. The dev group of the workspace takes zodburi for the tests.
- `backend` takes only `redb`. `early-locks` takes only a false boolean: `on` raises `ValueError` until early locks are built. `lock-timeout` is whole seconds, as ZConfig's `time-interval` gives them, and 0 or more. A refused value raises `ValueError`, which names the source, the key and the value. A section without `path` and without `ZOE_PATH` raises `ValueError`.
- `zoe.config` imports ZODB and ZConfig. `import zoe` does not import `zoe.config`. ZConfig and zodburi import it when they need it.
- `just plone zoe` builds a Plone instance from `plone/zoe.cfg`, whose `zope.conf` has the `<zoe>` stanza alone, and `just plone zoe check` creates a Plone site on it. No command line and no file of the build holds the admin password: see `plone/README.md`.

## `zoe.zeo.ClientStorage` and the `<zoeclient>` section

- `zoe.zeo.ClientStorage` is a Python subclass of `ZEO.ClientStorage.ClientStorage`, with the same arguments and `native`, false by default. With `native=False`, it runs ZEO's asyncio client and calls no Rust. With `native=True`, `__new__` gives a `zoe.zeo._NativeClientStorage`, a subclass, which runs the native client of the extension (see "The native client"). `native=True` on another subclass of `zoe.zeo.ClientStorage` raises `TypeError`, unless the subclass derives from `_NativeClientStorage`.
- Each connection declares `zoe.zeo.EXTENSIONS` (`sequences`) in a third argument of `register`. It never sends `None` there: a ZOE server refuses a third argument that is not a list of strings with `TypeError`. A stock ZEO server refuses the third argument with `TypeError`, and its connection stays open and unregistered: the connection then registers again with two arguments, and the client works as `ZEO.ClientStorage` does. The stock server logs that `TypeError` once for each connection, and the client logs it once as an error from the server. The read-only fallback keeps the declaration.
- The client gets the accepted names in `_info["extensions"]` from `get_info`. `notify_connected` updates `_info` first, then removes the `extensions` key when the new `get_info` has none. So a reconnection to a stock server leaves no `extensions` key, and a reconnection to a ZOE server never removes the key for a moment.
- The classes `_Protocol`, `_ClientIO` and `_ClientThread` copy three short methods of ZEO 6 (`Protocol.verify_connection`, `ClientIO.try_connecting`, `ClientRunner.setup_delegation`), each with one class changed. A new release of ZEO that changes these methods needs the same change here.
- `sequence(name)` takes a `str` (else `TypeError`) and returns a `zoe.zeo.Sequence`. Its `next()` returns an `int` from `sequence_next(name)`, with the rules of `zoe.Storage.sequence`. When the connection did not get `sequences` accepted, `next()` raises `ZODB.POSException.Unsupported` and sends no call. A read-only connection gets `ReadOnlyError` from the server.
- `%import zoe` declares `<zoeclient>`. It extends ZODB's `<zeoclient>`, so it takes each of its keys with the same datatypes and defaults, and adds `wait-timeout` (an integer, 30 by default), as ZEO's `<clientstorage>` has it, `native` (a boolean, false by default) and an `<ssl>` section. `zoe.config.ZoeClient.open` gives the keys to `zoe.zeo.ClientStorage` as `ZODB.config.ZEOClient` gives them to `ZEO.ClientStorage`, `wait-timeout` as `wait_timeout`, `native` as `native` and the `<ssl>` section as `_ssl_section`. The section has no environment twins, as `<zeoclient>` has none. A unit test checks that its keys are those of `<zeoclient>`, `wait-timeout` and `native`.
- `component.xml` declares the section type `ssl` with the keys of the `<ssl>` section of ZEO's `<clientstorage>` (`certificate`, `key`, `password-function`, `authenticate`, `check-hostname`, `server-hostname`) and the same datatypes and defaults, and no datatype: the section keeps its files. ZEO's component declares a type `ssl` too, so ZConfig refuses a configuration that imports `zoe` and `ZEO` together. Such a configuration uses `<zoeclient>` with `native false` and `<ssl>` in place of `<clientstorage>`: it opens ZEO's client with the same TLS.

## The native client

- `zoe._zoe.Client` holds a `zoe_client::Pool` (ADR 0036): its listener is the connection of `zoe_client::Client::open_first`, and each other connection opens with `Client::open_endpoint` on the endpoint of that server, registered as the listener (read-only after a fallback), without a fallback. `pool_bound` is `zoe.zeo._POOL_BOUND` (64). `begin` returns a `zoe._zoe.Transaction`, one for each transaction, on its own connection. It declares `zoe.zeo._NATIVE_EXTENSIONS`, which is `zoe.zeo.EXTENSIONS` (`sequences`, and `trace_context` when `opentelemetry` is installed), and speaks only `M5`: a stock ZEO server needs `msgpack true`. It has no cache, no blob, no reconnect and no conflict resolution.
- The addresses are `(host, port)` tuples and paths of unix domain sockets as `str`. Each round of the open resolves each host again, to its first IP address. A host that does not resolve leaves the round, and the other addresses still open; when no address resolves, the round fails as a failed connection. The final `ClientDisconnected` names the addresses and the hosts that did not resolve. The client connects to all of them and keeps one server: with `read_only_fallback`, a writable server before a read-only one (see `zoe-client`). `read_only()` and `address()` tell what it kept.
- TLS comes only from the files of an `<ssl>` section, as the tuple `tls`: the extension builds it in Rust with `zoe_client::Tls`. Its `authenticate` is a file, a directory, or `None` for the CA certificates of the system (`zoe_client::TlsOptions::system`). A file that does not read, and a directory or a system store without a CA certificate, raise `ValueError`, which names the source (`Opening::Tls`, apart from the errors of an address). The server name is `server_hostname`, else the host of the address. On a unix socket without `server_hostname`, `check-hostname` raises `ValueError`; without the check, the name is `localhost`, which the client does not check. With TLS, the client never connects without TLS.
- The import of the extension starts no thread. The first open builds one tokio runtime for the process, with 2 worker threads named `zoe-client`, which every client shares. The runtime is never dropped.
- Each call waits for the server inside `py.detach`. No mutex is held across a wait for the server outside `py.detach`, or while Python code runs. `pool()`, `is_connected` and `close` take the mutex of the client while attached, for a short section that runs no Python code.
- The client records the process that opened it. In a child of `os.fork()`, each call raises `RuntimeError`, and the drop of the client frees nothing of the connection: the threads and the locks of the parent are not in the child. `_NativeClientStorage._check_process` raises the same error first, before any Python lock, in `new_oid`, `lastTransaction`, `tpc_begin`, `tpc_finish`, `tpc_abort` and `close`: a thread of the parent can hold such a lock at the fork. A client that the child opens builds a runtime of the child. The mutex of the runtime of the process is held only while the runtime builds; a fork in that short window leaves it locked in the child, whose first open then waits for ever.
- The drop of a `zoe_client::Transaction` can start a task, so the extension drops a transaction, a `zoe._zoe.Transaction` and the pool only inside `Runtime::enter`. The pool starts its dispatcher inside `Runtime::enter` at the open.
- The open takes `traceparent`, a callable: `zoe.zeo._traceparent`, the reader of the client of ZEO. The client keeps it only when the server accepted `trace_context`. Then each call to the server calls it with the GIL, on the calling thread, when the call starts, before `py.detach` and while it holds no lock, and runs the call inside `zoe_client::traced`. A str result is the traceparent of the call. `None` gives a call of four elements, and another result raises `TypeError`. Without `trace_context`, a call calls no Python code for the trace. `__traverse__` reports the callable to the garbage collector.
- The open retries the addresses when every connection fails, or when the servers close them before `register`, every 100 ms until `wait_timeout` (30 seconds by default). Then it raises `ClientDisconnected`, whose message names the addresses. A failed TLS handshake is such a failure. Another error raises at once.
- The errors: `Error::Conflict` and `Error::ReadConflict` raise `ConflictError` and `ReadConflictError` with `oid` and `serials`. `Disconnected` and an error of the connection raise `ClientDisconnected`. `Unsupported` raises `Unsupported`, `Invalid` raises `StorageTransactionError`. A server error raises the exception class that it names when the class is an exception of `ZODB.POSException`, `ZEO.Exceptions`, `transaction.interfaces` or `builtins`, with the message, and `StorageError` otherwise. Another error raises `StorageError`.
- `_NativeClientStorage` keeps the arguments of `ZEO.ClientStorage`. Before anything else, the open checks each argument of `zoe.zeo._NOT_BUILT`, a dict of each argument whose feature is not built and the value that leaves the feature off: any other value raises `Unsupported` that names the argument. None is ignored. A later card takes its arguments out, and the gate checks that the dict is empty. The arguments that ZEO 6 ignores (`disconnect_poll`, `min_disconnect_poll`, `max_disconnect_poll`, `drop_cache_rather_verify`, `credentials`, `username`, `password`, `realm`) are ignored. The storage keeps `_addr`, the list of addresses, which ZEO's tests read. An empty host is `127.0.0.1`, as for ZEO.
- An `ssl` context raises `Unsupported`, which names `ssl`: a context does not give back the files of its certificate and key, and the TLS of the native client runs in Rust. The `<ssl>` section of `<zoeclient>` reaches the class as the private argument `_ssl_section`: the native client takes its files, and ZEO's client takes the context that `ZEO.zconfig.client_ssl` makes from it. `ssl_server_hostname` comes before its `server-hostname`. The native client refuses `password-function` (an encrypted key) with `Unsupported`. This refusal is a known limit: it is not in `_NOT_BUILT`, so the gate does not see it. As in `ZEO.zconfig.ssl_config`, a directory as `authenticate` is a directory of CA certificates, and no `authenticate`, or `DYNAMIC` that is not a directory, takes the CA certificates of the system. `isReadOnly()` is true after a read-only fallback.
- A thread named `<name> zoe native client invalidations` starts at the open. It waits in `next_delivery` for the next delivery of the dispatcher of the pool, gives it to the DB (`invalidate(tid, oids)`, or `invalidateCache()` for the stale mark of a lost listener), then calls `delivered`, also when the DB raises. The dispatcher gives the next tid only after that. `tpc_finish` calls `Transaction.finish`, which returns the tid at its turn: the DB got every tid below it. It then calls `f(tid)` and `Transaction.done`, in a `finally`; the dispatcher gives no later tid before `done`. `lastTransaction()` gives the last tid that the dispatcher delivered, and after `close` the last tid before the close. When `next_delivery` raises, the thread closes the client, so a call that waits for a turn fails and does not hang. From a thread that runs a delivery (a thread-local flag) it does not wait; from any other thread it waits first for the delivery that runs. So it gives a tid only after the DB got its invalidations or the callback of its commit ran, and ZODB's `test_tid_ordering_w_commit` sees the tid of a commit whose callback runs.
- `_transactions` maps each ZODB transaction that began to its `zoe._zoe.Transaction`; a lock covers the check and the change. Several transactions run at once. A second `tpc_begin` of the same transaction raises `StorageTransactionError`, a call with a transaction that did not begin raises `StorageTransactionError`, and `tpc_abort` of an unknown transaction does nothing. `tpc_begin` waits for a free connection when the pool is at its bound. `tpc_begin` with a `tid` sends it and the status to the server, as ZEO does: the transaction commits under that tid. `tpc_vote` returns the oids that the server resolved, or `None`. A vote that fails ended the transaction on the server; the later `tpc_abort` sends nothing. `tpc_transaction()` gives the transaction that began last and did not end, or `None`.
- The calls that the native client does not have yet (`history`, the iterators, `pack`, undo, blobs, `restore`, `deleteObject`) raise `Unsupported`. `prefetch` does nothing: there is no cache. `supportsUndo()` is false. The interfaces of `get_info` are not declared on the instance.
- `zoe.testing.native_client(address, **kw)` opens it. `zoe.testing.NATIVE_LAYER` puts `_NativeClientStorage` in place of the class of ZEO in each loaded module that binds the name `ClientStorage` to it, and makes `zoe.config.ZoeClient.open` open the native client whatever the key `native`. `tearDown` puts both back. So `ZEO.client`, `ZEO.DB`, `<zeoclient>` and `<zoeclient>` open the native client.

## The `<zoe-server>` section and `zoe.serve`

- `component.xml` also declares the `<zoe-server>` section and its `<storage NAME>` subsections. `python -m zoe.serve -C FILE` reads the section with the schema `zoe.serve.SCHEMA` and runs `zoe serve` with it. ADR 0028 records this.
- The keys of the section are `binary` and `zoe.serve.KEYS`, the top-level keys of the configuration file of `zoe serve`. A unit test compares `KEYS` with the options of `zoe serve --help`. So an option that the server adds must also go into `KEYS` and `component.xml`. The keys are strings: `zoe serve` checks their values, except `read-only`, which `zoe.serve` converts with ZConfig's boolean. An empty value counts as not set.
- A `<storage NAME>` subsection is a `[storages.NAME]` table, with `path` (required), `blob-dir` and `read-only` (a ZConfig boolean, false by default). ZConfig gives the name in lower case and refuses a name that comes twice.
- A leading `~` in `path` and `blob-dir` is the home directory.
- The section wins over the twins: the environment of the server has no twin of a key that the section sets. The other variables, the twins of the keys that it does not set included, reach the server.
- The wheel ships no server. The binary is the key `binary`, else `ZOE_BINARY`, else the first `zoe` on the PATH that is not a script, so the console script `zoe` of the wheel is skipped. A name with `/` is a path, and a leading `~` is the home directory.
- `zoe.serve` writes the TOML file into a `memfd_create` file without `CLOEXEC`, and `execve`s `BINARY serve --config /proc/self/fd/N`. So no Python stays in the process of the server, a SIGTERM reaches the server, and no value of the section is in the arguments of the process. The memory file stays open in the server.
- An error in the file exits with 2 before the exec, and a missing binary with 1. `zoe serve` refuses a bad value with 2 too.
- `zoe.testing.ZoeServer.binary()` gives the binary of the tests: `ZOE_BINARY`, else the debug build of the repository.

## Errors

| Core error | Python exception |
| --- | --- |
| `NotFound` | `POSKeyError(oid)` |
| `Conflict` | `ConflictError` with `oid`, and `serials == (current, read)` for a stale serial; a lock-wait timeout gives no serials. A conflict on a stored object also gives `class_name`, whether the core or `_p_resolveConflict` does not resolve it |
| `ReadConflict` | `ReadConflictError` with `oid` and `serials == (current, read)` |
| `WrongThread` | `zoe.WrongThread` |
| `Protocol`, `LockOrder` | `StorageTransactionError` |
| `Halted`, `CorruptRecord`, `CorruptBlob`, `CorruptTxn`, `CorruptSequence`, `Backend` | `StorageSystemError` |
| `Locked`, `Closed`, `Format`, `ReadOnly`, `NotClosedCleanly`, `RepairFailed`, `MissingBlobDir`, `NotBlobDir` | `StorageError` |
| `Io` | `OSError` |

A pack maps two errors in its own way. Each stops the pack and raises `StorageSystemError`, whose text starts with "pack stopped" and gives the text of the core:

| Core error of a pack | Cause | The text names |
| --- | --- | --- |
| `CorruptRecord` | a record fails its checksum. The pack keeps it, also when nothing can reach it. | the oid and the tid |
| `Format` | a record does not decode | the oid, the tid and the reason |
| `Format` | a row is in a format that this build cannot read or rewrite | the row |
