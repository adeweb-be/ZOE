# zoe-client

A Rust client for the ZEO protocol, with the ZOE extensions. `zoe.zeo.ClientStorage`, `zoe-bench`, the server mode of Loupe, `zoe mcp` against a server and the simulator use it. Specification: "Async and free-threading", F2 (client side), F28 and N18, and "The client cache" under "The native client (F28)".

## Layout

- `src/client.rs`: `Client`, `Options`, `Transaction`, `Invalidations`, the open on several endpoints (`Client::open_first`), and the three tasks of a connection (reader, writer, heartbeat).
- `src/pool.rs`: `Pool`, `PoolTransaction`, `Finished`, `Turn`, `Delivery`: several transactions at once on a pool of connections, with one listener and one dispatcher (ADR 0036, proposed).
- `src/cache.rs`: `Cache` and `CacheCounts`, the client cache in the layout of ADR 0034 (proposed), stage 1: one anonymous mapping. `src/cache/mapping.rs` holds the mapping. `src/cache/tests.rs` holds its unit tests.
- `src/endpoint.rs`: `Address` (TCP or the path of a unix domain socket) and `Endpoint` (an address, with TLS or without).
- `src/tls.rs`: `TlsOptions` and `Tls`, the TLS of a client on rustls.
- `src/protocol/`: the frames and the messages of ZEO 6 with msgpack. It has its own codec: the codec of `zoe-server` is private to that crate.
- `src/runtime.rs`: the trait `Runtime` (connect, connect_unix, spawn, sleep) and `Tokio`, its implementation for production.
- `src/error.rs`: `Error`.

## Invariants

- The client speaks the same ZEO 6 msgpack protocol as `ZEO.ClientStorage`: `M5`, then `register(storage, read_only)`, then calls with int ids from 1 and the flags `false`, and calls without a reply with the id 0 and the flags `true`. `loadBefore` has an int id too, not the `[oid, tid]` id of a stock client: the server echoes any id. `Client::connect` registers with `false` and two arguments.
- `Client::open` declares `Options::extensions` in a third argument of `register`, then calls `get_info`. A stock server refuses the third argument with `TypeError` (any module, such as `builtins.TypeError`) and keeps the connection open and unregistered: the client then registers again with two arguments. With no extension in `Options`, `register` has two arguments. `Client::info` gives the reply of `get_info`, and `Client::extensions` the names of its key `extensions` that the client declared.
- The client uses an extension only after the server accepted it in `get_info`. `sequence_next` needs `sequences`: without it, it fails with `Error::Unsupported` and sends nothing.
- `traced(traceparent, future)` gives a W3C traceparent to the calls of `future`, through a task-local of tokio. On a connection whose server accepted `trace_context` in `get_info`, each call and each call without a reply inside it carries the traceparent as a fifth element of its message: the map `{"traceparent": traceparent}`, the wire form of `zoe serve`. A call outside `traced`, a call with `None`, a call on another connection, the heartbeat and the abort of a dropped `Transaction` have four elements. So do the calls of the open (`register`, the read-only `register` of the fallback, `lastTransaction` and `get_info`), in `open`, `open_endpoint` and `open_first`: the flag of the connection comes from its own `get_info`, after them, so `open_first` keeps the flag of the server that it keeps. The caller reads the traceparent before it starts the future, so a call that waits keeps the traceparent of its caller.
- A call frame is built on the task of the caller, inside its `traced`. A task that the client spawns sees no traceparent, so a call that it sends has four elements.
- Each reply goes to its call by its message id, whatever the order of the replies. A reply with an id that no call waits for is dropped.
- A lost connection fails every call that waits with `Error::Disconnected`, and every later call too. The end of the stream, an error of the stream, a frame that does not decode, an `invalidateTransaction` in a bad shape, `Client::close` and the drop of the `Client` all close the connection.
- The client reaches the network, its tasks and the time only through `Runtime`: never `tokio::net`, `tokio::spawn` or `tokio::time` outside `Tokio`. It uses tokio's I/O traits and `tokio::sync`. Every `select!` is `biased;`, so a simulator runs it in one order. `Runtime::connect_unix` has a default that fails with `io::ErrorKind::Unsupported`, so a runtime without unix sockets, such as the simulator of `zoe-server`, needs no change.
- TLS runs on the stream that `Runtime` gives, with rustls and its ring provider: the TLS stack of `zoe-server`. `Tls::load` reads the PEM files of `TlsOptions`: the certificate chain of the client, its key (in the certificate file when no key file is set) and the CA certificates of `authenticate`. The client always checks the chain of the server certificate against `authenticate`. With `check_hostname`, the webpki verifier of rustls checks the chain and the server name of the `Endpoint`. Without it, the verifier `ChainOnly` calls `verify_server_cert_signed_by_trust_anchor` of rustls and never checks the name: the security of the chain never depends on the order of the checks inside rustls. An error names the file.
- Known limit: the server certificate must chain to a CA certificate of `authenticate`. A self-signed server certificate (a CA certificate or a v1 certificate, as the `server.pem` of ZEO's tests) given as `authenticate` is refused by webpki, while OpenSSL accepts it. `zoe serve` matches such a client certificate by its bytes; the client does not do it yet.
- An `Endpoint` with TLS never sends a frame outside TLS: a failed handshake fails the connection, and the client never falls back to a stream without TLS.
- `Client::open_first` opens the endpoints at once, in the task of the caller, and keeps one: the first that registers as `Options` asks. With `Options::read_only_fallback`, a server that refuses the writable `register` with `ReadOnlyError` gets a second `register`, read-only, on the same connection; that client waits until no other endpoint can open writable, or until the wait passes. The drop of the other attempts and clients closes their connections, so one connection stays open. Without a client, the open fails with the most specific error: the first error that is not of the connection (`Io`, `Disconnected`), else the last `Io` of the kind `InvalidData` (a failed TLS handshake or a bad stream), else the last error of a connection, or `Io` of the kind `TimedOut` when the wait passed first and no attempt failed. So a refused address never hides a certificate error of another address. A read-only fallback waits for the slowest attempt: an address that never answers delays it until the end of the wait. `Client::read_only` tells if the client registered read-only, and `Client::address` gives the address of its server.
- The client sends a heartbeat `[-1, 0, ".reply", nil]` every 60 seconds (`HEARTBEAT`), busy or idle, as a stock client does. So the `--idle-timeout` of `zoe serve` never closes it.
- One transaction at a time for each client, as the commit lock of `ZEO.ClientStorage`. A vote that fails, by an error or by a conflict that the vote lists to `vote` or `vote_resolved`, sends `tpc_abort` and waits for its reply, because the server keeps the locks of a listed conflict. `vote_listed` leaves a listed conflict to its caller. A `Transaction` dropped before the server confirmed `finish` or `abort` sends `tpc_abort` and does not wait, so a cancelled `vote` or `abort` still releases the locks. It keeps the commit lock of the client until its `tpc_abort` is in the outgoing channel, also when the channel is full, so the `tpc_begin` of the next transaction never reaches the server before that abort. After a failed vote or an abort, `store`, `vote` and `finish` fail with `Error::Invalid` and send nothing: `zoe serve` closes the connection on a `storea` for a transaction that is not open.
- `Transaction::store_blob` uploads a blob as `ZEO.ClientStorage` does without a shared blob directory: `storea`, `storeBlobStart`, one `storeBlobChunk` per chunk of `BLOB_CHUNK` (59,000) bytes, and `storeBlobEnd`, all without a reply. `store_blob_from` does the same from an `io::Read`, one full chunk in memory at a time; a failed read gives `Error::Io`, sends no `storeBlobEnd` and ends the transaction as a failed vote does: a later `store`, `vote` or `finish` fails with `Error::Invalid` and sends nothing, and the abort or the drop sends `tpc_abort`. `store_blob_shared` sends `storea` and `storeBlobShared(oid, serial, data, filename, id)`, without a reply, for a blob directory that the client shares with the server.
- `Client::send_blob(oid, serial, sink)` downloads a blob into an `io::Write`: `sendBlob`, which the server answers with `receiveBlobStart`, the `receiveBlobChunk`s and `receiveBlobStop` on the same connection, then the reply. The reader gives each of these calls to the download of its oid and serial through a bounded channel (`PIECES`), and waits while it is full; a call for a blob that no download waits for goes nowhere, and one in a bad shape closes the connection. The download succeeds only with the reply, `receiveBlobStart` first and `receiveBlobStop`; a piece out of order or a reply before the stop is `Error::Protocol`, an error reply is the error of the server, and a failed write of the sink is `Error::Io` after the reply, with no write after it. The writes run on the task of the caller. A connection runs one download of a blob at a time: a second `send_blob` of the same oid and serial waits until the reply of the first, also when the future of the first dropped after its `sendBlob` went out; the reader frees the blob at that reply, or at the close. The caller polls a download until it ends, or drops it: while its channel is full, the other replies and the invalidations of its connection wait. A reply scans the downloads for its id only when a download runs. `Pool::send_blob` takes a connection other than the listener, in turn, when one is open and not lost, so the delivery of the invalidations never waits for a download; else the listener.
- The client runs no resolution code. A `ConflictError` is `Error::Conflict`. A conflict that the vote lists is `Error::Conflict` for `vote` and `vote_resolved`, which then abort. A `ReadConflictError` with an oid, as the vote gives after `Transaction::check_current_serial`, is `Error::ReadConflict`. Every other error of the server is `Error::Server` with its class; its message is empty without an argument, the text of its one argument, or else the value.
- `Client::begin` sends `tpc_begin` with the tid nil and the status `" "`. `Client::begin_with` sends a tid and a status: a transaction with a tid commits under it.
- `Transaction::vote_resolved` gives the oids that a stock server lists as resolved: their pickle on the server is not the pickle of the client. `vote` drops them.
- `Transaction::vote_listed` gives a `Voted`: the oids that the server resolved and each `Listed` conflict (`oid`, `committed`, `read`, `data`, the pickle that the client stored), both in the order of the reply. A listed conflict does not abort: the transaction stays open, and the server keeps its locks. The caller stores each resolution over `committed` and votes again, or aborts. A map of the reply without both serials or without bytes as `data` is `Error::Protocol`, and the vote aborts. The caller of `PoolTransaction` stores a resolution with `store_resolved`, and calls `unresolved(oid)` for a conflict that it does not resolve.
- `Client::disconnect` closes the connection without waiting for its tasks, so a caller that does not own the `Client` can close it. `Client::is_connected` is false once the connection closed.
- `last_transaction` only goes up: it takes the maximum of the tid of `register`, of each invalidation and of each commit of the client. It is the position of the connection: the last tid that it read from its own stream. The reader raises it at the reply of a `tpc_finish`, and at each invalidation, before it gives them on. `Client::load_before_at` returns the position that the reader read when the reply of the load came, for the cache of ADR 0034.
- The invalidations go to a broadcast channel of 1,024 entries. A receiver that falls further behind gets `Error::Lagged`, and must treat its cache as stale. A consumer subscribes first, then reads `last_transaction`: the reader raises `last_transaction` before it sends the invalidation. A commit of the client gives no invalidation to the client, as from ZEO. `Invalidations::try_recv` reads without a wait. The reader dispatches the frames in order, so when the reply of `tpc_finish` comes back, each invalidation that the server sent before it is in the channel.
- `Pool` (ADR 0036, proposed) holds one open `Client`, the listener, which never commits, and opens the other connections with its `Connect` function, on demand, up to its bound. `begin_with` takes a free connection, opens one when none is free and the pool is below its bound, else waits. The connection goes back to the pool when the `PoolTransaction` ends; a lost connection closes and leaves the pool, also when it is lost while free: `begin_with` closes it and takes the next one. A slot of the bound comes back when a connect fails or its future drops. Loads use any connection that is not lost, the listener included, in turn; `new_oids` and `sequence_next` use the listener.
- One dispatcher task of the pool reads the invalidations of the listener and delivers each tid in turn, one at a time. A tid of another client goes to the consumer: `next_delivery` gives it, and `delivered` confirms it. A tid that a finish of the pool committed gives the turn to that finish: `Finished::turn` returns a `Turn`, and its drop confirms the tid. The dispatcher delivers no other tid until the confirmation. `Pool::last_transaction` is the last confirmed tid, from the last tid of the listener at `Pool::new` on, never `Client::last_transaction`. `settled_transaction` waits first for the delivery that runs. A tid at or below the start is skipped.
- The hold: a `PoolTransaction::finish` counts as in flight from before its frame goes out until its reply. The dispatcher takes a horizon when it takes a tid, and holds the tid until no finish of a lower count is in flight, or until a finish names the tid. A finish counted later commits a later tid. A finish that fails, whose connection is lost, or whose future drops, leaves the hold through the drop of its guard. A finish with its reply disarms the guard; nothing is forgotten, so the drop of the pool and the end of the dispatcher free the shared state. A lost listener (`Client::closed`) ends the hold at once. A `Finished` that drops before its turn leaves its tid to the consumer as a tid of another client.
- A lost or lagged listener is a lost connection: the dispatcher disconnects it, fails each finish that waits for its reply, gives the consumer `Delivery::Stale`, then gives each finish that has its reply its turn in tid order, with `Turn::stale`. Then `begin_with` and `finish` fail with `Error::Disconnected` and send nothing. A pool needs a consumer of its deliveries: the dispatcher waits for each one. The state of the pool is one `std::sync::Mutex`, held for short sections that never wait, with a `watch` channel that wakes the waiters.
- The client cache (ADR 0034, proposed). `Pool::with_cache` gives the pool a `Cache`; `Pool::new` gives none. The semantics are those of `ZEO.cache.ClientCache`. An entry is one revision of an oid with its start tid and its end tid; a current entry has the end word 0, and a dropped entry has its end equal to its start, so it serves no snapshot. `load_before_with(oid, before)` hits an entry with `start < before` and either `end ≥ before`, or no end and `before ≤ applied + 1`. `load_with(oid)` hits the current entry whatever `applied` is, as `ZEO.ClientStorage.load` does. A lookup follows at most 8 entries of an oid (`MAX_CHAIN`), and an index insert probes at most 32 slots (`MAX_PROBE`); an entry that no slot takes counts in `CacheCounts::unindexed`, and no lookup finds it.
- The layout is ADR 0034: a header page of 512 words (magic, size of the ring, number of slots, their checksum, boot id, clean flag, `applied`, `head`, state checksum; an anonymous mapping leaves the boot id, the clean flag and the state checksum at zero), an index of `max(ring ÷ 256, 1024)` slots rounded up to a power of two, each `(oid + 1, position)`, and a ring of `cache_size` bytes rounded down to a word. An entry has a head of 9 words (its logical position, oid, start, end, the position of the older entry of the oid, stored and raw lengths, codec and total bytes, the xxh3 of its data, the xxh3 of the first 8 words) and its data, aligned to 8 bytes. An entry never crosses the end of the ring. Logical positions start at one ring and never repeat. The same code must serve the file of a later stage: do not write a second layout.
- Every word of the mapping is an `AtomicU64`. A hit takes no lock and writes nothing: it loads `applied` (acquire), the slot (acquire), copies the entry with relaxed loads in one pass, 4 KiB at a time into a local buffer that it hashes (streaming xxh3) and then gives to the caller's sink (`Copier`), checks both checksums, then an acquire fence and a load of `head`: the entry is intact while `head ≤ position + ring`. A writer moves `head`, then a release fence, then writes the entry with relaxed stores, then points the slot at it with release stores. The end of an entry changes in place: the end word, then the head checksum (release). A doubt is a miss.
- The writers (`store`, `apply`, `commit`, `drop_current`, `clear`, `disable`, and the copy of a hit) take one `std::sync::Mutex`, never across an `await`. A hit of a current entry in the oldest fifth of the ring, no larger than a tenth of the ring, copies it to the head only when `try_lock` gets the mutex. An entry larger than half of the ring is never cached (`Cache::fits`).
- The store rule: `Cache::store` takes a current reply only when `applied` is not above `seen`, the position of the connection that carried it, which the reader took when the reply arrived (`Client::load_before_at`). A reply with an end always goes in. A newer current reply drops the older current entry of its oid: the older revision ended somewhere up to the new start, not surely at it. An older current reply than a current entry is refused. `store` returns true only when an index slot took the entry, so a lookup can find it. The oid `u64::MAX` is never cached: its key would be 0, the key of an empty slot. `Pool::load_before` stores each reply with its position, and `Pool::load` goes through it. Neither reads the cache: the caller looks up `Pool::cache` first.
- The order: the dispatcher calls `Cache::apply(tid, oids)` before it offers a tid of another client to the consumer, a dropped `Finished` included. `Finished::turn` calls `Cache::commit(tid, writes)` when its turn comes, before it returns the `Turn`: each write ends the current entry of its oid at the tid, and adds the committed data, unless the server resolved the oid (`vote_resolved`, `vote_listed`) or the data does not fit. The pickle of `store_resolved`, which the server stores unchanged, is a write like any other, as in ZEO. `PoolTransaction` keeps its stores only when the pool has a cache, and the turn applies the last store of each oid. A `Conflict` or a `ReadConflict` of a vote, and `PoolTransaction::unresolved(oid)`, call `Cache::drop_current(oid)`. A listed conflict alone changes nothing in the cache. `Pool::with_cache` moves `applied` of the empty cache to the last tid of the listener.
- `Cache::clear` moves `head` two rings forward and keeps `applied`. A lost or lagged listener and `Pool::disconnect` call `Cache::disable`: every entry goes, and the cache stores nothing more.
- `src/cache/mapping.rs` holds the only `unsafe` code of the crate: `mmap` and `munmap` of the anonymous mapping and its view as `&[AtomicU64]`, each item with its own `#[allow(unsafe_code)]` and a `SAFETY` comment. The crate needs it for two reasons: the kernel gives the pages of an anonymous mapping as zeros only at their first write, so an unused part of the cache costs no memory; and the cache file of ZOE-162 maps through the same `Mapping`, so one code reads and writes both. The workspace lint `unsafe_code = "deny"` stays. `libc` and `xxhash-rust` are dependencies for the cache.
- tokio is allowed in this crate. `zoe-py` depends on it for the native client of `zoe.zeo.ClientStorage` (ADR 0035), so `cargo tree -p zoe-py -e normal` lists tokio. This crate never depends on rmcp.
- `zoe.zeo.ClientStorage` is a drop-in for `ZEO.ClientStorage`, never a requirement.
- A change to the wire protocol is a stop-and-ask.

## Tests

- `tests/client.rs` is the acceptance test, against `zoe_server::serve::Server` in the test process.
- `tests/pool.rs` runs `Pool` against `zoe serve` in the test process: blob downloads on the connections of the pool, a turn, a foreign tid, the order of a finish behind a lower tid, `settled_transaction`, the bound, a dropped `Finished`, a lost listener, the position of a load, the free of the pool after its drop, and, through a TCP proxy that holds the reply of a finish, the hold, a finish future dropped after its frame went out, and a finish in flight when the listener is lost; and the hooks of the cache (a foreign tid applied before its delivery, a commit at its turn, a conflict, a conflict that the client resolves, whose resolution enters the cache, a conflict that it does not resolve, a dropped `Finished`, a lost listener).
- `src/cache/tests.rs` holds the unit tests of `Cache`: the rules of a hit, the race of ZEO issue 166 in a fixed order (a current reply that arrived at a position below T, stored after the cache applied T for its oid, is refused), commits, conflicts, `clear`, the bound of the ring, the copy of a hit, the index, and readers that check each hit against the history while a writer wraps the ring.
- `python/zoedb/tests/client/test_native_cache.py` is the acceptance test of the cache through `zoe.zeo.ClientStorage`, against `zoe serve --admin-listen`.
- `tests/runtime.rs` runs the client on a scripted server through a `Runtime` of the test: replies out of order, a lost connection, a bad frame, a listed conflict, a listed conflict that stays open for its resolution, a dropped transaction, the heartbeat, the declaration of `Client::open` and its fallback to two arguments, a read conflict, the resolved oids of a vote, `disconnect`, the traceparent of `traced` with and without `trace_context`, and the blobs: a download of more pieces than its channel holds, a piece of another blob, a reply before the stop, a chunk before the start, an error reply, a sink that fails, a second download of a blob behind a dropped first one, and the frames of `store_blob_from` and `store_blob_shared`.
- `python/zoedb/tests/client/test_native_conflicts.py` is the acceptance test of conflict resolution through `zoe.zeo.ClientStorage`, and `python/zoedb/tests/conformance/test_native_conflict_suites.py` runs the conflict tests of ZEO and ZODB on it. `python/zoedb/tests/client/test_native_conflict_units.py` holds their unit tests.
- `python/zoedb/tests/client/test_native_blobs.py` is the acceptance test of the blobs through `zoe.zeo.ClientStorage`, and `python/zoedb/tests/conformance/test_native_blob_suites.py` runs ZEO's blob tests on it. `python/zoedb/tests/client/test_native_blob_units.py` holds their unit tests.
- `tests/endpoints.rs` runs `Client::open_first` on scripted servers: a refused address, a writable server after a read-only one, the read-only fallback, an error of a server before an error of a connection, a unix socket, a runtime without unix sockets and the end of the wait.
- `tests/tls.rs` runs the TLS of the client against `zoe serve` in the test process, with certificates that the `openssl` command makes: the name check, a wrong name with and without it, a CA that does not sign the server with and without the name check, and a server without TLS.
- `python/zoedb/tests/client/test_native_transports.py` is the acceptance test of TLS, of unix sockets and of several addresses, through the native client against `zoe serve`. The repository holds no key: these tests make their certificates with `openssl`.
- `crates/zoe-server/tests/simulated_pool.rs` runs `Pool` under the deterministic simulator, with closes, losses and lost listeners. `python/zoedb/tests/client/test_native_concurrent.py` is the acceptance test of the pool through `zoe.zeo.ClientStorage`.
- `crates/zoe-server/tests/simulation.rs` and `crates/zoe-server/tests/simulated_kill_loop.rs` run the client under the deterministic simulator of `zoe-server`, through its `Runtime`, against the server code, with network faults, blobs and crashes of the server.
