# zoe-core

The storage core. It owns correctness: the data model, two-phase commit, per-OID locks, conflict handling, pack and blobs. Backends own bytes. Specification: "Storage core" and "Async and free-threading".

Red zones in this crate: `src/format/` and `src/pack/`. A change to the data model is a format change wherever its code lives.

Every test of this crate also runs under ThreadSanitizer with `just tsan`, once on `main` at the end of a phase (a phase gate, not a check of each pull request). A data race fails it. The ignored test in `tests/tsan_canary.rs` holds a deliberate race: `just tsan` runs it and passes only when ThreadSanitizer reports that race.

## Invariants

- The core is synchronous. It has no tokio, no async code and no Python inside.
- The core, not the backend, implements locking, two-phase commit, conflict resolution, invalidations and blobs.
- The backend never allocates tids. The core allocates the tid at `tpc_finish` under the commit sequencer: `max(now, last_tid + 1 tick)`.
- Tids always increase.
- A normal commit never gets `Tid::MAX`, the tid that `load` reads before. When no tid below `Tid::MAX` is left after the last tid, `finish` fails with `Protocol`, and the store does not halt.
- A client passes a tid only through a restore transaction (`tpc_begin_restore`), never through a normal commit. A restore transaction takes `store`, `store_blob`, `delete`, `restore` and `restore_blob`. `store`, `store_blob` and `delete` keep their serial check there.
- A restored oid is a written oid: the vote takes an exclusive lock on it, as for `store`. `restore` reads the current serial of the oid, and the vote fails with `Conflict` if another transaction changed the oid since.
- A restore transaction (`tpc_begin_restore`) commits under the tid of the client and allocates no tid. The tid must be after the last tid: `tpc_begin_restore` checks it, and `finish` checks it again under the commit sequencer. A tid that is not after the last tid, or `Tid::MAX`, fails with `Protocol`, and the store does not halt.
- `store` refuses an empty pickle with `Protocol`. Only `delete` and `restore` write a deletion. `delete` is the `deleteObject` of ZODB: it stages an empty pickle with the serial of the client, and the vote checks that serial as for `store` and takes an exclusive lock. The deletion replaces a staged pickle of the oid and counts 0 bytes toward the transaction size. It drops the staged blob of the oid. After a vote, `delete` fails with `Protocol`. Only the API of the commit path grows: a deletion is the record with a 0-length payload that the format already has.
- `Oid(u64::MAX)` is reserved: `store` and `restore` refuse it with `Protocol`. `new_oid` fails with `Protocol` when no oid below `u64::MAX` is left. It never wraps.
- Locks are acquired in ascending oid order, over the written and the read-current oids together. A request out of order is refused with `LockOrder`, never granted. The one exception is `LockManager::try_exclusive` of the split merge (ADR 0049): it takes the exclusive lock of an oid after the others, only when no request holds the oid, none waits for it and its entry carries no hand-off, and else takes nothing. It never waits, so it adds no wait out of oid order and never passes a request that waits.
- Written oids take exclusive locks. Oids passed to `checkCurrentSerialInTransaction` take shared locks. An oid that is both takes an exclusive lock. A shared lock is compatible only with shared locks.
- Each oid has a wait queue in arrival order. A lock request never passes a request that waits for the same oid, so a stream of readers cannot starve a writer.
- A transaction that must wait releases nothing and queues once.
- The thread that releases a lock grants it to the waiters at the head of the queue, under the lock-manager mutex. Then it releases the mutex and wakes them. A waiter holds its lock before it wakes up.
- A lock wait longer than `lock-timeout` (default 10 s) becomes a `ConflictError` on the oid waited for. The timeout covers all the waits of one vote, measured on the monotonic time of the store clock (`Clock::monotonic`) from the start of its lock acquisition.
- Another thread can end the lock wait of a vote with a `LockCancel` (`Txn::set_lock_cancel`). The vote then leaves the queue of the oid, releases each lock that it took and fails with `Conflict` on the oid that it waits for, with no serials, as at the lock timeout. A cancel is not lost: it stays, and a vote that must wait after it fails at once. A cancel does nothing to a vote that takes its locks without a wait, or that has its locks: its transaction keeps them until finish, abort or drop. `LockCancel::cancel` takes no mutex of the lock manager: it sets its flag, then wakes each waiter that it watches with `Waiter::wake`. The vote reads the flag before it queues and after each wake. One `LockCancel` can serve many transactions and many waits at once.
- The vote reads the current serials of its oids with `Backend::current_serials`, from the keys of the records: one read transaction for each chunk of 256 oids, and no record is decoded. Only a stale written oid that the caller can resolve reads its committed record, with `Backend::load_before`. A finish stages the records of each commit with `WriteTxn::put_records`, which opens the record tables once.
- Conflict detection and resolution happen at vote, before any disk write. A stale written serial is `Conflict`; a stale read-current serial is `ReadConflict`, unless rule 1 of the split merge lets it through (below). The vote checks the written serials first.
- A failed vote releases every lock that it took. `finish` releases the locks after the commit is durable and the sequencer holds the new tid, except the locks that it handed off (below). It releases them before it ends its commit in flight (`InFlight::end`), which wakes the votes that wait for that commit, so a woken vote finds them free. That release reads no clock: the log of `lock-warn` comes after the end of the commit. The finish of a deferred restore releases them after its commit is visible, not durable, and the sequencer holds its tid. `abort` releases them. Dropping a transaction aborts it.
- `vote_resolving` is the vote of a caller that resolves conflicts itself. A stale written oid can be resolved when `store` staged it with a serial other than `Tid::ZERO` and its committed record holds a pickle. A deletion is never resolved. When each stale written oid can be resolved, the vote keeps its locks and returns these oids with their committed records. Any other stale written serial fails it with `Conflict`, then a stale read-current serial fails it with `ReadConflict`. A read-current oid is never resolved: only rule 1 of the split merge lets one through, and the vote writes nothing for it.
- Tier 1 of the conflict resolution (`merge`, the structural merges) runs in the vote that takes the locks, `vote` or `vote_resolving`, and in `Txn::undo`. In the vote it runs on each stale written oid that a caller could resolve: staged with a serial other than `Tid::ZERO`, not restored, with a pickle, and a current record with a pickle. A vote without a stale oid decodes nothing. The class comes from the class pickle of the staged record alone (`merge::tier1_class`); only a class of tier 1 (the families of BTrees but `fs`, and `BTrees.Length.Length`) reads the record at the serial that the transaction read. A staged pickle that does not read back gives no answer, so the caller that reads it again reports the error, as without tier 1. `Txn::undo` runs tiers 1 and 2 without the locks of the vote, on the three records of an undo (see below): the vote then locks the staged oid and checks its serial, so a commit after the undo is a conflict of the vote.
- In mode `on`, a merge stages the merged pickle over the serial of the committed record, under the locks of the vote, after the check of every serial passed; the size limits apply to it, and a merged pickle over a limit gives no answer. A refusal fails the vote with `Conflict` on the oid, with `conflict_serials`. No answer leaves the conflict as without tier 1: listed for the caller of `vote_resolving`, `Conflict` for `vote`. In mode `shadow`, tier 1 runs and the vote goes on as without it. In mode `off`, tier 1 does not run. `StructuralMerges` gives the mode of tier 1 and of each class, and of the rules of ADR 0042.
- Tier 1 never guesses. A comparison that `zoe_pickle::python` cannot make (values of mixed types, a dict, an int against a float), a record that does not decode, or a state that holds a construct that the model does not hold, gives no answer. A refusal is a case where ZODB's resolver refuses too. Two next buckets that are references to one oid and one database, with two persistent ids (an alias of a class, for example), give no answer: ZODB's resolver can make one reference of them. The posting-dict rule and the first-key rule (ADR 0042, one mode, off by default) and the split merge (ADR 0048, below) are the merges where ZODB's resolver refuses. The posting-dict rule takes dicts of int to int, refuses its own cases and never keeps a dict of more than 10 entries or of none. The first-key rule lets a delete of the first key through only when the committed transaction deleted it, in the bucket that a tree holds inline, with no next bucket; a delete by the new transaction and a delete in a standalone bucket still refuse. The rule rests on the order of the vote: a merge of tier 1 counts only when every read-current serial is still current, so a stale read-current oid fails the vote and stages nothing. Rule 1 of the split merge lets a stale read-current node through only when the other side changed it by splits and replacements of other children alone, so the node above the bucket did not change for the delete. In shadow mode the rules write their outcome to `Merge::shadow`, and when a rule compared a dict or let a first key go, the merge runs again without them: that outcome ends the conflict, as with the rules off.
- A merged record is the record that ZODB's resolver writes, byte for byte, when that resolver imports each class under the name that the record gives (see `crates/zoe-pickle/CLAUDE.md`): the merge follows `bucket_merge` of BTrees step by step, and `zoe_pickle::python` keeps the identity of the objects as Python's unpickler gives them. `tests/structural_merges.rs` tests the vote, and the acceptance tests `test_native_merges.py` and `test_posting_dicts.py` compare with ZODB's resolver. The rules of ADR 0042 and the split merge are the exceptions: ZODB's resolver refuses their cases, so it writes no record to compare with.
- The split merge (ADR 0048, `merge::split`, `commit::split`) merges where ZODB's resolver refuses. The switch `split_merges` of the merge policy turns it on, in mode `on` or `shadow`; without the switch, or without a policy, it is off, and no key of the store sets it. Its rules run only in a class whose mode of tier 1 is not `off`, and only in the vote that takes the locks: the first conflict of that vote makes one plan for the transaction. A vote without a conflict makes no plan and reads nothing new. An undo runs no rule.
  - A node is a BTree or a tree set of a family of tier 1 whose state holds children. A node changed only by splits when it holds each child of the record that the transaction read, in the same order with the same separators and the same first bucket, and each other child comes right after its anchor or after another new child of that anchor. A child that is not the first one is replaced when a new child takes its place with its separator, and the child after the new child has the separator of the child after the replaced one, or neither has one. A node changed only by splits and replacements holds each child of the old record or the new child that replaced it, and every other child comes right after its anchor.
  - Rule 1: a stale node that the transaction marked read-current and did not store passes when the other side changed it only by splits and replacements, the transaction stored or marked read-current at least one of its children, and the other side split or replaced none of these children. The vote writes nothing for it, and its locks stay shared. The vote after `vote_resolving` lets it through again (`passed`). Its entry has the outcome `Merged`, the rule 1, and the line `passed`; `natively_resolved` leaves it out. A replaced child that the transaction stored or marked read-current gives no answer: the write under it is not stale, and the check of the node is the only check that stops it. The vote checks the written serials before the read-current oids. So a bucket before a replaced child, which the other side wrote with its new next bucket and the transaction stored, fails first: tier 1 refuses it with reason 0, and the vote fails before it checks the node. The entry of rule 1 for the node stays with `applied` false.
  - When the vote fails with `ReadConflict` on a stale read-current node for which rule 1 gave no answer, it gives one entry for that node, with the rule 1: in mode `on`, the outcome `Undecided` with the reason of rule 1 and `applied` false; in mode `shadow`, the outcome `Undecided("a read-current oid")` and the reason of rule 1 in `shadow`. The vote fails on the first stale read-current oid, so it gives at most one such entry. A read-current oid on which the rules did not run gives none.
  - Rule 2: in a node that the transaction stored and split, and that the other side changed only by splits (rules 2 and 3 take no replacement), the splits of children that the other side did not change merge: the merged node is the committed node with the new children of the transaction right after their anchors.
  - Rule 3: a bucket that the transaction split once, and that the other side split once or changed without a split, merges the keys of its range with `bucket_merge`, without the rules of ADR 0042: the old bucket is the base, the committed bucket and its new bucket are the committed side, the bucket and the new bucket of the transaction are the new side. Neither half may be empty.
    - When the other side changed the bucket without a split, the keys below the separator of the transaction go to the bucket, the others to the new bucket of the transaction, a new child of the node. The same holds for a root that the other side changed inline: both halves of the split of the transaction are new objects. A record cannot tell such a root from the last node of a tree that holds its one bucket inline (the corner of ADR 0042). The rule writes the same records there: the node and its two new buckets, which no other record refers to, so the node above does not change and no update is lost.
    - When the other side split the bucket too (ADR 0049), the rule needs `Txn::set_server_writes(true)`: without it, it gives no answer, so no rule takes a bucket out of the tree. With it, the rule takes the exclusive lock of the new bucket Y of the other side with `try_exclusive` before it reads Y, and gives no answer when the call fails: the node then gets one entry of rule 3 in mode `on`, with the outcome `Undecided("a bucket of the other side that another transaction locks")` and `applied` false, also for a root that held its bucket inline. The node keeps its entry of tier 1, and the vote goes on as without the rule. No other answer of rules 2 and 3 on a written node gives an entry. The keys below the separator of Y go to the bucket, the others to Y; the next buckets are those of the committed side. Y is written over the serial of its current record: the transaction did not store it, and `Txn::wrote_unstored` then says so. The new bucket of the transaction, and the node when its merged record is its committed record, are resolved without a record. For a root that the other side split, the two new buckets of the other side take the keys, and the root and the two new buckets of the transaction get no record.
  - An oid that the split merge resolves without a record leaves the staging when the vote passes: no batch writes it, the transaction index does not list it, and the finish never hands its lock off, because the finish hands off only staged oids. The vote keeps its exclusive lock until the end of the transaction. Its entry is `Merged` and applied, so `Txn::natively_resolved` lists it, and the reply of the vote of `zoe serve` gives it.
  - The rules write the records that the transaction stored, and, with `server_writes`, the new bucket of the other side that rule 3 keeps, each over the serial of its current record (`Tid::ZERO` for a new bucket), under the locks of the vote and with the size limits. They read a bucket that the transaction did not store only under its lock. The plan takes the locks of `try_exclusive`, gives them to the vote, and releases at once those of a group that the vote does not take. In mode `shadow` the plan takes no lock and reads Y without it: the outcome is a report.
  - The rules run on each node by itself, at any depth of the tree. Rule 2 merges a split of a child node that the other side did not change, as a split of a bucket. The rules give no answer for a node that changed by anything but splits (and replacements, for rule 1), a delete of a key in a range that they merge, two splits of one child on one side, a child node that the transaction split and the other side changed (rule 3 merges only buckets), a child that is not a bucket of the family of its node in rule 3, and a state that the model does not hold. A refusal of `bucket_merge` in a range refuses with its reason on the stale record of the range: the split bucket, or the root that held its bucket inline, with `conflict_serials`. In mode `shadow`, the vote goes on as without the rules, and the entry of each stale oid of a node carries the outcome of the rules in `shadow` and its rule in `split`.
  - Two key references of one class, `five.intid.keyreference.KeyReferenceToPersistent` or `zope.keyreference.persistent.KeyReferenceToPersistent`, whose `object` refers to an oid of the same database, compare by that oid, as `_get_cmp_keys` does in conflict resolution. The order applies to the keys and to the values of a merged range, since `bucket_merge` compares the values of the keys that both sides kept (`refs` of the intid utility holds key references as values). Only the split merge uses this order, with a heap of `Heap::with_instances`. Key references of two classes, or with a reference that names a database, give no answer.
  - Before the rules read the store, the plan waits until each commit in flight of a hand-off is durable or failed, until the lock deadline of the vote. A late wait gives no plan. `tests/split_merges.rs` tests each rule and each case without an answer; the unit tests of `commit::split` test a commit in flight.
- The order merge (ADR 0052, `merge::order`, `commit::order`) merges the order of a folder of plone.folder and its positions where ZODB has no resolver. The switch `folder_orders` of the merge policy turns it on, in mode `on` or `shadow`; without the switch, or without a policy, it is off, and no key of the store sets it. It merges only where the mode of tier 1 of `BTrees.OIBTree.OIBTree` and `BTrees.OIBTree.OIBucket` is not `off`, and only in the vote that takes the locks: the first conflict of a written oid makes one plan for the transaction. The plan finds the orders whenever the switch is not `off`, whatever the mode of tier 1. A vote without a conflict makes no plan. An undo runs no rule.
  - It runs on each stale written `persistent.list.PersistentList` L. It finds the folder among the records that the transaction stored: a state with `__annotations__`, a reference to an `OOBTree` A that holds its bucket inline and names L under `plone.folder.ordered.order` and the positions P, an `OIBTree`, under `plone.folder.ordered.pos`. It reads the current A; a staged A must name the same L and P. When no stored record names L, the list is not an order: it keeps the stock path, and gives no line.
  - The three records of L must have the class `persistent.list.PersistentList` and the state `{'data': [str, ...]}`. The old list is a prefix of the committed list c and of the new list, and the transaction appended at least one id; else no answer. An id that both sides appended refuses (`Reason::OrderSameId`). The merged list is `c + N`, N the appended ids.
  - The equation: over the buckets of P that the transaction stored, its new buckets and the root of P when one of its states holds its bucket inline, the union of the new states is the union of the old states plus exactly `{N[i]: len(old) + i}`. A stored node of P keeps each child of its old state that the transaction did not store. Else no answer. The rule reads only the nodes of P that the transaction stored or marked read-current.
  - After the check of every written and read-current serial, the vote gives each N[i] the value `len(c) + i` in the records of P that it stages: the merges of tier 1 and of the split merge, the bucket of the other side that rule 3 writes, and each record of P that the transaction stored and that is not stale. Each id of N must be in exactly one of them, and the rule reads its records back (the self-check). A record of P merged onto a commit in flight, a stale record of P without a merge, a record over a size limit, or a failed check gives no answer. Then the vote fails with `Conflict` on L, or gives L to the caller of `vote_resolving`.
  - The vote stages L over its committed serial, and stages again a record of P that it stored and that is not stale, over the serial that it read, which drops an encoded payload. The reply lists L and each changed record as resolved. The rule writes no record that the transaction did not store beyond the bucket of rule 3, and takes no lock.
  - Tier 2 never merges an order that the plan found, whatever the policy says. The lock of an order is never handed off: `persistent.list.PersistentList` is not a class of tier 1.
  - In mode `shadow` the vote goes on as without the rule. The line of L has `undecided` with the reason "an order in shadow mode", and `shadow` holds the outcome of the rule with its self-check on the stored records of P. The lines of the rule have the field `order`: `list` for L, `pos` for a record of P.
- `Txn::resolutions` gives what tiers 1 and 2 did in the undos of the transaction, then in the last vote that took the locks, and `Txn::natively_resolved` the merged oids of a vote that passed, the new bucket of a split merge among them. The vote after `vote_resolving` runs no tier 1 and keeps the entries of `vote_resolving`. The core writes no resolution log: `Txn::resolution_log_lines` gives its JSON lines, with the user and the description of both transactions, and the skins write them to the file of `resolution-log`. These lines never go to `tracing`.
- Tier 2 (`merge::fields`, ADR 0046) runs in the same votes as tier 1, after it, on each stale written oid that a caller could resolve, whose class is not a class of tier 1 and whose entry in the merge policy has `tier2` `on` or `shadow`. A class without an entry never merges in tier 2. Its outcomes are those of tier 1: in mode `on` a merge stages over the committed serial and a refusal fails the vote with `Conflict`; no answer leaves the conflict to the caller; in mode `shadow` the vote goes on as without it. Tier 2 decodes with a heap of `Heap::with_instances` and never with the heap of tier 1, so tier 1 does not change.
- The strategies of tier 2 (`merge::policy::Strategy`) are `strict`, `lww`, `max`, `sum`, `union`, `append` and `keys`. The strategy `keys` (ADR 0046, section 11) merges a field whose three values are dicts, key by key, with the rules of tier 2 one level down. A key that only one side changed, added or deleted takes that change. A key that both sides changed to values of one structure takes that value. A key that both sides deleted stays deleted. Any other change on both sides refuses: `KeyChanged` for two different values, `KeyDeleted` for a delete against a change. The merged dict holds the keys of the committed dict in its order, then the keys that only the new side added, in the order of the new dict. `keys` gives no answer when a value is not a dict, when a key is not an int, a str, a bytes or a tuple of those (`DictKey`), or when two keys of one dict hold one mutable object. In an undo, `keys` acts as `strict` for each key. The strategy `append` takes the option `state` of the entry (`ClassPolicy::append_state`, ADR 0046, section 12): after the checks of `append` (the kinds and the prefix, which refuse with `NotAppend`), each item that the committed side added must hold, under that key, the state of the last item of the old value, else the merge refuses with `StateChanged`. An old value without items, or an old last item or a committed item that is not a dict with the key, gives no answer. The items of the new side are not read. In an undo, `append` with `state` merges as in a vote.
- Each merge of tier 1 or tier 2 has a step budget of 64 steps for each byte of its three records (`merge::budget`): the comparisons of its heap (`Heap::set_budget`) and the canonical ids of tier 2 (`Canon`) stop there, and the merge gives no answer. Tier 2 never recurses over a value. Three records whose class pickles name different classes give no answer in tier 2. An entry with `blocked` never merges in tier 2.
- The merge policy is the record of `root['zoe.merge_policy']` (`merge::policy`). Only a vote with a conflict, and an undo that merges, read it: one read of the current serials of oid 0 and of the policy, and a new read of the two records when one serial changed (`PolicyCache`). A commit without a conflict reads nothing new. A root or a policy that does not read counts as no policy, with one warning for each serial. `policy::Rules` gives the settings of a vote: a switch of the policy wins over `StructuralMerges`, and a switch that the policy does not give keeps its key.
- A merge of tier 1 or tier 2 in mode `shadow` keeps the BLAKE3 digest of its record (`Txn::shadows`). The vote after `vote_resolving` compares it with the record that the caller stored over the committed serial and gives a `Verification` (`Txn::verifications`, `Txn::verification_log_lines`). A conflict that the caller does not resolve gives none.
- After `vote_resolving` gives conflicts, the transaction holds its locks and takes only a `store` of an oid in conflict, with the serial of the committed record. The next `vote` takes no lock. It checks every serial again with the locks held. An oid that is still stale fails it, and it releases the locks. So the locks are taken once, in ascending oid order. While the caller resolves, only an abort or a drop of the transaction releases them, from any thread: the in-process storage does this at `tpc_abort` and at `close`. The core runs no resolution code of a class: only the structural merges of tier 1 (below), in Rust.
- A transaction keeps its staged pickles in memory up to `staging-memory` bytes (default 16 MiB). Each other pickle goes to the spill file of the transaction, `staging/<n>.spill`. An index in memory keeps the serial of each staged oid, its restore flag and the place of its pickle. `staging-memory` bounds the bytes of the pickles, not the index. The vote and `vote_resolving` read only the index.
- A staged record can hold a payload encoded before the finish (`Encoded`, `Txn::set_encoded`). Only `Encoded::encode` makes one, with `format::encode_payload`, the encode of the finish. `set_encoded` attaches it only when the length and the xxh3-64 hash of the staged pickle and the compression of the store (`Store::compression`) match. Else it returns false and the finish encodes the pickle inline. A later `store`, `delete` or `restore` of the oid drops the payload. The payload is not counted in `staging-memory`. With the copies that the compression pool of `zoe serve` holds until its jobs run, the memory of one transaction can reach about three times `staging-memory`: the pickles, their copies and the payloads. Only pickles in memory are queued, so it stays bounded.
- The finish writes an attached payload into its frame as it is (`WriteTxn::put_payloads`, `format::encode_frame_payload`). The frame is byte for byte the frame of an inline encode of the same pickle with the same compression. No record is stored with another codec or other bytes because of an attached payload. `tests/encoded_payloads.rs` checks the frames, also of spilled pickles.
- A spill file is never part of the durable store. Nothing syncs it or `staging/`. A transaction removes its spill file when it drops, while it still holds its store, so finish and abort remove it too. A writer open removes the regular files in `staging/`, and other entries stay.
- A spill file is always a new file: `Vfs::create_new` fails when the name exists, a symbolic link included. So a spill never writes into an old file or through a link.
- A read-only store writes nothing in `staging/`. Its open removes nothing, and a pickle that would spill fails `store` with `ReadOnly`. A pickle that fits in memory stages, and the vote fails with `ReadOnly`.
- The index keeps the xxh3-64 hash of each spilled pickle, and each read checks it. So the bytes that `finish` writes are the bytes staged. A mismatch fails the read with `InvalidData`. `staged` reads a spilled pickle from the file and returns the error of a failed read, never `None` for a staged oid.
- A staged blob stays with its oid when the pickle of the oid spills.
- Every spill file operation goes through the `Vfs`, so the crash simulation covers it.
- The database file of an `OsVfs` (the `OsFile` of `Vfs::open`) holds the writes of redb, and makes them before the next sync, read, change of the length or close, in the order of their offsets, each run of adjacent writes as one. A sync, a change of the length and the close take its mutex, so they wait for a `make` that another thread runs. The flag that lets a read skip the mutex turns false only after the writes are made, and a failed `make` keeps its writes. So every call sees every write before it, and a sync makes durable every write before it. A growth of it of at most 64 MiB gets zeros. A spill file (`Vfs::create_new`) makes each write at once, so `staging-memory` still bounds the pickles in memory. On Apple systems, a sync of an `OsVfs` is `fsync(2)` (ADR 0040).
- The lock table has an entry only for an oid that a transaction holds or waits for.
- `Store::lock_table_is_empty` is a documented public method. It gives true when no transaction holds or waits for a lock, and it changes nothing. The lock table of a store that the process just opened is empty, so the readiness of `zoe serve` reads the method once after the open of each store. It tells nothing about other processes, because the lock table lives in the memory of one process.
- No conflict tier runs Python on the server.
- One backend write transaction holds the records, their keys in the transaction index, the blob records, the transaction row and the meta update of a commit, the object count included. It is durable before the client gets the acknowledgement, except for a deferred restore (below). In a commit batch, one backend write transaction holds all of this for every member of the batch.
- `finish` joins a commit batch (`commit::group`). A finish that finds no leader becomes the leader: it takes every finish that waits, writes them all under the commit sequencer in one backend write transaction, and commits it with one sync. Finishes that arrive while the leader writes wait and form the next batch. A member returns only after its batch is durable or failed. A batch of deferred restores has no sync, so its members return when the batch is visible or failed.
- A deferred restore is a restore transaction that begins with `Store::tpc_begin_restore_deferred` or `Txn::begin_restore_deferred`. Only it defers its sync: `tpc_begin`, `tpc_begin_restore` and `Txn::begin_restore` keep a durable finish. Its finish runs the same commit path: the tid check under the commit sequencer, the locks, and the placement of the blobs with all its syncs. A batch whose members are all deferred restores commits with `WriteTxn::commit_deferred` (redb `Durability::None`), with no sync of the database file. A batch with another member commits with a sync, which makes its deferred members and every earlier deferred commit durable. A deferred commit is visible to readers and sets the last tid when its finish returns. A crash loses every deferred commit after the last durable commit, and the store then ends at a whole commit. An error of a deferred backend commit halts the store as any failed batch does.
- `Store::sync` makes every commit before it durable. Under the commit sequencer, it calls the barrier `Backend::sync`, which commits one backend write transaction of its own, with a sync, that writes no record, no transaction row and no last tid, so the last tid does not change. It fails with `ReadOnly` on a read-only store and with `Halted` on a halted store. An error of its write halts the store as a failed finish does.
- `WriteTxn::commit_deferred` has a default that calls `commit`, so a backend that cannot defer stays durable. `commit` stays durable on return.
- The members of a batch commit in arrival order. Each member gets a tid after the tid of the member before it. A restore tid or a new tid that fails its check fails only its member with `Protocol`, and the store does not halt. An error of the batch write fails each member that wrote, and the store halts. The leader releases no lock of a member: each member releases its own locks after the batch.
- The unit tests of `commit::group` count the syncs of the database file. Finishes that wait while a batch writes join the next batch, so 16 such finishes take at most 3 syncs. The crash simulation checks that each batch is whole or absent and that no acknowledged member is lost.
- A crash before the fsync leaves no record, no index key, no blob record and no transaction row. It can leave blob files in their place in the blob tree; an intent file in `blobs/tmp/` names them, and the next open removes them. The same holds for a deferred commit that a crash loses: its intent file stays until a durable commit covers it. A crash after the fsync leaves a complete transaction. No other repair step exists.
- Invalidations go out only after the acknowledgement.
- Locks that group-commit members hold stay held until the batch is durable, except the locks that a finish handed off. A batch of deferred restores has no fsync: its members hold their locks until the batch is visible. A failed fsync fails every member.
- The lock hand-off (ADR 0044, `lock::handoff`). Once the member of a normal transaction is in the queue of group commit, its finish hands the lock of each oid that it writes to the exclusive request at the head of the queue of the oid, when the staged record of the oid is of a class that tier 1 merges in mode `on`. A restore hands off nothing. The new owner gets a copy of the staged pickle of the holder and its commit in flight (`InFlight`), never its spill file. The entry of the oid keeps the hand-off until the store holds the last commit of the oid (`LockManager::settle`): the finish of the holder settles it when its commit is durable or failed, and the finish of a new owner settles the hand-off that it got when its own commit is durable, because that commit comes after the commit of the holder. While the entry has it, only an exclusive request takes the lock, and it takes the hand-off with it, also after the new owner released the lock; a shared request waits. So no vote reads the oid from the store while the store does not hold its last commit. A finish releases only the locks that it did not hand off.
- An intent owner (`IntentLocks`, ADR 0045) takes exclusive locks in the mode `Intent` before the vote. One call takes oids in strictly ascending order, above every oid that the owner holds; any other call fails with `LockOrder` and takes nothing. It waits within the lock timeout of the store and with its `LockCancel`; a timeout or a cancel fails it with `Conflict`, and it keeps no lock that it took; so does a failed read of the current serials. An intent request never takes a hand-off: it waits while an entry has one, so the current serials that it returns are those of the last commit. The drop of the owner releases its locks, and `Observer::intent_locks_acquired` gets each call: the locks that the call keeps, and 0 for a call that fails.
- `Txn::adopt_intents` moves the locks of an owner of the same store into a transaction before its vote; another store or a call after the vote fails with `Protocol`. The vote counts the adopted locks as its own exclusive locks and asks for none of them again. When it has adopted locks, it first tries its other locks without a wait; when one is not free, it releases the adopted locks above the lowest oid that it asks for, and takes them again with the others in oid order, with waits, so it never waits for an oid below a lock that it holds. Its deadline for a commit in flight is then the lock timeout after its start. The end of the transaction releases the adopted locks with the others.
- A vote that holds a lock with a hand-off whose commit is in flight checks the oid against the copy, not the store. Tier 1 in mode `on` merges onto it: the vote stages the merged pickle with the serial `Tid::ZERO` as a placeholder, and the batch writes the tid of the holder as its previous serial. A refusal fails the vote at once, with no `serials` when the holder has no tid yet. A restore, a new object or a deletion fails at once. Any other case waits until the commit of the holder is durable or failed, until the lock deadline of the vote and with its `LockCancel`, then checks the oid against the store as without the hand-off. A hand-off whose commit is durable or failed, or whose tid is the serial that the transaction read (its batch is visible, and the transaction read it), checks against the store. When the split merge is on or in shadow mode, a refusal of a bucket split (reason 0) or of an internal node (reason 11) waits for the commit in flight as no answer does, so the rules can run on the store. A read-current oid held with a hand-off whose commit is in flight fails the vote with `ReadConflict` at once, unless the transaction read that commit. The vote after `vote_resolving` does not check an oid that it merged onto a commit in flight again.
- The finish of a merged member starts after the finish of its holder, so the member is later in the batch of the holder or in a later batch, and its tid is after the tid of the holder. A failed write halts the store, so a member of a later batch fails with `Halted`. A member whose holder got no tid fails with `Protocol`. The leader gives a member with a commit in flight its tid under the commit sequencer; after `GroupCommit::finish` returns, its own finish settles the hand-offs that it got (when its commit is durable), releases the locks that it did not hand off, then ends the commit, and the observer then gets `locks_handed_off`. A finish gets its waiter from the store clock, and reads the time of its hand-offs, before its member joins the queue: while the member is in the queue, the finish calls no code but the lock manager, so a clock that panics never leaves a queued member whose transaction released its locks.
- Only the commit-batch leader, a pack batch, `Store::sync`, a sequence reservation, a restore of a sequence end (`Sequence::restore_end`), a sweep step of the KV namespaces (`Store::sweep`) and a restore of durable namespace rows (`Store::kv_restore_durable`) open a backend write transaction. The commit-batch leader, a pack batch and `Store::sync` open it under the commit sequencer; `Store::sync` writes nothing in it. The other four open it outside the commit sequencer and write no record, no blob record, no transaction row and no `meta` row: a sequence reservation and a restore of a sequence end write only the row of their sequence, a sweep step only ephemeral rows and their keys in `kv_expiry`, and a restore of durable rows only durable rows. redb has one writer, so the backend orders these transactions. Readers use snapshots and never block them.
- The thread that begins a transaction drives it. `store`, `store_blob`, `store_blob_at`, `delete`, `restore`, `restore_blob`, `restore_blob_at`, `check_current_serial` and `vote` from another thread fail with `WrongThread`, and the refused call changes nothing. A refused `store_blob` or `restore_blob` stages nothing and drops its blob file, which removes the file. A refused `store_blob_at` or `restore_blob_at` leaves the file in its place. `finish` and `abort` may run on any thread, because ZODB lets another thread finish or abort a transaction.
- `Txn` reaches its store through `S: Deref<Target = Store>`. `Txn<&Store>` borrows the store. `Txn<Arc<Store>>` shares it and borrows nothing, so a skin can keep it across calls and threads.
- A successful vote hands its locks to the transaction with `Locks::keep`. The transaction then releases them with `LockManager::release` at `finish`, at `abort` or when it is dropped. A failed vote drops its `Locks`, and that releases them.
- After a vote fails on a stale serial, `conflict_serials` gives the current serial and the serial that the transaction read, the `serials` of a ZODB `ConflictError`. After a lock-wait timeout it gives `None`. `staged` gives the read serial and the pickle that the transaction staged for an oid. `staged_class_name` gives the class of that pickle as `module.name`, the `class_name` of a ZODB `ConflictError`: `zoe_pickle::decode_class_name` reads the class pickle and never unpickles. A deletion, a class pickle that does not decode or names no class, and a spilled pickle that does not read give `None`.
- `finish_after` commits as `finish` does and also returns `previous`, the tid of the commit just before it in commit order: the member before it in its batch, or the last tid of the store before the batch. A skin runs its post-commit work in commit order with it, and holds no lock across commits.
- The lock manager, group commit, the commits in flight of the hand-off, the pack state and the sequence counters are the only shared mutable state. The core is `Send + Sync`. The lock order is the lock that one pack holds, then the commit sequencer, then the notes of the pack state, the kept intent files of the blob store or the mutex of a commit in flight. The mutex of a commit in flight is held with no other lock taken under it, and its waiters are woken without it. The queue mutex of group commit is held with no other lock. A sequence mutex is held with no other lock of the core.
- Every read verifies the record checksum. A mismatch raises `CorruptRecord` with the oid and the tid, never `POSKeyError`.
- The phase 1 gate "every injected bit flip detected" covers the stored frames of ZOE and the blob files: records of both codecs, transaction rows, blob records and blob files. A flipped bit there makes every read of the damaged item raise `CorruptRecord`, `CorruptTxn` or `CorruptBlob`. No read of the store gives wrong, stale or hidden data. A flip in a zstd payload fails the checksum before decompression.
- The bit-flip harness puts each read in one class. Ok is the exact answer. Error is a failed read. Hidden is committed data that is missing: `NotFound`, `None`, or a missing history entry, transaction, record or current record. Stale is an older record as the current one, or a next serial that is missing or skips a record. Wrong is data that the store did not commit, or committed data under another oid, tid or snapshot.
- A flipped bit in the pages of redb, outside the stored frames, is not in the gate. redb does not check its pages on a read. So such a flip can give a stale or a hidden read, make the open fail, panic, abort the process, or hang a read. A probe of every single-bit flip of the non-zero bytes outside the stored frames, 116,928 flips in release, measured 0 wrong, about 1.6 % stale, about 12 % hidden, about 4.8 % panic and 11 aborts. The harness asserts no wrong read on its default seeds. It prints the other counts and does not assert them.
- The checksum input of every frame starts with the one-byte tag of its key space, then the key, header bytes 0 to 23, the slots and the payload. The tags are 1 `records`, 2 `blobs`, 3 `txns`, 4 intent files, 5 `sequences`, 7 `kv_ephemeral`, 8 `kv_durable`. 0 is never a tag. 6 is reserved for `vectors`. A tag never changes and is never given to another key space. A new kind of frame takes a tag, with one new variant of `KeySpace`. ADR 0029 records this.
- A reader checks a frame with the tag of the table or the file that it reads, never with a byte of the stored data. So a frame moved to another key space under the same key fails its checksum: `CorruptRecord` in `records`, `CorruptBlob` in `blobs`, `CorruptTxn` in `txns`, `CorruptSequence` in `sequences`. An intent file that fails it names nothing. So a damaged branch page that leads a read of `records` into `blobs` gives `CorruptRecord`, never a blob record as a pickle.
- A key space whose values are not frames, such as `meta`, `txn_oids` and `kv_expiry`, has no tag.
- Every scan of `records` and `txns` checks that each key it gives is inside its range and after the key before it in the order of the scan. redb checks only one bound of a scan, so a damaged branch page can give a key outside it, and the frame of that key passes its checksum. Such a key raises `CorruptRecord` with the oid of the read and the tid of the key, or `CorruptTxn` with the tid of the key.
- The open takes the last tid from `last_tid` in `meta` and from the key of the last transaction row. The key counts only when the frame of the row passes the checksum under it. So a flipped bit in that key cannot raise the last tid.
- `tests/bit_flips.rs` and `tests/bit_flip_harness.rs` check these flips. Each flip comes from a seeded generator, so a failure reproduces. The harness prints its counts with the seed and the build profile. `ZOE_FLIP_SEED` and `ZOE_FLIPS` run the harness on another seed and with more flips. The harness runs each raw-file flip in a child process, so an abort stops only the child. `just test` runs the harness in debug and in release, because the debug build of redb changes what a damaged file does.
- The test hook `zoe_core::testing` reads and rewrites the stored bytes of a row, and writes or removes a row of `meta` (`write_meta`, `remove_meta`). It also gives the codec of the record frames to the tests of other crates: `encode_payload`, `decode_payload` and `FRAME_HEADER_LEN`. The feature `testing` builds it, the test-only methods of `Backend`, and `Store::remove_index_key_for_test`, `Store::remove_record_for_test` and `Store::open_vfs_uncached`. Only dev-dependencies turn the feature on: the one of this crate on itself, and those of zoe-server, zoe-convert and zoe-bench. So only test builds have the hook, never a release build.
- `load_before(oid, tid)` reads one snapshot: a reverse range scan from `(oid, tid - 1)` gives the record, and a forward scan from `(oid, tid)` gives the serial of the next record. Both records are verified; the next record is not decoded, because its serial is in its key. An oid with records, but none before `tid`, gives `None`. An oid with no record raises `NotFound`.
- A record with a 0-length payload is a deletion. `load`, `load_before` and `load_serial` of a deletion raise `NotFound`. `history` lists it with size 0. The iterator gives it with `data: None`. `record_iternext` skips the oid.
- The transaction iterator stops at the last tid at the time of the call. A later transaction always has a greater tid, so the iterator gives each transaction with all of its records. This is correct only because `finish` publishes `last_tid` after the commit is visible to readers. Group commit must keep this: it publishes `last_tid` after the whole batch is visible.
- `object_count` in `meta` is an 8-byte big-endian number. In every snapshot it is the number of distinct oids that have at least one row in `records`, a deletion included. ADR 0033 records it.
- Each backend write that changes records updates the count in that write. The redb write notes each oid that it puts or removes a record of, and reads, before its first change of the oid, if the oid has a record. Before its first put, it reads `next_oid` of `meta` once: an oid at or after it has no record, because each write that puts a record raises `next_oid` above its oid in the same write, so the note reads no record for that oid. For a put whose previous serial is not zero, a point read of that record answers first, and the scan of the oid runs only when that record is gone. A `next_oid` that does not decode makes each note scan. At its commit it reads each oid that it removed a record of again. It adds 1 for an oid that had no record and has one, and subtracts 1 for an oid that had one and has none. So a commit batch counts each new oid once, for a normal commit, a restore and a deferred restore alike, and a pack batch lowers the count by the oids whose last record it removes, with or without garbage collection. The commit-batch leader and a pack batch write under the commit sequencer, and redb has one writer, so the read sees every earlier write: a pack batch that removes an oid between the vote and the finish of a commit that writes it leaves the count exact. The vote decides nothing about the count.
- A write that changes no record writes no count: a sequence reservation, a restore of a sequence end, `Store::sync`. A dry run opens no write. A close writes no count. A count lower than its change, which only a damaged row gives, saturates at 0 and does not fail the write.
- The backend keeps the count of the last write that changed records in an atomic, and stores it after the commit of that write, under the commit sequencer. `Store::object_count()` gives `Some(count)` and reads no row, so after `finish` returns it counts the commit. `Backend::object_count` has a default that gives `None`.
- The format name is `ZOE format 2` (`format::FORMAT_NAME`). A new store starts with it and a count of 0. A store of format 2 without `object_count`, or with a row that is not 8 bytes, fails the open with `Format`. Another format name, `ZOE format 1` included, fails the open with `Format`. The refused open writes no row, so the store keeps its format name. A read-only open changes no byte. A writer open lets redb write its own state into `zoe.redb` when the database closes, as for any other format name. A read-only open of a store of format 2 reads the row.
- In every snapshot, the oid count of a transaction row equals the number of its records and the number of its index keys. Pack keeps this: one backend write removes records with their index keys, lowers the oid count of their rows, and removes a row that keeps no record, except the row at T, which stays with an oid count of 0. Pack never removes a row that keeps a record, so a row that pack removes has no index key left.
- The iterator reads the rows of its range a slice at a time (`Backend::iter_txns`), then the tids of the index that these rows cover, a slice at a time (`Backend::indexed_tids`). Each slice is one snapshot, and it never reads the index of a tid before the rows of that tid, so a pack between two reads cannot make an index key look like a key without a row. A slice holds at most 1,024 tids, and the iterator keeps only the tid of each row. So it holds one transaction and a slice of tids, whatever the length of its range. A slice of rows ends only after a row that reads, because the next slice starts after the tid of that row. The error of a row that does not read does not always name its tid, and an error with a tid can come from a failed scan. So a run of rows that do not read stays in one slice, and the iterator holds the error of each row of the run: its memory grows with the length of the run. Then it reads each transaction, its index keys and their records in one snapshot (`Backend::txn_records`). It skips a transaction whose row and index keys are gone at or before `pack_watermark`: a pack removed it after the first read. A transaction that is gone after `pack_watermark` raises `CorruptTxn`, because no pack removed it. It raises `CorruptTxn` when the records of a transaction do not match the oid count of its row, when an index key has no record, and when index keys of a tid have no row. A failed scan of the rows gives its error and ends the iterator. A failed scan of the index gives its error once, and the iterator then gives the rest of its range without the check of index keys without a row. A record without its index key gives a count that does not match. The iterator does not see a record that no row counts and no index key names. `load` and `history` do not read the index.
- The transaction iterator does not borrow the store, so a skin can keep it across calls and threads. It holds only a weak reference to the store and keeps it open only during one call. After the `Store` is dropped, the next call gives `Closed`, and the iterator ends.
- The open database, the blob store and the staging area live together in `Opened`. The blob store and the staging area share the directory, which holds the lock. Nothing outside `Opened` holds the directory. The database closes before the directory releases the lock, because closing a redb database writes to the file.
- A blob file holds only a weak reference to `Opened`, so it never keeps a store open. After the `Store` is dropped, a write to the file fails with `Closed`, and the next open removes the file. `store_blob` refuses a blob file of another store with `Protocol`, because the same temporary name can exist in both stores.
- `Store::open_read_only` opens an existing store for reads only. It takes the store lock, so a writer gets `Locked`, and it opens the database file read-only, so it changes no byte. It creates the lock file only when the store has none, and nothing in a directory without a store. Every write call fails with `ReadOnly`: `new_oid`, `tpc_begin`, `tpc_begin_restore`, `Txn::begin_restore`, `Sequence::next`, and `vote` and `vote_resolving` of a `Txn` that `Txn::begin` began. redb opens a read-only database only from a path, so this open does not go through the `Vfs`. A store that a crash left open fails with `NotClosedCleanly`: a writer open rebuilds the free-space map of its database. This open is strict: it never repairs, so the tests of a clean stop use it to prove that a stop closed the store cleanly. Do not make it repair.
- `Store::open_read_only_with` is `open_read_only` with `Options`. The other options matter to writes, which fail with `ReadOnly`, except `Options::cache_size`, which sets the page cache of the read-only database too. `Options::blob_dir` is the other one that counts: the store reads its blob files in that directory, through `blob::ReadOnlyDir`, which reads through `std::fs` and refuses every write, sync and lock. So the open changes no byte and creates nothing in the blob directory or in its parent, and neither need exist. It checks the path as `open_with` does, and creates nothing.
- `Store::open_read_only_repairing(dir, options)` is the open of the tools that read a store (ADR 0032). It takes the lock of the store as `open_read_only_with` does, and holds it from its start to its end, so no other open comes between the repair and the read-only open. On a store that was closed cleanly, it is `open_read_only_with` and changes no byte. When the read-only open of redb fails with `RepairAborted`, and only then, it opens `zoe.redb` for writes with `redb::Builder::open`, which creates no file and repairs the database. It drops that database, which writes the allocator state and clears the recovery flag, then opens the store read-only. The repair uses `Options::cache_size`. It writes only `zoe.redb`: no removal of `zoe.redb.new`, of a file of `blobs/tmp/` or of `staging/`, no replay of an intent file, no sync of a directory, nothing in the blob directory or in its parent. The next writer open does these. `Store::repaired` tells that the open repaired the store; the core logs nothing for it. A failure of the open for writes or of the repair is `RepairFailed`, with the error of the system as it is (for example `Read-only file system (os error 30)`); the open for writes fails before redb writes a byte. Another holder of the lock gives `Locked` before any write.
- A read-only open does not refuse a blob directory without a layout file. `Store::check_blob_dir` makes the check of a writer open on demand: `MissingBlobDir` when the store has blob records and the blob directory has no layout file. `Store::has_blob_file` tells if the file of a blob record exists, without a read of its bytes.
- The `txn_oids` key space is the transaction index. It has one key per record: the tid, then the oid, both big-endian. Its value is empty. `WriteTxn::put_record` writes the record and its index key in the same backend write transaction, and `WriteTxn::remove_record` removes both in the same write. So every commit and every restore indexes each of its records, a deletion included, and a crash leaves both or neither. A blob record has no index key of its own: the record of the same `(oid, tid)` has it.
- `Backend::txn_oids` and `Backend::indexed_tids` read only the index keys of their tid range, and `Backend::txn_records` only the index keys of one tid. The redb `indexed_tids` keeps only the tids, at most `limit` of them. The trait default goes through `txn_oids` and holds every oid of the range, so a backend must override `indexed_tids` to bound the memory of the iterator. The iterator takes the tids of its range from `indexed_tids` and the oids of each transaction from `txn_records`. Neither scans `records`. So a read of one transaction, or of a tid range, costs the size of its result, not the size of the store.
- Each scan of the index checks that each key is inside its range and after the key before it, as the scans of `records` and `txns` do. A key that breaks this raises `CorruptTxn` with its tid. `txn_records` uses the tid of each key, never only its oid.
- `WriteTxn::remove_record` refuses a record without its index key with `CorruptTxn`. A pack batch that meets one fails and removes nothing, so pack never erases the evidence of a damaged store.
- A store without the `txn_oids` table fails to open with `Format`. No migration exists, because no real store was written without the index.
- Only tests call `remove_index_key_for_test` and `remove_record_for_test`. They damage a store on purpose. Only the feature `testing` builds them.
- An error in `finish` leaves the outcome unknown until the store is reopened. Until then, every later finish is refused with `Halted`.
- Every record carries a codec byte, a branch id and a typed-field-slot header. Every blob record carries its BLAKE3 hash. This holds from the first store written.
- `CODEC_NONE` is 0 and stores the data as it is. `CODEC_ZSTD` is 1 and stores one zstd frame that states the data length. These values never change. An unknown codec on read is a `Format` error, never data.
- The checksum and the payload length cover the payload as stored. A read verifies the checksum before it decompresses.
- `decode_frame` decodes every codec. A read path gets the data, never the stored form.
- Compression never changes what a load returns. A store reads every codec, whatever its `compression` option.
- Blob records and intent files are written with `encode_frame`, so they keep the codec `CODEC_NONE` whatever the `compression` option. A blob file is never compressed.
- A record is kept compressed only when zstd makes it smaller. Otherwise it is stored as it is, with codec 0. The zstd level is an option, 3 by default.
- Each thread keeps one zstd compression context, with its level, and one decompression context, and uses them for every record. A new context costs more than the work on a small record. The bytes of a kept context are the bytes of a new one, so the stored frames do not depend on it.
- Decompression is bounded. The length that a zstd frame states is at least 1, at most `u32::MAX` and at most 32,768 times the stored length, and the payload decodes to exactly that length. Any other zstd payload is `CorruptRecord`, never data and never a deletion.
- `max-record-size`, `max-transaction-size` and `max-blob-size` refuse a `store` or a `store_blob` with `TooLarge` before anything is written. The refused call stages nothing. A refused `store_blob` checks the size before it syncs the blob file, and drops the file, which removes it. The size limits come after the order checks, and in `store_blob` after the checks of the file: a call out of order is `Protocol`, and a file of another store or of a closed store is `Protocol` or `Closed`, whatever its size.
- The record size is the length of the pickle. The transaction size is the sum of the pickles that `store` and `store_blob` staged, with the pickle of the call; a later pickle of the same oid replaces the earlier one in the sum. Blob bytes do not count. The checks read the length of a staged pickle, never its bytes, so a spilled pickle costs no read. A size equal to the limit passes. No limit is set by default.
- A restore transaction (`tpc_begin_restore`) checks no size limit: not in `restore`, `store` or `store_blob`, and not on a blob file. A copy never refuses what its source took.
- A lock held longer than `lock-warn` is logged when it is released, also when a lock-wait timeout releases it. Shared locks count. One release logs at most 10 such locks, the first in oid order, one event each with the fields `oid` and `duration_ms`. Then one summary event gives `locks`, the number of such locks, and `max_duration_ms`. The hold time runs from the time when the vote took the lock, so a lock taken before a wait counts the wait.
- A transaction open longer than `transaction-warn` is logged once when it ends (finish, abort, a failed finish or a drop), with `duration_ms`, `oids` (the number of oids that it writes), `oid` (its lowest written oid, if it writes one) and `tid` (if it committed). Its time runs from `Txn::begin`. Both thresholds are off by default. A duration equal to the threshold is not logged.
- A store can have one observer (`Store::set_observer`, the trait `Observer`), for the metrics of a skin. The leader of a commit batch calls `batch_synced` with the number of commits that its sync made durable, after it released the commit sequencer. A batch without a sync does not call it, and `Store::sync` calls no observer method. Each vote that takes locks calls `locks_acquired` once, at its end, with the time of its lock acquisition and of its waits for the durability of commits in flight, measured on `Clock::monotonic` as the lock timeout is, also after a lock-wait timeout. A finish that handed off locks calls `locks_handed_off` with their number. The core keeps no metric and has no metrics dependency. A store without an observer reads no clock for it. Each method has a default that does nothing, so a new method breaks no observer. An observer method must not block or panic: the leader calls `batch_synced` before it gives the members of the batch their outcomes.
- The core emits `tracing` spans, never an OpenTelemetry type, and names no storage: a wait for the lock of an oid is the span `lock_wait` (field `oid`), the write and sync of a commit batch the span `fsync` (field `commits`; a batch without a sync has none), and each batch of a pack the span `pack_batch` (field `records`). They are INFO spans. The lock manager opens and closes `lock_wait` without its mutex. A span changes nothing of what the code does: what a pack removes and when stays the same. A span field holds only oids and counts.
- Logging goes through the `tracing` crate only, as WARN events. A log line holds only oids, tids, counts and durations, never pickle bytes, user or description bytes. A `TooLarge` error holds the oid, the limit and the sizes, never pickle bytes. The locks are released before their log line, so logging never lengthens a hold.
- Pack never blocks readers. A finish waits for at most one batch of a pack: the pack holds the commit sequencer from its last read of the noted finishes to the backend commit of the batch. redb has one writer, so a batch write also waits for a finish, and the other way round.
- A blob file is removed after the removal of its blob record is durable. Before the backend commit of a batch, the pack writes and syncs an intent file in `blobs/tmp/` for each tid of the blob records that it removes. After the commit, it removes the files, syncs their directories, and then removes the intent files. A crash after the commit leaves the intent files, and the next open removes the files that have no blob record. An intent file of the same tid that exists already keeps its oids: the new file names both sets and replaces the old one by a rename.
- A blob file is immutable per `(oid, tid)` and read-only once committed. It lives at the BushyLayout path of `(oid, tid)` under `blobs/`, and `blobs/.layout` holds `bushy`.
- `store_blob` syncs the blob file. `finish` writes and syncs an intent file in `blobs/tmp/`, then renames each blob file into place and syncs its directory, all before the backend commit. A new directory is synced into its parent before anything goes into it. So a durable blob record always has its file.
- The intent file of a deferred commit stays in `blobs/tmp/` after its backend commit. The core removes it only after a durable commit that covers it: a durable batch or `Store::sync`. A crash before that leaves the intent file, and the next writer open removes the blob files that it names and that have no blob record, then the intent file. So a lost deferred restore leaves no blob file, and recovery has no new step. A kept intent file that a pack already removed is not an error. The mutex of the kept intent files is taken only under the commit sequencer, and no other lock is taken under it.
- Known limit: a pack can merge its removal intent into a kept intent file of the same tid. A durable batch or `Store::sync` can then remove that file before the pack commits its batch. A crash after the pack commit and before the pack removes the blob files leaves those files without a blob record and without an intent file. They are orphan files: wasted space, not lost data. Only the converter uses deferred restores, and it runs no pack.
- A directory that exists is not always durable: a killed process can stop between a mkdir and the sync of the parent. So the first blob file of a process syncs the parents of `blobs/` and `blobs/tmp/` also when they exist, and an open syncs the parent of each existing level of each oid directory that an intent file names, from the top down. A finish creates oid directories only after its intent file is durable, so the intent files name every such directory.
- The first blob writes `blobs/tmp/layout.tmp`, syncs it and syncs `blobs/tmp/`, then renames it to `blobs/.layout` and syncs `blobs/`. So the layout file is durable before any temporary file or intent file exists.
- A writer open runs the recovery of `blobs/tmp/` only when the layout file exists, because only such a directory can hold leftovers of the store. A writer open refuses with `NotBlobDir` a blob directory without a layout file that holds anything but an empty `tmp/`, or a `tmp/` with only `layout.tmp`, which a stopped first blob leaves. The first blob checks the same before it writes the layout file. So the store never removes, and never adds a layout file to, a directory of another program. `Vfs::list_entries` lists every entry of a directory for this check.
- Opening a store reads only `blobs/tmp/` and the oid directories that its intent files name, never the whole blob tree. It removes the blob files in the tree that an intent file names and that have no blob record, and syncs the directory of each such oid, also when the file is already gone: an open that a crash stopped can have removed it without that sync. Then it removes the intent files and the temporary files. In `blobs/tmp/` it removes only the regular files whose names the store owns: `<digits>.tmp` (one or more ASCII digits), an intent file (`0x`, 16 hex digits, `.intent`) and `layout.tmp`. Every other regular file stays with its bytes, and other entries stay. With a shared blob directory, `blobs/tmp/` is the `temporaryDirectory()` of each ZEO client, so a restart of the server keeps the uncommitted and savepoint files of the clients. A client that crashed leaves its files there, as with ZEO's server. The rule is the same with or without a shared blob directory or `blob_dir`. The open syncs `blobs/tmp/` after a removal there, and only then.
- A read through `open_blob` checks the size and the BLAKE3 hash at the end of the file. A mismatch or a missing file is `CorruptBlob` with the oid and the tid.
- Every blob file operation goes through the `Vfs`, so the crash simulation covers it.
- `Options::blob_dir` puts the blob directory outside the store directory. In this file, `blobs/` names the blob directory wherever it is. `Relocated` maps `blobs` and the names in `blobs/` onto that directory, and the store directory `""`, the parent of `blobs`, onto the directory that holds it. So the first blob file of a process syncs that directory, and the crash rules stay the same. `open_with` checks the path before it creates anything: it must end in a UTF-8 name, and an existing entry must be a directory. Then it creates the parent of the blob directory, then the store directory, each durably. So a blob directory that fails leaves no lock file and no database.
- The store does not record its blob directory: each open must give the same one. A writer open refuses with `MissingBlobDir` a store with blob records (`Backend::has_blobs`) whose blob directory has no layout file, because the first blob makes the layout file durable before any blob record. So a forgotten or wrong `blob_dir`, or a directory that is not mounted, never starts a second blob directory. Two open stores never share a blob directory: a writer takes an exclusive `flock` on a descriptor of the blob directory itself (`Vfs::lock_dir`), at its open when the directory exists and in the first blob right after it creates the directory, before it reads or removes anything there. `BlobStore` keeps the lock until the store closes. Another holder fails the open, or the first blob, with `Locked`. A filesystem that cannot lock a directory fails the open: the store never runs without the lock. The lock adds no file, so the format does not change. It does not cover a store that opens after another one closed: a crashed store's intent file can meet the open of another store given the same blob directory by mistake, and only a store identity in the format would tell them apart.
- `store_blob_at` and `restore_blob_at` take a file of the blob temporary directory by its path, by rename, never by copy. `Store::blob_temp_dir` gives the path of `blobs/tmp/`; the file can also be in a subdirectory of it. The call checks the transaction first. Then it syncs the file, syncs the directory of a file in a subdirectory, renames the file to a temporary name of the core in `blobs/tmp/` and computes its BLAKE3 hash. So the crash rules of `store_blob` hold: the blob is a temporary file in `blobs/tmp/`, synced before the intent file, placed at `finish`. After the rename the transaction owns the file: an error, an abort or a drop removes it.
- `store_blob_at` and `restore_blob_at` refuse with `Protocol` a path outside `blobs/tmp/` and a name that the core makes in `blobs/tmp/`: `<digits>.tmp`, an intent file and `layout.tmp`. `Vfs::sync_file` refuses a file that is not a regular file, a symbolic link too. The file then stays in its place.
- `store_blob_shared` takes the file `name` in the directory of its oid, as ZEO's `storeBlobShared` gives it. `name` has no `/` or NUL and ends in `.tmp` or `.tmp-`; another name is refused with `Protocol` before the call reads or changes anything. The client created the levels of the oid directory and the file without a sync. So the call syncs the file (`Vfs::sync_file` refuses a symbolic link), then the parent of each level from the top down, then the oid directory, then renames the file to a temporary name of the core in `blobs/tmp/` and computes its hash, as `store_blob_at` does. So the oid directory is durable before `finish` places the blob in it, and the crash rules of `store_blob` hold. A crash before the rename leaves the file of the client in the oid directory: the store never removes it. The shared blob directory trusts its clients as ZEO does: the server and its clients run as the same user. `Vfs::sync_file` refuses a symbolic link only at the moment of the check. A client can put a link in place of the file, of `blobs/tmp/<n>.tmp` or of a level of the oid directory after it, and the rename, the hash and `set_read_only` then follow the link. The crash simulation covers it (`every_crash_image_of_a_shared_blob_opens_without_an_orphan`).
- `restore_blob` and `restore_blob_at` are `restore` with a blob, the `restoreBlob` of ZODB. The record gets the current serial of the oid as its previous serial, a change of the oid before the vote fails the vote with `Conflict`, and `vote_resolving` never resolves it. `store_blob` in a restore transaction takes the serial of the client and checks it at the vote. `restore_blob` refuses an empty pickle with `Protocol`, because a deletion has no blob.
- A staged blob stays with its oid until `finish` or `abort`, also across the two votes of `vote_resolving`. A later `store` of the oid, the store of a resolved conflict too, and `restore` replace only the pickle and keep the blob, as ZODB's blob storages do. A restored deletion drops the blob. A second `store_blob` of the oid replaces the blob.
- A read-only open writes nothing under `blobs/`: no intent replay, no removal in `blobs/tmp/`, no directory sync. It only checks the layout file. A blob file that a crash left without its blob record stays invisible to it, because every blob read starts from the blob record, and the next writer open removes it. `new_blob_file` and `blob_temp_dir` fail with `ReadOnly`.
- A staged blob holds only a weak reference to the store, as a blob file does. So it works the same in `Txn<&Store>` and in `Txn<Arc<Store>>`.
- Nothing is undoable past the last pack. `pack_watermark` in `meta` holds the tid of the last pack, and `Store::pack_watermark` reads it. The first backend write of a pack writes it, in the same write as the first removals. A store that was never packed has no such row and reads as `Tid::ZERO`.
- `Txn::undo(tid)` stages the undo of the transaction `tid` (`crate::undo`, `commit/undo.rs`). It refuses with `Undo` the tid 0, a tid at or before `pack_watermark` and a tid that has no transaction row, and with `Protocol` a restore transaction and a transaction after its vote. It holds every record of `tid` in memory at once (`Backend::txn_records`), as the transaction iterator does for one transaction. For each oid of `tid`, the current state is the record that the transaction staged for the oid, else the committed record. When that state is byte for byte the record of `tid`, the undo stages the record before `tid` over the serial of the current state, or a deletion when the record of `tid` has the previous serial `Tid::ZERO`. The revisions of a blob have one pickle, so when the current state is not the committed record of `tid` itself and its blob record is not the blob record of `tid`, the undo fails with `Undo`: it never drops a later revision of a blob, where FileStorage gives the earlier blob back. A previous serial whose record is gone, which only a pack of an unreachable object leaves, fails with `Undo`. Else the tiers merge the record of `tid` (old), the current state (committed) and the record before (new), through `commit::undo_tiers`, which picks the tier with `Tier::of` and merges with `Tier::merge`, as the vote does: tier 1 for a class of BTrees or `Length`, tier 2 for a class that the merge policy names, each in its mode. In an undo, a field of strategy `lww` that both sides changed refuses as `strict` does (ADR 0046, section 4). A merge in mode `on` is staged over the serial of the current state, a refusal fails with `Undo`, and no answer, mode `shadow` or `off`, or a class of no tier gives the oid back in `Undone::conflicts` and stages nothing for it. A merge of shadow mode of an undo goes to the resolution log only: the check of the resolution of the caller (`Txn::verifications`) is for the merges of the vote. A creation, a deletion, a current deletion or a blob that a later transaction changed fails with `Undo`. The undo takes no lock: the vote locks the staged oids and checks their serials as for `store`. Its pickles count toward the size limits. A failed undo can leave earlier oids staged, so the caller aborts the transaction.
- The entries of the merges of the undos come first in `Txn::resolutions`, and a vote keeps them (`undo_resolutions`, `Txn::undo_resolution_count`). `Txn::resolution_log_lines_of` gives the lines of a range of entries, so the in-process storage writes the lines of an undo when it ends, also when it fails, and the vote writes only its own; `zoe serve` stages its undos in the vote and writes all the lines of the vote. `Txn::natively_resolved` gives only the merges of the vote. Their lines of the resolution log say `"undo":true`.
- The vote of a transaction that undoes checks, with its locks held, that the lowest undone tid is after `pack_watermark`, so the common case fails before the finish. The transaction records that tid as soon as the undo passes its own check of the watermark, before it stages anything. A read of the undo that fails while a pack has passed the undone tid (a missing row, record or record before, or a count that does not match) gives `Undo`, not `CorruptTxn`. The finish checks the watermark again, under the commit sequencer, and fails only its member with `Undo` when the tid is not after it, as a restore tid that fails its check fails only its member: a pack that ran after the undo read its records can have removed what the undo gives back. The store does not halt.
- A blob undo stages the blob of the record before through `BlobStore::link`: a hard link of the committed blob file to a new temporary name in `blobs/tmp/`, through `Vfs::hard_link`, which `finish` renames into place as any other blob, without `set_read_only`, because the committed file is read-only already. No byte is copied, and no blob file is written again. The blob record copies the hash and the size of the earlier blob record. When the filesystem cannot link (`CrossesDevices`, `PermissionDenied`, `Unsupported`, `EMLINK`, and `ENOTSUP`, which FAT and exFAT give on macOS and Rust does not map to `Unsupported`), the link copies the bytes into a new temporary file and syncs it: a new file, so still no file is written again. `Vfs::hard_link` is a required method: `OsVfs` makes a link, the simulator of `zoe-server` forwards it to its `MemVfs`, and `MemVfs` gives the new name the bytes of the old one, recorded as `Op::Link`, durable with a sync of the directory of the new name.
- `Store::undo_log(before, limit)` gives the rows of at most `limit` transactions before `before`, newest first, after `pack_watermark`, from `Backend::txns_before`. The redb backend reads back from `before`, so a read costs the size of its result. The default of `txns_before` reads every row before `before`. `zoe_core::undo_id` gives the base64 text of a tid, as FileStorage gives an undo id, and `undo_tid` reads it back, or 8 bytes of a tid.
- A pack at `at` packs at T, the lower of `at` and the last tid. A pack at a tid before `pack_watermark` does nothing. One pack runs at a time. A halted store refuses a pack with `Halted`, and a read-only store with `ReadOnly`, before the pack reads anything.
- Pack at T keeps every record after T. For each oid that a reader at or after T can reach, it keeps the newest record at or before T, also when that record is a deletion. It removes every other record at or before T, with its blob record and its blob file. It removes rows of `records`: it writes no deletion record.
- The roots of the mark are the root oid and each oid that a record after T refers to. The mark follows the references of the newest record at or before T of each oid that it reaches. Weak references (`w`) and references into another database (`m`, `n`) keep nothing.
- References come from `zoe_pickle::persistent_ids`, never from an unpickler. It reads opaque nodes too, and it decodes with a node budget equal to the record length. Any refusal is a hard error: a record that the mark reads and that does not decode fails the pack with `Format`, whose text names the oid and the tid of the record, before the pack removes anything. Such a record that a finish writes during the pack stops the pack before its next batch.
- `Options::pack_gc` false packs without garbage collection, as FileStorage's `pack-gc` does. Such a pack at T has no mark and reads no reference, so a record that does not decode does not stop it. It keeps every record after T and, of each oid, the newest record at or before T, whether a reader can reach the oid or not. When that record is a deletion, it removes each record of the oid at or before T, with their blob records and blob files. It reads the newest record at or before T of each oid to tell a deletion, so a record there that fails its checksum stops it with `CorruptRecord`. The finishes still note their oids, for the report only. The batches, the watermark, the intent files, the stop between batches and the rule that a finish waits for at most one batch stay the same. A dry run of such a store selects what such a pack removes. `pack_gc` is an option of the open store, true by default, and the store does not record it: `Store::pack` keeps its signature, and a store packed both ways stays valid. With `pack_gc` true, a pack is the pack with garbage collection of the invariants above.
- A finish during the pack writes records after T only, so the records at or before T change only by the removals of the pack. While a pack runs, each finish notes its tid and its oids under the commit sequencer, after its backend commit. Before each batch, under the commit sequencer, the pack reads the noted records and marks what they refer to, and then commits the batch. So a record that links an object again keeps it, when the record is durable before the batch that would remove the object.
- A client that links an object from a reference that it read before T can link an object that an earlier batch removed. ZODB's own pack has the same limit. Pack does not detect it.
- The batches remove records in key order, and the records of one oid from the oldest. So the newest record at or before T of an oid goes last, and a crash between two batches leaves the newest record of each oid that the pack did not finish.
- The scan cursor of the plan names the next key, an oid and a tid. A plan skips the records of the oid at the cursor that a plan before it selected. So the selection does not depend on the removals of the batch before it.
- A crash at any point of a pack leaves a store that opens without repair. Each batch is one backend write transaction. A later pack at the same tid removes what the crashed pack left.
- `Store::pack_until(at, stop)` calls `stop` after each batch, and only there: never during the mark and never inside a batch. When `stop` returns true, the pack ends with `Closed`, an existing variant, and removes no more. A stopped pack leaves the store of a crash between two batches: it opens without repair, and a later pack at the same tid removes what the stopped pack left. `Store::pack` and `Store::pack_in_batches` never stop. Only the stop of `zoe serve` stops a pack.
- The mark holds the set of reachable oids in memory, so the memory of a pack grows with the number of objects.
- The backend has no pack method. Pack goes through `Backend::record_keys`, `Backend::pack_watermark` and the removal methods of `WriteTxn`.
- An error of the backend write of a pack batch leaves its outcome unknown, so the pack empties the commit sequencer, as a failed `finish` does. Every later finish and pack fails with `Halted` until the store is reopened.
- A record that fails its checksum stops the pack with `CorruptRecord`, which names its oid and tid, also when nothing reaches the record. A pack never deletes the evidence of a corruption.
- `replace_txn` keeps the branch id and the previous serial of the row that it rewrites. It refuses a row with typed-field slots with `Format`, because it cannot write them.
- The report reads the class of a removed record from its class pickle alone (`zoe_pickle::decode_class_name`). Only `persistent_ids` decodes a whole record, one record at a time.
- The report keys a class by `module.name`. A deletion, a record of a persistent class and a record whose class pickle does not decode go under `PackReport::UNKNOWN_CLASS`, `<unknown>`. That key holds no dot, so no class key is equal to it.
- `Store::pack_dry_run(at)` reports what `pack(at)` would remove, in the same `PackReport`. It packs at the same T and does nothing before the same watermark. It runs the code of pack: the mark, the plan, the confirmation and the report. It adds each selected record to the report and removes nothing. With no commit between them, the dry run and the pack give equal reports.
- A dry run writes nothing. It opens no backend write transaction, writes no watermark and no intent file, removes no blob file, and the finishes note nothing for it. It holds the commit sequencer only to read the last tid. A read-only store runs a dry run, and a halted store refuses it with `Halted`. A dry run holds the lock of a pack, so a dry run and a pack never run together.
- A record that fails its checksum stops a dry run with `CorruptRecord`, and a record that the mark reads and that does not decode stops it with `Format`, as for a pack.
- A dry run holds the reachable oids of the mark, as a pack does, one batch of selected records and the report. The report has one entry for each class, so it grows with the number of classes, not with the number of records.
- ADR 0025 records the decisions of pack and of the dry run.
- Every writable open syncs the store directory, also when `zoe.redb` exists, so a creation or a rename that an earlier open left unsynced becomes durable before the open acknowledges anything.
- A store creates its database as `zoe.redb.new`, syncs it, renames it to `zoe.redb` and syncs the directory. After a clean close, opening never repairs a store. After a killed writer, the first writer open repairs the file and can take longer: redb rebuilds its free-space map (see "Known limits"). Apart from that, opening only removes a `zoe.redb.new` that a crash left before the rename, and the leftovers of an unfinished commit: the blob files in the tree that an intent file names and that have no blob record, then the files in `blobs/tmp/` whose names the store owns, and the spill files in `staging/`.
- `next_oid` in `meta` is always greater than every committed oid.
- `finish` raises the next oid of the store above every oid that it writes, before the write. So `new_oid` never gives an oid that a restore wrote.
- A sequence gives values that are unique and strictly increasing per store and per name. The first value is 1. Within one open store, the values of a name are consecutive, across threads. When no value below `u64::MAX` is left, `next` fails with `Protocol`.
- The store reserves sequence values in blocks of 100. A reservation is a backend write transaction of its own, and it writes only the row of the name in `sequences`. The row holds the end of the block: the first value that the store has not reserved. The write is durable before `next` gives a value of the block. An open store reads the stored end at the first use of a name and starts there. Each later block starts at the next value of the name, so a retry after a failed write writes the same end. So a crash or a reopen never gives a value twice. Each reopen, after a crash or not, skips at most 100 values of a name. The skips add up: a session that reserves a block and gives none of its values adds the whole block to the gap that a caller sees. That happens when it crashes right after the reservation, closes before it gives a value, or gets an error from a reservation whose row reached the disk all the same. Values stay unique and increasing. The stored end never decreases.
- `Sequence::restore_end(end)` raises a sequence so that its next value is at or above `end`, and lowers nothing. When the reserved values of the open store end below `end`, it writes `end` as the stored end, in a backend write transaction of its own, durable before it returns. Otherwise it only skips the reserved values below `end`. It holds the mutex of the name, as a reservation does. The stored end never decreases. A failed write can reach the disk all the same, so after it the open store forgets the block of the name, and the next call reads the stored end. A read-only store refuses it with `ReadOnly`. A restore of dumps calls it, so that no value of the source store comes again (ADR 0030).
- A sequence value is not part of a transaction: an abort does not give it back. `next` takes no per-OID lock and not the commit sequencer. One mutex per name orders the allocations of the name, and a reservation holds it. So `next` waits only for that mutex, and a reservation also waits for the single writer of the backend.
- Pack never reads or changes the `sequences` key space.
- The blocks of the sequences live in the memory of the process. A `fork()` after the open copies them, so the parent and the child can give the same values. No ZODB storage is safe across a `fork()`: open the store after it.
- The core reads the time only through the `Clock` trait and the filesystem only through the `Vfs` trait, so the crash simulation and the deterministic simulator can replace them. The tids and the durations of `lock-warn` and `transaction-warn` come from the `Clock`. A lock wait uses the monotonic time and a `Waiter` of the `Clock` (`Clock::monotonic`, `Clock::waiter`), and the time of a lock acquisition that the observer gets uses the same monotonic time. Their defaults use `Instant` and a `Condvar`, and a simulator gives its own, so a lock wait runs on simulated time. A `Waiter` has permit semantics: a `wake` before the `wait` is not lost. A request takes a waiter only when it must wait. The lock manager never calls the `Clock` or a `Waiter` under its mutex, so a slow clock stops no other lock request, and a clock that panics leaks no lock. `Waiter::wake` must not panic, because the drop of a transaction can call it during the unwind of a panic.
- `MemVfs::crash_now` gives the state that a crash leaves now: every synced operation and a prefix of the pending ones, in their recorded order, as a new filesystem with an empty record. The deterministic simulator of `zoe-server` takes its crash images with it.
- A change to an existing `Backend` or `WriteTxn` signature is a stop-and-ask. A new method needs no stop while no crate outside `zoe-core` implements the traits, unless it needs a new key space, `meta` key or frame field: that is a data-model change, a red zone and a stop-and-ask.
- `Options::cache_size` is the most bytes that the page cache of redb holds, for a writer open and for a read-only open: the pages that the reads keep and the pages that a write buffers. `None`, the default, keeps the default of redb, 1 GiB. The cache does not grow with the size of the store, so it bounds the memory that the reads of a large store cost (N6).
- An open reads the free-space map of redb, about 128 bytes for each MB of the file, then a fixed number of pages: the format, the object count, the transaction index table, the last tid, the last transaction row and the next oid. It rebuilds no index. So N7 holds after a clean close. After a killed writer, the first writer open repairs the file and can take longer (see "Known limits"). A new step of the open that reads every record, every key or every blob breaks N7.

- The KV namespaces (ADR 0043) live in three key spaces: `kv_ephemeral` (tag 7) and `kv_durable` (tag 8), one row per key, and `kv_expiry`, the index of the expiries. The key of a row is the length of the name in one byte, the name, then the key (`format::kv_key`). A name is 1 to 255 bytes of UTF-8, a key 1 to 1,024 bytes. The keys of the tables are bytes, never `&str`. The payload of an ephemeral row is its expiry, a little-endian `u64` of milliseconds since the Unix epoch, then the value. The row of a durable namespace with the empty key is its generation row: the tid of the last commit that wrote the namespace. A key of `kv_expiry` is the expiry big-endian, then the key of the row; its value is empty.
- The first write of a flavour creates its tables. A store that never writes a namespace has no namespace table and keeps its bytes. The format name stays `ZOE format 2`.
- `Txn::kv_set` and `Txn::kv_delete` stage a namespace write between the begin and the vote, from the thread that drives the transaction. They share the staging of the pickles: the key of each row and its value count in `staging-memory`, and a value that does not fit goes to the spill file while its key stays in memory. A later write of a key replaces the staged one. A value counts toward `max-record-size` as a pickle does, and the key of its row and the value count toward `max-transaction-size`; a refusal is `KvTooLarge`. A bad name, key or TTL is `InvalidKv`. A call after the vote or in a restore transaction is `Protocol`. A refused call stages nothing.
- A namespace write takes no lock. The vote checks nothing for it. When two transactions write one key, the commit with the later tid wins.
- The leader of a commit batch writes the namespace writes of each member after its records, in the backend write of the batch. An ephemeral key gets the expiry of the time of that write plus its TTL, and its key in `kv_expiry`. Each durable namespace that a member writes gets the tid of the member in its generation row. A delete removes the row and leaves its index key. A transaction with only namespace writes commits with a tid and a transaction row with an oid count of 0.
- An abort, a failed vote and a drop drop the staged namespace writes. An acknowledged namespace write is as durable as the records of its commit.
- A read of a namespace gives the last committed value, not the value at a snapshot. It verifies the checksum before it reads the expiry, so a flipped bit is `CorruptKv`, never an expired, absent or other value. An expired key reads as absent. `CorruptKv` names the flavour, the namespace and the length of the key, never the key. A scan gives at most `SCAN_LIMIT` pairs, and stops after the pair that brings its keys and values to `SCAN_BYTES`, so its reply holds at least one pair and stays near that size. A reply with fewer pairs than the limit is not the end of the range.
- A sweep step (`Store::sweep`) takes the keys of `kv_expiry` with an expiry at or before now, at most its limit, in key order, and removes them in one backend write with a sync. In the same write it removes the row of each key when the row passes its checksum and its own expiry is at or before now. So a refreshed row stays, a damaged index key never removes a live key, and a row that fails its checksum stays. The core starts no thread for it: the skins run the steps.
- Pack never reads or changes `kv_ephemeral`, `kv_durable` or `kv_expiry`. After its last batch of records, a pack at T removes each transaction row before T whose oid count is 0, the row of a commit that wrote no record (ADR 0043), at most a batch of rows in one backend write under the commit sequencer. The row at T stays: a pack at the last tid keeps the last transaction, which a later backup and the clients name. A row with an oid count of 0 and keys in the transaction index stops the pack with `CorruptTxn`, and stays.
- `Store::verify_kv` checks every namespace row for `zoe verify`. A finding names the namespace and the xxh3-64 hash of the key, never the key.

## Known limits

- An open after a killed writer reads every page of the database file. The commits are not two-phase, so redb has no valid free-space map after a kill, and it rebuilds it with a walk of every page. The repair commit is two-phase but writes no free-space map, so a second kill before a clean close repairs again. A clean close writes the map, and the next open reads it. `open_read_only_repairing` runs the same repair, so the first tool that reads such a store takes as long, shows no progress and cannot stop. It needs write access to `zoe.redb`: on a read-only file system it fails with `RepairFailed`.
- `meta` has no frames, so a flipped bit in `object_count` is outside the bit-flip gate, as for `last_tid` and `next_oid`. The count is then wrong, and later writes add to and subtract from the wrong value. `zoe verify` compares the count with the oids of `records` and reports a difference.
- redb walks every page of the database at each open when its debug assertions are on. The workspace builds redb without them in the dev profile, so the tests of a debug build start a large store as fast as a release build does.

- Four faults of redb with a damaged database file, to file upstream later. Do not file them from a card.
  - redb does not verify its page checksums on a read, only in `check_integrity`.
  - The walk of `prepare_leaf` has no bound. A damaged page can make it loop, and the read hangs.
  - The commit that closes the database can panic on a damaged page tree, then panic again while it unwinds. That double panic aborts the process.
  - redb decodes a `&str` key with `from_utf8(..).unwrap()`: when it gives the key, and in each comparison of a lookup. The tables `sequences` and `meta` have `&str` keys. A flipped bit can make a stored key invalid UTF-8. Then a lookup in that table that compares against the damaged key panics, for example `sequence_end` or the reservation of `Sequence::next`. `Backend::sequence_names` catches the panic of its scan and returns a `Backend` error with redb's `Corrupted`, so `zoe verify` reports one finding. The default panic hook still prints the panic message to stderr. The key type stays `&str`, because a change of a table definition is a format change.
