# zoe-loupe

The Rust side of Loupe, the desktop inspector and editor. Specification: "Loupe: desktop inspector and editor".

## Invariants

- Loupe never opens a `Data.fs`. It converts one.
- Folder mode opens a store with `Store::open_read_only` (`Folder::open`). `Folder::open_with_blob_dir` opens it with `Store::open_read_only_with` and a blob directory, for `zoe mcp`; the window of Loupe uses `Folder::open`. It holds the store lock, so a running instance and Loupe never share a store. It never writes to the folder: the acceptance test compares the bytes of every file before and after browsing.
- Every decode goes through zoe-pickle, with the default node budget (`decode_record`) and one `Tree::resolver()` per record. A record that zoe-pickle refuses gives an `Object` with the refusal in `error`, not an error of the call and not a crash. `persistent_ids` runs only after `decode_record` accepts the record, so its own decode stays inside the default node budget. The first tree is dropped before it, so one tree at a time is in memory.
- The state of an object is JSON. The module documentation of `src/state.rs` gives the form of each node. A memo get shows the value that it stands for. A get inside its own value is a cycle marker. A dict with a key that starts with `$` is a list of pairs, so no key of the store looks like a tag. So is a dict with a key longer than 256 bytes, because each key is a segment of the pointers below it.
- A crafted record cannot exhaust the stack, the memory or the time of a call. The JSON has a depth limit and a value budget. Each text, bytes, opaque or large-int value has a cap, and the state has a text budget. Both count the bytes of the JSON, escapes and hex digits included. A value that is cut shows its start and its size in the record. The decoders and the int formatter read no more of a value than the cap needs.
- Each get of one value at one depth converts the value once. The other gets reuse its JSON and pay for it from the budgets. The reused JSON holds at most 2^18 values in all, so a chain of gets cannot multiply the memory. A JSON with a cycle marker for a value outside it is not reused, because the marker is wrong in another place.
- `references` lists the strong persistent references of the record, in pickle order, as ZODB's `referencesf` gives them: `zoe_pickle::persistent_ids` gives the list, as it does for pack, so the references inside opaque nodes are in it too. Each reference has a JSON pointer into `state`, and the value at the pointer holds the reference, except a reference from the class pickle. A reference that the state shows points to its place, and each place serves one reference of its oid. A memo get adds no reference: the place of the value has it. Each other reference points to the deepest value that holds every place where a reference that the state does not show can be: an opaque node, a persistent id that Loupe does not read (such as one built from memo gets into an opaque node), and a value that the state leaves out. With one such place, the reference points to it. A persistent id in the class pickle, as an instance of a persistent class has, is not in the state; then those references point to the root. A weak reference and a reference to another database show in the state only. A pointer has a cap, and the pointers of a state have a budget: past them, a reference points to a value that holds it, at most the root. No reference is left out.
- A record whose references `persistent_ids` refuses, or with an oid that is not 8 bytes, gives an `Object` with its state, no references, and the refusal in `error`. A list that misses a reference and says nothing is false.
- Ids cross the IPC boundary as ZODB-form strings, as `ZODB.utils.oid_repr` writes them: `0x00`, `0x0100`.
- A view as of a tid, a `Snapshot`, reads every record with `load_before` at that tid, the steps of a path included. The view includes its own tid. So it never mixes the revisions of two tids. The folder reads through the view of its last tid.
- An object with no record at or before the tid of a view gives `NoRecordAsOf`. A deletion at or before that tid gives the store error `NotFound`.
- The history of an object comes from `Store::history`, newest first, with at most `HISTORY_LIMIT` revisions. A user or a description shows at most 4 KiB of the record, and bytes that are not UTF-8 become U+FFFD.
- A diff compares the decoded trees, not the bytes. It walks the two JSON states and the trees under them together: into a dict with text keys by key, into a tuple or a list by index. Every other pair of values compares in the trees, as Python compares them with the type counted. Key order, memo puts and opcode width are not changes. A set compares by item, a reference by oid, an opaque node by its bytes. A NaN equals a NaN, and the sign of a zero counts, so the diff shows each difference that the pane shows. The module documentation of `src/diff.rs` gives the rules.
- Known limit: the type of a dict key or a set item counts. Python finds `1`, `1.0` and `True` one key; the diff finds three keys.
- A deletion has no state. A diff against a deletion is one change of the whole state, `""`, without a value on the side of the deletion. `load_before` gives `NotFound` for a deletion and for an oid without a record; only the oid of a deletion has a history, and that tells them apart.
- The budgets and caps of the state also apply to a diff. Its inputs are the JSON states with every limit of `state`. A value that the JSON cuts or leaves out still compares whole in the tree, and a change in it shows as a change of that value. The pointers of the changes have the cap and the budget of the reference pointers: past the cap, a change shows at a value that holds it; past the budget, the diff is one change of the whole state. The comparisons have a work budget. Each pair of nodes, each item or entry that a comparison collects and each byte that it reads takes from it, and a comparison checks the lengths before it collects. Past the budget, each pair that the diff did not compare is a change. The JSON cannot replace the comparison, because it gives a tuple and a list one form, and bytes and a Python 2 `str` too. So past the budget a diff can show a change that is not one, but it never misses a change. The comparisons use explicit stacks, so a deep value cannot overflow the stack.
- A diff decodes each of its two records once and makes one `Tree::resolver()` for each. The JSON conversion and the comparison share it.
- The space screen reads only, as of the last transaction, whatever the "as of" switch holds. `Folder::space` reads every current record with `record_iternext` and every transaction with the iterator of the core. It keys a class by `module.name` from the class pickle alone (`decode_class_name`), or by `PackReport::UNKNOWN_CLASS` when the class pickle gives no name. A deletion is not a current record, and it adds 0 to the growth. A blob counts with the size of its file. A blob record without its file is `CorruptBlob`, as for a read of the blob. The growth has one entry for each transaction.
- The size of a path counts each object once. One walk from the object at the path follows the strong references that `Object` gives: none for a record that zoe-pickle refuses. Each object adds the size of its current record. A reference to an oid without a current record adds nothing. `path_size` is this walk, and the `reach` of `path_space` is the same walk.
- The items of a path are the names that a step of a path can take from its object, by the rules of `resolve`. Each name is one segment. The items share the size of the path: the walk goes breadth first, an item owns itself, and each other object takes the owner of the object that the walk reached it from first. The object at the path owns the start. So the object, the listed items and `others` add up to the size of the path. An item that the walk does not reach, such as a weak reference, is not listed. `path_space` lists at most `ITEM_LIMIT` items, biggest first, and adds up the rest in `others`.
- What a pack would reclaim is the report of `Store::pack_dry_run`, unchanged. `Reclaim` only gives it a JSON form.
- Each long call takes a progress function. The call runs it after each item that it reads: a record, a transaction, an object or a BTree node. When it gives `Break`, the call stops with `Stopped`. The dry run of the core has no steps, so it cannot stop.
- A walk of a path holds the set of the oids that it reached, so its memory grows with the number of objects, as for the mark of a pack.
- A path starts at `root["Application"]`. Each segment goes through the key of a BTree or a mapping, the `_tree` item of a folder, or an attribute that holds a reference. A BTree lookup reads the separating keys to pick one child when they have the type of the segment. A BTree with int keys, such as an `IOBTree`, holds only a segment that is an int.
- Every Loupe write is one ZODB transaction: user `loupe:<operating-system user>`, a description that the operator types, and extension data with the tool name and version.
- Writes need expert mode for the session.
- Opaque pickle nodes are not editable.
- A delete is refused while inbound references exist, unless the operator chooses cascade.
- Every commit shows the pickle diff first.
- Credentials live in the operating-system keychain, never in a configuration file.
