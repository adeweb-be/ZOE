# zoe-server

The `zoe` command: the binary `zoe`, its subcommands, and the `zoe serve` process, a tokio server that speaks the ZEO 6 msgpack protocol. Specification: "Server mode", the naming table, F8, F14, F25 and F26. ADR 0028 records the decisions of the command.

## Layout

- `src/main.rs`: the binary `zoe`. It only calls `cli::main` and exits with its code.
- `src/cli/`: `zoe_server::cli`, the command line. `mod.rs` parses and runs, `convert.rs` holds `zoe convert`, `pack.rs` holds `zoe pack`, `verify.rs` holds `zoe verify` and its `--backup`, `backup.rs` holds `zoe backup`, `restore.rs` holds `zoe restore`.
- `src/cli/serve.rs`: `zoe serve`. Without the feature `serve` it fails with 1 and names the `zoe` binary.
- `src/cli/config.rs`: the TOML configuration file of `zoe serve`. It compiles only with the feature `serve`, so the extension never links the TOML parser.
- `src/cli/mcp.rs`: `zoe mcp`. It calls `zoe-mcp`. Without the feature `serve` it fails with 1 and names the `zoe` binary.
- `src/serve.rs`: `zoe_server::serve::{Server, ServeOptions, StorageOptions}`, the server as a library. The binary and the Rust tests run it.
- `src/admin.rs`: the admin port, a small HTTP/1.1 server with `/healthz`, `/readyz` and `/metrics`. `respond` routes a path to its reply: a new path is one arm there. It compiles only with the feature `serve`.
- `src/protocol/`: the frames, the messages, the extension pickle, the negotiation of the ZOE extensions (`negotiation.rs`), the session of a connection, the concurrent calls of a connection and the read pool (`pipeline.rs`), the iterators of a connection (`iteration.rs`), the blob streaming (`blob.rs`), the status of a storage, the times of the protocol, the invalidations of a storage (`invalidation.rs`) and the two queues of each connection (`outbox.rs`) and the metrics of each storage with their text format (`metrics.rs`). It compiles only with the feature `serve`.
- `src/runtime.rs`: the trait `Runtime` (spawn, spawn_blocking, sleep), `Tokio`, its implementation for production, and `block_on`, the wait of a blocking thread for a channel. It compiles only with the feature `serve`.
- `src/sim/`: `zoe_server::sim`, the deterministic simulator (N18). `mod.rs` holds the API (`Simulation`, `Faults`, `Report`) and the driver, `world.rs` the shared state, the timers and the baton of the threads, `net.rs` the simulated network, `disk.rs` the clock, the waiter and the disk of the store, `server.rs` the runtime of the simulation and the accept of a connection, `client.rs` the clients on `zoe-client`, `rng.rs` the seeded numbers. It compiles only with the feature `sim`.
- `src/protocol/fuzz.rs`: `zoe_server::fuzz`, the entry of the fuzz targets. It reads bytes as the server reads the bytes of a client. It compiles with the feature `fuzz`, and in the unit tests, so `just check` and `just test` cover it.
- `fuzz/`: the cargo-fuzz targets `frame` and `handshake`, and their seeds in `fuzz/corpus/`, which `fuzz/corpus/generate.py` writes from the wire traces. It is a workspace of its own with its own `Cargo.lock`. `just check` checks its format and that its lock needs no change. `just fuzz` builds and runs the targets.

## Invariants of the command

- One binary, `zoe`, in this crate. The console script `zoe` of the `zoedb` wheel calls `zoe_server::cli::main` through `zoe._zoe.main`. So both run the same code. Never add a second parser.
- `cli::main(args: Vec<OsString>) -> i32` takes the program name first and returns the exit code. It never exits the process and never panics on a user error.
- The subcommands and their names follow the naming table of the specification.
- Every option has a `ZOE_*` environment twin in SCREAMING\_SNAKE: the option name without `--`, in capitals, with `_` for `-`. The help of the option names its twin. An option on the command line wins over its twin.
- The store is `--path` (`ZOE_PATH`) in every subcommand. The blob directory of a `Data.fs` is `--data-fs-blob-dir` (`ZOE_DATA_FS_BLOB_DIR`). The blob directory of the store is `--blob-dir` (`ZOE_BLOB_DIR`, the twin of the key `blob-dir` of the `<zoe>` section) in `zoe verify`, `zoe convert` and `zoe serve`, `<path>/blobs` by default. In `zoe serve`, it is the blob directory of the store of `--path`, a key of the configuration file too, and it needs `--path`: a `[storages.NAME]` table has its own `blob-dir`. `zoe convert --from-data-fs` puts the blobs of the store there.
- `zoe serve` serves the store of `--path` under the storage name `1`, each store of `--storage NAME=PATH` (`ZOE_STORAGE`, one store) under `NAME`, and each store of a `[storages.NAME]` table of its configuration file. One store at least is necessary, and a name that comes twice is a usage error.
- `--config FILE` (`ZOE_CONFIG`) of `zoe serve` reads a TOML file. Its top-level keys are the long names of the options of `zoe serve`, except `config` and `storage`, so a new option is a key of the file with no other change. A key takes a string, an integer or a boolean, and the file gives it to clap as `--KEY=VALUE`, so it has the syntax of the option. The file gives only the options whose value source is neither the command line nor the twin. So the command line wins over the twin, and both win over the file. A `[storages.NAME]` table takes `path` (necessary), `blob-dir` and `read-only`. The stores of the file add to the stores of the command line. `cli::main` reads the file after the parse of the arguments and before it runs the command, and each error of the file is a usage error that changes nothing on disk.
- The exit code is 0 on success, 1 on a failure, and 2 on a usage error. A conversion whose report lists a problem fails with 1, and so does the `Mismatch` of `zoe-convert`. `zoe verify` fails with 1 when its report lists a finding, and `zoe verify --backup` when it lists a difference or a dump does not restore. `zoe backup` with nothing new writes nothing and exits with 0.
- The report goes to stdout. A message goes to stderr, and starts with `zoe <subcommand>:`. The help and the version go to stdout with the code 0. A reader that closes stdout before the end of the report, as `head` does, does not fail the command, because the work is done. A conversion that does not verify still fails.
- The command parses all its arguments before it opens a file. A usage error changes nothing on disk.
- `cli::main` flushes stdout before it returns, because the Python process does not flush the stdout of Rust when it ends.
- `cli::main` does not hold the lock of stdout. `zoe mcp` writes MCP messages to stdout from another thread, and writes no report.
- A command that only reads opens the store read-only. `zoe pack --dry-run`, `zoe backup`, and `zoe mcp` through Loupe's `Folder` use `Store::open_read_only`. `zoe verify` (with `--backup` too) and `zoe convert --to-data-fs` read the blob files: they open the store with `Store::open_read_only_with` and its `--blob-dir`, then call `Store::check_blob_dir` (`cli::open_with_blobs`). A store with blob records whose blob directory has no layout file then fails with 1 before the walk and before the conversion writes anything, and the message names the blob directory and `--blob-dir`. The other commands do not make this check. `zoe restore` creates a store only in a new or an empty directory, after it checked every dump (ADR 0030). A command that writes to an existing store refuses a directory without `zoe.redb` and creates nothing: `zoe pack`. Only `zoe convert --from-data-fs` creates a store. Before it opens the store, it checks that the `Data.fs` is a regular file that starts with `FS30`, so a wrong source creates no store.
- `--days N` gives the tid of the time of the clock minus N days of 86,400 seconds, by `zoe_core::timestamp`. The command reads the time only through the `Clock` trait, so a test gives its own time. `cli::main` uses the system clock.

## Invariants of the server

- This crate uses tokio only under the feature `serve`: the server code, and `zoe-mcp` for `zoe mcp`. The feature is on by default. `zoe-py` depends on this crate without it, so the extension never links tokio or rmcp: `cargo tree -p zoe-py -e normal` must list neither.
- The server has no Python inside and needs no Plone eggs. It ships as one static binary.
- The connection code (`protocol::serve_stream` and what it calls) reaches its tasks, its blocking threads and the time only through `runtime::Runtime`: never `tokio::spawn`, `tokio::task::spawn_blocking`, `tokio::time` or `tokio::net` there. A blocking thread waits for a channel only through `runtime::block_on`, never with `blocking_recv` or `blocking_send`. `Tokio` is the runtime of production, and the simulator gives its own. The accept loop, the stop and the admin port in `serve.rs` and `admin.rs` stay on tokio.
- Every `select!` is `biased;`. By default `select!` polls a random branch first, from a generator that no seed fixes outside a tokio runtime, so the simulator could not run it in one order.
- The simulator is a test feature: only the dev-dependency of this crate on itself turns on `sim`, which brings `zoe-client` and `redb`. A build of `zoe` and `zoe-py` never links it. It runs the production code, not a model: one thread runs at a time, one seed gives one trace, and a simulated wait takes no real time.
- Core calls run on blocking threads of the runtime, never on the async runtime threads. The calls of one connection run concurrently (`pipeline::Calls`). `register` runs first, alone: the reader starts no other call before it ends. So does `set_client_label`, so each later call logs with the label. Each call runs in a `connection` span of its own (`Session::span`), with the label or the peer and the storage at its start. The thread of the transaction drops the transaction in such a span, so the log lines of the abort name the client and the storage. The calls of the transaction (`session::in_transaction`: `tpc_begin`, `storea`, `restorea`, `checkCurrentSerialInTransaction`, `deleteObject`, `vote`, `tpc_finish`, `tpc_abort`, `storeBlobStart`, `storeBlobChunk`, `storeBlobEnd`) wait in the lane of the connection and run in their order on one thread, which holds the `session::Transaction`. That thread starts at the first call and ends when no call waits and no transaction is open. It waits for the next call through `runtime::block_on`, so the simulator runs it. The metrics of the transaction (`Transaction::measure`) read only its own state, so concurrent calls do not change them. So one thread drives each core transaction from `tpc_begin` to its end, and the core never answers `WrongThread`. A new thread starts only after the last one marked its end, under the mutex of the lane.
- `sendBlob` and `pack` (`session::runs_long`) run on a thread of their own, because a download waits for its client and a pack runs long. Each other call runs on the read pool (`pipeline::Pool`): at most `--blocking-threads` (`ZOE_BLOCKING_THREADS`, the number of cores by default, at least 1; `ServeOptions::blocking_threads`) of these calls run at once, for all the connections together, each on a thread of the blocking pool of tokio. The `ruok` status runs there too, so a read pool that is busy delays a health check. So a vote that waits for a lock holds no thread of the read pool, and the loads go on, also with one thread. A call on the read pool never waits for a client or a lock, only for the hub mutex.
- A connection with no call that runs and no open transaction holds no thread. A connection with an open transaction holds the thread of its transaction until the transaction ends, also while the client sends nothing. A connection holds at most 5 threads: the thread of its transaction and 4 calls that run (`QUEUE`), downloads and packs included. A client that reads nothing keeps up to 4 download threads while its reader waits for room, because the idle timeout does not count then. A download runs until it ends, so the idle timeout does not count while it waits for room for a chunk either: the threads of a client that reads nothing stay until it reads or closes. Limit: the blocking pool of tokio has at most 512 threads. The threads of the transactions, the downloads, the packs and the read pool all come from it. When it is full, the calls of the read pool wait for a thread too.
- A call takes a ticket (`pipeline::Ticket`) before it starts, and the reader waits for it: first a slot among the calls of its connection that run or wait (4 slots, `QUEUE`), then room for its reply in the session queue (`outbox::Room`), which holds at most 4 frames (`QUEUE`). So at most 4 calls of a connection run or wait at once, a call never waits to put its reply, and a client that reads or writes slowly slows down only its own connection. A call gives back its slot when it ends. A call without a reply gives back its room when it ends. A download keeps its slot until it ends, puts its first frame in the room of its call, and waits for room for each later frame without holding room, so downloads never wait for each other in a circle. A `loadBefore` that fails puts its error at the place that it took with its room, as a value, so it never waits for the client. An upload or a download holds a few chunks in memory, whatever the size of the blob.
- A frame of the session takes its place and goes into the session queue under one lock of the outbox (`order`), so the session queue holds its frames in the order of their places, whatever the thread. `loadBefore` takes its place under the mutex of the hub and fills it after the call (`outbox::Place`): the place goes into the session queue at once, and the writer waits for its frame. A place that gets no frame is empty. Lock order: the hub mutex, then the lock of the outbox. Only a `loadBefore` place takes the lock of the outbox under the hub mutex. The `push` of the hub never takes it, and no thread waits for the hub while it holds it.
- The server announces `M5` and takes only `M5`. A frame is a 4-byte big-endian length, then the bytes. A reply carries the message id of its call, whatever its msgpack type. The id -1 is a heartbeat and gets no reply. An error goes out with the flags 2 and `[class, args]`, with the class names of ZODB's exceptions. An error of a call without a reply closes the connection, as in ZEO.
- A frame with the id -1 is a heartbeat whatever its other parts: it gets no reply and changes nothing. The bounds of the decode below apply to it too.
- A frame longer than `--max-frame-size` (`ZOE_MAX_FRAME_SIZE`, 256 MiB by default) closes its connection. The server checks the length before it reserves memory for the frame. The limit applies to the frame of the protocol too. A frame inside the limit reserves at most 1 MiB before its bytes arrive. A `storea` or `restorea` frame holds a whole record, so the limit must stay above the largest record: the default is 16 times the size at which ZODB warns about a large record. A copy through the server, as `zodbconvert` to a ZEO client does, fails on a longer record of its source. `ServeOptions::max_frame_size` takes a `NonZeroU32`, and the option refuses 0.
- The decode of a frame has a bound of 100,000 msgpack values, the message included (`MAX_VALUES` in `message.rs`). A scan of the markers and the lengths counts them before rmpv builds any value, and it counts each value that an array or a map announces, so a false count fails at once. A frame over the bound closes its connection. Without the bound, rmpv makes a `Value` of 40 bytes or more for each 1-byte value, so a frame of nils costs about 40 times its size. With it, the values of one frame take at most about 16.2 MiB (measured: chains of arrays of one element, about 176 bytes for each value, because rmpv gives each array room for 4 values). So one frame costs at most its buffer, the copies of its `bin` and `str` values, and these 16.2 MiB: about twice its size, plus 16.2 MiB. A message of a stock client has at most 17 values in the traces of `docs/spikes/zeo-wire/`: a record is one `bin` value.
- A frame that is too long, cut, not msgpack, over a bound of the decode, not a message, or a call before `register` closes only its connection. No input that the tests and the fuzz targets tried made the server panic or abort. `tests/fuzz_smoke.rs` runs in each `just test`, and the targets of `fuzz/` run in `just fuzz`.
- While the reader waits for a ticket, it reads no more bytes, so TCP makes the client wait, and the connection stays open. So a connection holds at most 5 decoded calls: 4 that took their ticket and 1 that the reader holds. The reader drops the bytes of a frame after the decode, before it waits for its ticket. A decoded call costs at most the size of its frame plus 16.2 MiB. At its peak, a connection holds 4 decoded calls, and the frame that the reader decodes with its decoded call: at most about 6 times the frame size plus 81 MiB. That is about 1.6 GiB with frames of 256 MiB that each hold one `bin`, and about 82 MiB with frames of 100 KB. The calls of a transaction stop while a vote waits for the lock of an object. A call of the read pool waits for a thread of the pool. `tests/frames.rs` checks that 64 costly calls behind a vote that waits for a lock add less than 64 MiB to the server.
- The writer task empties the queues of a connection without its reader. So the reader, the calls and the writer never wait for each other in a circle. A client that sends calls and reads no reply stops only its own connection: its replies fill the session queue, then the reader waits for a ticket. A stock client reads its replies while it sends.
- The bounds of memory hold per frame and per connection. Nothing bounds the memory of many connections together, and the replies that wait for a client have no bound in bytes.
- The decode of a frame has a depth bound of 128 steps of rmpv, about 60 levels of arrays or maps. A deeper frame closes its connection, and the server stays up. A stock server takes deeper frames, but a ZEO message nests at most about 3 levels, and a transaction extension nests as deep as its dict.
- `tpc_finish` replies only after the core made the commit durable.
- A client can send `ruok` in place of `M5`. It needs no `register` and is not a connection of the status. The server sends `M5`, then one JSON payload `{storage id: status}` as Python's `json.dumps` writes it, then closes. The status reads the store on the blocking pool.
- `server_status` and the `ruok` reply have the 13 keys of ZEO 6's server, in its order. All the connections of a storage share its counters through `NamedStorage`, and the session counts each call where ZEO counts it. The store has no storage-wide commit lock: `lock_time` is nil, `waiting` is 0 and `timeout-thread-is-alive` is `"stub"`. `conflicts_resolved` counts each conflict that a vote listed and that the second vote then passed; ZEO 6's server keeps it at 0. `conflicts` counts the votes that fail with a conflict, the second vote too.
- `get_info` says `supportsUndo` false and `supports_record_iternext` true. Its `interfaces` are those of `zoe.Storage`, in `__iro__` order: never `IStorageUndoable` or `IExternalGC`. Its `length` is 0, as `len(zoe.Storage)`, and its `size` is the size of the files in the store directory. `get_size_info` gives the same `length` and `size`; a stock ZEO server does not answer it.
- `getTid(oid)` is a read: it needs no transaction and takes no lock. It gives the serial of the record of `oid` before the last published tid plus 1, as `loadBefore` reads, so a client never gets a tid before the invalidation of its commit. It takes no place before its read: its reply goes out after the invalidation of the commit that it shows, and can go out after the invalidation of a later commit, because a stock client keeps nothing of the reply. An oid without a record there, an oid whose records are all after the last published tid, and an oid whose record there is a deletion fail with `POSKeyError` as a reply, and the connection stays open. A stock ZEO server reads the latest record of the storage instead.
- `history` is newest first, with at most `size` entries. A size of 0 or less gives none. The `time` of an entry is `TimeStamp(tid).timeTime()` to the last bit.
- stdout carries only the lines `admin <address>` and `listening <address>`. The logs go to stderr.
- The server logs only through `tracing`, never with `eprintln!`. `zoe serve` installs a `tracing-subscriber` that writes to stderr from the level INFO on: one line of text for each event, or with `--log-format json` (`ZOE_LOG_FORMAT`, the key `log-format` of the configuration file) one JSON object for each line, with the fields of the event and of its spans. Text is the default. A process that has a subscriber already keeps it, and a server that a Rust test starts with `Server::start` installs none. A usage error and a failure of the start are messages of the command, not log lines: they stay plain text.
- Each call of a session runs in the span `connection`, with `client` and, after `register`, `storage`. So each log line of a call has both, the lines of the core too, such as the lock that `--lock-warn` logs. The client is the label of the last `set_client_label` that ended before the call started, with each control character replaced by a space and at most 200 characters, or else, also after an empty label, the address of the peer. A text that a client sends (a method name, a label, the args of a fault) goes only into a field of text, never into the message or a `%` field: the text format writes a `&str` field quoted and escaped, so a line feed cannot forge a log line. `tests/log_lines.rs` checks it. A log line of the connection outside a call has `client`, the address. A log line holds no pickle bytes, user or description.
- `--lock-warn` (`ZOE_LOCK_WARN`) and `--transaction-warn` (`ZOE_TRANSACTION_WARN`) are `lock-warn` and `transaction-warn` of the core, in whole seconds with the syntax of `--lock-timeout` (`ServeOptions::lock_warn`, `ServeOptions::transaction_warn`). Without them, or with 0, the core logs no lock and no transaction.
- `--admin-listen` (`ZOE_ADMIN_LISTEN`, `ServeOptions::admin_listen`) opens the admin port. Without it, the server opens no admin port. `Server::start` binds it after the ZEO port and before the stores open, so a port that does not bind creates no store. The command writes `admin <address>` before `listening <address>`.
- `/metrics` gives the metrics of each storage in the Prometheus text format, with the content type `text/plain; version=0.0.4; charset=utf-8`, once every store is open, and 503 before. Each sample has the label `storage`. A duration is a histogram in seconds, and a counter ends in `_total`: `zoe_loads_total`, `zoe_load_latency_seconds`, `zoe_commits_total`, `zoe_vote_latency_seconds`, `zoe_finish_latency_seconds`, `zoe_fsync_batch_size`, `zoe_lock_wait_seconds`, `zoe_conflicts_resolved_total{path="native"|"python"}`, `zoe_conflicts_raised_total`, `zoe_clients_connected` and `zoe_invalidation_queue_depth`. `NamedStorage::new` gives the store its `Metrics` as the `zoe_core::Observer`, which gets the size of each sync batch and the lock wait of each vote. The session times `loadBefore`, `vote` and each `tpc_finish` that ends a transaction, and counts the commits that it publishes. `zoe_loads_total`, `zoe_clients_connected` and `zoe_conflicts_resolved_total{path="python"}` (oids) are the counters of the status; `native` stays 0, because the server resolves no conflict. `zoe_conflicts_raised_total` counts transactions: the votes that fail with a conflict, and the transactions that end between the two votes (abort, a finish before the second vote, the end of the connection). `zoe_invalidation_queue_depth` is the messages that wait in the deepest hub queue among the connections of the storage, read under the mutex of the hub at each scrape. Each help text gives the unit.
- `/healthz` gives 200 while every store is open, and 503 before. `/readyz` gives 200 when every store is open, its open loaded its last tid, and its lock table held no entry after the open (`Store::lock_table_is_empty`, read once at the open). It gives 503 before, and from the stop signal on (`Server::stop_signal`). Each other path gives 404, and another method than `GET` or `HEAD` on a known path gives 405. The body has one line for each storage.
- The admin port holds no store and no `Storages`: `Health` keeps only the names, what the open found, and for the metrics the counters, the histograms and the hub of each storage (`metrics::Exported`), none of which holds a store. So it never keeps a store open, and `Storages::held` does not count it. It is not a task of `Tasks`: a stop does not wait for it. It answers until the end of the stop, when the stop of the runtime drops it, before the stores close.
- The admin port never speaks ZEO and sends nothing before a request. It reads one request head on each connection, of at most 8 KiB with its empty line (`\r\n\r\n` or `\n\n`; 431 past it, also when the head arrives in one read) and within 2 seconds (a close without a reply past it), replies and closes. A reply to `HEAD` has no body, whatever its status. It serves at most 64 connections at once, so 64 silent clients hold the probes for up to 2 seconds: the admin port belongs on a private address. A port that does not bind fails the start with `Error::AdminListen`, whose message names the admin address.
- Each reply of the admin port has its own `Status` (code and reason phrase) and content type. `/metrics` gives the content type of the Prometheus text format.
- SIGTERM and SIGINT stop the server, and the command exits with 0. A second SIGTERM or SIGINT during the stop does nothing. `Server::stop` and the drop of a `Server` stop it the same way (see the stop below). `Server::start` opens the stores one after the other, after it binds the port. When a store does not open, the stores that opened close, and the start fails.
- An unmodified `ZEO.ClientStorage` works. A stock client never sees an extension that it did not declare in `register`.
- `register(storage, read_only)` stays as ZEO's. A ZOE client adds a third argument, the list of the extensions that it declares. The server accepts the names of `negotiation::SERVED`, once each, in the order of the declaration, and leaves out the other names, never with an error. A third argument that is not a list of strings fails `register` with `TypeError`, and the connection stays open and unregistered. `get_info` gives the accepted names under the key `extensions`, after the other keys, also when it accepted none. A connection that declared nothing gets no `extensions` key. A declaration holds for its connection only. A call to a method of an extension of `negotiation::SERVED` that the connection did not accept fails with `ValueError`, and the connection stays open. A new extension is one entry of `negotiation::SERVED`, with its methods, and one arm of a dispatch. The server serves no extension yet.
- Every reply carries the message id of its request, and goes out when its call ends. So the replies of one connection can go out in another order than their calls. The replies of the calls of one transaction keep the order of their calls. A stock client sends the calls of one thread in order and waits for the reply of each call that has one.
- After each commit, every other registered client of the storage gets `invalidateTransaction(tid, oids)`. The client that committed gets `info {length, size}`, then the reply of its `tpc_finish`, and no invalidation, as from ZEO. The oids come from the transaction index of the store (`Store::written_oids`), each oid once. A commit that wrote no oid sends `invalidateTransaction(tid, [])` to the other clients, as ZEO 6.2 does. A commit whose oids do not read closes the other connections, so each client verifies its cache when it reconnects.
- Each client gets the replies of its own commits and the invalidations in commit order, so the tids that it sees always increase: the cache of a stock client raises an error on a tid that goes back. The hub (`Invalidations`) orders the commits by the `previous` tid of `finish_after`. A commit waits in the hub for the commit before it, and the session that publishes a commit also publishes the commits that wait for it: no thread waits for another commit. A finish that fails gives no tid, so it publishes nothing and no commit waits for it. A guard publishes a commit also when its session panics between `finish_after` and the publication. No guard covers a panic inside `finish_after` after its batch is durable: the session never gets the tid, so the hub cannot publish it, and each later commit waits for it. A panic of the batch leader before it sets the new last tid halts the store, so no later commit comes. After that, `finish_after` only marks the transaction committed, releases its locks and logs long holds.
- Every commit of a store passes through the hub of that store exactly once, and each store has one hub, in its `NamedStorage`. A commit that bypasses the hub never publishes its tid, so each later commit waits for it forever. A new way to commit, a restore transaction included, must publish through the hub, and named storages must keep one hub for each store.
- `register`, `lastTransaction` and `getInvalidations` give the last published tid, not the last tid of the store. `register` adds the connection to the hub under the same mutex, so the connection gets the invalidation of each later commit and of no earlier one. These replies take their places after they read the tid, outside the mutex: each comes after the invalidation of each commit up to its tid, and the invalidation of a later commit can come before it. A stock client applies only the invalidations after the tid of these replies, so it accepts that.
- Each connection has two queues. The calls put their replies in the session queue, in the room that each took before it started. The hub puts the invalidations, and the `info` and the reply of each `tpc_finish`, in the hub queue, which holds at most `--client-queue-size` messages (`ZOE_CLIENT_QUEUE_SIZE`, default 1,000, at least 1). An invalidation is one message, and so is the `info` of a pack. The `info` and the reply of one commit are one message of two frames (`Outbox::push_message`): they take one place and go in together, or the queue is full and the connection closes. So a hub queue of one message lets a client commit. The hub never waits: when a hub queue is full, the server closes that connection, and its writer stops at once. So a slow or dead client, or a client that keeps its session queue full, never stops a commit or the other clients. The hub holds its mutex while it puts frames in the queues, never while a frame goes out to the network.
- One counter per connection gives each frame its place when it goes into either queue, and the writer sends the frames strictly in the order of their places. The frames of one message of the hub share one place and go out one after the other, in their order. So a client gets its frames in the order in which the server queued them. A frame can take its place before it exists, and a place without a frame is skipped. A place whose sender is gone does not stop the writer.
- A `loadBefore` reply shows only the commits that the hub published, and it goes out after their invalidations and before the invalidation of each later commit. The stock client keeps a record without a next serial as current and never checks it again, and the store makes a commit visible before the hub publishes it. So the session reads the last published tid `seen`, reads the record before `min(tid, seen + 1)`, and gives its next serial only when it is at or before `seen`. Then it takes its place under the mutex of the hub, only when no commit was published since `seen`. Otherwise it reads again. After 3 reads, it reads once under the mutex of the hub, which then waits for that read.
- `getInvalidations(tid)` returns `[last published tid, oids]`: each oid that a transaction after `tid` wrote, read from the transaction index of the store, so a restart keeps the answer. It returns nil when more than `--invalidation-queue-size` (`ZOE_INVALIDATION_QUEUE_SIZE`, default 100,000) transactions that wrote records come after `tid`, and when the index does not read. Then the client verifies its cache.
- Commits on different named storages never wait for each other. Each store has its own `Store`, so its own lock manager, and its own `NamedStorage`, so its own hub, status and counters. All the connections share `Storages`, the list of the named storages.
- A connection has no storage until `register`. The first call must be `register`: another call closes the connection. A `register` with a name that the server does not serve fails with `ValueError("unknown storage: NAME")`, as in ZEO, and the connection stays open without a storage. A `register` with a known name selects that storage for the life of the connection. The hub queue of a connection holds at most `--client-queue-size` messages, the same for every storage, because the connection gets its queues before `register`.
- `ruok` gives the status of each storage, in the order of the configuration: `--path`, then `--storage`, then the tables of the file in the order of their names.
- A read-only storage refuses a transaction with `ReadOnlyError`, at the vote.
- `--read-only` (`ZOE_READ_ONLY`, `ServeOptions::read_only`) makes every store read-only, and `read-only = true` of a `[storages.NAME]` table (`StorageOptions::read_only`) makes one store read-only. `Server::start` opens a read-only store with `Store::open_read_only_with` and the options of the store, its blob directory included, never with the opener of `Server::start_with`. So the store must exist, the server changes no byte of it, and it holds the lock of the store: a writer open gets `Locked`. A read-only open does not check the blob directory, so the start then calls `Store::check_blob_dir`, as `zoe verify` does: a store with blobs whose blob directory has no layout file fails the start with `MissingBlobDir`, and the message names that directory. A store that a killed writer left open fails the start with `NotClosedCleanly`: only a writer open repairs it, and `zoe verify` opens read-only, so it fails the same way. The lock timeout does not matter, because a read-only store has no transaction.
- `NamedStorage::read_only` marks the storage. On it, `register(name, false)` fails with `ReadOnlyError`, as in ZEO, and the connection stays open without registration, so a client with `read_only_fallback` registers again read-only on the same connection. A client without it gets the error and does not connect. Each registered connection of a read-only storage is read-only: `tpc_begin` fails the vote and `new_oids` fails at once, with the `ReadOnlyError` of the connection. `pack` fails with the `ReadOnlyError` of the store.
- `tpc_begin` has no reply. An error in it, the `ReadOnlyError` of a read-only connection too, fails the vote of the transaction, never as a closed connection. A stock server closes the connection on such an error instead. `tpc_begin` with a tid begins a restore transaction (`Txn::begin_restore`), which commits under that tid. A tid that is not after the last tid at `tpc_begin` fails the vote with `StorageTransactionError`. When another commit passes the tid before the finish, `tpc_finish` fails with `StorageTransactionError`. A second `tpc_begin` while a transaction is open does nothing, whatever its id. A stock server does nothing for the same id, and closes the connection for another id. A stock client never sends it, because its commit lock holds until the end of the transaction.
- `storea`, `checkCurrentSerialInTransaction` and `deleteObject` have no reply. The first error of a transaction ends its core transaction, and the vote fails with that error, as ZEO reports these errors at the vote. A call for a transaction that is not the open one fails with `StorageTransactionError`, so the server closes the connection, as ZEO does.
- A nil serial in `storea` and in `storeBlobEnd` is the zero tid, the serial of a new object, and nothing else (`store_serial`). An oid without a record commits. An oid with a record fails the vote with `ConflictError`, as with a zero serial: the core never hands back a stale zero serial. A serial that is not nil must be 8 bytes. `checkCurrentSerialInTransaction` and `deleteObject` take no nil serial.
- `checkCurrentSerialInTransaction` is `Txn::check_current_serial`: the vote takes a shared lock, and a stale serial fails it with `ReadConflictError`. `deleteObject` is `Txn::delete`: it writes a deletion, a record with an empty payload, with the serial check of `storea`.
- The locks are the per-OID locks of the core. A transaction that holds the lock of one oid never stops a commit on another oid. A failed vote ends the transaction and releases its locks, so the `tpc_abort` that follows gets None. An abort after the vote releases the locks.
- The client resolves conflicts through the vote, as with the `client-conflict-resolution` option of a stock ZEO 6 server, for every client and with no negotiation. The first `vote` is `Txn::vote_resolving`: it takes the locks once, in oid order. Its reply lists each stale written oid that the core hands back as `{oid, serials: [committed, read], data}`, in this key order, where `data` is the pickle that the client stored (`Txn::staged`), not the committed one. The transaction keeps its locks. The client loads the two other states with `loadSerial`, runs `_p_resolveConflict`, sends `storea` over the committed serial and votes again. That second `vote` is `Txn::vote`: it takes no lock and checks every serial again. It replies `[]` or fails. The server runs no resolution code.
- A stale read-current serial is never resolved: the first vote fails with `ReadConflictError`. A stale serial that the core does not hand back (a new object, a deletion, a deleted object) fails the first vote with `ConflictError`. A class that does not resolve raises `ConflictError` in the client, which then aborts or closes. A stock server releases its commit lock between the two votes; `zoe serve` keeps the per-OID locks until the second vote fails, `tpc_finish`, `tpc_abort` or the end of the connection.
- `--lock-timeout` (`ZOE_LOCK_TIMEOUT`) is the lock timeout of the core, in whole seconds with the syntax of the key `lock-timeout` of the `<zoe>` section: a number, with the suffix `s`, `m`, `h` or `d` or none. A lock wait longer than it fails the vote with `ConflictError` on the oid waited for.
- The end of a connection ends its calls: a client that closes or resets it, a full hub queue, the idle timeout, and a stop of the server. The calls that arrived before the end run, the calls of the transaction in order, as ZEO does. A reply that a call cannot queue because the writer is gone, a call that closes the connection and an error of a call without a reply end the connection at once (`pipeline::Ended`): the reader stops, and no call that waits starts, in the lane or on the read pool. A call that started runs whole: a `tpc_finish` commits whole. A panic of a call, on the read pool, on the thread of the transaction, of a download or of a pack, ends the connection too. When the task of a connection drops before its calls end, as at the stop of the runtime, the drop of `Calls` ends the lane, so the thread of the transaction runs the calls that wait, then ends and aborts the open transaction. When the client, the hub or the idle timeout closed the connection, the writer is gone, and the client gets no reply. At a stop of the server, the writer stays until each call ends, so the client gets the reply (see the stop below). Then the thread of the transaction drops its open transaction, which aborts it and releases its locks, at each state: after `tpc_begin`, after a store, after the vote and between the two votes. Its upload file goes too (see the upload below). A server killed during a vote commits nothing of the transaction, because nothing is durable before `finish`. The restarted server binds the same port at once.
- `--idle-timeout` (`ZOE_IDLE_TIMEOUT`, 300 seconds by default, in whole seconds with the syntax of `--lock-timeout`; `ServeOptions::idle_timeout`) closes a connection that sends no frame for that time while no call of the connection runs. A client that waits for the reply of its own call is not idle. A call runs from the time that the reader starts it, after its ticket, until it puts its reply in the session queue, or until it ends when it has no reply; it keeps its slot that long (`Calls::quiet` waits for each slot). A download runs until it ends. A heartbeat starts no call. The thread of a transaction that waits for its next call runs no call, so a client that stalls after its vote is closed after the timeout. The time counts from the accept until the protocol of the client, then from the later of two times: the last frame that the reader read, a heartbeat included, and the end of the last call that ran. The time while the reader waits for room for a call does not count, because the client cannot send then. The time counts from the last whole frame, so one frame that takes longer than the timeout to arrive is cut. The close is an end of the connection (see above): the writer stops at once, as at a close of the hub, also when it waits for a client that reads nothing. No call runs at the idle close, so the calls that arrived run, up to the first reply that cannot be queued, then the open transaction aborts and its locks go. A stock client sends a heartbeat every 60 seconds, busy or idle, so the default never closes it. 0 closes no idle connection. The server sets no TCP keepalive. A client that stalls between two calls, or a host that dies without a FIN or a reset while no call runs, keeps its connection, its transaction and its locks for the idle timeout at most (for ever with 0). While a call runs, the time starts at the end of the call. Limit: a host that dies while a vote of its connection waits for a lock keeps its locks for `--lock-timeout` plus the idle timeout; a host that dies while its `pack` runs keeps the locks of its voted transaction for the whole pack plus the idle timeout, and a pack has no limit; a host that dies with a `sendBlob` in flight keeps them until the write to its socket fails, when the kernel gives up on the socket, plus the idle timeout. A client that never reads the chunks of one `sendBlob` keeps its download thread and the locks of a transaction that it voted until it reads or closes.
- Limit: a vote that waits for the lock of an object does not see the end of its connection. Its transaction keeps the locks that it took until it gets the lock or the lock timeout ends, and then aborts. The core has no way to stop a lock wait from another thread.
- The error forms are those of a stock ZEO 6.2 server (`docs/spikes/zeo-wire.md`). `ConflictError` and `ReadConflictError` carry the map `{message, oid, class_name, serials}`. `serials` is `[current, read]`, or nil after a lock-wait timeout. The `class_name` of a `ConflictError` is the class of the pickle that the transaction stored (`Txn::staged_class_name`), or nil when it does not decode or is a deletion. A `ReadConflictError` has `class_name` nil. The `StorageTransactionError` of a call for a transaction that is not the open one has the args `[open id or nil, given id]`. `tpc_finish` and `tpc_abort` for a transaction that is not the open one give None.
- `--shared-blob-dir` (`ZOE_SHARED_BLOB_DIR`, `ServeOptions::shared_blob_dir`, a key of the configuration file) lets the clients share the blob directory of each store, as the option `shared_blob_dir` of a ZEO client does. `Server::start` then calls `Store::blob_temp_dir` on each store that is not read-only, so the blob directory has its layout file and `tmp/` before a client connects: a client creates the directories of an oid before the first blob of the store, and the core refuses a directory without a layout file that holds such entries. A layout file or a `tmp/` that a client made before is accepted, when the layout file says `bushy`.
- `storeBlobShared(oid, serial, data, filename, id)` has no reply. It is `Txn::store_blob_shared`: `filename` is a name in the directory of the oid, never a path. It has no `/` and ends in `.tmp` or `.tmp-` (a stock client sends `.tmp-`); the core refuses another name with `Protocol`, and the vote fails with `StorageTransactionError`. A `filename` that is not a str, or bytes that are not UTF-8, fails the vote with `TypeError`. The core syncs the levels of the oid directory and the file, then takes the file by rename into `blobs/tmp/`, so the crash rules of the core hold, and `finish` places it at the BushyLayout path of `(oid, tid)`. A client reads a committed blob file in place. Without `--shared-blob-dir`, the vote fails with `StorageError`, whose text names `--shared-blob-dir`. Each refusal leaves the file in its place. A crash before the rename leaves the file of the client in the oid directory, and nothing removes it: ZEO's server has the same leak. A stock server counts no store for it, and neither does `zoe serve`. The shared blob directory trusts its clients as ZEO does: the server and its clients run as the same user, and a client can put a symbolic link in place of a file after the check of the core (see the `CLAUDE.md` of zoe-core).
- The iterators of a connection belong to it. `iterator_start` and `iterator_record_start` take their ids from one counter of the connection, from 0, as ZEO does, and never reuse an id. An iterator at its end is gone. `iterator_gc` removes the ids that it lists and ignores an id that names no open iterator: a stock client lists each record iterator that it dropped, also one at its end. The end of a connection removes its iterators. A call that names no open iterator fails with `KeyError` of the id.
- A connection keeps at most 1,000 open iterators of both kinds (`iteration::MAX_OPEN`). Over it, `iterator_start` and `iterator_record_start` fail with `StorageError`, and the connection stays open. Between two calls, an open iterator holds no pickle (`iteration::Open`). A transaction iterator keeps only the tid of the last transaction that it gave, for `iterator_record_start`. The iterator of the core under it holds a slice of tids and only a weak reference to the store. A record iterator keeps its tid, the oids of its transaction and its place, and reads each record at `iterator_record_next`. The connection keeps the one transaction that it read last, with its records (`Iterators::read`). A stock client reads a transaction, then its records, so the store reads each record once. So the iterators of a connection hold the slices of tids, the oids of the transactions of the record iterators and one transaction, whatever the size of the pickles. `tests/open_iterators.rs` measures it. A stock client sends `iterator_gc` only at its next `tpc_finish` or `tpc_abort`, so a read-only stock client never sends it, and only the end of its connection frees its iterators. The text of the `StorageError` over the bound says that `iterator_gc` or a new connection frees them.
- `iterator_next` gives `[tid, " ", user, description, extension]`. The extension is the msgpack map of the extension bytes that the store keeps, as a stock server sends it, because a stock client keeps the value of the wire as `extension` and does not unpickle bytes. `extension::unpickle` reads the pickle of a dict in protocol 3 or lower, as ZODB's `loads` reads it. A value that msgpack cannot carry, a key that is not a `str` or `bytes`, a list or a dict that the memo shares, an int of more than 64 bits, and more than 100 levels fail the call with `ValueError` that names the tid, as a stock server fails a reply that it cannot encode. The iterator stays open.
- `iterator_record_start` takes only the tid of the last transaction that its transaction iterator gave, as ZEO does. `iterator_record_next` gives `[oid, tid, data, nil]`, in oid order, with nil data for a deletion. The store keeps every pickle whole, so `data_txn` is always nil. The oids come from the transaction that the connection read last, or else from `Store::written_oids`. A record comes from that transaction, or else from `Store::load_serial`. A record that does not load and that `Store::record_info` finds is a deletion. A record that neither finds is gone. At or before `Store::pack_watermark`, a pack removed it after the iterator started: the iterator leaves it out, never gives it as a deletion. After the watermark, no pack explains it: the call fails once with `CorruptTxn` of the tid, as the core iterator does for an index key without its record, and the iterator moves past it. Another error of the core fails the call as `Fault::of` maps it, and the iterator stays at its place.
- `tpc_begin` takes the status `" "` and the status `"p"` of a transaction that a pack of FileStorage changed, as `zoe.Storage` does, so a copy of a packed `Data.fs` works. The store keeps no status. Another status fails the vote with `StorageTransactionError`.
- `restorea` has no reply. It is `Txn::restore` in the open transaction: the record gets the tid of the transaction, nil data copies a deletion, and `serial` and `prev_txn` are not used, as in `zoe.Storage`. In a transaction that `tpc_begin` began without a tid, the vote fails with `StorageTransactionError`. A restore transaction finishes with `finish_after` and publishes through the hub, as any commit: the other clients get its invalidation.
- `pack(time, wait)` packs the store online at `TimeStamp(*time.gmtime(t)[:5] + (t % 60,))`, as FileStorage computes it (`clock::pack_tid`), or at the last published tid of the hub when that is lower. The store makes a commit durable before the hub publishes it, and a `loadBefore` reads only the published commits: a pack past the last published tid can remove the record that such a read gives. It runs on a thread of its own, and replies nil after the pack, also when `wait` is false. The other calls of the connection run while it packs. After the pack, the hub (`Invalidations::send_to_all`) puts `info` with `length` and `size` in the hub queue of every registered connection, under its mutex, so the `info` takes its place among the frames of the commits. The packing connection gets it before the reply. A full hub queue closes its connection, as for a commit. When the sizes do not read after the pack, no client gets `info`, and the reply is nil, as for a commit: the pack is done. A read-only connection packs, as a stock ZEO server lets it (`zeopack` connects read-only), and the pack keeps the clamp to the last published tid. A store that the server opened read-only refuses the pack with its own `ReadOnlyError`, for every connection. A record that fails its checksum or does not decode stops the pack with `StorageSystemError`, as in `zoe.Storage`. A store without a root object packs as the core packs it: a stock FileStorage fails with `KeyError` instead. A stop of the server stops the pack between two batches (see the stop below).
- `storeBlobStart` needs an open transaction, and opens one upload file in the blob temporary directory of the core (`Store::blob_temp_dir`). The file is new (`create_new`), and its name is `upload-<n>`, a name that the core never makes, so `Txn::store_blob_at` takes it. `storeBlobChunk` appends to the file. `storeBlobEnd` stages it with `Txn::store_blob_at`, which takes it by rename. A stock client sends `storea` for the oid first: the core keeps that pickle and adds the blob. `storeBlobEnd` stages through `Open::stage`: an oid, a serial or a pickle that does not parse, and an error of `store_blob_at`, fail the vote, as an error of `storea` does.
- An error of `storeBlobStart` or `storeBlobChunk` closes the connection, as in ZEO: a call out of order, a chunk that is not bytes, an error of the disk. After an error of the transaction, the three upload calls do nothing and write no file. So a read-only connection, whose `tpc_begin` fails, never writes an upload file.
- The upload belongs to the open transaction. The end of the transaction removes a file that the core did not take: finish, abort, a failed vote, the end of the connection and a refused `storeBlobEnd`. After `storeBlobEnd`, the core owns the file, and its abort or drop removes it. A crash leaves the file in `blobs/tmp/`, and the next writer open of the store removes it.
- A blob over a stale serial is a conflict like a pickle: the first vote lists it. The class `ZODB.blob.Blob` does not resolve, so a stock client raises `ConflictError` and sends `tpc_abort`. That abort, or a second vote that fails, ends the transaction and removes the staged blob and an upload that is still open.
- `sendBlob` first reads the whole blob with `Store::verify_blob`, which checks the size and the BLAKE3 hash. Then it sends the blob from `Store::open_blob` in chunks of 64 KiB: `receiveBlobStart [oid, serial]`, one `receiveBlobChunk [oid, serial, bytes]` per chunk, `receiveBlobStop [oid, serial]`, then the reply nil. The client needs the file before the reply, so this order is part of the protocol. A blob that fails the check (`CorruptBlob`) goes out as an error reply and no chunk. A read that fails after the first chunk goes out as an error reply without `receiveBlobStop`. Then the stock client does not put the bytes in its blob cache, but it keeps a partial `<blob>.dl` file, and its next `receiveBlobStart` for that blob fails an assertion. So the check comes before the first chunk: only a file that changes between the check and the stream reaches this path. A blob that the store does not have is a `POSKeyError`.
- During a download, the call puts the chunks in the session queue and keeps it full while the client reads. The invalidations of the commits during the download go to the hub queue and take their places between two chunks. The stock client handles each message on its own. So a commit never waits for a client that downloads, and that client stays connected, unless more than `--client-queue-size` messages of the hub wait for it.
- A stop takes at most `--shutdown-timeout` (`ZOE_SHUTDOWN_TIMEOUT`, 30 seconds by default, in whole seconds with the syntax of `--lock-timeout`; `ServeOptions::shutdown_timeout`). It sends one signal (`Stopping`) to the accept loop and to each connection. The accept loop drops the listener, so the server accepts no more connections. A connection that did not answer the protocol closes at once. Each other connection reads no more frames. The calls that the reader already started run, the calls of the transaction in order, so a `tpc_finish` that the server received commits and gets its reply before the close. Then the thread of the transaction ends, and that aborts the open transaction, staged or locked, as at the end of a connection. The writer sends the frames that wait and closes the connection.
- The stop waits for the connections (`Tasks` in `serve.rs`) until the timeout less 1 second, or less half the timeout when that is shorter. Then the stop of the runtime drops the tasks that remain: their connections close at once, and their calls end after the calls that run. So a client that does not read its replies holds the stop until then, and not longer. The stop waits for the sessions until the end of the timeout, then closes the stores. After `register` selects its storage, the calls of a connection keep only that storage (`pipeline::Calls::register`). So a session that still runs then keeps only the store of that session open, and the other stores close. That store does not close cleanly: the process exits, a read-only open refuses the store with `NotClosedCleanly`, and the next writer open rebuilds the free-space map of its database. The server writes a line to stderr when it closes the connections that remain, and one line for each store that a session still holds (`Storages::held`). A timeout longer than 2^32 - 1 seconds counts as 2^32 - 1 seconds.
- A stop stops a running pack between two of its batches. The pack runs on a thread of its own, and gives the signal of the stop (`Stopping::is_set`) to `Store::pack_until`, which checks it after each batch. The pack call then fails with `StorageError` ("pack stopped: the server stops"), and the client normally gets that reply before the close. No test checks that reply over the wire, and the reset of the limit below can drop it. The store keeps the records that the pack did not remove, and a later pack at the same time removes them (ADR 0025). Only the stop of the server stops a pack: a session that the calls of a connection did not make, as in the unit tests, gets a signal that never stops.
- Limit: the mark of a pack does not stop. The mark reads every reachable record before the first batch, and the pack checks the stop only after a batch. So a stop during the mark waits for the mark and for the first batch, and a stop after the mark waits for the batch that runs: at most one batch of removals runs after the stop. When the mark lasts past the timeout, the stop ends at the timeout while the pack runs, and the store of the pack does not close cleanly. A killed pack loses no data: each batch is one backend write, and the next open needs no repair of the pack (ADR 0025).
- Limit: when a client sent bytes that the server did not read, the close of its connection is a reset, not a FIN. The kernel then drops the bytes that it did not send yet, and a reply of a `tpc_finish` can be among them. The commit is durable, and the client sees a lost connection.
- A change to the wire protocol is a stop-and-ask.

- `tests/cli.rs` is the acceptance test of the binary and of `cli::main`.
- `tests/named_storages.rs` and `python/zoedb/tests/server/test_named_storages.py` are the acceptance tests of named storages and of the configuration file. `tests/serve_config.rs` tests the twins of the configuration file and of `--read-only`.
- `python/zoedb/tests/server/test_read_only_server.py` is the acceptance test of read-only serving: `--read-only`, `read-only = true` of one store, the fallback of a stock client and the `ReadOnlyError` of each write call.
- `tests/serve.rs` and `python/zoedb/tests/server/test_walking_skeleton.py` are the acceptance tests of `zoe serve`. `tests/wire_faults.rs` is the acceptance test of the faults on the wire: a disconnect at each state of the two-phase commit and after `tpc_finish`, an upload that stops, a server killed during a vote, and a client that does not read. `python/zoedb/tests/server/test_commit_over_zeo.py` is the acceptance test of the commit methods: read-current, `deleteObject`, conflicts, the lock-wait timeout, restore transactions and per-OID locks. `python/zoedb/tests/server/test_conflict_resolution_over_zeo.py` is the acceptance test of the conflicts that a stock client resolves through the vote. `python/zoedb/tests/server/test_iteration_over_zeo.py` is the acceptance test of the copy, backup and pack methods: the iterators, `restorea` and `pack`. `tests/wire/mod.rs` is a raw ZEO 6 client and a `zoe serve` process for the Rust tests of the server; it is part of the acceptance tests. The Python tests find the binary through `ZOE_BINARY`, which `just test` sets. `python/zoedb/tests/acceptance/test_console_script.py` is the acceptance test of the console script.
- `tests/zeo_mixin_methods.rs` is the acceptance test of `storea` with a nil serial and of `getTid`.
- `python/zoedb/tests/server/test_shared_blob_dir.py` is the acceptance test of `--shared-blob-dir`, `storeBlobShared` and `--blob-dir` of `zoe serve`.
- `tests/idle_timeout.rs` is the acceptance test of the idle timeout. `tests/idle_timeout_calls.rs` is the acceptance test of the idle timeout while a call runs: a vote that waits for a lock longer than the timeout keeps its connection without heartbeats.
- `tests/pipelining.rs` is the acceptance test of the concurrent calls of a connection and of `--blocking-threads`. `tests/idle_connections.rs` is the acceptance test of idle connections: 650 of them hold no thread, and a new client registers and commits at once.
- `tests/simulation.rs` is the acceptance test of the deterministic simulator (N18): the same trace for a seed run twice, the methods of the protocol in the trace, no lost commit and no stale read under network faults, simulated time without real time, and a deliberate durability bug that a seed catches and reproduces. `ZOE_SIM_SEED` runs one seed.
- `tests/log_lines.rs` tests that a line feed in a method name or a label forges no line of the text logs.
- `tests/metrics.rs` is the acceptance test of `/metrics` and of the JSON logs: each metric with the label `storage`, the counters that follow the work, and a lock held past `--lock-warn` logged with its oid, its client label and its storage, without pickle bytes.
- `tests/health.rs` is the acceptance test of the admin port: `/healthz`, `/readyz`, 404, the option and its twin. The unit tests of `admin.rs` and `serve.rs` test the replies, the 503 during a stop and the bind that fails.
- `tests/shutdown.rs` is the acceptance test of the stop on SIGTERM. `tests/shutdown_pack.rs` is the acceptance test of a stop during a pack. `tests/stop.rs` tests that SIGINT does what SIGTERM does, and that the timeout bounds a stop that a client that does not read holds.
- `tests/mcp.rs` is the acceptance test of `zoe mcp`. It compiles only with the feature `serve`.
- `tests/backup.rs` is the acceptance test of `zoe backup`, `zoe restore` and `zoe verify --backup`.
- `tests/blob_dir.rs` is the acceptance test of `--blob-dir` in `zoe verify` and `zoe convert`, and of the texts of a missing and a damaged blob file.
- `tests/open_iterators.rs` is the acceptance test of the memory of open iterators (N6): 24 record iterators open over transactions of 8 MiB grow the peak resident memory of the server by less than 64 MiB, and each still gives its record.
- `tests/fuzz_smoke.rs` is the acceptance test of the fuzz smoke: mutated messages, bad handshakes and false lengths against a `zoe serve` process.
- `just fuzz [seconds] [targets]` builds the targets of `fuzz/` with libFuzzer and AddressSanitizer, with the flags of `cargo fuzz build`, and runs them. It needs no cargo-fuzz. The new inputs and the crash files go to `target/fuzz`, and the seeds in the repository do not change. The Dagger function `fuzz` runs it for an hour.
