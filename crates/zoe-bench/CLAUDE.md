# zoe-bench

A load generator that speaks the ZEO protocol. It measures what `zodbshootout` cannot: contention and server saturation. Specification: "Performance and testing harness", B2 and N3.

## Layout

- `src/main.rs`: the command, with clap: `conflicts`, `hot`, `load` and `saturate`.
- `src/conflicts.rs`: the ranking of the ConflictErrors of Zope logs.
- `src/hot.rs`: `hot`, the writers of one hot object (F7, N5). Each writer increments a `BTrees.Length`, which tier 1 merges, or a `PersistentMapping`, which no tier merges, with vote-time locks or with early write-intent locks (`--early-locks`, ADR 0045). The report gives the commits, the `ConflictError`s, the transactions that gave up, and from `GET /metrics` of the admin port the syncs, the lock hand-offs and the intent locks of the run.
- `src/load.rs`: `load` and `saturate` on `zoe-client`, and their reports.
- `src/schedule.rs`: the seeded generator, the Zipf law and the schedule of a client.
- `src/machine.rs`: the description of the machine and of the run.
- `bench/schema/zoe-bench.schema.json`: the JSON schema of the reports of `load` and `saturate`. A unit test in `src/load.rs` checks that the schema requires each key of a report.
- `tests/finish_time.rs` and `tests/load_time.rs`: two measurements of the core in the process, `finish` and `load_before`, on a store on the disk. They are ignored tests, and no recipe runs them: run them in release with `--ignored --nocapture`. They print text for a person, not a report of `zoe-bench`.
- `tests/shrink_ratio.rs`: the shrink ratio and the time of each zstd level on a synthetic record set with the shape of a Plone store, through the codec of the record frames (`zoe_core::testing::encode_payload`). The measurement is an ignored test, as the two above. A test that is not ignored checks that the set goes through the codec unchanged and shrinks.

## Invariants

- Public CI runs only on synthetic corpora. Production data never enters this crate, its fixtures or its outputs. `load` and `saturate` create their own objects: `PersistentMapping` records that hold generated bytes.
- Benchmark results are JSON, one document per run, with the machine described in it. The reports go to stdout.
- A report holds no host name, user name or path. It does not hold the address of the server.
- `zoe-bench conflicts` reads only the paths it is given and writes only to stdout and stderr. Its report names classes and oids, never request paths or user names.
- The repository holds only the synthetic conflict sample, never a real log.
- The schedule of a client depends only on `--seed`, the index of the client and the settings, never on the time. A retry runs the same transaction again and takes nothing from the generator.
- A vote that fails with a conflict counts as a conflict, and the next attempt of the transaction counts as a retry. Each retry counts. A transaction ends committed or read-only; after `MAX_ATTEMPTS` attempts the run fails instead of a hang.
- `saturate` measures the read path: its `--write-ratio` is 0 by default. `load` writes in 10 % of its transactions by default. A unit test in `src/main.rs` checks the defaults.
- The default `--zipf` is 0.8. `--zipf 1.0` is the hot-spot case: the hottest object is in almost every transaction, and contention is high.
- Each step of `saturate` runs for `--warmup-seconds` (0.2 by default) that do not count, then for `--step-seconds` (1.0 by default). `--transactions` limits the transactions of a client in a step after the warm-up. The schedule repeats with the seed; the number of transactions of a timed step depends on the time.
- The default `--p99-ceiling` of `saturate` equals the number of N3 (0.3 ms). A run on the small default store is not an N3 verdict: N3 is a cache miss on a 10 GB store.
- `machine.name` is a slug of `ZOE_BENCH_MACHINE`, or a slug of the CPU model.
- The lock wait is the time of the vote, because the server takes the locks of the oids at the vote.
- zoe-bench uses `zoe-client` and does not change its API. tokio is allowed in this crate.
