# 0046. The merge policy: a persistent object under the root, read at the vote, and the field merges of tier 2

Status: accepted. The first checkpoint of ZOE-205. The human asked Claude to settle the questions that had no proposal and to mark each answer as its own choice, then approved the ADR as written, with the answers of "Questions for the human". During the build the human approved two changes, which the text below holds: the digest of a merge of shadow mode is BLAKE3, the hash that the core already links, in place of sha256; and the strs and bytes that CPython shares in every record (the empty ones, those of one character below U+0100, and the interned keys of dict states) do not count as an object that two fields share. The second checkpoint of the card, the classes of `zoe.plone` (section 9), is approved too. The review of the build then asked for changes; the human was away and asked Claude to decide them, and section 10 holds those decisions, which are Claude's. Sections 11 (the strategy `keys`) and 12 (the option `state` of `append`) are later changes, each with its own status.

## Context

Section 5 of the specification names three tiers. Tier 1 (ZOE-203, ADR 0042) merges the buckets, the sets, the one-bucket trees and the `Length`s of BTrees in Rust, at the vote. Tier 3 sends the conflict to the client, which runs the `_p_resolveConflict` of the class. Tier 2 is between them: "for any persistent object whose class the merge policy marks mergeable, decode the old, committed and new states, compute the two changed-key sets, merge when they are disjoint or agree, and apply the per-field strategies the policy names". The specification also says: "The merge policy is a versioned object in the store, so it is transactional and the server reloads it on change."

The card asks the ADR to say:

- where the server finds the policy without a new key space;
- how the server loads it again when it changes;
- what it holds: the mergeable classes, the coupled fields, the strategy of each field, and the switches of shadow mode and of the posting-dict rule of ZOE-203.

Facts that the design rests on:

- A ZODB database has one root object, oid 0, a `persistent.mapping.PersistentMapping` whose state is `{'data': {name: value}}`. Zope keeps its application under `'Application'`; other names are free. The root record is an ordinary record: the core can load it and `zoe_pickle` can decode it.
- The state of an ordinary persistent object is the dict of its attributes, from `Persistent.__getstate__`. A Dexterity item keeps its fields as attributes. So the "keys" of tier 2 are the keys of that dict: the fields.
- Each save of a Dexterity item changes `modification_date`, so two saves of one item always change at least one field on both sides. A merge of two saves needs a strategy for that field.
- `zoe_pickle::python` models the values of BTrees: `None`, bools, ints, floats, `str`, `bytes`, tuples, lists, dicts, classes and persistent references. A Dexterity item also holds instances of other classes, such as `DateTime` and `RichTextValue`, which ZODB pickles with `NEWOBJ` or `REDUCE`, then `BUILD`.
- Tier 1 gives the bytes of ZODB's resolver. Tier 2 has no resolver in ZODB to match. The acceptance test compares tier 2 with a Python reference of each strategy, which pickles its result with ZODB's pickler.
- Point 5 of the review of #418: a shadow mode that verifies. In shadow mode the client resolves the conflict and stores its record again, so the server sees the answer of ZODB and can compare it with its own merge.

## Decision

### 1. Where the policy is

The policy is the persistent object `root['zoe.merge_policy']`, of the class `zoe.policy.MergePolicy`, a `Persistent` subclass that `zoedb` ships. It needs no key space, no `meta` key and no frame field: it is a record like any other, with its history, its undo and its place in a pack. A store without the name has no policy.

Its state holds plain values only (`str`, ints, lists, tuples, dicts), so that the core reads it with `zoe_pickle::python` and a client loads it without `zoe.plone`:

```python
{
    "version": 3,                      # an int; each write adds 1
    "structural_merges": "on",         # optional: the mode of tier 1
    "posting_dicts": "on",             # optional: the rules of ADR 0042
    "classes": {
        "BTrees.IOBTree.IOBucket": {"tier1": "shadow"},
        "plone.app.contenttypes.content.Document": {
            "tier2": "on",              # on, shadow or off
            "default": "strict",       # the strategy of a field that "fields" does not name
            "fields": {"modification_date": "max", "subject": "union"},
            "coupled": [["start", "end"]],
        },
    },
}
```

- `zoe.policy.install(connection, policy)` validates a dict of this form, writes it to the object (it creates the object and the name of the root the first time), and adds 1 to `version`. The caller commits, so a policy commits or aborts with its transaction. `zoe.policy.read(connection)` gives the dict, or `None`. `zoe.policy.validate(policy)` checks a dict of this form and gives a copy of plain values: each text a plain `str`, each mode and strategy one of the constants of the module, so the core reads every value.
- An entry can also hold `"blocked": True`: the class never merges in tier 2, whatever its other keys say. `zoe.plone` blocks a class whose invariant it cannot read (section 9).
- `zoe.plone` writes the policy with its profile (step 4 of the card); a site without `zoe.plone` writes it with `zoe.policy.install`.

### 2. How the core reads it, and when it reads it again

- The core reads the policy only on the conflict path: in the vote that takes the locks, when at least one written oid is stale. A commit with no conflict reads nothing new (an invariant of the card).
- At such a vote, the store reads the current serials of oid 0 and of the oid of the policy (one backend read). When both are the serials of the policy that it holds, it uses that policy. Else it loads the root, finds the reference under `'zoe.merge_policy'`, loads that record, decodes it and keeps it, with both serials. So a committed change of the policy applies from the next vote with a conflict, in both modes and on every connection.
- The vote does not lock the policy. A vote that runs while another transaction commits a new policy uses one of the two versions; the resolution log names it.
- A record that does not decode, or a policy that breaks the rules of section 1, counts as no policy, and the store writes one warning to its log for each serial of it. `zoe.policy.install` refuses such a policy in the client first.

### 3. The policy and the settings of ZOE-203

The keys `structural-merges`, `structural-merge-class` and `posting-dicts` of `<zoe>` and of `zoe serve` stay. They are the defaults: a switch that the policy gives wins over its key, and a switch that it does not give keeps the value of the key. The tier 1 mode of a class is the `tier1` of its entry, else `structural-merge-class`, else `structural_merges` of the policy, else `structural-merges`. So a site that writes no policy works as with ZOE-203 alone. A shadow mode from the policy without a `resolution-log` changes nothing at the open; the store writes one warning to its log for that version of the policy, because the policy can change while the store is open.

### 4. Tier 2: the field merge

Tier 2 runs at the vote, after tier 1, on a stale written oid whose class is not a class of tier 1 and whose entry has `tier2` `on` or `shadow`. A class without an entry, or with `tier2` `off`, never merges in tier 2 (strict by default). The class comes from the class pickle of the staged record, as in tier 1.

1. The three states (old, committed, new) are decoded with `zoe_pickle::python`, which also models an instance of another class as its class, its arguments and its state (`NEWOBJ` or `REDUCE`, then `BUILD`), so that a `DateTime` compares and pickles again. Each state must be a dict with `str` keys; a state with slots, a value that the model does not hold, or an object that two fields share in one state (the same memo object under two keys) gives no answer. The strs and bytes that CPython shares in every record (the empty ones, those of one character below U+0100, and the interned keys of dict states, which `load_build` and `Persistent.__setstate__` intern) are not such an object: they are the same object whatever record they come from (approved by the human). The model interns the keys of dict states as CPython does, so a merge writes a key once, as a client that loads the record does. In the build, only a mutable object counts (a list, a dict, a set, or an object of another class but `DateTime.DateTime`): a Plone Document shares strs between its fields (the user id in `creators`, `_owner` and its local roles) and, until its first change, one `DateTime` between `creation_date` and `modification_date`, and splitting an immutable value changes neither the meaning nor the record that a client writes. This wider rule is Claude's choice, for the human's review.
2. A field changed on one side when its value there is not equal to its value in the old state, with the equality of the model: the same kind, the same items in the same order, the same class and state for an instance, the same oid for a reference. A field that is in one state and not in the other is changed too: added or deleted. Two values that Python finds equal but that the model does not (two dicts in another order, for example) count as changed, so the merge errs toward a conflict, never toward a lost change.
3. A field that only one side changed takes that change. A field that both sides changed to equal values takes it.
4. A field that both sides changed to different values takes the strategy of its entry in `fields`, else `default`:
   - `strict`: refuses.
   - `lww`: the value of the new record: the transaction that votes now is the last writer. In an undo (ZOE-206), `lww` refuses, as `strict` does: there the new record is the state before the undone transaction, so `lww` would drop the later change without a word, and an undo is a rare act of an administrator, for whom a refusal (`UndoError`) is the safe answer. `max`, `sum`, `union` and `append` merge an undo as they merge a vote. This is Claude's decision under the delegation of the human.
   - `max`: the greater of the two values, with the order of Python 3 (`Heap::lt`); values that it cannot order give no answer. For `modification_date`, two `DateTime`s order by their time.
   - `sum`: committed + new − old, for ints only.
   - `union`: for lists, tuples, sets and frozensets, on all three sides: the items of the old value that neither side removed, then the items that the committed side added, then the items that the new side added, each item once, in the kind of the new value. Two items are one when they have the same structure (their canonical ids, section 10), so items of every kind merge: dicts, sets, objects of other classes and persistent references too. A set keeps the order of the model.
   - `append`: for lists and tuples: the old value must be a prefix of both; the result is the committed value, then the items that the new side added after the old prefix. Else it refuses.
   A delete of a field against a change on the other side refuses, whatever the strategy.
5. Coupled fields stay strict: when the committed side changed a field of a group of `coupled` and the new side changed a field of the same group, the merge refuses, unless the two sides gave every field of the group the same value.
6. The merged state is the dict of the committed state, with the merged values in place and the fields that only the new side added after them, in the order of the new state. The record is the class pickle of the new record, then that state, pickled as `zoe_pickle` pickles for tier 1. It is stored over the committed serial under the locks of the vote, as a merge of tier 1, and the reply of the vote gives the oid as resolved, as in tier 1.

A refusal of tier 2 fails the vote with `ConflictError` at once. No answer leaves the conflict to tier 3: the client resolves it if the class has a `_p_resolveConflict`, else raises `ConflictError`, as today.

The merge is linear in the size of the three records, within a step budget in proportion to their lengths: a value that shares its parts many times costs its objects, not its expansion, and past the budget the merge gives no answer. Three records whose class pickles name different classes give no answer: a merge would undo the change of class of the committed transaction. No Python runs in the core or on the server.

### 5. F30: the merge primitives as strategies

F30 asks for append-only fields, CRDT sets and registers. They are the strategies `append`, `union` and `lww` of tier 2, with no change of the wire protocol and no change of the format. The stored primitive `append(oid, field, record)`, materialised on load, comes only if B5 shows that rewriting the history costs too much (the human's answer before Ready). Counters are the sequences of F29.

### 6. Shadow mode, and a shadow mode that verifies

- In shadow mode (`tier2: shadow`), tier 2 merges, writes its result to the resolution log, and the conflict goes on as without it.
- When a merge of tier 1 or tier 2 in shadow mode gives a record, the transaction keeps a digest of that record for the oid (BLAKE3, the hash that the core already links). When the client then stores its own resolution of the oid and votes again (the vote after `vote_resolving`), the store compares the digest of the record of the client with it, and writes a second line to the resolution log for the oid, with the outcome `verified` and the field `same`: `true` or `false`. So shadow mode proves, on the conflicts of a real site, that a class of tier 1 gives the record of ZODB's resolver, before a site switches it on. A conflict that the client does not resolve (a class without `_p_resolveConflict`, or the posting-dict rule, which ZODB refuses) writes no second line: there is nothing to compare.
- `zoe serve` counts `zoe_shadow_verifications_total{tier, same}`.

### 7. The resolution log

A line of tier 2 has `"tier": 2`, the class, the outcome, the reason (the strategy that refused, the coupled group, or why there is no answer), the fields that the new record changed in `keys`, and the `version` of the policy in the new field `policy`. A line of tier 1 also has `policy` (or `null` without a policy). Section 5 of the specification lists the fields.

### 8. Both modes

Tier 2 and the policy are in `zoe-core`, so `zoe.Storage` and `zoe serve` have the same merges, the same switches and the same log. A stock `ZEO.ClientStorage` sees a vote that resolved an oid, as from a ZEO 6 server.

### 9. The classes of `zoe.plone` (the second checkpoint)

- `zoe.plone.history.WorkflowHistory` holds `workflow_history`: a `Persistent` mapping of workflow id to the tuple of its status dicts, whose state is the mapping itself, so each workflow is a field. Its `__setstate__` interns the keys. Its entry is `{"tier2": "on", "default": "append"}` (`zoe.plone.history.policy()`). The opt-in Dexterity behaviour `zoe.plone.history` gives an object of a type with the behaviour a `WorkflowHistory` at its next status, through its status adapter; the import step of the profile moves the stock `PersistentMapping` histories of the content with the behaviour (section 10). A type without the behaviour keeps the stock history.
- `zoe.plone.properties.PrincipalProperties` holds the properties of one member or one group of a mutable property sheet of PAS (`ZODBMutablePropertyProvider` of Products.PlonePAS): a `Persistent` `MutableMapping` of property name to value, whose state is the mapping itself, so each property is a field. Its `__setstate__` interns the keys. Its entry is `{"tier2": "on", "default": "strict", "fields": {"login_time": "max", "last_login_time": "max"}}` (`zoe.plone.properties.policy()`), and `update_policy` adds it to the policy of each site, as it adds the entry of `WorkflowHistory`.
  - Why. The sheet keeps the properties of each principal as a plain dict, the value of the principal id in its `OOBTree` `_storage`. A login writes `login_time` and `last_login_time` (`setLoginTimes` of `portal_membership`), so it writes the bucket of `_storage`. The resolver of BTrees compares the values of a key with `<`, and a dict does not support `<`, so it refuses any two changes of one bucket, also of two principals; tier 1 gives the same answer. With the class, the bucket holds a reference for each principal. A login sets the key of its principal to the same reference again, so tier 1 merges the bucket, as ZODB does for two equal `PersistentReference`s, and the login changes the record of the principal. Tier 2 merges two logins of one member: each of `login_time` and `last_login_time` takes the greater of the two values written, field by field, and two changes of another property of one principal still conflict. So after two concurrent logins `login_time` is the time of the later login, and `last_login_time` can be the time before both logins, where two logins one after the other give the time of the earlier login: from `(t1, t0)`, the logins `(t2, t1)` and `(t3, t1)` merge to `(t3, t1)`, not `(t3, t2)`, and two first logins give `(t3, t3)`. `last_login_time` is never later than `login_time`.
  - On from the install, an exception to shadow first (a decision of the human), as for the stock container classes below. The evidence: the acceptance test of concurrent logins (`zoe/plone/tests/test_concurrent_logins.py`: two logins of one member and of two members from one snapshot, first and later logins, commit at the first attempt with the `login_time` of the later login), and the B6 numbers of the log of a B5 `edit` run on `zoe-native-qi-kv` (the specification, lever 4).
  - The import step `zoe.plone.properties` of the profile `zoe.plone:default` (the file `zoe-plone-properties.txt`) gives each dict of `_storage` of each mutable property sheet of the site the class, groups included: one dict left in a bucket is enough for the resolver to refuse it. It depends on `zoe.plone.merge_policy`, so the entry is in the policy first. It commits after each batch of 100 values; the last batch commits with the import. It marks the sheet (the attribute `_zoe_principal_properties`). The move changes the bucket, so a write of the dict from the same snapshot conflicts with it in both orders, and the retry sees the class. A principal created during the import, in a bucket that a later batch moves, can keep its old type until its next write of properties or the next import of the profile; the same holds for the uninstall.
  - `zoe.plone.properties.install`, a ZCML action of `zoe.plone`, patches two methods of the sheet. `setPropertiesForUser` on a marked sheet gives the stored value of the principal the class after the stock write, so a new member or group gets it at its first write. `getPropertiesForUser` copies a stored `PrincipalProperties` before it adds the default values, where the stock method adds them to the stored value: so a read writes nothing. On a sheet without the mark, and for a dict value, the stock methods run.
  - The readers. Products.PlonePAS reads the values of `_storage` only in the sheet itself: `getPropertiesForUser`, `setPropertiesForUser` (with `update`) and `enumerateUsers` (with `get`), which a mapping supports. plone.app.users, plone.restapi, plone.exportimport and PAS read the properties through the property sheet or `getProperty` of the member, never the stored value, and no code checks the stored value with `isinstance(..., dict)`. A search through `enumerateUsers` loads the record of each principal once, where the dicts were in the buckets.
  - A client without `zoedb` loads each record of the class as a broken object, so it cannot read the properties of the members and groups: a stock Plone on a ZEO client of `zoe serve`, or on a `Data.fs` copy of the store. A site with the profile imports `zoe.plone:uninstall` before it leaves `zoedb`, or before a copy of it opens without `zoedb` (a decision of the human). The uninstall retires only the records that the site still references: the record of a deleted member (`deleteUser` removes its key) or the history of deleted content stays current until a pack. So the way out is the uninstall, then `zoe pack` with its GC (the default) at a pack time after the uninstall, which removes the records that no object references, then the conversion. `zoe convert --to-data-fs` refuses a store with a current record of the class, or of `WorkflowHistory`, whose uninstall also gives the stock mappings back: its message names the classes, their first oids, the profile and the pack, and `--force` converts anyway. A retired record does not count; the guard matches by class, with no walk of the object graph, so an unreachable record counts until the pack. A stock ZEO client of `zoe serve`, or a client of the `Data.fs` copy of a forced conversion, loads the records as broken objects, and nothing refuses it.
  - The way back. The import step of the profile `zoe.plone:uninstall` (its file `zoe-plone-uninstall.txt`) removes the mark and gives each value back as a dict. It retires each `PrincipalProperties` as `restore` retires a history: it writes it with the one item `{0: None}`, which tier 2 does not take, so a login from the same snapshot conflicts with it in both orders, and the retry writes the dict. The entry stays in the policy. It acts only on records of the class: after the uninstall the values of the site are dicts in the buckets, and the only records of the class left are the retired ones, which the entry must refuse. Another site of the same database can still keep its properties in the class, so the uninstall of one site must not turn the entry off; `update_policy` adds it again at each update.
- Audit entries get no class: Plone 6.1 keeps no audit log in the ZODB. A package that keeps an append-only list in an object gives its class an entry with `append`.
- The profile of `zoe.plone` writes the policy with `zoe.policy.install`. It derives an entry for the class of each Dexterity type: the class merges field by field; the fields that an `@invariant` of the schema or of a behaviour of a type of that class names are a coupled group; a class with an invariant whose group would be empty is blocked; `modification_date` takes `max`, and the other fields `strict`. An overrides file of the profile changes the mode or the strategies of a class.
- As built (`zoe.plone.merges`): the derivation reads the names that the code of an invariant uses, and a field that the factory of its behaviour stores under another name (`effective` as `effective_date`) takes both names in its group. The derived entries are in shadow mode, as the specification asks a class to merge only after shadow mode showed that its merges are right (the stock container classes are the exception, below); the key `tier2` of the overrides gives another mode. The overrides are the file `zoe-merge-policy.json` of a profile, and the import step `zoe.plone.merge_policy` runs for each profile that holds one, so a policy package of a site gives its own. The import step moves the histories in batches of 100 objects, one transaction each.
- The stock container classes, an exception to shadow first (a decision of the human, ZOE-239). The overrides file of `zoe.plone:default` switches on the entries of the two Dexterity container classes of stock Plone 6.1, `plone.app.contenttypes.content.Folder` and `Products.CMFPlone.Portal.PloneSite` (the site root), and the switches `split_merges` and `folder_orders`: `{"folder_orders": "on", "split_merges": "on", "classes": {"plone.app.contenttypes.content.Folder": {"tier2": "on"}, "Products.CMFPlone.Portal.PloneSite": {"tier2": "on"}}}`. Each entry keeps its derived fields and groups: `modification_date` takes `max`, the other fields `strict`. So on a stock site the profile alone gives the order merge of ADR 0052: a creation in a folder changes only `modification_date` of the folder (ADR 0052, section 5), and two creations from one snapshot commit at the first attempt. The evidence: the acceptance test of concurrent creations in one folder (ZOE-221), and its B5 numbers, `create-shared` in one folder with the entry of `Folder` on, `split_merges` and `folder_orders`: 0 and 1 `ConflictError`s at 4 and 16 users, against 106 and 42 on ZEO (ADR 0052, section 15). The acceptance test of ZOE-239 runs the rounds of ZOE-221 on the policy of the profile alone. With `tier2` on, these two classes also merge any two edits of different fields, not only creations, under the derived groups and the default `strict`; the evidence covers creations only.
  - The entries of the other classes keep their derived mode, shadow: a Document still conflicts in tier 2. An add-on with a container class of its own keeps its derived entry in shadow mode; its site switches it on in its overrides.
  - The decision covers the derived entries only. `update_policy` removes the entry of a container class from the overrides of `zoe.plone:default` when the derivation of the site gives no entry for the class (the site has no type of it) or blocks it (`zoe.plone.merges.profile_overrides`). So the profile adds no entry without the derived groups, and a blocked class stays blocked with no warning. The overrides of a policy package of the site that try to unblock a class still log a warning.
  - `split_merges` composes across the sites of one database as `folder_orders` does: the database keeps the latest mode that each site asked for, and the policy takes the lowest (ADR 0052, section 6). So an `off` in the overrides of one site lasts when another site imports the profile.
  - The `tier2` of the two container classes composes in the same way, an exception to the rule of the composition that the new value wins (`zoe.plone.merges.SITE_CLASSES`, one root of the database for each class, `root['zoe.plone.tier2:<class>']`). So an import of the profile on one site, or an edit of one of its types, does not raise a container class over the lower mode that the overrides of another site give it. A site without an entry for the class asks for no mode, and the database keeps no root for it. A site whose overrides remove the class (`null`) asks for `off`, so the update of another site does not switch it on again. A rise of the class logs at INFO when the database had no root for the class before the update and the stored `tier2` is the derived `shadow`, as at the first update after an upgrade; it logs a warning otherwise, as for a switch. No line reports a rise of a class that the database keeps blocked. The log lines name the class as `tier2 of <class>`. The entries of the other classes keep the rule that the new value wins.
  - A later profile of the site lowers the containers: its key `tier2` sets the mode of every derived class, the containers among them, and an entry of a container class with `"tier2": "shadow"` or `"off"` lowers that class alone. The overrides of the profiles apply in the order in which the site first imported them.
  - An uninstall turns off what the install turned on, for its site (a decision of the human). The overrides file of `zoe.plone:uninstall` sets `folder_orders`, `split_merges` and the entries of the two container classes to `off`. Its overrides replace the kept overrides of `zoe.plone:default` at the same place, and a later import of `zoe.plone:default` replaces them again (`zoe.plone.merges.keep_overrides`), so the overrides of a policy package of the site still apply after them. The site asks for `off` through the roots of the sites, so the policy of the database is `off` while the database keeps the mode of that site; the other sites keep their own modes. The other derived entries keep their mode, shadow.
  - A site that imported the profile before keeps the overrides of that import, `{"folder_orders": "on"}`, until it imports `zoe.plone:default` again.

### 10. The review of the build (Claude's decisions, under the delegation of the human)

The core:

- **No recursion, a budget.** The structure of a value is its canonical id (`zoe_pickle::python::Canon`): a value gets a small id from its kind and the ids of its parts, with an explicit stack, once for each object. Change detection, `union`, `append` and the coupled groups compare these ids, so no merge recurses over a value and a shared part costs one step. Each merge has a step budget of 64 steps for each byte of its three records, and the comparisons of tier 1 (`Heap::eq`, `Heap::lt`) take the same budget: past it, the merge gives no answer. A merge of records of normal shapes stays far under it, so the merges and the bytes of tier 1 do not change for them; a bucket whose values share their parts many times can pass the budget, and its conflict then goes to the client, which resolves it as it does without tier 1 (a cache of the answers of `eq` for each pair of objects would lift this, and is not built).
- **Sets.** A set compares without order: two sets with the same items are the same value, whatever the order of their pickles.
- **The loader.** The loader of opaque values keeps the place of each key of a dict that it fills, and a count of the lists, dicts and objects on its stack, so a large record loads in linear time.
- **One walk for sharing.** The check of an object that two fields share is one walk of the state: an object that a second field reaches stops the merge only when it is mutable or holds a mutable object, which is known once for each object.
- **The log and the metric.** A refusal of tier 2 names the field whose strategy refused, or the coupled group, in the field `fields` of its line. `zoe_structural_merges_total` has the label `tier`, so it counts the results of tier 2 too.
- **The root.** The reader of the root decodes it with a heap of instances, as the root can hold objects of other classes.

`zoe.plone`:

- **The status adapter.** The behaviour gives an object its `WorkflowHistory` at its next status, through a status adapter (`zoe.plone.status`) whose `set` moves the history first. So a history that a check-in of plone.app.iterate or an import of a site puts back is moved at the next transition, and an object of a type without a workflow gets no history: the import step that moves the histories leaves an object without a history as it is.
- **The moves.** The move of a history marks the stock history as changed, so a move and a transition from one snapshot conflict in both orders, and the retry loses no status. The import step `zoe.plone.history` of the profile moves the histories at each import; an upgrade step would not run, as the profile has one version. It finds the objects by the types whose behaviours resolve to the marker, by name or by interface, as the index `object_provides` of an object indexed before the behaviour does not hold the marker. The profile `zoe.plone:uninstall` removes the behaviour and gives each history back as the stock `PersistentMapping` of Zope.
- **The coupled groups.** An invariant couples every field of the interface that declares it, the fields that its code reads, and their stored names, never a part of them. A class whose group would be empty is blocked.
- **The names.** The policy names a class by its `__module__` and `__qualname__`, as its records do, not by the text of the type.
- **The import of the policy.** The import step depends on `typeinfo`. The site keeps the overrides of each profile under its profile id, so the import of one profile keeps those of the others. An override adds its coupled groups to the derived ones and cannot unblock a class: the class stays blocked and the import logs a warning. The policy composes with the one in the database, so several sites in one database add up: the coupled groups of a class join, its fields join, a blocked class stays blocked, and the other keys take the new value. A change of a Dexterity type derives the policy again.
- **The mapping.** `WorkflowHistory` is a `MutableMapping`.
- **The way back loses no status.** `restore` retires the `WorkflowHistory` before it gives the history back as the stock mapping. It writes the old history with the one item `{0: ()}`. Tier 2 does not take that state, as its key is not a str. A transaction that writes the old history from the same snapshot then conflicts with the restore, whichever commits first. This holds whatever workflow the transaction adds a status to, a new one included, and also for an empty history. Tier 2 gives no answer, and the client raises `ConflictError`, as the class has no `_p_resolveConflict`. The retry sees the stock history. A stale reader that loops over the values of the old history sees an empty workflow. A delete of the workflows alone would let tier 2 merge the status of a new workflow, and an empty history would not be written at all.
- **A blocked class stays blocked.** An override can neither switch a blocked class on, nor give it `"blocked": false`, nor remove it. The set of the classes that the derivation blocks holds through the overrides of every profile, so a removal in one profile and an entry in another do not unblock it. A class that the database blocks, for another site maybe, stays blocked too: an override of one site cannot remove it. The import keeps the block and logs a warning.

### 11. The strategy `keys`: a mapping merges key by key (ZOE-210)

Status of this section: accepted. The human accepted this change before its text was written, then confirmed the text as written, and later approved the correction of point 6 on tuples. Claude settled its open choices, which "Questions for the human" lists (8 to 13).

ZODB gives `PersistentMapping` no `_p_resolveConflict`, so ZODB refuses each conflict on it, also when two transactions change different keys. The state of a `PersistentMapping` is `{'data': {...}}`: one field, `data`. Two changes of different keys both change `data`, and `strict` refuses. In the B5 log, `PersistentMapping` gives 6 of the 64 `ConflictError`s that are left after ZOE-203: 3.5 for each 1,000 transactions.

1. **The strategy.** `keys` is the seventh strategy of step 4 of section 4. It takes a field that both sides changed to different values, when its three values (old, committed, new) are dicts, and merges the dicts key by key with the rules of steps 2 and 3, one level down:
   - A key changed on one side when its value there does not have the structure of its value in the old dict (its canonical id, section 10), or when it is in one of the two dicts and not in the other: added or deleted.
   - A key that only one side changed takes that change: its new value, its add or its delete.
   - A key that both sides changed to values of the same structure takes that value. A key that both sides deleted stays deleted.
   - A key that both sides changed to different values refuses. A key that one side deleted and the other side changed refuses too.

   A key has no strategy of its own: the policy names fields, and the values of a mapping can be any objects. A refusal fails the vote with `ConflictError` at once, as for the other strategies. Its reason is `Key of a mapping changed on both sides` or `Key of a mapping deleted on one side and changed on the other`, and the field `fields` of its line names the field.
2. **No answer.** The strategy gives no answer, and the conflict goes to tier 3, when one of the three values is not a dict (the old state does not hold the field, for example, because both sides added it), when a dict holds a key of another kind (point 3), when two keys of one of the three dicts hold one mutable object, or when the merge passes its step budget. The rule of the shared objects is the rule of step 1 of section 4, one level down: a merge that takes the two keys from two records would split the object in two.
3. **The keys.** A key is a `str`, an `int`, a `bytes`, or a tuple of `str`, `int` and `bytes` items. The model knows when two such keys are one key of a Python dict: the same kind and the same value, item by item for a tuple. Other keys give no answer: a `bool` or a `float` can be equal to an `int` (`1 == 1.0 == True`), an object of another class can define its own `__eq__` and `__hash__`, and a tuple in a tuple would need a key that holds keys. The model of tier 2 (`Heap::with_instances`) loads a dict whose keys are such tuples; the model of tier 1 does not change. The merge needs no order of the keys; only the log orders them (point 6).
4. **The merged dict.** The merged value is a new dict. It holds the keys of the committed dict, in its order, with their merged values and without the deleted keys, then the keys that only the new side added, in the order of the new dict. A key of the committed dict is the key object of the committed dict; a key that only the new side added is the key object of the new dict. The value of a key is the object of the side whose change it takes: the committed object when only the committed side changed the key, when no side changed it, or when both sides gave it the same value; the new object when only the new side changed it. A reorder of the keys on the new side does not show in the result, as for `union`. The merged state is the committed state with the merged dict in place of the field, as in step 6 of section 4, and the record pickles as there. So a Python reference that builds the same objects and pickles them with ZODB's pickler gives the bytes of tier 2.
5. **Which fields.** The strategy applies to any field of any class whose entry names it, in `fields` or as `default`. It is not only for the `data` of the mapping classes. This is Claude's choice, because:
   - the core needs no list of mapping classes, so the subclass that a site names (point 7) merges with no change of the core;
   - the rules are those of tier 2, one level down, so the coupled groups, `blocked`, shadow mode, the log and the undo work for `keys` as for the other strategies;
   - a class with a dict attribute, such as a Dexterity item, can use it too.

   A field whose three values are not dicts gives no answer, as `union` gives none for values that are not lists, tuples or sets.
6. **The resolution log.** When `keys` merges a field, or refuses it, the line lists in `keys`, in place of the name of that field, the keys of its dict that the new record changed, added or deleted, and `changed` counts them with the other fields that the new record changed. Each key is written as tier 1 writes a key of a bucket: a `str` in double quotes, an `int` in digits, a `bytes` as `b'...'`, a tuple in parentheses, cut after 80 characters. So a key of a mapping looks the same in the lines of both tiers, and it never looks like the name of a field, which has no quotes. The keys of one dict come in the order of the model: the ints, then the strs, then the bytes, then the tuples, each kind in the order of Python. Two tuples whose items at the first place where their items differ are of two kinds, which Python does not order, order by the kind of those items, in the same order. A field that the new record changed and that `keys` did not merge keeps its name in the line.
7. **How a policy marks a mapping class.** The state of `persistent.mapping.PersistentMapping` and of `Persistence.mapping.PersistentMapping`, its subclass in Zope with `ExtensionClass`, is `{'data': {...}}`. (`persistent.dict.PersistentDict` is a name of `persistent.mapping.PersistentMapping`.) So the entry of a mapping class gives the field `data` the strategy `keys`:

   ```python
   {"classes": {"mysite.registry.Registry": {"tier2": "on", "fields": {"data": "keys"}}}}
   ```

   An entry names one class, by the name that its records give (section 10, the names): a subclass does not take the entry of its base. A site makes a subclass of its own (`class Registry(PersistentMapping): pass`) for the mappings whose keys are independent, and names that subclass.
8. **Why a site should not mark the stock classes.** The policy cannot tell one mapping from another of the same class: an entry for `persistent.mapping.PersistentMapping` or `Persistence.mapping.PersistentMapping` merges every object of that class in the database. ZODB makes the root of each database a `persistent.mapping.PersistentMapping`. Zope and CMF use `Persistence.mapping.PersistentMapping` in many places, some where the keys depend on each other: the WebDAV locks of `OFS.Lockable` (`_dav_writelocks`, which `plone.locking` uses: two transactions that each lock the same unlocked object would both commit, and the object would hold two exclusive locks), the workflow chains of `portal_workflow`, the role map of `portal_membership`, the stock `workflow_history`. Add-ons do the same. The B5 log shows it: each conflict of a mapping that tier 2 merges there is on the `_dav_writelocks` of a Document or on the lock settings that `plone.locking` keeps beside them, in a `persistent.mapping.PersistentMapping`. So `zoe.plone` marks no stock class, and the measure of the card marks the stock classes only to count what the strategy can reach on the B5 log, not as a policy for a site. `zoe.policy.validate` does not refuse such an entry: a site can know its stock mappings, and shadow mode shows what the merges do before a site switches them on.
9. **Shadow mode.** With `tier2` `shadow`, tier 2 merges with `keys`, writes the line, and the conflict goes on as without it (section 6). A `PersistentMapping` has no `_p_resolveConflict`, so the client raises and no line `verified` follows: shadow mode of `keys` on a mapping logs its merges and checks none of them, as for a Dexterity class.
10. **Undo.** An undo merges through tier 2 (section 4): the base is the record of the undone transaction, the committed side is the current record, and the new side is the record before the undone transaction. `keys` merges an undo as it merges a vote, so it acts as `strict` for each key. A key that only the undone transaction changed gets its value from before that transaction back. A key that only a later transaction changed keeps the later change. A key that the undone transaction and a later transaction both changed refuses with `UndoError`, unless the later change gave it its value from before the undone transaction again. A key that the undone transaction added and a later transaction changed refuses too. `keys` has no part that takes the value of one side, as `lww` does, so the undo uses it as it is.
11. **The code.** `merge::policy::Strategy::Keys` reads `"keys"`, and `zoe.policy.STRATEGIES` holds it, so `zoe.policy.validate` takes it in `fields` and as `default`. The merge is in `merge::fields`, with the same `Canon` and the same step budget as the other strategies, and no recursion. `zoe_pickle::python` keeps the tuple keys of a dict in a heap of `Heap::with_instances` only.

### 12. The option `state` of `append`: a history that refuses two changes of state from one state (ZOE-214)

Status of this section: accepted. The rule and the option are a decision of the human, recorded on the card (#436). The human then approved this text with the recommendation of each of points 14 to 21 of "Questions for the human", which are Claude's choices.

DCWorkflow keeps the history of an object in `workflow_history`: a mapping of workflow id to the tuple of its statuses. A status is a dict. It holds the state of the object after the transition, under the state variable of the workflow (`review_state` in every workflow of Plone). The last status of a workflow gives the state of the object in that workflow. DCWorkflow treats two transitions that change the state from one state as exclusive: the second one starts from a state that is no longer the state of the object.

With the entry of section 9, `append` merges two transitions of one object from one snapshot. So two changes of state from one state can both commit, when the permission fields of the object and the `review_state` index of the catalog do not conflict (a site with another index, or a class that a site switches on). The history then holds both statuses, and the last voter gives the state. A worse case: a comment from the old snapshot that commits after a change of state lands after it. The comment holds the old state, so the object goes back to the old state, and the change of state is lost. The acceptance test of the card shows both.

1. **The rule.** A field of strategy `append` whose entry gives the option `state` (point 3) merges as `append` does, with one more check. When both sides appended statuses to the field, the merge goes ahead only if every status that the committed side appended keeps the state of the old value. The state of the old value is the value under the key `state` of its last status. A status keeps that state when its value under the key has the same structure (its canonical id, section 10). Else the merge refuses: the vote fails with `ConflictError` at once, as for the other strategies. Zope retries the request, and the retry runs the transition again from the state that committed. There DCWorkflow runs it, or refuses it when the new state does not allow it.

   The check reads only the old value and the committed side. The statuses of the new side can change the state: their last status gives the state of the result.

2. **The cases.** The old history ends in `private`.

   | Committed side | New side | Result |
   | --- | --- | --- |
   | `publish` (`published`) | `submit` (`pending`) | refuses: the committed status changes the state |
   | `publish` (`published`) | `publish` (`published`) | refuses: the same target does not help |
   | `publish` (`published`) | a comment (`private`) | refuses: the stale status would land after the change of state |
   | a comment (`private`) | `publish` (`published`) | merges: the comment, then `publish`; the state is `published` |
   | a comment (`private`) | a comment (`private`) | merges: both comments; the state stays `private` |
   | `publish`, then `retract` (`private`) | a comment (`private`) | refuses: a committed status changes the state, even if a later one changes it back |

   The committed side can hold the statuses of several transactions since the snapshot of the new one. The rule reads each of them.

3. **The option.** The class entry gets the key `options`: a dict of strategy name to the options of that strategy. Only `append` takes options, and its only option is `state`, the name of the state key, a non-empty `str`:

   ```python
   {"tier2": "on", "default": "append", "options": {"append": {"state": "review_state"}}}
   ```

   The option applies to each field of the entry whose strategy is `append`, in `fields` or as `default`. The fields of a history are its workflow ids, which the policy cannot name before a site has them. So the option goes with the strategy of the entry, not with a field. A field of strategy `append` in an entry without the option merges as section 4 says.

   `zoe.plone.history.ENTRY` becomes the entry above, so `zoe.plone.history.policy()` sets `state` to `review_state`. `zoe.policy.validate` takes `options`: a strategy other than `append`, an option other than `state`, or a `state` that is not a non-empty `str` is an error. The core reads the option into `merge::policy::ClassPolicy`, and a key of `options` that it does not know makes the policy unreadable, as an unknown key of an entry does today (section 2).

4. **An option of `append`, not a named strategy.** The human chose a policy option. The code allows it: the strategy stays a name, the entry carries the option, and `append` reads it. The core learns the name of a key, not the shape of a DCWorkflow history. A named strategy would need the same name of the key, so it would be a second name for `append` with an option.

5. **No answer.** The merge cannot read the state, and gives no answer, when:
   - the last status of the old value, or a status that the committed side appended, is not a dict, or has no key `state`;
   - the old value has no status (an empty tuple): the state of the object is then the initial state of the workflow, which the store does not know.

   The conflict then goes to tier 3. `WorkflowHistory` has no `_p_resolveConflict`, so the client raises `ConflictError`. The checks run in this order: the checks of `append` (the kinds and the prefix, which refuse), then the last status of the old value, then the statuses of the committed side in their order, where the first status without the key gives no answer and the first status of another state refuses. A field that the old state does not hold (both sides added the first status of a workflow) refuses as `append` does today, before the option is read.

6. **No update is lost.** Let the old value be H, with the state s. The committed value is H then c1 … ck, and the new value is H then n1 … nm, with k and m at least 1. The merge gives H, c1 … ck, n1 … nm. When every ci keeps s, the object is in state s after the committed transaction, the state that the new transaction read. So the new transaction, run after the committed one, starts from the same state and appends the same statuses: the serial order gives the merged value. Its last status is nm, so the state is the state that the new transaction set, as in the serial order. When a ci changes the state, the new transaction started from a state that is no longer the state of the object, and no merge can give the serial order: the rule refuses. The rule speaks for the history alone. The other effects of a transition (the permission fields of the object, its entry in the catalog) are in other fields and oids, and merge or conflict by their own rules.

7. **A chain of two workflows.** Each workflow id is a field of `WorkflowHistory`, so each workflow merges alone. Two changes of state of one workflow from one snapshot refuse. A transition of one workflow and a transition of another workflow from one snapshot both commit, as today. A transaction that appends to two workflows is checked field by field, and one refusal refuses the record. A guard of one workflow that reads the state of another is outside what the merge sees.

8. **Undo (ZOE-206).** `append` with `state` merges an undo as it merges a vote, as section 4 says for `append`. In an undo of a transaction T, the base is the record after T, the committed side is the current record, and the new side is the record before T. When T appended a status and a later transaction appended to the same workflow, the base is not a prefix of the new side: the undo refuses with `UndoError` before the option is read, as today. When no later transaction changed that workflow, only the new side changed the field: the undo takes the history before T, and no strategy runs.

9. **A site on ZEO.** Nothing changes. A ZEO server runs no tier 2, and `WorkflowHistory` has no `_p_resolveConflict`, so two transitions of one object from one snapshot conflict there, as with the stock history. The policy object is data that the ZEO server does not read. A stock `ZEO.ClientStorage` on `zoe serve` gets the merge of the server core, as in-process.

10. **The resolution log.** A refusal writes a line of tier 2 with the outcome `refused`, the reason `State changed by a status of the committed side` (the new `Reason::StateChanged`), and the workflow id in `fields`. `keys` lists the workflow ids that the new record changed, as for every line of tier 2. A line of an undo says `"undo":true`. A case of point 5 writes the outcome `undecided`, with the reason `a status without the state key` or `an old value without a status`, and the workflow id in `fields`. `zoe_structural_merges_total` counts the line with the label `tier` 2, as each result of tier 2. In shadow mode the line is written and the conflict goes on, as section 6 says.

11. **A site that has the old entry.** A database whose policy holds the entry of section 9 without `options` merges as before. The site gets the option at its next import of the profile `zoe.plone:default` (the step `zoe.plone.merge_policy`), or at the next change of a Dexterity type, which derives the policy again (section 10). The composition of section 10 gives `options` the new value, as for the other keys of an entry.

12. **The tests that the build adds.**
    - The acceptance test of the planner, `python/zoedb/tests/acceptance/test_workflow_states.py`, in-process and through `zoe serve` with `ZEO.ClientStorage` and with the native client: two changes of state from one state conflict (to another state and to the same state), the history holds the first status, and its record equals the record of that one transition on FileStorage; a comment then a change of state merge, with no call of `tryToResolveConflict`, and the record equals the two transitions one after the other on FileStorage; a comment from the old snapshot after a change of state loses no state; transitions one after the other commit.
    - Rust unit tests in `crates/zoe-core/src/merge/`: `policy.rs` reads `options.append.state`, and refuses an unknown strategy or option and a `state` that is not a `str`; `fields.rs` checks each case of the table of point 2, each case of point 5, that the prefix check refuses first, that `append` without the option still merges two changes of state, and an undo of point 8 (the base after T, the record before T as the new side); `mod.rs` checks the reason and the `fields` of the line.
    - Python unit tests: `zoe.policy.validate` of `options`, and the entry of `zoe.plone.history.policy()`.
    - The acceptance tests of ZOE-205 (`test_append_fields.py`), whose statuses all keep the state `private`, stay green unchanged.

## Consequences

- Section 5 of the specification changes: tier 2, the policy object and its reading, the precedence of the keys, the verifying shadow mode, the fields of the log; F5, F6 and F30 and the feature triage change to match.
- `zoedb` gets a public module, `zoe.policy`, with the class `MergePolicy` and the functions `install` and `read`.
- `zoe_pickle::python` models instances of other classes. Tier 1 refuses or gives no answer on them as today: the merges of BTrees do not change.
- A wrong policy can merge two changes that the application meant to exclude each other. That is why a class is strict until its entry says otherwise, and why shadow mode comes first.
- A change of the policy applies from the next conflict, without a restart.
- `append` merges two transitions of one object from one snapshot. Two transitions that change the state from one state can then both commit, when the permission fields of the object and the `review_state` of the catalog do not conflict: the history holds both statuses, and the last one gives the state. A named merge that refuses two changes of state is a later card. Section 12 refuses them with the option `state` of `append`.
- `union` keeps no reorder of the items on one side: the order of the result is that of the old value, then of the committed one, then of the new one.
- Shadow mode verifies a merge only when the client resolves the conflict with a `_p_resolveConflict`. A Dexterity class has none, so shadow mode of tier 2 on it logs its merges and checks none of them.
- With `keys` (section 11), two transactions that change different keys of one mapping of a marked class both commit. A site that marks a mapping class says that its keys are independent: a wrong mark merges two changes that the application meant to exclude each other, as the locks of section 11, point 8, show.
- An entry cannot couple two keys of one mapping. A mapping whose keys depend on each other stays strict.
- The model of tier 2 loads the tuple keys of a dict, so a record with such a dict can merge its other fields in tier 2, where it gave no answer before.
- With the option `state` (section 12), two transitions of one workflow from one snapshot both commit only when the committed one keeps the state. Two changes of state, or a change of state and a later status of the stale state, conflict, and Zope retries. Comments still merge, and a comment then a change of state still merge.
- The rule errs toward a conflict: a committed side that changes the state and changes it back refuses, though the state at its end is the old one.
- The public module `zoe.policy` takes the key `options` in a class entry. A core of an older build reads a policy with `options` as no policy: tier 2 is off on every class, and the store writes a warning. A site updates its servers before it writes the new policy.
- Section 5 of the specification, F30 and the paragraph on the classes of `zoe.plone` change to name the option.

## Alternatives

- **A key space or a `meta` key for the policy.** It would be a change of the on-disk format (a red zone), and the policy would lose its history, its undo and the transaction that writes it. The card asks for none.
- **A policy file next to the store, or in the configuration of the server.** It would differ between the two modes and between the instances of a site, and it would not commit with the profile that writes it.
- **Watch the commits for the oid of the policy.** It puts a check on every commit; reading two serials at a vote with a conflict costs nothing on the path of a commit without one.
- **Fields as the keys of a nested mapping** (for example the `data` of a `PersistentMapping`). The fields of a persistent object are its attributes; a mapping of its own can be a class with its own entry. Section 11 keeps this: the keys of a dict do not become fields, and the strategy `keys` merges the dict of one field key by key.
- **`keys` only for the `data` of the mapping classes** (section 11). The core would need a list of those classes, and the subclass of a site would need a change of the core.
- **A strategy for each key of a mapping**, such as `lww` or `max` for one key. The policy would need a key space under each field, and the values of a mapping can be any objects. A key that both sides changed to different values refuses.
- **A refusal in `zoe.policy.validate` of `keys` on the stock mapping classes.** It would also stop a site that knows its stock mappings, and a measure on a log of stock mappings. Section 11 warns instead.
- **A named native merge per class** (the specification's "or a named native merge such as an append-only `workflow_history`"). The five strategies cover the classes of step 4 when `workflow_history`, comments and audit entries move to classes of their own; a named merge comes when a class needs one.
- **Verify in the client.** The client would need to know the merge of the server: a change of the protocol. The server already sees both records.
- **The rule of the card** (section 12): refuse when both sides appended a status whose state differs from the state of the old value. A comment from the old snapshot holds the old state, so it passes after a change of state, lands last, and puts the object back in the old state. The change of state is lost.
- **Rewrite the stale status** (section 12): give a status of the new side the state that committed. The human rejected it. The history would hold a status that no transaction wrote, and the other effects of the stale transition, which DCWorkflow computed from the old state, would not match it.
- **Read only the last status of the committed side** (section 12). It would merge a change of state and a change back. The rule of the human reads every committed status: it is simpler, and it errs toward a conflict.
- **A named strategy for the history** (section 12). It would need the name of the state key too, so it would be `append` with an option under a second name. The human chose an option.
- **A flat key `state` in the entry** (section 12). It is one level less deep, but it does not say which strategy reads it.
- **A strategy as a dict**, such as `"default": {"strategy": "append", "state": "review_state"}` (section 12). It changes the type of every strategy value that `zoe.policy.validate`, the composition of `zoe.plone.merges` and the core read. `options` is one new key.
- **Read the state variable from the workflow** (section 12). The workflows are in `portal_workflow`, other objects, and the core runs no Python.
