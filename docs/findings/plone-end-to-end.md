# Finding: where ZOE helps a Plone site, and where it does not yet

The Plone end-to-end benchmark (B5, `just bench plone`, see `bench/README.md`). One repetition of each run, by the choice of the human, in two series: a Linux VM (items 1–9) and an Apple M3 Pro (items 10–29). Never compare numbers across the two series. Every run here predates ADR 0040 and ADR 0041: `zoe serve` synced with `F_FULLFSYNC` on macOS and compressed its records with zstd at level 3. Since then it syncs with `fsync(2)` on macOS and writes raw records by default, so the sync times and the bytes of a commit on `main` differ from the ones below; the harness now gives both servers `fsync(2)` on macOS by default (`--zeo-fsync plain`). Every scenario ran on its stacks with the harness of the series on macOS, on the small fixture and partly on the medium fixture; every run passed its verification. The commits named here are on the ref of pull request #409: `git fetch origin pull/409/head` gets them.

## Published results

The later campaigns of B5 publish their summaries in the format of ADR 0054 to the results repository, `adeweb-be/zoe-bench-results`. Its dashboard, <https://adeweb-be.github.io/zoe-bench-results/>, shows the latest summary of each fixture. Those runs use other stacks and other defaults (ADR 0040, ADR 0041, the backends of `zoe.plone`), so their numbers do not compare with the numbers below. Git keeps the tables and the JSON summaries of the runs below: `git show f35d7c7a:docs/findings/plone-end-to-end/` lists them.

## Method

`bench/README.md` ("The Plone end-to-end benchmark") describes the harness: the scenarios, the ledger, the verification, the probes and the report. The runs of this finding used it as follows.

- **Stacks.** Every setting but the storage section is the same on each stack.

  | Stack | Server | Client |
  | --- | --- | --- |
  | `zeo` | ZEO 6.2 `runzeo`, FileStorage, pickle protocol Z5; the server resolves conflicts | `<zeoclient>`: `ZEO.ClientStorage` |
  | `zoe-native` | `zoe serve` with no option: zstd at level 3, a lock timeout of 10 s, a redb cache of 1 GiB | `<zoeclient>` with the native client, the `sequences` extension and `zoe.plone`, which gives `portal_uidgenerator` its ids from a store sequence |
  | `zoe-asyncio` | the same | `<zoeclient>` with `native false`: the asyncio client of ZEO with the ZOE extensions |
  | `zoe-stock` | the same | `<zeoclient>`: the stock client, with no extension |

  On `zoe serve` the clients resolve the conflicts (tier 3). No stack had a merge of tier 1 or tier 2, shadow mode or early write-intent locks: none of them was built.
- **Constants.** Two Zope instances of two threads each. A ZODB cache of 30,000 objects per connection and a pool of 7. A client cache of 128 MB in memory for each instance, with no persistent cache file. A blob cache for each instance. Zope runs with `debug-mode off`. Plone 6.1.5, Zope 5.14.2, ZODB 6.2, ZEO 6.2, plone.restapi 9.15.6, CPython 3.13 with the GIL. Both servers make a commit durable before `tpc_finish` returns. On Linux, the server runs on CPU 0, the instances on CPUs 1 and 2, and Locust on CPU 3.
- **Fixtures.** `small-ba01ff255313`: 685 content objects (57 Folders, 468 Documents, 104 News Items, 52 Files of 16 KB, 128 KB and 1 MB, 4 Collections), 48 editors, 32 members, an importer and a maintainer. `Data.fs` holds 31 MB and the blobs 21 MB. `medium-8ecaa36fc3c4`: 4,865 content objects. `zoe convert` copied each `Data.fs` to a store whose logical digest is equal. The ZOE store of each fixture holds zstd records.
- **Steps.** A closed workload with no think time and no client retry. Unless an item says otherwise: steps of 1, 4 and 16 users of 45 s each, the first 5 s of each step left out, and a warmup of 45 s with 8 users that saves no content.
- **Conflict oids.** A script walked a read-only copy of the fixture: the catalog (metadata, uids, paths, each index down to its buckets and tree sets), the lexicons and three tools. It named the structure that holds each oid of a conflict. An oid that a run created, such as the bucket of a split, needs the store that the run kept (`--keep-store`). Git keeps the script: `git show f35d7c7a:bench/plone/src/plonebench/inzope/oidmap.py`.
- **Bytes of a commit** (items 14 and 28). A program outside the workspace replays commits on a copy of the fixture store, through a `Vfs` that counts the writes to `zoe.redb`. Each commit rewrites k existing objects with their own pickles, 100 commits for each case: k objects at random oids, k adjacent oids, or the oid sets of the transactions of the kept ZEO stores.

## The Linux series

- Commit under test: `0f03dfb` (the harness changed after it, the stores and the servers did not).
- Label: a **synthetic realistic-site benchmark**, not a production-site benchmark. Fixture `small`: 685 objects, the same logical site in a `Data.fs` and in its `zoe convert` copy (digest equal).
- Machine: 4 vCPU (Xeon 2.1 GHz, shared VM), 16 GiB, ext4 on a virtual disk. Server on CPU 0, two Zope instances of two threads on CPUs 1 and 2, Locust on CPU 3 (under 5 % of its CPU in every run). CPython 3.13, GIL on.
- Closed workload, no think time: 1, 4 and 16 users, 45 s each, first 5 s of each step left out.
- Every run passed its verification: no lost acknowledged write, no phantom, no refused write committed, versions, workflow history, permissions, catalog entries and search all as the ledger says.

## Measured

1. **Pages and searches: parity.** `browse`, `catalog`: ZEO and ZOE within 5 % on rate and p95 at every load (18–20 pages/s at saturation). Both Zope processes are CPU-bound (about 90–110 ms of Zope CPU per operation); the storage server uses under 1 % of a CPU. A faster storage cannot move these numbers on a warm, small site.
2. **Write requests: the storage is a small slice.** On both stacks a save takes 400–650 ms of request time. The vote and the finish take about 10 ms of it, the whole commit phase (pickling, catalog, storage) 60–90 ms. The native client loads faster: 25–31 ms of storage reads per write request against 38–48 ms on ZEO, about 3–4 % of the request.
3. **Edits fail under concurrency on both stacks, for the same reason.** `edit` at 16 users: 16.9 % failed saves on ZEO, 15.3 % on ZOE, after Zope's three retries. Most of these were an artifact of the harness, not conflicts (item 9). Then: 60–67 % of saves succeed at their first attempt at 4 and 16 users. The objects that conflict are catalog structures. A map of the conflicting oids (see Method) puts most of them in the `_wordinfo` buckets of the ZCTextIndex indexes `SearchableText` and `Description`, then `sortable_title`, `UID`, `cmf_uid`, `path`, `id`. The `modified` DateIndex holds very few.
4. **ZOE removes the `portal_uidgenerator` conflict, and the next object takes its place.** On ZEO, every conflict of `create-spread` and `create-shared` is on `portal_uidgenerator` (135 in `create-spread`). On ZOE (`zoe.plone` sequence), none is there; about as many land on catalog buckets and read conflicts instead. The failure rate of creations barely moves (2–5 % on both).
5. **Workflow transitions do not conflict.** `workflow`: no failure on either stack at any load, and every anonymous visibility check after a transition passed. The ZOE clients resolved about 640 bucket conflicts per step, all with success.
6. **Resolution work is thrown away.** The clients of ZOE resolved 800–1,750 bucket conflicts per 45 s step in `edit` and `create-*`. The ZEO server resolved 2,588 in the `edit` run and failed on 160. A vote that resolves many buckets and then meets one that does not resolve fails whole, and the publisher retries the request from the start.
7. **ZOE writes far more to disk per operation.** Bytes that the server process wrote, per successful operation: `edit` about 2.2–2.7 MB on ZOE against 0.43–0.46 MB on ZEO; `workflow` 0.86–0.94 MB against 0.04 MB; `create-*` 1.7–2.6 MB against 0.85–1.05 MB. The mean fsync batch of `zoe serve` is 1.0 in every run: no group commit at these rates. This VM has fast enough storage that it does not show in latency; a site with a slow or metered disk would see it.
8. **The harness itself:** a hex token in each title made each concurrent save add a new word to the text index lexicons, and two such saves always conflicted on the new word id. That inflated the conflicts of the first `edit`, `create-*` and `mixed` runs (the Linux series). Titles now carry four known words (`corpus.op_code`). A sanity run of `edit` with the codes at 4 users on ZOE still had 63 conflicts in 30 s, in the same `_wordinfo` buckets: the text index contention is real, the lexicon part was the artifact. These four scenarios must run again.
9. **The harness, again:** the warmup opened edit forms as `editor-000` and never saved or cancelled them. Plone locks an item when its edit form opens, so these Documents stayed locked. At 16 users, other editors own some of them, and their edit form showed the locked item: the ledger counts that as `rejected`. In the macOS series, all 27 rejected Documents were Documents that the warmup opened, and only the editors of `section-00` met them. The warmup now cancels each edit form that it opens. A rerun of `edit` on macOS: failed and rejected saves at 16 users fell from 25 % to 1.4 % on ZEO and to 0 % on ZOE. The Linux failure share of item 3 holds the same artifact; the conflict counts and classes do not.

## The macOS series

- Commit under test: `5b83b25` (`c50c71d` in the results, before the rebases on `main`); the three `edit` runs ran with the warmup fix of item 9 on top of it.
- Machine: Apple M3 Pro, 6 performance and 6 efficiency cores, 36 GiB, APFS on the internal SSD. No CPU pinning: macOS has none. CPython 3.13, GIL on. Both servers sync with `F_FULLFSYNC` (the harness makes the ZEO server use it, as `zoe serve` did then).
- The same fixture (`small-ba01ff255313`), steps, warmup and trim as the Linux series. Every run passed its verification. Locust used under 10 % of a CPU in every step.

Measured:

10. **Reads: parity.** `browse` and `catalog`: ZEO and ZOE within 2 % on rate and p95 at every load; 44–45 pages/s at saturation from 4 users on. Zope CPU per page is 36–47 ms, against 90–110 ms on the Linux VM.
11. **Writes: no loss, small gains not yet proven.** `edit`, `create-spread`, `create-shared`, `workflow` and `mixed`: ZOE is equal to ZEO or ahead in rate at every load, by up to 15 % (`create-spread` at 4 users: 6.3 against 5.5 ok/s; `edit` at 4 users: 8.1 against 7.4). With one repetition, this is not significant. `edit` at 16 users: 7.0 ok/s on ZEO, 7.5 on ZOE; failed 1.4 % against 0 %.
12. **Conflicts.** `edit`: about 300–400 conflicts per 1,000 operations at 4 and 16 users on both stacks, nearly all on `IOBucket` (the `_wordinfo` buckets of item 3). Creations: on ZEO every conflict is on `UniqueIdGeneratorTool` (101 in `create-shared`, 214 in `create-spread`); on ZOE none is, and read conflicts take most of their place (42 and 115). Workflow transitions: 3 conflicts on ZEO, none on ZOE; the ZOE clients resolved 3,909 bucket conflicts, the ZEO server 4,874.
13. **Full durability costs ZEO about 4 ms per commit.** A second ZEO series with stock `fsync` (`--zeo-fsync plain`; the drive keeps the data in its cache): `tpc_finish` takes 1.6–3.5 ms with `fsync` and 5.4–7.5 ms with `F_FULLFSYNC` in `edit`, up to 27 ms against 18 ms in `create-shared` at 16 users. Rate and p50 change by at most 3 %.
14. **Why ZOE writes more bytes: two layers, measured.** The server process wrote 2.7–3.4 MB per `edit` operation on ZOE against 0.38–0.48 MB on ZEO. A replay of commits on a copy of the fixture store through a counting `Vfs` (100 commits each; the store holds 31,126 objects, median pickle 245 bytes) gives:
    - redb rewrites each changed page and its branch pages copy-on-write, 4 KiB at a time. A commit costs about 53 KB for one object, and about 630 KB for 80 objects at random places: 16 times their pickle bytes. 80 adjacent objects cost 150 KB, 4 times. A Plone save writes about 80 objects, most of them catalog buckets far apart.
    - On this machine the OS counts each scattered 4 KiB write as 16 KiB of disk write, with `F_FULLFSYNC` or with `fsync`; contiguous writes count about 1×. A plain file test gives the same factor without redb. So the 630 KB of redb become 2.3 MB on disk: the 2.7–3.4 MB per operation above. The Linux VM has 4 KiB pages; its own factor is not measured.
    - FileStorage appends each record once, so ZEO writes about the pickle bytes plus their headers.
    - The mean fsync batch of `zoe serve` stays 1.0: one sync per commit, as on Linux.

Then the remaining steps of the plan, on the same machine, commit `88b0b27` (`ee42ff8` in the results), one repetition, every run `verification pass`.

15. **The native client is the part of ZOE that saves time; `zoe serve` behind the stock ZEO client does not.** Four stacks, 4 and 16 users. In the REST scenarios `contention-fields` and `contention-same`, `zoe-native` does 38.5–40.3 ok/s against 36.6–38.0 on ZEO, and `zoe-stock` and `zoe-asyncio` 33.6–34.4: about 10 % below ZEO. Zope CPU per operation follows: 19–20 ms on `zoe-native`, 24 ms on ZEO, 23–26 ms on the two stacks with the ZEO client. In the form scenario `contention-folder`, `zoe-native` is 12–14 % ahead of ZEO (8.0 and 8.7 against 7.0 and 7.8 ok/s); the other two ZOE stacks are level with ZEO. `zoe-stock` and `zoe-asyncio` are equal everywhere, so the sequence wiring costs nothing.
16. **Conflicts on two fields of one Document are catalog conflicts first.** In `contention-fields` (two users on each Document, one writes the title, the other the description), 190–210 conflicts per stack land on `IOBucket` and 16–37 on the `Document` itself. A field-level merge of the content object alone would remove about one conflict in ten. `contention-same` (incompatible writes of one field) conflicts on `IOBucket` only. Failed requests stay at 0.9–2.3 % on all stacks. The servers resolve the bucket conflicts of `contention-fields`: 6,939 on the ZEO server, 4,862–7,403 in `zoe serve`.
17. **`UniqueIdGeneratorTool` conflicts come back without the `zoe.plone` sequence.** `create-shared` on `zoe-stock`: 55 conflicts on it, as on ZEO (139); none on `zoe-native` or `zoe-asyncio`. Rate is level on all four stacks (3.9–5.1 ok/s).
18. **Background work: no difference.** `mixed-background` (one SearchableText reindex and one REST import in loops beside the users): `zoe-native` 4 % ahead of ZEO at 4 and 8 users (40.1 and 33.9 against 38.7 and 32.5 ok/s), p95 at 4 users 222 against 338 ms. One repetition: not significant.
19. **Cold start and the probe cost little.** With new processes and empty ZODB caches (the page cache stays warm), the first 10 s of `browse` run at 38–39 pages/s, then 42–44, the same on both stacks. With the probe and without it, `browse` at 4 users differs by under 1 % in rate and by 1 ms at p95.
20. **Ten minutes of creations.** `create-spread`, 8 users, 600 s: `zoe-native` 5.6 ok/s against 5.1 on ZEO, failed 1.5 % against 3.6 %, retries exhausted 51 against 113. Both lose 15–25 % of their rate over the 10 minutes while Zope CPU per operation rises, the same on both stacks: the site grows, not the storage. Three things differ:
    - `zoe serve` wrote 19 GB (process counter; 22.5 GB at the disk), ZEO 2.7 GB (8.6 GB at the disk): about 32 MB/s against 5 MB/s. The mean fsync batch stays 1.0 at 8 users.
    - The resident memory of `zoe serve` grew from 5 MB to 1.07 GB, about 100 MB a minute, and still grew at the end. The ZEO server stayed at 82 MB. The redb cache defaults to 1 GiB and ZOE does not set it: this is the likely cause, not measured.
    - Each Zope instance on `zoe-native` holds about 150 MB more (486–493 MB against 330–343 MB): the native client keeps its 128 MB cache in memory, the ZEO client in a file.

## The macOS series, final steps

Same machine, `--zeo-fsync full`, one repetition, every run `verification pass`. Commits `b7b5f53` (the conflict reasons; `431a403` in the results, a merge with the same change) and `3a238af` (the rest; `3f9e4cd` in the results); the working tree held only harness changes that the runs do not use (the report, the counters of lost resolutions in the first group). The probes now record the reason of each failed resolution and the resolutions that a failed attempt or vote loses. The investigations of items 24, 26, 27 and 28 read the stores that the runs kept (`--keep-store`).

21. **A medium site: reads still at parity.** Fixture `medium-8ecaa36fc3c4`: 4,865 content objects; `Data.fs` 272 MB, `zoe.redb` 362 MB, blobs 117 MB. `browse`: 16.4 / 26.3 / 30.4 pages/s on ZEO and 15.8 / 27.6 / 29.1 on ZOE at 1, 4 and 16 users. `catalog`: 16.8 / 33.6 / 34.8 against 16.9 / 33.7 / 34.6. Zope CPU per page is 57–77 ms; the server uses at most 0.2 ms of CPU per page. The storage still does not show in a warm read.
22. **A medium site: saves at parity.** `edit`: 3.9 / 6.3 / 6.2 ok/s on ZEO and 3.8 / 6.1 / 6.7 on ZOE; failed 0 / 2.7 / 1.2 % against 0 / 0.8 / 0.7 %; p95 at 16 users 4.3 s against 4.0 s. The ZOE server wrote 3.8–4.1 MB per save, ZEO 0.44–0.53 MB.
23. **A medium site: the cold start is shorter on ZOE.** `browse`, 4 users, 60 s, no warmup, new processes and empty ZODB and client caches (the page cache stays warm). ZEO runs at 20–23 pages/s for its first 30 s, then at 27–28. ZOE runs at 22.5 for its first 10 s, then at 27–28. Over the minute: 27.9 against 25.6 pages/s, p95 187 against 261 ms. On the small site (item 19) the two stacks were level. One repetition.
24. **Why saves conflict: posting dicts inside the buckets of the text indexes.** `edit` and `create-spread` on the small site, 4 and 16 users, with the reasons:
    - `edit`: 209 of the 219 failed resolutions on the ZEO server, and 192 of 195 in the ZOE clients, are `IOBucket: Conflicting changes`: both transactions changed the value of the same key. The oid map puts them in `SearchableText._wordinfo` (113 on ZEO, 98 on ZOE) and `Description._wordinfo` (95 and 94).
    - ZCTextIndex keeps the postings of a word that 10 documents or fewer hold as a plain `dict` inside the `_wordinfo` bucket (`DICT_CUTOFF = 10`), and as an `IIBTree` of its own above that. Two saves that add or remove the same rare word change the same key of the same bucket, and the bucket resolver of BTrees compares the values whole, so it cannot merge two changed dicts. The ten buckets that conflicted hold 212 keys with a dict value and 185 with an `IIBTree`.
    - The harness rewrites the whole title and description of a Document at each save, so the first save of a Document removes it from the postings of every word of its old text. A real editor changes fewer words: these counts are an upper bound of the churn of the text indexes per save.
    - `create-spread` on ZEO: 238 of 242 failures are on `portal_uidgenerator`. The ZEO server resolved no conflict in that run: each creation that overlaps another one fails on the tool before any bucket resolves. On ZOE no failure is on the tool; 108 land on `SearchableText._wordinfo`, and the read conflicts spread over catalog, path and CMFEditions trees.
25. **The resolutions of a failed vote are lost, and in these scenarios that is nearly all of them.** In `edit` (medium) and `create-spread` (small), 3,189 of 3,190 resolutions on the ZEO server and 2,785 of 2,785 and 5,938 of 5,938 in the ZOE clients happened in attempts that failed after them. A save that overlaps another one resolves its `Length` counters and buckets, then meets a posting dict that does not resolve. In `workflow` every resolution succeeds (item 12). The time is small: a resolution costs 0.11 ms in the ZEO server and 0.70–0.76 ms in the ZOE clients, 2.1–4.1 s per run against 127–194 s of Zope CPU in the requests. The class that fails is `IOBucket`, which has a resolver, so trying the classes without a resolver first would change nothing. The native client calls `tryToResolveConflict` without the committed data, so ZODB loads the old and the committed state with `loadSerial`: two requests to the server per resolution. This is the probable cause of the 7× cost; it is not measured.
26. **The read conflicts of ZOE replace write conflicts; they are not extra failures.** Every stack on `zoe serve` has `ReadConflictError`s, `zoe-stock` too (`create-shared`: 51–61 on `zoe-native`, 52 on `zoe-asyncio`, 81 on `zoe-stock`; 0 on ZEO in every run). Write and read conflicts of ZOE add up to about the write conflicts of ZEO (`create-spread`: 95 + 131 against 254; `create-shared`: 113–171 against 125–168). The code says why: the vote of `zoe serve` lists the stale written oids that the client can resolve, and fails on a stale read-current oid before the client resolves them. The ZEO server resolves each written oid while it replays the stores, and the first write that does not resolve fails the vote before the read check. A stale read-current oid fails the transaction on both servers; only the label differs.
27. **Why the fsync batch stays 1.0: every save writes the same counters.** In the kept stores, 49.3 % of the transactions of `edit` (all the saves; the others lock and unlock the edit form) write the same 11 `BTrees.Length` objects, and 97.1 % of those of `create-spread` write at least 14 of them and `portal_uidgenerator`. The catalog indexes keep their counts in such objects, and ZCTextIndex, for one, calls `length.change(n)` at each indexing, also with 0, so the counter is written. `zoe serve` holds an exclusive lock on each written oid from the vote until the commit is durable, so two saves can never be in one sync. ZEO holds one commit lock for all transactions, so ZOE loses nothing against it here. The locks cost little time: in the sustained run, 4,710 votes waited 6.5 s for locks in all, and 3,422 commits made 3,422 syncs.
28. **The bytes of real Plone commits.** The replay of item 14, with the oid sets of the transactions of the kept ZEO stores (the oids that the fixture holds; the new oids of the run are left out):

    | commits | objects per commit | pickle KB per commit | redb KB per commit | redb ÷ pickles | OS disk KB per commit |
    | ---: | ---: | ---: | ---: | ---: | ---: |
    | 758 (`edit`) | 82 | 108 | 658 | 6.1 | 2,220 |
    | 551 (`create-spread`) | 122 | 77 | 822 | 10.7 | 2,792 |

    The objects of a Plone commit are as far apart as random oids (item 14: 632 KB for 80 random objects, 149 KB for 80 adjacent ones). The factor of the Linux file system is not measured: no Linux machine ran this step.
29. **The resident memory of `zoe serve` is its page cache.** The sustained `create-spread` (8 users) with `--zoe-cache-size 128MB`: the RSS of `zoe serve` goes 18, 165, 218, 224, 229, 231 MB at each minute, flat after 3 minutes. With the default of 1 GiB it went 164, 290, 406, 515, 614 MB in the same 5 minutes, and 1.07 GB after 10. Rate 5.7 ok/s against 6.1 in the first 5 minutes of the default run, mean load 9.8 against 8.4 µs, mean finish 13.4 against 12.3 ms, about the same bytes written per minute (1.7–1.9 GB against 1.7–2.1 GB). `zoe serve --cache-size` exists already.

## Not measured

- Field-level merges, structural merges in Rust, shadow mode and early write-intent locks: no stack of these runs had them, so nothing here measures them.
- Raw records against zstd: every run here used zstd, the default before ADR 0041. `--zoe-compression` now chooses it.
- Free-threaded Python: Plone 6.1 supports CPython up to 3.13; the instances run 3.13 with the GIL on (recorded in each result).
- Cold filesystem pages: neither machine can drop the page cache in the harness.
- The `large` fixture, and a site larger than the caches: the medium site still fits.
- On the medium fixture: only `browse`, `catalog`, `edit` and the cold start ran.
- The factor of the Linux file system for the bytes of a commit (item 28), and every macOS step on Linux.
- The words of the `_wordinfo` keys that conflicted: the stores give the final state of each bucket, not the key of each conflict.
- The cost of the two `loadSerial` requests of a client resolution (item 25).
- More than one repetition: differences of a few percent between ZEO and ZOE are within run-to-run noise.

## What followed

Row 1 of the table led to the spike [`posting-dicts.md`](../spikes/posting-dicts.md) and to the posting-dict rule of ADR 0042. Row 2 led to the lock hand-off of ADR 0044. The spike [`server-write-volume.md`](../spikes/server-write-volume.md) measured the bytes of row 3 again, on Linux.
