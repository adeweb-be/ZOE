## What blocks

The scope fence is `crates/zoe-mcp/**`. Three needs of the card are not reachable from there:

1. `explain_conflict(tid)` and the prompts `explain_transaction` and `summarise_changes` need the transactions of a tid range: the oids that each one wrote, with its user and description. Only `Store::iterator` gives this. Loupe's `Folder` does not expose it, and its `Store` is private.
2. `verify` needs `zoe_convert::verify(&Store, None)`. `Folder` gives no `&Store`.
3. `zoe-mcp` cannot open a second `Store` next to the `Folder`: the lock of the store is exclusive (`flock`), also for two read-only opens in one process.

## Options

A. (Recommended, smallest.) Add one method to `crates/zoe-loupe/src/lib.rs`:

```rust
impl Folder {
    /// Return the store of the folder. It is open for reads only, so each
    /// write call fails with `ReadOnly`.
    pub fn store(&self) -> &Store {
        &self.store
    }
}
```

Then `zoe-mcp` depends on `zoe-convert` (for `verify`) and `zoe-pickle` (for `decode_class_name`, as Loupe's space does). `space`, `object_get`, `history`, `diff` and `references` still call Loupe. `verify` calls `zoe_convert::verify(folder.store(), None)`. `explain_conflict` and the prompts read the transactions with `folder.store().iterator(..)` and the neighbours with Loupe's `Folder::history`. The invariant "each tool calls zoe-loupe and never reads the store itself" in `crates/zoe-mcp/CLAUDE.md` changes to say this.

B. Add Loupe functions instead: `Folder::transaction(tid)`, `Folder::transactions(after, limit)` and `Folder::verify()` (Loupe then depends on `zoe-convert`). This keeps the invariant, but it puts more code outside the fence, in `crates/zoe-loupe/`.
