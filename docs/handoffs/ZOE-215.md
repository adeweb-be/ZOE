# ZOE-215 handoff

## State

The spike is done. The cause is not in the timeout code of `zoe serve`, and the fix is outside the scope fence of the card. So the card stops and asks. The branch `card/ZOE-215` holds this file only. No code changed.

## The cause

`zoe.testing` (the forker of ZEO's tests) maps the key `transaction-timeout` of the `<zeo>` section to `--idle-timeout`. `TimeoutTests` sets it to 1 second.

- ZEO's server closes the connection of a transaction that holds its lock past the timeout. It closes nothing else. The client reconnects once, and the new connection stays open.
- `zoe serve` closes each connection that sends no frame for `--idle-timeout` while no call runs (N20). That also closes the connection that the client opened again, 1 second after its reconnect, then the next one, and so on.

`checkTimeoutAfterVote` votes, sleeps 3 seconds, then calls `_wait()`, checks `is_connected()`, calls `tpc_finish` and `load`. Against `zoe serve`, the third idle close comes about 3 seconds plus two reconnects after the vote, so a few milliseconds after the test wakes up. When the test is late by a few milliseconds, the close hits its last calls:

- `load` raises `ClientDisconnected` where the test wants `KeyError` (line 1044). This is the failure seen on macOS in ZOE-206.
- or `assertTrue(storage.is_connected())` after `_wait()` fails (line 1037).

The timeout itself fires on time. It does not fire early or late, and it does not race with the abort of the client:

| Measure (CPython 3.13, Linux, the `zoe` debug build of `main` at 582fb0a) | Result |
| --- | --- |
| End of the vote reply to the first close, as the client sees it | 1.000 to 1.003 s (76 tests) |
| A reconnect to the next close | 1.000 to 1.004 s (132 closes) |
| Closes before the `tpc_abort` of the test | 2 or 3 against `zoe serve`; 1 against ZEO's server |
| `load` after the close | `KeyError` in each passing run: the timed-out transaction left nothing |

## How the spike measured it

A driver outside the repository runs `TimeoutTests.checkTimeoutAfterVote` (File and Mapping) through the `walk`, `name_of` and layer code of `test_zeo_suites.py`, under `zoe.testing.ZEO_LAYER`, or without it for ZEO's own server. It logs the ZEO client at DEBUG with milliseconds and logs each call of the test. The server log of `zoe serve` has only INFO lines, and they hold the idle close with its time.

| Run | Result |
| --- | --- |
| Baseline, 40 runs in a row (80 tests), `zoe serve` | 1 failure, on the first assertion (line 1031) |
| 60 + 4 x 50 runs, `zoe serve`, 4 loops at once for the second set | 0 failures in 520 tests |
| The `time.sleep(3)` of the test made 9 to 11 ms longer, `zoe serve` | 6 failures in 26 tests: lines 1037 and 1044 |
| The same offsets (0 to 30 ms), ZEO 6 server | 0 failures in 48 tests |

On Linux the window is narrow (the reconnect takes 2 to 4 ms). So the failure is rare here (0 in 720 unchanged tests on lines 1037 and 1044), and more frequent on macOS (6 in 20 runs in ZOE-206). The machine had other agents' load during the runs; the 4 parallel loops added more, and gave no failure.

The baseline failure on line 1031 (still connected, and no reconnect, 3 seconds after the vote) came once, and the logs of that run were not kept. A later set of 100 logged runs (200 tests, 0 failures) shows how it comes. In one test, the server logged the second idle close on time, 1.002 s after the reconnect. The networking thread of the client saw the end of that connection 1.7 s later, and took 300 ms more between two steps of one callback. The next test started 14 s after the end of this one. So the client process stalled on the shared machine. A stall of 2 s between the first close and the check makes line 1031 fail: the client did not yet see the close. ZEO's own server cannot prevent that either, because its close also needs the client to run. Line 1031 is not a fault of `zoe serve`.

## Why the card stops

No change inside the fence (`crates/zoe-server/src/protocol/**`, `crates/zoe-server/tests/**`, `python/zoedb/tests/**`) makes the test pass every time:

- The idle timeout behaves as N20 says, and `tests/idle_timeout.rs` asserts that an idle connection without a transaction closes. The protocol code must keep it.
- The mapping is in `python/zoedb/src/zoe/testing.py`, outside the fence. No option of `zoe serve` gives ZEO's semantics, so a change of the mapping alone cannot fix it.
- `test_zeo_suites.py` is the acceptance test.

## Question for the human

- A. Add a transaction timeout to `zoe serve` with ZEO's semantics: `--transaction-timeout` (`ZOE_TRANSACTION_TIMEOUT`, a key of the configuration file and of `<zoe-server>`) closes the connection of a transaction that holds its locks after its vote for longer than the timeout, and nothing else. The forker maps `transaction-timeout` to it. This is a feature that the specification does not name: a new option, `cli/serve.rs`, `ServeOptions`, the thread of the transaction in `protocol/`, `zoe/testing.py`, the spec (N20 or a new row) and `timeout-thread-is-alive`. A new card, or this card with a wider fence.
- B. Keep the mapping, and put `TimeoutTests.checkTimeoutAfterVote` in `OUT` of `test_zeo_suites.py`: the forker maps `transaction-timeout` to `--idle-timeout`, which also closes the connection that the client opens again, so the test's calls 3 seconds after the vote can meet a close. `tests/idle_timeout.rs` covers "a client that stalls after its vote loses its locks". The reason of `TimeoutTests.checkTimeout` then names `tests/idle_timeout.rs` instead of `checkTimeoutAfterVote`. This changes the acceptance test.

B is the smallest change that the specification allows. A gives ZEO's behaviour to a user who sets a short transaction timeout without closing idle clients.

## The floor of `test_zeo_suites.py` on macOS

The card comment says that macOS runs 486 tests and the floor is 488. On Linux, a walk of the suites with `OUT` now counts 576 tests. `test_cache.py` removes 2 tests on other platforms, so macOS counts 574, above the floor. No change is needed now. Not run on macOS.

## Next step

The human picks A or B. For B, a planner edits `OUT`, then 100 runs of the driver confirm the test is out and `test_zeo_suites.py` passes. For A, a planner writes the card of the option with its acceptance test.
