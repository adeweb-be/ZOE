## What failed

`report --json` refuses its own summary: `the summary is not valid against plone.schema.json: -0.01007133152173913 is less than the minimum of 0`. The number is `store_write_kb_per_op` of the step at 16 users of `catalog` on `zoe-native-qi-kv`. The sampler gives the bytes that `zoe serve` writes to its store as the growth of `wchar` minus the growth of the bytes of its TCP sockets (and of its other files). In that step, `wchar` grew by 237206 bytes and the socket bytes by 238392 bytes: the store bytes are -1186 bytes, for 115 operations. The sampler reads the two counters one after the other, so the bytes that the server sends between the two reads count on one side only. In a step that writes almost nothing, such as a read-only scenario, the difference can be below 0. Every number of `plone.schema.json` has `"minimum": 0` (`$defs/number`).

The fix is in `bench/schema/plone.schema.json` or in `plonebench/summary.py`, which ZOE-243 owns and which are outside the scope fence of this card. It changes what a published B5 summary holds. So the builder stops and asks.

The real showcase can meet it too: `browse`, `catalog` and the reads of `mixed` write almost nothing. With steps of 60 s, the writes of the server that `wchar` counts grow with the step and the error of the two reads does not, so a value below 0 is less likely, but it can occur.

## The question

How does a B5 summary hold a store write that the method gives below 0?

- A. `store_write_kb_per_op` takes its own definition in `plone.schema.json`, a number or null with no minimum, and its description says that the method can give a small value below 0 when the server writes almost nothing. The summary holds the number as measured. Recommendation: it keeps the numbers as the report prints them.
- B. The summary holds null for a value below 0, as for a counter that gives no number. The page then shows no value where the server wrote almost nothing.
- C. The summary holds 0 for a value below 0. This hides the error of the method.
