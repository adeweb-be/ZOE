## Where `main` compresses a record

- `storea` does not compress. `Session::storea` (`crates/zoe-server/src/protocol/session.rs`) calls `Txn::store` of the core, which puts the pickle in the staging buffer (`crates/zoe-core/src/commit/staging.rs`, `Staging::put`) as it is.
- The finish compresses. `commit::group::write` (`crates/zoe-core/src/commit/group.rs`) calls `WriteTxn::put_records` for each member of the batch. `RedbWrite::put_records` (`crates/zoe-core/src/redb_backend.rs`) calls `format::encode_frame_with`, which calls `codec::encode`. So the leader of a group commit compresses the records of every member of its batch, one after the other, inside the redb write transaction.
- The card and the spike describe the prototype of ZOE-077 (`ZOE_POC_STORECOMPRESS` on the branch `poc/ZOE-077-server-performance`), which compressed at `storea`. `main` never took that prototype. On `main`, the 100 compressions of a 100 KB `add` are on the finish, and they serialize all the transactions of a batch.

## Why the fence blocks the card

A pool in `zoe-server` can compress, but the core must then write the bytes of the pool. No public API of the core does that:

- `codec::encode` is `pub(crate)` in `crates/zoe-core/src/format/codec.rs`. The server cannot make the payload of the core without it. A copy of the zstd call in the server puts a rule of the format outside the core.
- `Txn` has no call that stages a pickle with its encoded payload. `Staged` has no place for one, also for a spilled pickle.
- `WriteTxn::put_records` takes the data and encodes it. No method frames a payload that the caller encoded.

So the card needs changes in `crates/zoe-core/src/commit/` (the staging, the group write, a new method of `Txn`), `crates/zoe-core/src/backend.rs` (`WriteTxn`), `crates/zoe-core/src/redb_backend.rs`, and `crates/zoe-core/src/format/` (expose `encode`, and frame an encoded payload). The fence is `crates/zoe-server/src/**`. `format/` is a red zone. The data model does not change: the frames are byte for byte the same.

## The acceptance tests of the card on `main`

- "The `storea` call of a large record returns before its compression ends" passes on `main` already, because `storea` does not compress. A test of it does not fail before the change.
- "The vote waits for every compression of its transaction and fails when one fails" has no meaning on `main`: the vote does not compress, and a compression in the core cannot fail (`codec::encode` stores the data as it is when zstd fails or does not shrink it).
- The CPU per 100 KB object of the spike (445 to 734 µs) is a number of the prototype, with compression at `storea`. The number of `main` is not measured.

## Proposed design, if the human widens the fence

1. Core, `format/` (red zone, no data-model change): a public `encode_payload(data, Compression) -> (Codec, Vec<u8>)`, the same function as `codec::encode`, and a frame around an encoded payload. `encode_frame_with` calls both, so the bytes are the same.
2. Core, `commit/`: an opaque type `Encoded` that only `encode_payload` makes, with the length and the xxh3-64 of its data. `Txn::set_encoded(oid, Encoded)` attaches it to the staged record of `oid` when the hash matches the staged pickle, also a spilled one. A later `store` of the oid drops it. `Store::compression()` gives the level of the store.
3. Core, the finish: `group::write` writes the attached payload of a record. It encodes a record without one inline, as now. So no race stores a record uncompressed, and the bytes are the same either way. `WriteTxn` gets a method that puts an encoded record.
4. Server: `protocol/compress.rs`, one pool for the process, `available_parallelism` threads, one shared queue. `storea` and `restorea` stage the pickle, then queue a job (the data, the store level, a cancel flag of the transaction) and reply. The transaction thread keeps the pending jobs of its transaction.
5. Server, the vote: it waits for each pending job of its transaction through `runtime::block_on` (so the simulator runs it), attaches the results, then calls `vote_resolving`. It takes no lock before that wait. A failed or lost job fails the vote, and the transaction aborts. A store after a conflict at the vote queues a new job, and the next vote waits for it.
6. Server, abort and a lost connection: the drop of the transaction sets the cancel flag. A queued job of a cancelled transaction does not run. A running job ends, and nothing reads its result.

## Other options for the human

- Compress at the vote inside the core, on the transaction thread. This takes the compression off the write of the group commit, with no pool and a smaller change of the core. It does not meet the invariant of the pool.
- Lower the zstd level, or add a size limit above which a record is stored as it is. This cuts CPU and is an option of the store, not a change of the path.
