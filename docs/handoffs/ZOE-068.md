## What the Plone 6.1 code does

The sources read are the versions that `plone/versions.cfg` pins through Plone 6.1.5 and Zope 5.14.2: Products.ZCatalog 7.2.1 (it ships Products.ZCTextIndex), zope.intid 6.0, five.intid 3.1.0, Products.CMFUid 4.2, Products.CMFEditions 4.0.6, plone.app.versioningbehavior 2.0.5, Products.BTreeFolder2 5.1, Products.CMFPlone 6.1.5.

1. The ZCTextIndex lexicon has no `_nextwid`. `Lexicon._getWordIdCreate` takes a new wid from `_v_nextid`, a volatile attribute that starts at a random value in each connection, and checks it against `_words`. It writes `_wids`, `_words` (two BTrees) and `length` (a `Length` that counts the words; `clear()` sets `_wid_length_based = False`, so the length is no id). It never writes the lexicon object.
2. The lexicon of Plone is `plone_lexicon`, of class `Products.ZCTextIndex.ZCTextIndex.PLexicon`, not `Products.ZCTextIndex.Lexicon.Lexicon`.
3. The intid utility does the same. `zope.intid.IntIds._generateId` takes the id from the volatile `_v_nextid`, random at the start, and checks it against `refs`. `register` (and the override in `five.intid.intid.IntIds`) writes `refs` and `ids`, two BTrees. It never writes the utility object.
4. So a `ConflictError` names the class of a BTree or a bucket (`BTrees.OIBTree.OIBTree`, `BTrees.IOBTree.IOBucket`, ...), never `Lexicon`, `PLexicon` or `IntIds`. The count over `ID_ALLOCATION` is 0 with or without the wiring. `test_without_the_wiring_the_load_meets_these_conflicts` cannot pass, and the two other tests pass without any wiring.
5. No `Length` of Plone 6.1 hands out ids. The `Length` objects are counts (`_count` of BTreeFolder2, `_length` of the catalog and its indexes, `length` and `document_count` of ZCTextIndex) or change counters (`_counter` of the indexes and of `CatalogTool`, a cache key).
6. One id allocator does write a shared counter: `Products.CMFUid.UniqueIdGeneratorTool.UniqueIdGeneratorTool` (`portal_uidgenerator`). Its `__call__` adds 1 to the int `_uid_counter` of the tool and returns it. Its docstring says that it "may cause ConflictErrors under high load". CMFEditions calls it through `portal_historyidhandler` when it saves the first version of an object. `plone.app.versioningbehavior.subscribers.create_initial_version_after_adding` saves that version when an object with the versioning behaviour is added and its type has the policy `at_edit_autoversion`. Each new Document thus writes `portal_uidgenerator`.

These points come from reading the code. No test ran locally (the human's rule).

## Sequential ids and BTree buckets

With a sequence, the 50 threads take consecutive wids and intids, so their inserts go to the last bucket of `_words` and `refs`. Inserts of different keys in one bucket resolve, but a split of that bucket is a conflict on the BTree that does not resolve. The random start of each connection spreads the inserts today. A wiring of wids and intids to sequences can raise more conflicts on these BTrees, not fewer. Merges of BTrees in Rust are out of scope (phase 3).

## The question

Which edit of the acceptance test does the human want?

- Option A (proposed): count the conflicts on the one counter that hands out ids. In `plone/tests/test_id_allocation.py`, replace the set with

      ID_ALLOCATION = {
          "Products.CMFUid.UniqueIdGeneratorTool.UniqueIdGeneratorTool",
      }

  and change the module docstring to name `portal_uidgenerator` in place of `_nextwid`, the intids and the `Length` counters. `zoe.plone` then takes the value of `UniqueIdGeneratorTool.__call__` from a sequence on `zoe.Storage` and `zoe.zeo.ClientStorage`. The first value must be above the `_uid_counter` of a site that already exists; the card must say how (for example, the sequence value plus the counter that the tool holds when the wiring first acts). The spec (F29 and the Step 0 list) changes in the same pull request.
- Option B: keep the lexicon and the intids, and attribute each conflict to the object that owns the BTree (for example `plone_lexicon._words`, `intids.refs`). That needs a map from oid to owner in the creators script and a new test. The conflicts it counts are bucket splits, which sequences do not remove.
- In both options: does `zoe.plone` still wire the wids and the intids to sequences, as F29 says, or does it leave them alone, because Plone 6.1 has no shared counter there?

## CI does not run this acceptance test

PR CI (`.github/workflows/pull-request.yml`) calls the Dagger functions `check`, `test` and `docs`. `test` runs `just test`, whose pytest runs in `python/` and collects only the tests under `python/`. The nightly function `plone` runs `just plone zoe suites` and `just plone zeoclient suites`, the Plone suites through `bin/test`. No CI job collects `plone/tests/`, so no CI job runs `plone/tests/test_id_allocation.py`. A job for it needs a change in `ci/`, which is outside the scope fence of the card, and a Plone build, which needs the network.
