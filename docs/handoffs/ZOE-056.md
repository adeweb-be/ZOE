# ZOE-056 — handoff

## State

The branch `card/ZOE-056` holds blob streaming for `zoe serve`. All of it is in `crates/zoe-server/src/protocol/` and `crates/zoe-server/CLAUDE.md`:

- `blob.rs`: `Upload` and `Download`.
  - `Upload` is one new file, `upload-<n>`, in the blob temporary directory of the core (`Store::blob_temp_dir`). The core never makes such a name, so `Txn::store_blob_at` takes the file. Dropping an upload removes its file. After the core took the file by rename, the removal does nothing.
  - `Download` sends a blob from `Store::open_blob` in chunks of 64 KiB: `receiveBlobStart`, then `receiveBlobChunk` for each chunk, then `receiveBlobStop`. A read that fails stops the download before `receiveBlobStop`.
- `session.rs`:
  - `storeBlobStart`, `storeBlobChunk` and `storeBlobEnd` keep the upload in the open transaction (`Open::upload`). So each end of the transaction removes a file that the core did not take: finish, abort, a failed vote, the end of the connection, and a refused `storeBlobEnd`. An error of `store_blob_at` fails the vote, as an error of `storea` does.
  - `sendBlob` reads the whole blob first with `Store::verify_blob`. Then it returns `Outcome::Blob`, and `run` sends the chunks before the reply nil. So a `CorruptBlob` goes out as an error reply and no chunk.
- `mod.rs`: the queues between the tasks of a connection and its session are bounded (`QUEUE`, 4 frames) in each direction. The session uses `blocking_recv` and `blocking_send`. So an upload or a download holds a few chunks in memory, whatever the size of the blob.
- `message.rs`: `call_async`, the frame of a call from the server, `[0, true, method, args]`.

Green:

- `just check`.
- The Rust tests of `just test`. The `zoe-server` lib has 60 tests: 46 before, 14 new.
- The Python suite on 3.12, 3.13, 3.14 and 3.14t, except for two acceptance tests. The result is 2 failed and 259 passed on 3.12, 3.13 and 3.14, and 2 failed and 260 passed on 3.14t.
- `test_a_blob_goes_up_and_comes_back_down` and `test_an_aborted_blob_leaves_no_file_on_the_server` pass on all four interpreters.
- A stock client sent a 512 MiB blob up and down through the debug build of `zoe serve`. The peak RSS of the server stayed at 11 MiB to 12 MiB.

## What failed

`test_load_blob_gives_a_file_in_the_client_cache` and `test_the_server_keeps_the_blob_in_its_own_blob_directory` read the serial of the blob with `conn.root()["blob"]._p_serial`. In ZODB, `Connection._store_objects` calls `_p_invalidate()` on a blob after `storeBlob`, and `tpc_finish` does not update a ghost. So after the commit, the blob is a ghost with the serial `z64`. Reading `_p_serial` does not load a ghost. So the tests ask the server for the blob at tid 0:

- The first test calls `loadBlob(oid, z64)`. The server has no blob at that tid, and it replies `POSKeyError`.
- The second test looks for `blobs/.../0x00.blob`, and the server has no such file.

A stock ZEO 6.2 server with a FileStorage gives the same serial. The script (not in the repository) printed `ghost: True oid: 0000000000000001 serial: 0000000000000000`. So no correct server can make these two tests pass as they are written.

## The question (on the card)

May the two tests load the blob before they read its serial? The change is the same in both tests:

```python
with db.transaction() as conn:
    blob = conn.root()["blob"]
    blob._p_activate()
    oid, serial = blob._p_oid, blob._p_serial
```

With this change in a copy of the file outside the repository, the four tests pass on 3.12, 3.13, 3.14 and 3.14t against the binary of this branch.
