# ZOE-060 — named storages and the configuration file of the server

## State

The build is done on `card/ZOE-060`, and `origin/main` is merged in. One acceptance test fails, and the server cannot make it pass: the test itself breaks a rule of ZODB. Changing an acceptance test is a stop-and-ask, so the session stops here. The question is on the card (#114).

- `crates/zoe-server/tests/named_storages.rs`: 5 of 5 pass.
- `python/zoedb/tests/server/test_named_storages.py`: 4 of 5 pass. `test_a_database_per_store_like_a_mount_point` fails.

What is built:

- `--storage NAME=PATH` (`ZOE_STORAGE`, one store) adds a store and repeats. `--path` gives the storage `1`. `--config FILE` (`ZOE_CONFIG`) reads a TOML file. Its top-level keys are the options of `zoe serve` without `--`, except `config` and `storage`. Each `[storages.NAME]` table takes `path`, `blob-dir` and `read-only`. `read-only = true` is a usage error until ZOE-061 builds read-only stores.
- The file gives an option only when its value source is neither the command line nor the twin. So the command line wins over the twin, and both win over the file. The stores of the file add to the stores of `--path` and `--storage`. A name twice, no store, a store without a path, an unknown key, a wrong type and a file that does not read or parse are usage errors (exit 2) that create nothing.
- `Storages` (in `protocol/mod.rs`) holds one `NamedStorage` per store: its own `Store` (so its own lock manager), its own hub, status and counters. A connection gets its storage at `register` (`session::select`). `ruok` gives every store.
- `ServeOptions::with_storages` and `StorageOptions` (with `blob_dir`) are the library API. `ServeOptions::new(path)` still serves one store under `1`.
- The TOML parser (`toml` 1.1, without its default features) compiles only with the feature `serve`. `cargo tree -p zoe-py -e normal` lists no `toml`, `tokio` or `rmcp`.
- The specification, ADR 0010 (consequences) and `crates/zoe-server/CLAUDE.md` describe the behaviour.

## What failed

`test_a_database_per_store_like_a_mount_point` raises `ZODB.POSException.InvalidObjectReference: A new object is reachable from multiple databases. Won't try to guess which one was correct!`.

The test puts a new `PersistentMapping` in the root of `catalog`, and refers to it from a new object in `main`, in the same transaction, without `add`. ZODB refuses this on every storage: the first connection that commits adds the new object implicitly, and the second connection then finds a reference to an object that another database adds implicitly. The server takes no part in this check.

## What was tried

- The same code with two `MappingStorage` databases, with no server: the same `InvalidObjectReference`, with the names `main`/`catalog` and with `a`/`b`. So no storage and no server can make the test pass as written.
- A copy of the test outside the repository, with one change: `index = PersistentMapping(kind="catalog")`, `other.add(index)`, then `other.root()["index"] = index`. All 5 tests of the copy pass against `zoe serve` on CPython 3.12. The `add` is what ZODB asks for a cross-database reference to a new object, and it is the usual pattern of a mount point.
