## Blocked on

The acceptance tests of the card are not in the repository. `python/zoedb/tests/acceptance/test_kv_namespaces.py` and `test_writes_on_get.py` exist in no branch. The orchestrator said that a planner writes them on `plan/ZOE-207`; the branch merges them when they land. Until then, the card cannot be marked ready.

Questions for the human:

1. **The `zoe.plone` backends (step 4).** The ADR says that `zoe.plone` builds them on `zoe.kv`, each opt-in, and gives no more. Three facts need a decision:
   - The doctest of plone.locking reads `lockable.context.wl_getLock(token)._timeout`. So a locking backend must also replace the WebDAV lock mapping of the object (`OFS.Lockable.LockableItem.wl_lockmapping`), not only the adapter `TTWLockable`. Proposal: an opt-in ZCML file `zoe.plone:locking.zcml` that registers an `ILockable` adapter whose lock types live in the ephemeral namespace `zoe.plone.locks`, and a `wl_lockmapping` of `ITTWLockable` objects whose mapping reads and writes the same namespace, keyed by the oid of the object, with the TTL of the lock.
   - The test layers of plone.testing stack a `DemoStorage` on the store, so `zoe.kv.Namespace` gets a `DemoStorage`, which raises `Unsupported`. A write through to the base store would outlive the layer. Proposal: `zoe.kv` keeps an overlay in memory for a `DemoStorage` on a ZOE base, which the layer drops with its `DemoStorage`.
   - The session data manager and the registry storage: their interfaces (`Products.Sessions`, `plone.registry.Records`) and how a site switches each one on.
2. **The writes-on-GET report (step 5, F32).** No ADR gives its design: how `zoe.plone` marks a transaction of a GET or a HEAD (a key of the transaction extension, a call of the protocol), where the counts live in-process, and the name of the metric (for example `zoe_get_writes_total{storage, class}`). The card names "the protocol extension and the in-process API" as a checkpoint. Proposal: a key `zoe.request_method` in the extension of the transaction, which needs no protocol change; the finish counts the records of such a transaction by class.
3. **The scope fence and section 7 of the ADR.** The dump version 2 (`zoe backup`, `zoe restore`, `zoe verify --backup`) and the copy of the durable rows by `zoe convert` live in `crates/zoe-convert` and `crates/zoe-server/src/cli`, outside the fence of the card. The checks of `zoe verify`, which step 2 names, are built there with a few lines. Is the rest of section 7 in this card or a card of its own? Until it is built, a backup leaves the durable rows out.
4. **Pack and the rows of namespace-only commits.** Section 7 says that pack removes the transaction rows of namespace-only commits, "as every row that keeps no record". Today's pack removes only a row whose count it lowered to 0, so it keeps the row of any commit that never had a record, an empty commit too. The branch leaves pack (a red zone) as it is. Should pack remove such rows, or does the ADR change?
