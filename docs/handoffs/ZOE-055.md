# Handoff: ZOE-055

## State

The implementation is done and committed on `card/ZOE-055`. The calls of a connection run concurrently (`crates/zoe-server/src/protocol/pipeline.rs`):

- `register` runs first, alone.
- The calls of the transaction run in order on one thread, from `tpc_begin` to the end of the transaction. The thread ends when no call waits and no transaction is open.
- `sendBlob` and `pack` run on a thread of their own.
- The other calls run on the read pool of `--blocking-threads` (`ZOE_BLOCKING_THREADS`, the number of cores by default).
- Each call takes room for its reply in the session queue before it starts. A frame of the session takes its place under one lock of the outbox, so the session queue stays in the order of the places. `loadBefore` puts a placeholder at its place under the mutex of the hub and fills it after the call.

The specification and `crates/zoe-server/CLAUDE.md` describe the new model.

`idle_connections.rs` passes. `pipelining.rs` passes 2 of 4 tests.

## Blocked on

The acceptance test `pipelining.rs` has a wrong assumption. In `a_load_passes_a_waiting_vote`, `waiter` registers before `holder` commits, so the first message that `waiter` reads is the `invalidateTransaction` of that commit, not the reply of the load. The question is on the card, with the exact edit. With that edit, applied locally and not committed, the 4 tests of `pipelining.rs` pass.
