## The test that cannot pass

The test commits `PCounter()` without a call to `inc()`. `PCounter` keeps `_value = 0` as a class attribute, so the committed state is `{}`: it has no key `_value`. The second commit lists a conflict, and the client calls `tryToResolveConflict`. `PCounter._p_resolveConflict` reads `oldState['_value']` and raises `KeyError`. `tryToResolveConflict` logs "Unexpected error while trying to resolve conflict" and raises `ConflictError`.

The stock `ZEO.ClientStorage` against `zoe serve` fails the same scenario with the same `KeyError` (a scratch test with two `ZODB.DB` on `ZEO.ClientStorage`, run on CPython 3.13). No client can make this test green: the old state has no `_value`.

A fix of the test, for the human to choose: commit the counter with a value, for example `counter = PCounter(); counter.inc()` before the first commit, as ZODB's `checkResolve` does. The assertions then expect 3, not 2. The builder did not edit the test.

## Decided after the review

- After nine rounds that each list a conflict, the vote raises `ConflictError`. ZEO goes on to the finish there, which a stock server refuses. Kept.
- The cache keeps the pickle that the client resolved, as ZEO's `tpc_finish_co` does. Only the oids that the server resolved stay out.
