## What blocks

1. The acceptance test cannot pass against a server that follows MCP. `post()` asserts `HTTP/1.1 200` and a JSON-RPC reply for each message. The test also sends the notification `notifications/initialized` through it. MCP 2025-06-18 (streamable HTTP) says that a server answers an accepted notification with `202 Accepted` and no body. rmcp 3.5.1 does that in the stateful and the stateless modes (`accepted_response()`). So `post()` fails on the second call.
2. "It registers read-only" needs a change to `zoe-client`. `Client::connect_with` always sends `register(storage, false)`. `crates/zoe-client` is outside the scope fence.
3. "The same tools against a server" need Loupe over a server. Loupe's `object`, `history` and `diff` read a `zoe_core::Store` only, and the state decoder is private to `zoe-loupe`. ZOE-090 adds `zoe_loupe::Remote` for this, but ZOE-090 is not merged. Without it, `zoe-mcp` decodes states itself, which breaks its invariant "No tool decodes a state itself". `space`, `verify`, `explain_conflict` and the prompts read the whole store or the transaction iterator of the core. `zoe-client` has neither.

A smaller point: streamable HTTP needs the rmcp feature `transport-streamable-http-server` and an HTTP server for its tower service (`hyper-util`). That changes `Cargo.lock`, which is outside the fence.
