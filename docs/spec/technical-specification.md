# ZOE — technical specification

@Antoine Duchêne

This document is the technical specification: what ZOE is and how it works. The way of working, the units of work, the sessions, the roadmap and the project organisation are in ZOE — working methods and roadmap (`working-methods.md`). The decisions and their reasons are in the ADRs (`docs/adr/`).

The sections describe the design, built or not. The section "Status" says what works today.

## Summary

ZOE (Zope Object Engine) is a ZODB storage written in Rust that Plone can use unchanged: in-process for a single Zope instance, or behind a tokio server that speaks the existing ZEO wire protocol for a cluster. It aims to be the fastest storage backend available for Plone while staying ACID, and it attacks ConflictError at the storage layer with per-object locking and native conflict resolution.

### Goals

1. Drop-in for Plone 6: the only configuration change is the storage stanza in `zope.conf` (`<zoe>` or a `<zeoclient>` pointed at the Rust server). No change to application code, `persistent`, `BTrees` or `transaction`. A `<zeoclient>` against `zoe serve` needs the `msgpack` package, because the server speaks only the msgpack protocol `M5` (F2); `zoedb[plone]` installs it.
2. Fastest measured Plone storage: beats `FileStorage`, ZEO and RelStorage on Postgres on the same `zodbshootout` harness, cold, warm and hot.
3. Async where it pays: the server is fully asynchronous (tokio), handles pipelined requests per connection, and exposes an async storage interface for future async clients. The ZODB object model stays synchronous.
4. ACID by construction: atomic two-phase commit, durable on `tpc_finish` (fsync or replicated acknowledgement; the one exception is the deferred restore of the `Data.fs` converter, durable at its next batch sync, see "Tids"), snapshot isolation through MVCC keyed by `(oid, tid)`, and crash recovery without a repair step of ZOE: the last durable commit is the state. After a killed writer, the first writer open repairs the file and can take longer, because redb rebuilds its free-space map.
5. Fewer ConflictErrors under heavy writes: per-OID commit locks, optional early write-intent locks, and conflict resolution in Rust for structures and for fields, with Python only on the client for the long tail.
6. Two deployment shapes from one crate: in-process (no server) and clustered (server), same on-disk format, switchable by restarting.
7. Cloud-native on Kubernetes in three tiers: single-replica StatefulSet, leader/follower with automatic failover, stateless fronts over FoundationDB or TiKV.
8. Free-threading ready: the Python extension declares `Py_mod_gil_not_used` and commits in parallel inside one free-threaded Zope process.
9. Loupe, a Tauri desktop inspector and editor for ops and developers: browse, time-travel, tail live commits, full CRUD without Python, and converters from `Data.fs` and RelStorage, so ZOE replaces `Data.fs` entirely.
10. A faster catalog behind the unchanged ZCatalog API: an in-memory mirror answering queries in Rust as of the client's snapshot, a native BM25 text index on tantivy with real multilingual handling, and later a delta-based projection that ends bucket conflicts.
11. AI-native: an MCP server for ops and content agents with Plone's permissions enforced before ranking, and native retrieval with chunked passages, local-by-default embeddings, hybrid BM25 and vector search, and a choice of vector backend, ZOE's own index stored in the DB or Qdrant.
12. Operations as a feature: a checksum on every record, compression and encryption at rest, repozo-style dumps (continuous backup with point-in-time recovery comes after the roadmap), copy-on-write forks, a public change feed, named storages for mount points, and the data tools (verify, rename-class, export) in Rust.

### Non-goals

- Rewriting `persistent` and `BTrees` in Rust. That is a separate, client-side project ("What stays on persistent and BTrees" says what is left there).
- An asynchronous persistent-object API (`await obj.load()`). It would break every Plone add-on; the design keeps lazy loading synchronous.
- ZODB 5 and ZEO 5. ZOE targets ZODB ≥ 6.0 and ZEO ≥ 6.0, which means Plone 6.1 and later; older clients are not supported (ADR 0006).
- Requiring a new client. `ZEO.ClientStorage` stays supported for the life of the project; the native Rust client of F28 is a drop-in, never a requirement; the server replaces `runzeo`.
- Multi-tenancy inside one server. Isolation is by process and by named storage (F22); per-storage quotas are the only shared-server feature.
- The sixteen features triaged as Won't in the roadmap's Feature triage section, among them agent branches with merge-back, actor-tagged transactions, read replicas with session tokens, WASM plugins, server-side subtree clone and blocks as CRDT documents. Everything else from that triage has a requirement below (F29 to F38, N18, N19) or waits after the roadmap.

### Success criteria

- Plone 6 test suites (`Products.CMFPlone`, `plone.app.contenttypes`, `plone.restapi`) pass against both modes with no skips attributed to the storage.
- `ZODB.tests` conformance suites and the ZEO client test suite pass against the server.
- On the reference benchmark machine, `zodbshootout` shows lower latency and higher throughput than ZEO and RelStorage/Postgres in every scenario, by the margins of "Acceptance thresholds".
- A crash test (`kill -9` or power cut at any point of `tpc_finish`) never loses an acknowledged transaction and never needs manual repair.
- On a write-heavy replay of production traffic, ConflictErrors raised to Zope drop by at least an order of magnitude against ZEO with the same data.

## Naming

ZOE, the Zope Object Engine, is the project name: an anagram of ZEO, a first name, and an acronym in the ZODB/ZEO/ZRS tradition. The stem for every identifier is `zoe`, written ZOE in prose. The distribution ships as `zoedb`, because other projects hold the PyPI name `ZOE` and the crates.io name `zoe`; a PEP 541 transfer of `ZOE` is requested, and no bare `zoe` crate is published (ADR 0017).

## Context

The ZODB stack is mostly Python; the C lives in three client-side packages, and the upstream projects have started free-threading work.

| Package | Role | Free-threading status |
| --- | --- | --- |
| [ZODB](https://github.com/zopefoundation/ZODB), Python | Connection, DB, FileStorage, MVCC adapter, 2PC | pure Python; one Connection per thread |
| [ZEO](https://github.com/zopefoundation/ZEO), Python | asyncio client and server, msgpack wire protocol | pure Python |
| [persistent](https://pypi.org/project/persistent/), C and Python | `Persistent` base class, pickle cache, LRU ring | cp314t wheels; does not declare `Py_mod_gil_not_used` |
| [BTrees](https://github.com/zopefoundation/BTrees), C and Python | persistent containers, bucket conflict resolution | no free-threading work |
| [zodbpickle](https://github.com/zopefoundation/zodbpickle), C | `noload`, `binary` shim for py2 data | does not declare `Py_mod_gil_not_used` |
| [zope.interface](https://pypi.org/project/zope-interface/), C and Python | component architecture | declares `Py_mod_gil_not_used` since 8.3; cache races found ([#384](https://github.com/zopefoundation/zope.interface/issues/384)) |

What this means for the design:

- A storage server or in-process storage touches none of the C above. It plugs in through `ZODB.interfaces.IStorage`, the same seam `FileStorage` and `RelStorage` use.
- Any extension loaded on 3.14t without `Py_mod_gil_not_used` silently re-enables the GIL. Today `persistent`, `BTrees` and `zodbpickle` all do, so free-threaded parallelism in Zope needs those three declared before ZOE's own declaration matters.
- `persistent` and `BTrees` ship pure-Python reference implementations with full test suites, which makes a later Rust port of them a differential-testing job rather than a rewrite in the dark.

### Targets

CPython 3.12, 3.13 and 3.14, with 3.14t as the free-threaded build; 3.13t is not a target and 3.15 joins when it ships. Linux x86-64 and macOS on Apple silicon, and a run on either is evidence (ADR 0006). The release builds for macOS come later, for the wheels, the server binary and Loupe alike.

### Prior art

- byteserver, a ZEO server in Rust: the per-OID lock manager at vote time, and a server that treats data as opaque.
- filestorage2: the crash-safety pattern of the append-only log backend (aligned segments, a marker flip after the fsync, a CRC per record).
- RelStorage on PostgreSQL: the `(zoid, tid)` data model and `zodbshootout`.
- NEO: a global tid sequencer over replicated storage nodes works, and its complexity is the warning.
- ZEO 5 and 6: the wire protocol and the client, unchanged; `prefetch` is the way to overlap I/O under a synchronous ZODB API.

The links are in "References".

## Architecture overview

One Rust crate implements the storage; two thin skins expose it, in-process and over the ZEO wire. Everything above the storage seam is today's Plone, untouched.

### Layers, top to bottom

1. **Plone / Zope, unchanged.** Worker threads, one `ZODB.Connection` and pickle cache each, `persistent` and `BTrees` as they are, `transaction` as it is. Lazy loading stays synchronous.
2. **Storage seam.** In simple mode, `zoe.Storage` implements `IStorage` and friends and is wrapped by ZODB's own `MVCCAdapter`, exactly like `FileStorage`. In clustered mode, the unmodified `ZEO.ClientStorage` talks msgpack to the server.
3. **Server skin (clustered mode only).** A tokio process: one task per client connection, pipelined requests with out-of-order replies, invalidation fan-out, blob streaming, health and metrics, in a single static binary with no Python inside.
4. **Storage core (the crate).** Synchronous, no tokio and no Python inside: the transaction coordinator (2PC state machine), the per-OID lock manager, conflict detection and resolution, pack, the blob store, and the `Storage` trait that backends implement.
5. **Durable store.** A backend behind the trait: redb first (embedded, ACID, single writer, MVCC), an append-only log with in-memory index as the speed option, FoundationDB or TiKV for Tier 3. Blobs are files beside the store, or an S3-compatible bucket with a local cache.

### Two modes from one core

`zoe.Storage(path)` and `zoe serve --path …` open the same directory with the same format: `zoe.redb` (the database), `lock` (the single-writer lock, an exclusive `flock` held while the store is open) and the blob store. A new database is written as `zoe.redb.new`, synced, renamed to `zoe.redb` and the directory synced, so a crash during the creation leaves no store or a complete empty one. Moving from one Zope instance to a cluster is: stop the instance, start the server on the directory, point the instances at it.

### One write, clustered mode

1. A worker thread changes objects; on commit, `ClientStorage` sends `tpc_begin`, one `storea` per changed pickle, then `vote`.
2. The protocol layer decodes each frame and hands it to the coordinator, which stages the pickles for that transaction in a per-transaction buffer.
3. On `vote`, the lock manager acquires per-OID locks for the written oids in oid order. A second transaction on the same oids queues; transactions on disjoint oids proceed in parallel.
4. For each staged oid whose current serial is newer than the serial the client saw, resolution runs in Rust: a structural merge for BTree buckets, sets and `Length`, then a field-level three-way merge where the merge policy allows it. What neither tier resolves goes back in the vote reply, as ZEO 6 lists a conflict for the client to resolve; the client runs the class's own `_p_resolveConflict` locally, re-stores and votes again, with the locks still held; a class that does not resolve raises `ConflictError` in the client.
5. On `tpc_finish`, the coordinator allocates the tid, writes all records under one backend transaction, fsyncs (group commit coalesces concurrent finishers), releases the locks, acknowledges the client, and broadcasts one invalidation message per other client with the oid list. A lock of an oid that tier 1 merges passes to the vote that waits for it when the finish starts, before the fsync ("The lock hand-off (ADR 0044)").

### One read

`loadBefore(oid, tid)` → protocol layer → core → backend range lookup on `(oid, < tid)` → the pickle and its serial, written to the socket without an intermediate copy. In simple mode the same call is a Python method into the core with no wire.

### Where async lives

In the server skin, and in the crates that talk to a network or to an agent: `zoe-client`, `zoe-bench`, `zoe-mcp` and the server mode of Loupe. The core is synchronous. The extension module `zoe._zoe` links tokio only through `zoe-client`, for the native client of F28, and starts its threads when the first native client opens, never at import; it never links rmcp (ADR 0001). The ZODB side of a client is synchronous; `prefetch` is how a client overlaps I/O, and the server answers prefetched loads out of order on the same connection.

## Storage core

The core is a synchronous Rust library, `zoe-core`, with no Python and no tokio inside; both skins call it. It owns correctness: the data model, 2PC, locking, conflict handling, pack and blobs. Backends own bytes.

### Data model

| Key space | Key | Value | Notes |
| --- | --- | --- | --- |
| `records` | `(oid: u64, tid: u64)` big-endian, 16 bytes | a record frame, checksum tag 1; its header carries the serial of the previous record, its payload the pickle bytes or their zstd frame, as the codec byte says | one row per object version; a 0-length payload marks a deletion by `deleteObject`; pack removes rows and writes no deletion |
| `txn_oids` | `(tid: u64, oid: u64)` big-endian, 16 bytes | empty, not a frame, so no checksum tag | the transaction index: one key per record, deletions included, written in the same backend transaction as the record; a range scan over one tid gives the oids of that transaction in oid order; the iterator reads the oids of its range only from it; pack removes a key with its record; a store without the table does not open; ADR 0026 |
| `txns` | `tid: u64` big-endian, 8 bytes | a frame, checksum tag 3, whose payload is the status byte, the oid count as a `u64`, then user, description and extension, each with a `u32` length; the oid count and the three lengths are little-endian | the transaction log; status is `committing` until the finish record lands; pack lowers the oid count to the records that remain, and removes each row before its tid that keeps no record or never had one, such as a commit of KV namespace writes only; the row at its tid stays, with an oid count of 0 when the pack removes all its records |

| `kv_expiry` | the expiry, a big-endian `u64`, then the key of the `kv_ephemeral` row | empty, not a frame, so no checksum tag | the index of the expiries: an ephemeral write adds the key of its expiry; a write that replaces a row and a delete leave the key of the old expiry, which a sweep step removes; a sweep step removes the keys whose expiry has come, at most 1,000, and each row that passes its checksum and whose own expiry has come |

`loadBefore(oid, tid)` is a reverse range scan from `(oid, tid - 1)`; `load(oid)` is `loadBefore(oid, MAX)`; `loadSerial` is a point read. This is the RelStorage history-preserving layout, which makes MVCC and `history()` free.

The key spaces above are the tables. Beside them, the directory `wal/` of the store holds the write-ahead log (ADR 0056): segment files `wal/<n>.wal`, each with a header of 32 bytes (the state "in use" or "spare" and an epoch, under an xxh3-64 checksum), then the entries of its use. An entry is one commit batch: a header of 56 bytes with the epoch of its use, the last tid of the store before the batch and the last tid of the batch, under two checksums, then each commit of the batch, its transaction row first, each frame byte for byte as the tables store it. `last_tid` in `meta` is the folded tid: the tables hold each commit up to it, and the log holds the commits after it. `ZOE format 3` names the tables and the log together: an open refuses a store of format 2, and creates nothing in it.

### KV namespaces (F31, ADR 0043)

A namespace holds keys and values beside the object graph: the ephemeral flavour gives each key a TTL, for sessions and locks, and the durable flavour keeps a key until a delete, for the registry. `Txn::kv_set(flavour, name, key, value, ttl)` and `Txn::kv_delete(flavour, name, key)` stage a write between the begin and the vote, from the thread that drives the transaction, in the staging of the pickles: a value counts in `max-record-size`, and the key of its row and the value count in `staging-memory` and `max-transaction-size`. A later write of a key replaces the staged one, and a restore transaction refuses them. A write takes no lock, and the vote checks nothing for it: of two transactions that write one key, the later tid wins. The leader of the commit batch writes the namespace writes of each member after its records, in the backend write of the batch, so they commit or abort with the transaction and are as durable as its records. A transaction with only namespace writes commits without a record: a tid, and a transaction row with an oid count of 0.

A read gives the last committed value, not the value at a snapshot, and an expired key reads as absent. A scan gives keys in byte order, at most 1,000 pairs a call, and stops after the pair that brings its keys and values to 1 MiB: a reader scans again from after its last key until a reply is empty. A sweep step is a backend write of its own, outside the commit sequencer, with a sync, that removes expired keys without a pack. `zoe serve` runs a step for each writable store with the ephemeral table once a minute, and `zoe.Storage` on a thread of the extension, from the open of such a store or its first ephemeral write; a step that takes 1,000 keys is followed by another at once. A store that never writes a namespace has none of the three tables. `zoe verify` reads every row; its findings name the namespace and the xxh3-64 hash of the key, never the key.

### Tids

A tid is ZODB's 8-byte `TimeStamp`, strictly increasing. The core allocates it at `tpc_finish` under the commit sequencer: `max(now, last_tid + 1 tick)`. A normal commit never gets `MAX`; when no tid below it is left, `tpc_finish` is refused. In Tier 3 the sequencer is one key updated inside the backend transaction (or an FDB versionstamp).

Clients pass a tid only through `restore` (copy and replication): `tpc_begin` with a tid starts a restore transaction, which takes both `store` and `restore`, and its `tpc_finish` commits under that tid. The tid must be after the last tid, both at `tpc_begin` and at `tpc_finish`, and below `MAX`; otherwise the call is refused, and a refusal at `tpc_finish` does not halt the store.

A deferred restore runs the same commit path, the tid check, the locks and the placement of the blobs with all their syncs, but its backend commit has no sync. The commit is visible and sets the last tid when `tpc_finish` returns, and becomes durable with the next durable commit or `Store::sync`, one backend write under the commit sequencer that writes nothing else, with a sync. A crash loses every deferred commit after the last durable commit, and the store then ends at a whole commit. `Store::sync` fails with `ReadOnly` on a read-only store and with `Halted` on a halted store, and its own error halts the store as a failed finish does. Only the converter of `Data.fs` uses deferred restores; every other path keeps a durable finish.

### Two-phase commit, per transaction

```
Begin ──storea*──▶ Staged ──vote──▶ Locked ──tpc_finish──▶ Durable ──▶ Invalidated
   │                 │                │
   └── tpc_abort ────┴── tpc_abort ───┴── tpc_abort (locks released, staging dropped)
```

- `Staged`: the pickles sit in a buffer of the transaction: in memory up to `staging-memory` bytes, and beyond it in a spill file of the transaction under `staging/` in the store directory. `staging-memory` is the option `Options::staging_memory` of the core, 16 MiB by default; no key of `<zoe>` or `zoe serve` sets it. A spill file is never durable data: nothing syncs it, the transaction removes it at its end, and a writer open removes the spill files that a crash left. Nothing is visible. A staged record can carry its payload, encoded before the finish on another thread, when the length and the hash of the pickle and the compression of the store match; a later store of the oid drops it.
- `Locked`: per-OID locks held for every written oid and every oid passed to `checkCurrentSerialInTransaction` (shared lock). Conflict detection and resolution happen here, so a failed vote releases locks before any disk write.
- `Durable`: one backend write transaction holds the records, their keys in the transaction index, the txn row with status `committed`, and the meta update; it is fsynced before the client is acknowledged, except for a deferred restore (see "Tids"). A crash before the fsync leaves nothing; a crash after it leaves a complete transaction. No repair step of ZOE exists because there is nothing half-written to find. After a killed writer, the first writer open repairs the file and can take longer, because redb rebuilds its free-space map.
- `Invalidated`: after acknowledgement, the oid list is pushed to every other client (server skin) or applied to the in-process invalidation queue.

### Lock manager

A `HashMap<oid, LockState>` with a wait queue per oid, protected by one mutex (contention on the map is negligible against disk time; a sharded map is a later optimisation). Locks are acquired in ascending oid order, so two transactions cannot deadlock on each other; a transaction that must wait releases nothing and queues once. Shared locks (readCurrent) and exclusive locks (writes) follow the usual compatibility matrix. A lock-wait timeout (default 10 s) turns a wait into a `ConflictError`, so a stuck client cannot stall the store.

### Early write-intent locks (extension, ADR 0044)

An intent owner takes exclusive locks before the vote of its transaction, before the transaction reads the oids: `lock_intent(oids)` takes the lock of each oid, in ascending order, and returns the current serial of each one when it holds them all. A competing request waits in the queue of the oid, as a vote waits, within `lock-timeout`; a longer wait, or the end of the connection, fails it with `ConflictError`, and the call keeps no lock that it took. An intent request never takes a lock hand-off: it waits until the store holds the last commit of the oid, so the serial that it returns is the serial of that commit.

Intent locks come in oid order: a request for an oid at or below an oid that the owner holds fails with `LockOrder` (`StorageTransactionError` for the client) and takes nothing; the client releases its intent locks and asks again for the whole set in order. The next transaction of the owner adopts its locks: the vote counts them as its own and takes its other locks in oid order. When it must wait for an oid below an intent lock that it holds, it first releases the intent locks above that oid, then takes them again in order, and the serial check catches a commit that came in between. The locks are advisory: the vote still checks every serial.

Through `zoe serve`, the session owns them: `lock_intent` and `unlock_intent()` run on the thread of the transaction of the session; the next `tpc_begin` adopts them, a session that holds them 60 s without a `tpc_begin` loses them, with one WARN event, and a `tpc_begin` that fails releases them. In-process mode calls the same core. "Lever 3: early write-intent locks (ADR 0044)" says how the client uses them.

### Conflict resolution dispatch

#### 1. Detect

For each staged `(oid, serial_seen)`, compare with the current serial; equal means no conflict.

#### 2. Tier 1, structural

BTree buckets, sets and `Length` whose keys Rust can order (ints, floats, strings, bytes and tuples of those) merge in Rust with the rules of `BTrees._base` and `Length._p_resolveConflict`; object keys that need Python ordering fall through. The vote that takes the locks, in both modes, runs tier 1 on each stale written oid that the client could resolve and whose class, read from the class pickle alone, is a bucket, a set, a BTree or a tree set of a family of BTrees but `fs`, or `BTrees.Length.Length`. The merge follows `bucket_merge` of `MergeTemplate.c` step by step; a BTree or a tree set merges only when it holds one bucket inline, as in BTrees. `zoe-pickle` keeps the identity of each object as Python's unpickler gives it and pickles as zodbpickle does with protocol 3, so the merged record is the record of ZODB's resolver, byte for byte, when that resolver imports each class under the name that the record gives (`crates/zoe-pickle/CLAUDE.md`).

The values of a bucket can hold a `DateTime`, an i18n `Message` and `Missing.Value`, as the metadata of a catalog does (`docs/spikes/catalog-metadata.md`). Tier 1 keeps them as ZODB's resolver unpickles them and compares them as their classes do: a `DateTime` by its instant and its zone, so the same instant in another zone is a change; a message as a str; `Missing.Value` above every other value. A zone that is not in the zone table of DateTime 6.0 with pytz 2026.5, or an object of any other class, gives no answer.

A merge is stored over the committed serial under the locks of the vote, and the reply of `vote` gives the oid as a bare oid, as a ZEO 6 server does for a conflict that it resolved; `tpc_vote` of `zoe.Storage` returns it. A refusal of BTrees fails the vote with `ConflictError` at once. Tier 1 never guesses: a comparison that Rust cannot make (values of mixed types, a dict, an int against a float; lists compare as in Python), a record that does not decode, or a construct that the model does not hold, leaves the conflict to the client.

Three switches, each off by default, add rules that merge where ZODB's resolver refuses, so that with one on, tier 1 is no longer byte for byte ZODB's resolver:

- the key `posting-dicts` (ADR 0042): the posting-dict rule merges the posting dicts of ZCTextIndex, dicts of int to int in a bucket with integer keys, entry by entry against the old dict, and the first-key rule lets a delete of the first key by the committed transaction through in the bucket that a BTree or a tree set holds inline (their refusals: "Lever 1: resolve in Rust, never in Python on the server");
- the switch `split_merges` of the merge policy: the split merge (ADR 0048), below;
- the switch `folder_orders` of the merge policy: the order merge (ADR 0052), below.

**The split merge.** ZODB's resolver refuses every conflict on a node of a BTree and every bucket that a side split, and the vote of ZODB fails on any change of a node that BTrees marked read-current. Where the switch is on, the first conflict of the vote that takes the locks runs three rules on the nodes of BTrees, in the classes where tier 1 runs, on each node by itself at any depth:

1. A stale node that the transaction only marked read-current passes when the other side changed it only by splits of children under which the transaction did not write, and by replacements of such children: a new child in the place of a child that is not the first one, with its separator and the separator after it, as rule 3 writes it. The vote writes nothing for it. A replaced child under which the transaction wrote gives no answer. When the vote fails with `ReadConflict` on a node for which rule 1 gave no answer, the resolution log gets one line for that node, with `split` 1 and the reason of rule 1, in modes `on` and `shadow`.
2. In a node that both sides changed only by splits, the splits of different children merge into the committed node, with the new children of the transaction right after their anchors. So a split of a child node that the other side did not change merges under rule 2 in its parent.
3. A bucket that the transaction split once, and that the other side split once or changed without a split, merges the keys of its range with `bucket_merge`. When the other side changed it without a split, the keys go to the bucket and to the new bucket of the transaction, at the separator of the transaction. When the other side split it too, the keys go to the bucket and to the new bucket Y of the other side, at the separator of Y, and no bucket leaves the tree (ADR 0048, part B). The vote takes the lock of Y without a wait before it reads Y, writes Y over its current serial though the transaction did not store it, and resolves without a record the new bucket of the transaction, and the node when its merged record is its committed record: they leave the staging, are never handed off, and the reply lists them as bare oids. This needs a client that declares `server_writes` (see "Extension negotiation"), or `zoe.Storage` under a ZODB database. For any other client, and when the lock of Y is taken, rule 3 gives no answer there, and the vote goes on as without it. A lock of Y that is taken gives a line of rule 3 on the node, with the outcome `undecided` and the reason "a bucket of the other side that another transaction locks", next to the line of tier 1 of the node. The same holds for the bucket that a root holds inline.

Two key references of one class (five.intid or zope.keyreference) compare by the oids of their objects, as keys and as values, as in conflict resolution, so the two trees of the intid utility merge too. The rules write only the records that the transaction stored, and the bucket Y of rule 3; the reply of `vote` lists them as resolved, the new bucket among them, so a stock `ZEO.ClientStorage`, the native client and `zoe.Storage` need nothing. The rules give no answer for a node that changed by anything but splits (and replacements, for rule 1), a delete in a merged range, two splits of one child on one side, or a child node that the transaction split and the other side changed: rule 3 merges only buckets. An undo runs no rule.

**The order merge.** A folder of plone.folder keeps its order, a `persistent.list.PersistentList`, and its positions, an `OIBTree` of id to index, in its attribute annotations. Each creation appends its id and gives it the index `len(order) - 1`, so two creations from one snapshot give their ids one index, and ZODB has no resolver for the list. The switch is off in the core and on in the profile `zoe.plone:default`. At the first conflict of a written oid, the vote finds the folder of each stale order among the records that the transaction stored, through `__annotations__` and the keys `plone.folder.ordered.order` and `plone.folder.ordered.pos`. When both sides only appended, and the buckets of the positions that the transaction stored hold their old items plus exactly its appended ids at their old indexes, with no stored node that drops a child, the vote stages the committed order followed by the ids of the transaction. After the check of every serial, it gives each of these ids its new index in the records of the positions that it stages: the merges of tier 1 and of the split merge, and the records that the transaction stored and that are not stale, which it stages again. It reads the records back before it stages them. The reply lists the order and each changed record as resolved; the rule writes no record that the transaction did not store beyond the bucket of rule 3, and takes no lock. The same id on both sides refuses; a delete, a move, a sort, a rename, or a rebuild of the positions into new buckets gives no answer. Tier 2 never merges an order that the vote found, and `zoe.policy.validate` refuses a tier 2 entry for `persistent.list.PersistentList` while `folder_orders` is not `off`.

**The switches of the sites of one database.** The profile alone gives the order merge on a stock site: its overrides also switch on `split_merges` and the tier 2 entries of the two Dexterity container classes of stock Plone 6.1, `plone.app.contenttypes.content.Folder` and `Products.CMFPlone.Portal.PloneSite`, whose record a creation changes only in `modification_date` (`max`); a folder of an add-on container class conflicts on its record until its site switches the entry of its class on. The database keeps the latest mode of `folder_orders`, of `split_merges` and of the `tier2` of each of the two classes that each of its sites asked for (`root['zoe.plone.folder_orders']`, `root['zoe.plone.split_merges']`, `root['zoe.plone.tier2:<class>']`), and the policy takes the lowest, so an `off` of one site lasts when another site imports the profile. A site that removes a container class with `null` asks for `off`, and a site that imports `zoe.plone:uninstall` asks for `off` for all four; so each update of another site that asks for a higher mode logs up to four warnings, one for each mode that the site asked `off` for, until that site is removed or imports `zoe.plone:default` again (unless a later profile of that site asks for less). Every other switch takes the new value (ADR 0046). A mode for the whole database goes in the overrides of a site: an `off` that `zoe.policy.install` writes lasts until the next `update_policy` at which the lowest mode of the sites is higher, which replaces it with a warning that names the switch and the replaced mode when no site asked for that mode (it is lower than the lowest mode of the sites before the update, or no site had a mode); a rise of the lowest mode logs at INFO. `update_policy` drops the mode of a site that is gone from this database by the rule of ADR 0052, section 6, and writes the mapping only when a mode changes.

#### 3. Tier 2, field-level

For a persistent object whose class the merge policy marks mergeable, tier 2 (ADR 0046) decodes the old, committed and new states, computes the two changed-key sets, merges when they are disjoint or agree, and applies the strategy that the policy gives each field; coupled fields stay strict. It runs at the vote that takes the locks, after tier 1, on a stale written oid whose class is not a class of tier 1 and whose entry has `tier2` `on` or `shadow`. The state of each record must be a dict of str fields, which `zoe-pickle` decodes with the objects of other classes and the sets that it holds. A field changed on one side when its value does not have the structure of the old one (the same kind, the same items in the same order, the same class and state for an object). A field that one side changed takes that change, a field that both changed to equal values takes it, and a field that both changed differently takes its strategy:

- `strict`, the default, refuses;
- `lww` takes the value of the transaction that votes;
- `max` takes the greater value (two `DateTime`s by their time);
- `sum` adds the two changes of an int;
- `union` keeps the old items that neither side removed and adds the items of both sides once;
- `append` adds the items of the new side after the committed value when the old value is a prefix of both. With the option `state` of the entry, `"options": {"append": {"state": KEY}}`, it merges only when each item that the committed side added holds the state of the last old item under KEY, else it refuses; an item without KEY, or an old value without items, gives no answer (ADR 0046, section 12);
- `keys` merges three dicts key by key with these rules (ADR 0046, section 11): a key that one side changed, added or deleted takes that change, a key that both sides changed to equal values takes it, and two other changes of one key refuse. The keys are strs, ints, bytes or tuples of those, else there is no answer, and two keys that hold one mutable object give none either. The merged dict holds the committed keys in their order, then the keys that only the new side added, in its order.

A delete against a change refuses, and so do two changes of a coupled group that disagree. A state where two fields hold one mutable object (a list, a dict, a set, or an object of another class but `DateTime`) gives no answer; immutable values can be shared. Three records of different classes give no answer. Values compare by their canonical ids, a set without order. The merge walks each object once with an explicit stack, within a budget of 64 steps for each byte of the three records, which the comparisons of tier 1 take too; past it, the merge gives no answer. A refusal names its field or its coupled group in the field `fields` of its line of the resolution log; a line where `keys` merged or refused a field lists in `keys` the keys of its dict that the new record changed. The merged state is the committed dict with the merged values, then the fields that only the new side added, pickled as zodbpickle does under the class pickle of the new record. A named native merge, such as an append-only `workflow_history`, is not built; the classes of `zoe.plone` take `append`.

The state of a `PersistentMapping` is `{'data': {...}}`, so a mapping class merges key by key when its entry gives the field `data` the strategy `keys`. An entry names one class, so a site names a subclass of its own for the mappings whose keys do not depend on each other, and never `persistent.mapping.PersistentMapping` or `Persistence.mapping.PersistentMapping`, whose objects include the root of each database and the WebDAV locks that `plone.locking` keeps in `_dav_writelocks`.

#### 4. Tier 3, the long tail

Classes with their own `_p_resolveConflict` and no policy. The core keeps the locks of the vote and returns the committed states. In server mode, the reply of `vote` lists each such conflict as a ZEO 6 server with `client-conflict-resolution` does: `{oid, serials: [committed, read], data}`, where `data` is the pickle that the client stored. Every stock `ZEO.ClientStorage` accepts this reply, with no negotiation: it loads the read and the committed states with `loadSerial`, runs the method locally, where the class already lives, re-stores the resolved state over the committed serial and votes again. The locks stay held between the two votes, where a stock ZEO server releases its commit lock. The second vote takes no lock, checks every serial again, and replies `[]` or fails. A class that does not resolve raises `ConflictError` in the client, which aborts; a client that disconnects between the two votes releases the locks. In-process mode runs the method through the `ConflictResolvingStorage` mixin, with the same vote. A stale read-current serial is never resolved, nor is a new object, a deletion or a deleted object: the vote fails at once. Only rule 1 of the split merge lets a stale read-current node through, and it writes nothing.

#### 5. Unresolved

The vote fails with `ConflictError`, or the client raises it when the class does not resolve. No tier ever runs Python on the server.

#### Modes and the resolution log

The structural merges have a mode, `on`, `shadow` or `off`, for all their classes (`structural-merges`, `on` by default) and for each class (`structural-merge-class CLASS MODE`); `posting-dicts` is the mode of the posting-dict rule and the first-key rule (`off` by default); and `resolution-log FILE` names the resolution log, a file of JSON lines outside the store, one for each result of tier 1, with the user and the description of both transactions (ADR 0042). The keys are the same in `<zoe>` and in `zoe serve`. In shadow mode, tier 1 writes its result to the log and the conflict goes on as without it; the rules of ADR 0042 write their result in the field `shadow` of the line. A shadow mode without `resolution-log` raises `ValueError` at the open in-process, and is a usage error of `zoe serve`.

These keys are the defaults of the merge policy: a switch that the policy gives (`structural_merges`, `posting_dicts`, the `tier1` of a class) wins over its key. The mode of tier 1 for a class is the `tier1` of its entry, else `structural-merge-class`, else the `structural_merges` of the policy, else `structural-merges`. The switches `split_merges` and `folder_orders` have no key: only the policy sets them, so they are the same in both modes and a copy of the store keeps them. The lines of the order merge have the field `order`, `list` or `pos`. In shadow mode, the order merge and the split merge write their outcome in the field `shadow` of the line of each stale oid, and the conflict ends as with the switch off. Each record that a rule of the split merge writes gives a line with the field `split`, the rule, and a node that rule 1 lets through gives the outcome `passed`, which `zoe_structural_merges_total` counts as `merged`. A policy that sets a shadow mode on a store without `resolution-log` makes the store write a warning for that version of the policy.

### The classes and the profile of `zoe.plone`

ADR 0046, section 9, gives the decisions. `zoe.plone.history.WorkflowHistory` keeps `workflow_history` as a mapping of workflow id to the tuple of its statuses, whose state is the mapping itself, so each workflow is a field that `append` merges, with the option `state` set to `review_state`. Two transitions of one object from one snapshot both commit when each status of the committed one keeps the state of the old history (a comment, then a change of state), and the record equals the record of the two one after the other; two changes of state from one state, or a status of the old state after a change of state, conflict, and Zope retries. A site that wrote the policy before the option gets it at its next import of `zoe.plone:default`. The opt-in Dexterity behaviour `zoe.plone.history` gives an object of its type a `WorkflowHistory` at its next status; the import step of the profile moves the stock histories of the objects of those types, and the profile `zoe.plone:uninstall` gives them back. Comments need no class: plone.app.discussion keeps them in BTrees and a `Length`.

`zoe.plone.properties.PrincipalProperties` keeps the properties of one member or group of a mutable property sheet of PAS, whose state is the mapping itself, with the entry `{"tier2": "on", "default": "strict", "fields": {"login_time": "max", "last_login_time": "max"}}`, on from the install. The bucket of `_storage` then holds references, which tier 1 merges, where the resolver of BTrees refuses any two changes of a bucket of dicts. Two logins of one member merge in tier 2, each time field taking the greater of the two values written; two changes of another property conflict. The import step `zoe.plone.properties` moves each dict of the sheets of the site, groups included, and marks the sheet; on a marked sheet a write of a new principal stores the class, and a read copies the stored value before it adds the defaults, so it writes nothing. The profile `zoe.plone:uninstall` gives the dicts back.

The profile `zoe.plone:default` writes the policy. Its import step derives an entry for the class of each Dexterity type, named by its `__module__` and `__qualname__`: fields merge one by one; an `@invariant` couples every field of its interface and the fields that it reads, under their names and the names that their behaviour stores them under; a class whose group would be empty is blocked; `modification_date` takes `max`, and the other fields `strict`. The derived entries are in shadow mode, but for the two container classes of stock Plone 6.1, which the overrides of the profile switch on with `folder_orders` and `split_merges`; the profile changes derived entries only, and skips a container class that the site has no type of or that the derivation blocks. The step applies the overrides of the file `zoe-merge-policy.json` of each profile, which the site keeps by profile id and which can switch a class on, add groups and fields, but not unblock a class, and composes the result with the policy in the database, so several sites in one database add up. A change of a Dexterity type derives the policy again.

A client without `zoedb`, a stock ZEO client of `zoe serve` included, loads the policy object, and on a site with the profile each `PrincipalProperties` and each `WorkflowHistory`, as broken objects: it cannot read the properties of the members and groups of that site, nor these histories. So a site imports `zoe.plone:uninstall` and packs its store before it leaves `zoedb`, or before a copy opens without `zoedb`; `zoe convert --to-data-fs` refuses a store that still holds these records. `just plone <scenario> history THREADS` checks it in a Plone site.

### The merge policy

The merge policy is a versioned object in the store, so it is transactional and the server reloads it on change (ADR 0046). It is `root['zoe.merge_policy']`, a `zoe.policy.MergePolicy` whose state holds plain values only: `version`, the optional `structural_merges`, `posting_dicts`, `split_merges` and `folder_orders`, and `classes`, a dict of `module.Class` to an entry with `tier1`, `tier2`, `default`, `fields`, `coupled` and `options`, whose only option is `{"append": {"state": KEY}}`. An entry with `"blocked": True` never merges in tier 2. `zoe.policy.validate(policy)` checks a policy and gives a copy of plain values, `zoe.policy.install(connection, policy)` writes it in the transaction of the caller and adds 1 to `version`, and `zoe.policy.read(connection)` gives it back. The core reads it only at a vote with a conflict, and at an undo that merges, and reads it again when the serial of oid 0 or of the policy changed, so a change applies from the next conflict in both modes. A policy that does not read counts as no policy, with a warning for each serial of it. `zoe.plone` generates it from Dexterity schemas plus a short overrides file, and Loupe shows and edits it.

Shadow mode runs tiers 1 and 2 on every conflict but leaves the outcome of the conflict as without them, recording what would have been merged by class, tier and field. A class is switched on once a production run shows that its merges would have been right; the two stock container classes are the exception (see "The classes and the profile of `zoe.plone`"). Every resolution, merged or raised, is logged with oid, class, tier, the keys merged, both transactions' user and description, and `policy`, the version of the policy of the vote. A merge in shadow mode keeps the BLAKE3 digest of its record; when the client then resolves the oid and votes again, the second vote compares the record of the client with it and writes a second line with the outcome `verified` and `same`, true or false, which `zoe_shadow_verifications_total{tier, same}` counts. So shadow mode checks, on the conflicts of a site, that tier 1 gives the record of ZODB's resolver. The test suite replays the merges of tiers 1 and 2 through the Python resolvers, which must produce identical pickles, but for the rules of ADR 0042 and the split merge: their tests check the merged trees with `BTrees.check` and a lookup of every key.

### Pack

Pack at tid T keeps what a reader at T or later needs; T is the lower of the requested tid and the last tid. It keeps every record after T and, for each object that such a reader can reach, the newest record at or before T, a deletion included; it removes every other record at or before T with its blob record, then its blob file. It removes rows and writes no deletion record. The roots of the mark are the root object and every object that a record after T refers to, so an object that a later record links again stays; from each root the mark follows the newest record at or before T. References come from `zoe-pickle`, which reads the persistent id of every BINPERSID of a record, opaque parts included, as ZODB's `referencesf` does, and never unpickles; weak references and references into another database keep nothing. A reachable record that does not decode fails the pack before it removes anything.

Pack runs in batches, in key order, the oldest record of an object first. Each batch is one backend write transaction that removes records with their keys in the transaction index and their blob records, lowers the oid count of their transaction rows and removes a row that keeps no record, except the row at T, so `history` and the iterator stay consistent. After the last batch, the pack removes the transaction rows before T that never had a record. The row at T stays, so a pack at the last tid keeps the last transaction, which a backup continues from. Readers never wait. A finish waits for at most one batch: while a pack runs, each finish notes its oids, and before each batch the pack holds the commit sequencer, marks what the noted records refer to and commits the batch, so a record committed during the pack that links an object again keeps it. The first batch writes `pack_watermark`; nothing is undoable past it, and a pack at an earlier tid does nothing. Blob files are deleted after the removal of their blob records is durable, and an intent file in `blobs/tmp/` names them first, so a crash leaves no blob file that the next open does not remove. A client that links an object from a reference read before T can still link an object that a batch removed, as with ZODB's own pack. A failed batch write halts the store as a failed finish does; a record that fails its checksum stops the pack, which never deletes the evidence of a corruption; a read-only store refuses a pack. ADR 0025 records these decisions.

`pack` is exposed on both skins and as a CLI (`zoe pack --days 7`). With `pack-gc` false (true by default), a pack collects no garbage, as the `pack-gc` of FileStorage and RelStorage, for a site with mount points, whose references across databases a pack of one database cannot see. Such a pack has no mark and reads no reference, so a record that does not decode does not stop it. It keeps every record after T and, of each object, the newest record at or before T, except when that record is a deletion: then the object goes, with each of its records at or before T, their blob records and their blob files, as FileStorage's pack without garbage collection does. The batches, the watermark, the intent files and the stop between batches stay the same, and a dry run reports what such a pack removes. `pack-gc` is an option of the open store, not a record of the store, so a store packed both ways stays valid: `zoe.Storage(path, pack_gc=False)`, the key `pack-gc` of `<zoe>` and of a `[storages.NAME]` table, `zoe serve --pack-gc=false` and `zoe pack --pack-gc=false` (`ZOE_PACK_GC`) set it.

### Blobs

The blob store is a trait with two implementations: a directory tree beside the store, and an S3-compatible store with a local LRU cache. The directory tree is `blobs/` in ZODB's `BushyLayout`, or the directory of the `blob-dir` option (ADR 0023), so existing tools understand it: `blobs/.layout` holds `bushy`, and the file of `(oid, tid)` is one directory per big-endian byte of the oid, then the tid as ZODB's `tid_repr` writes it, for example `blobs/0x00/0x00/0x00/0x00/0x00/0x00/0x12/0x34/0x03f6db4f24444444.blob`. A committed blob file is read-only and immutable. `storeBlob` writes into a temp file in `blobs/tmp/`, computes its BLAKE3 hash on the way, and syncs it.

`tpc_finish` places the files before the backend commit: it writes and syncs an intent file in `blobs/tmp/` that names the tid and the oids, renames each file into place and syncs its directory. The backend write transaction then holds each blob record (hash and size) next to its record, and the intent file is removed; for a deferred restore, only when a durable commit covers it. So a crash never leaves a blob record without its file, and a lost deferred restore leaves no blob file. A crash can leave a file without its record: the next open reads only `blobs/tmp/` and removes the files that an intent file names and that have no blob record. In `blobs/tmp/` a writer open removes only the files whose names the server owns: `<digits>.tmp`, the intent files and `layout.tmp`. With a shared blob directory, `blobs/tmp/` is the `temporaryDirectory()` of each ZEO client, so a restart of the server keeps the files of the clients, as with ZEO's server. Every read through the core checks the size and the hash at the end of the file; a mismatch is a distinct `CorruptBlob` error with the oid and tid. `loadBlob` returns a path (simple mode) or streams chunks (server mode). ADR 0023 records the blob record and the crash order.

### Undo

Every `(oid, tid)` record stays until pack, so undoing a transaction T is a read and a write: for each oid in T, the undo transaction stores the state the oid had before T, or a delete record when T created it. The undo reads the current state of each oid as its own transaction sees it, so several undos in one transaction undo one over the other. When that state is T's, that is the whole job; when later transactions changed it, the write goes through the resolution tiers as a three-way merge, with T's state as the base, the current state as ours and the pre-T state as theirs: tier 1 for BTrees and `Length`, tier 2 for a class that the merge policy names, through the same function as the vote; a refusal fails the undo with `UndoError`. In an undo, a field of strategy `lww` that both sides changed refuses as `strict` does, so the undo never drops a later change without a word (ADR 0046, section 4); the other strategies merge an undo as they merge a vote, and for `keys` a key that a later transaction changed again refuses. The lines of the resolution log of an undo say `"undo":true`, and both modes write them when the undo ends, also when it fails. In-process, an oid that no tier resolves goes to `tryToResolveConflict`, as in FileStorage; `zoe serve` runs no Python, so there such an undo fails with `UndoError`, which a stock client gets as a `MultipleUndoErrors` of one error. An undo of a creation, of a deletion or of a blob that a later transaction changed fails with `UndoError`.

The undo takes no lock: the vote locks its oids and checks their serials as for `store`. A blob undo gives the new record the earlier blob file through a hard link, or a copy where the filesystem cannot link; an undo of a blob whose current blob record is not the blob record of T fails with `UndoError`, where FileStorage gives the earlier blob back. Nothing is undoable at or before the last pack (`pack_watermark`): the undo checks it, the vote checks it again with its locks held, and the finish once more under the commit sequencer, so a pack between the undo and its finish fails that commit alone with `UndoError`; a read of the undo that a pack makes fail gives `UndoError` too. An object whose state before T a pack removed fails the undo. `undoLog` and `undoInfo` read the transaction rows newest first, back from the last tid, and stop at the last pack; an undo id is the base64 text of the tid, as in FileStorage. The records of an undo are whole pickles: the iterator gives their `data_txn` as `None`. In server mode `undoa` queues the undo into the running transaction and `vote` does the work, as ZEO's own server does.

### Record framing: checksums, compression, encryption

Every record, blob record, transaction row, sequence row, KV namespace row and intent file is a frame: a 32-byte little-endian header, then the typed-field slots, then the payload. The header holds the frame version (byte 0), the flags (1), the codec (2), a reserved byte (3), the branch id as a `u32` (4 to 7), the previous serial (8 to 15), the payload length as a `u32` (16 to 19), the length of the typed-field slots as a `u16` (20 and 21), two reserved bytes (22 and 23) and the checksum (24 to 31). The checksum is xxh3-64 with seed 0 over a one-byte tag of the key space, the key that the frame is stored under (the 16-byte `(oid, tid)` key, the 8-byte tid key of a transaction row or an intent file, the UTF-8 name of a sequence row, the name length, name and key of a KV namespace row), bytes 0 to 23, the slots and the payload, so a frame under the wrong key or in the wrong key space fails it. The tags are 1 for `records`, 2 for `blobs`, 3 for `txns`, 4 for the intent files, 5 for `sequences`, 7 for `kv_ephemeral` and 8 for `kv_durable`; 0 is never a tag, 6 is reserved for `vectors`, and a tag never changes and is never reused (ADR 0020, section 3; ADR 0043). The tag is not stored: a reader checks with the tag of the table or file that it reads. The checksum (xxh3-64, CRC32C on backends that already keep one) is verified on every read, and a mismatch is a distinct error, never a `POSKeyError`: `CorruptRecord` with the oid and tid, `CorruptBlob` for a blob record, `CorruptTxn` with the tid for a transaction row, `CorruptSequence` with the name for a sequence row, and `CorruptKv` for a KV namespace row.

The codec byte says how the payload holds the data: 0 is the data as it is, 1 is one zstd frame that states the data length in its own frame header, and a codec that a build does not know is refused as a newer format. By default the store writes each record with codec 0: the setting `compression` is `none` (ADR 0020, section 6). With `zstd`, it compresses each record at a configured level, 3 by default, and keeps the result only when it is smaller than the data. Transaction rows, blob records and intent files use codec 0. A store reads every codec whatever its own setting. The checksum covers the stored bytes, so a read verifies them before it decompresses. A zstd payload is valid only when it is exactly one standard zstd frame (its magic number is checked), the length that it states is at least 1 and at most `u32::MAX` and 32,768 times the stored length, and it decodes to exactly that length; any other payload is a `CorruptRecord`.

A later codec adds a dictionary trained on a sample of the store's own records, kept in the store header and versioned, so a pickle-heavy Plone store shrinks three to five times and the page cache holds proportionally more objects. With encryption on, the frame is sealed with AES-256-GCM under a per-store data key, itself wrapped by a key from a file, the environment or a KMS; the tid and oid are the nonce material, so no two records share a nonce. `zoe scrub` reads every frame at low priority, in the background or on a schedule, and reports mismatches to the metrics and the admin log; Loupe's integrity screen shows the last scrub.

### Forks

A fork is an overlay store: reads fall through to the base at a fixed tid, writes land in the overlay, and the overlay has its own tids, pack and blobs. `zoe fork base sandbox --at TID` opens one without copying the base; discarding it is deleting a directory. It is ZODB's `DemoStorage` done natively, so `plone.app.testing` layers stack forks instead of DemoStorages, an upgrade is rehearsed on a fork of a production copy before it touches the real store, and Loupe opens a fork as it opens any store. A fork is never merged back; what is kept is reapplied as a normal transaction.

### Pack safety

`zoe pack --dry-run` prints what a pack would remove, by class and by size, without touching the store. Two more mechanisms are not built: the retention window and incremental pack. Until they exist, a pack removes records at once and every pack is a full pack. With the retention window (`pack-retention`, a number of days), a pack will not delete at once: removed records will move into the window, `zoe pack --revert` will restore them during it, and physical deletion will happen when the window closes. Incremental pack will be the default: a bounded slice of oids per step interleaved with normal traffic, so there is no pack weekend; a full pack will stay available for migrations.

### Guardrails

`max-record-size`, `max-transaction-size` and `max-blob-size` refuse a `store` with a clear error before anything is written; a lock held longer than `lock-warn` and a transaction open longer than `transaction-warn` are logged with their oid, client and duration, and counted in the metrics. The record size is the length of the pickle, the transaction size is the sum of the pickles of the transaction, and the blob size is the length of the blob file; blob bytes do not count toward the transaction size. A size equal to a limit passes, and no limit is set by default. A restore transaction checks no size limit, blobs included, so a copy such as `zodbconvert` never refuses what its source took. Over the wire, `--max-frame-size` of `zoe serve` (256 MiB by default) also bounds one record, because a `storea` or `restorea` frame holds it whole: a copy through the server needs a limit above the largest record of its source. The error is `TooLarge`, which names the configuration key of the limit and holds no pickle bytes.

The core, not the backend, implements locking, 2PC, resolution, invalidations and blobs, so a backend is a few hundred lines. The logged backend of `zoe-core` (`src/wal/`) implements the trait over the redb backend: it holds the segments, the unfolded table, the backlog, the replay and the fold. The methods of the log have defaults, so a backend without a log takes each batch as a direct batch.

### Backends

| Backend | When | Durability | Trade-off |
| --- | --- | --- | --- |
| redb (embedded, pure Rust, MVCC, single writer), with the write-ahead log of ADR 0056 | first release, both modes | a commit batch is durable with the sync of its entry of the log; the fold writes the tables in slices, each ACID with a sync | the log takes the write amplification of the copy-on-write B-tree off the commit path; a load still makes one lookup |
| append-only log + in-memory oid→offset index (filestorage2 design) | when `zodbshootout` shows redb's write path is the bottleneck | sequential appends, one fsync per group, marker flip | custom format: own backup, verify and index-rebuild tools |
| FoundationDB or TiKV | Tier 3 | replicated before acknowledgement | network hop per operation; FDB caps a transaction at 5 s and 10 MB, so large commits stage locally and write in one short transaction |

### The database file

The core opens the redb file and the segments of the write-ahead log through its `Vfs`. On a disk, the database file holds the page writes that redb makes for a commit and makes them before the sync, in the order of their offsets, each run of adjacent pages as one write; a read, a change of the length and the close make them first too. A growth of the file of at most 64 MiB gets zeros, so a commit that later writes into the new space syncs no allocation of blocks; the sync after a growth writes the zeros once. On macOS, a sync is `fsync(2)`, as for FileStorage, and not `F_FULLFSYNC` (ADR 0006). On Linux, a sync is `fdatasync` for the database file and the segments of the log, and `fsync` for the other files and the directories. A segment makes each write at once and holds no copy of an entry, and each growth of it gets zeros, so an append to the space that the fold grew syncs no allocation of blocks.

### The write-ahead log (ADR 0056)

A finish appends its commit batch to a segment of `wal/` as one entry, with one write, and syncs that segment alone: the copies of the B-tree pages leave the commit path. The batch goes into the unfolded table in memory, under one write lock, and then the leader stores the published tid P of the log. Every read reads the table before the tables and ignores what is after P, so a reader sees a prefix of the commits, and a load still makes one lookup: a record of the backlog comes from memory, a folded record from redb. When the backlog is empty, a read takes no lock.

The fold, one thread for each writable store, writes the commits of the log into the tables in slices of `slice_bytes` (4 MiB), each one backend write with a sync, when the backlog reaches `fold_bytes` (16 MiB), when its oldest commit reaches `fold_age` (5 s), or on a request: `Store::fold`, a pack, `kv_restore_durable`, a finish that waits, and the close. A slice checks each frame, waits for the end of a log sync that runs, commits, and only then removes its commits from the table. The backlog is bounded by `backlog_bytes` (256 MiB): a finish that would pass it waits for the fold, and fails none. A batch of deferred restores, the batch after a deferred commit that no sync covered, a batch of mostly records of at least `large_record` (64 KiB) on an empty backlog, a batch larger than half of the bound, and each batch when the log is off go into the tables directly, as each batch did before. The settings are `Options::write_log`; the skins do not expose them.

The fold prepares spare segments and grows the current segment ahead of the leader, so the commit path writes no zeros. The epochs of the uses never repeat, and the open replays each segment in use in epoch order: a passing header gives the length of its entry, the entries at or before the folded tid are skipped by that length, and the entries after it go back into the table and the backlog. A damaged entry with a valid entry after it, a broken chain of previous tids, or a header that fails in the middle fails the open with `CorruptTxn`; an I/O error fails it with that error. A damaged last entry reads as a torn write: the open cuts it, logs its tids at ERROR and gives them through `Store::cut_at_open` (the one exception of N13). A clean close folds the whole log and writes the state "spare" into each header, so the next open reads 32 bytes of each segment.

### Group commit

`tpc_finish` calls join a commit batch; the batch leader writes all members as one entry of the write-ahead log, or in one backend transaction for a direct batch, syncs once, and wakes every member. The leader writes an attached payload as it is and encodes only the records without one, so the frames are the same either way. A batch whose members are all deferred restores commits without the fsync; a batch with any other member fsyncs, which makes the deferred commits before it durable too. A finish waits for its batch on the store clock, so the simulator runs other threads meanwhile. On a 10 ms fsync device this is the difference between 100 and several thousand commits per second.

### The lock hand-off (ADR 0044)

A lock passes from a commit whose finish started to the vote that merges onto it, and the merge commits after it. Once its member is in the queue of group commit, a finish cannot abort, and its staged records are the records that its batch writes. So it hands the lock of each oid that it writes, of a class that tier 1 merges in mode `on`, to the exclusive vote at the head of the queue of the oid, with a copy of its staged record. That vote merges onto the copy at once, and a refusal fails it at once. When tier 1 does not decide, the vote waits until the commit of the holder is durable, within `lock-timeout`, then goes on as without the hand-off. The finish of the new owner starts after the finish of the holder, so its commit lands in the batch of the holder after it, or in a later batch, with the tid of the holder as the previous serial of the merged record. A failed write or sync halts the store, so no commit is durable before the commit that it merged onto, and an acknowledged commit stays durable (N1).

The lock table keeps the hand-off until the store holds the last commit of the oid: until then, a new owner that aborts or fails passes the lock with the same hand-off to the next exclusive vote, and a shared request (`readCurrent`) waits, so no vote reads a state that the store does not hold. The commits of a hot `Length` then share a batch: A, then B merged onto A, then C merged onto B. `zoe_lock_handoffs_total` counts the hand-offs. When its commit is durable or failed, the finish releases the locks that it did not hand off, then wakes the votes that wait for its commit. A restore never hands off a lock.

### Opening

`zoe.Storage(path, *, read_only=False, lock_timeout=None, blob_dir=None, pack_gc=True, compression=None, structural_merges=None, structural_merge_classes=None, posting_dicts=None, resolution_log=None, early_locks=False, early_lock_classes=None)` opens the store in the directory `path` and creates the directory when it is missing. The keyword arguments are the keys of the `<zoe>` section below; `lock_timeout` is in seconds. `blob_dir` is the blob directory, `path/blobs` when it is `None` (ADR 0023). The store does not record its blob directory, so each open gives the same one: a store with blobs refuses a blob directory without a layout file with `StorageError`, and a blob directory without a layout file that holds other files, or that another open store holds, raises `StorageError` and keeps its files. A `blob_dir` that is not a directory raises `OSError` before anything is created.

A read-only storage refuses `tpc_begin`, `new_oid`, `store`, `deleteObject`, `pack`, `restore`, `storeBlob`, `restoreBlob` and `temporaryDirectory` with `ReadOnlyError`, and a missing directory with `FileNotFoundError`: it creates nothing. It opens the store for writes and takes the exclusive lock. `close` aborts the open transactions, and the storage then refuses every call; a call in progress keeps the store open until it returns. `zoe.Storage` is `zoe.storage.Storage`, a Python subclass of the extension class `zoe._zoe.Storage` and of ZODB's `ConflictResolvingStorage` that declares `IStorage`, `IBlobStorage`, `IStorageIteration`, `IStorageCurrentRecordIteration`, `IBlobStorageRestoreable`, `IStorageUndoable` and `IExternalGC`. `import zoe` does not import ZODB.

### Thread model

`Storage` is thread-safe and shared by all Connections of a process. Per-transaction state is a core transaction in a table of the storage, keyed by the identity of the ZODB transaction object. A second `tpc_begin` of the same transaction, or a call with a transaction that the storage did not begin, raises `StorageTransactionError`; `tpc_abort` of an unknown transaction does nothing. The thread that calls `tpc_begin` drives the transaction: `store`, `deleteObject`, `restore`, `storeBlob`, `checkCurrentSerialInTransaction` and `tpc_vote` from another thread raise `zoe.WrongThread`, a subclass of `StorageTransactionError`, and change nothing; `tpc_finish` and `tpc_abort` may run on any thread, as ZODB's own tests do. On a free-threaded build, worker threads can be inside `tpc_finish` at the same time. No mutex of the core or of the extension is held while Python code runs; the per-OID locks of a vote stay held while `_p_resolveConflict` runs, until the second vote ends, the transaction aborts or the storage closes. The module declares `Py_mod_gil_not_used`.

### Commit publication

The core makes a commit durable and visible before `tpc_finish` calls its callback, which hands the invalidations to the other Connections. A commit is published when its callback has run, and `lastTransaction` gives only a published tid: it waits for the callback of the last commit, so a Connection never starts a snapshot after a commit whose invalidations it did not get. Callbacks run in commit order: a commit waits until the commit before it is published. A callback that calls `lastTransaction` gets the tid before its own commit. A callback cannot commit in its own storage, because that commit would wait for the callback: its `tpc_finish` raises `StorageTransactionError` and commits nothing.

### Stop by a signal

When `zoe.Storage` opens a store, read-only too, the extension installs a handler of SIGTERM and one of SIGHUP, each only when `signal.getsignal` gives `signal.SIG_DFL` for that signal; an ignored signal and a handler of the application keep their action, and a handler that the application sets later replaces the handler of the extension for good. The handler wakes the watcher thread of the extension, one per process, which runs no Python code. The watcher closes each open storage of the process as `close` does, so the database closes cleanly and Loupe, `zoe mcp` and `zoe verify` open it with no repair; a `tpc_finish` whose commit started before the signal commits, durably. The wait lasts at most 5 seconds for all the storages together; a store that a call still holds then, such as a running pack, stays open. Then the watcher restores the default action of the signal and raises it again, so the process ends with the status of the signal. A child of `os.fork()` has no watcher: an at-fork hook gives it the default action back where Python sees `SIG_DFL`. SIGINT needs no handler, because `KeyboardInterrupt` ends the interpreter, whose drop closes the store. ADR 0031 records the design.

### Errors

Core errors arrive as the exceptions of ZODB: `NotFound` as `POSKeyError(oid)`; `Conflict` as `ConflictError` and `ReadConflict` as `ReadConflictError`, both with `oid` and, for a stale serial, `serials == (current, read)`; a `ConflictError` on a stored object also gets the stored pickle as `data`; a conflict that `_p_resolveConflict` does not resolve raises the `ConflictError` of `tryToResolveConflict`; `Protocol` and `LockOrder` as `StorageTransactionError`; `WrongThread` as `zoe.WrongThread`; `Halted`, `CorruptRecord`, `CorruptTxn` and `Backend` as `StorageSystemError`; `Locked`, `Closed`, `Format`, `TooLarge` and a call on a closed storage as `StorageError`; `Io` as `OSError`.

### Migration from `Data.fs`

1. `zoe convert --from-data-fs`, or `zodbconvert` from `<filestorage>` to `<zoe>`: tids, oids, pickles and blobs are copied unchanged.
2. Verify with `zodbverify` or `zoe verify` on the new store, then compare `lastTransaction()` and a random sample of `loadSerial` results between the two.
3. Swap the stanza, start the instance.
4. The reverse direction works the same way, which is the exit path if something goes wrong.

## Server mode

`zoe serve` runs a tokio server that speaks ZEO's msgpack protocol so that `ZEO.ClientStorage` connects unchanged; it replaces `runzeo`, not the client. This section gives the contract of the server; `crates/zoe-server/CLAUDE.md` holds the invariants of its mechanisms.

### Command line

`zoe serve --path STORE --listen HOST:PORT` serves one store under the storage name `1`, the default of ZEO. Each option has an environment twin and, but `--config` and `--storage`, a key of the configuration file; the option wins over its twin, and both win over the file. The server announces and takes only `M5`. stdout carries only the lines `admin <address>` and `listening <address>`, the second once the server accepts connections, so a port of 0 gives a free port; the logs go to stderr. The listening TCP socket takes `SO_REUSEADDR`, so a restarted server binds the same port at once. A store that does not exist is created, except a read-only store. `tpc_finish` replies only after the commit is durable, so a SIGKILL at any point loses no acknowledged commit. The extension of `tpc_begin` comes as a msgpack map, which the store keeps pickled in protocol 3, or empty for an empty map, as `zoe.Storage` stores `extension_bytes`. The console script of the wheel has no server: `zoe serve` there fails with 1 and names the `zoe` binary.

| Option | Twin | Default | Value |
| --- | --- | --- | --- |
| `--path STORE` | `ZOE_PATH` | none | the store of the storage name `1` |

A boolean option alone means `true`, and it takes a value only with `=`: `--pack-gc=false`. `--pack-gc false` is a usage error (exit code 2). The same holds for `--read-only`, `--shared-blob-dir`, and `--dry-run` and `--force` of the other subcommands.

The transaction timeout counts from the end of a vote that passed until the transaction ends, also through the second vote of a conflict that the client resolves, because the locks stay held between the two votes. When the thread of the transaction waits for the next call past that time, or gets a call after it, the server logs one ERROR line, `transaction timeout after the vote: closing the connection`, with the field `seconds`, and closes the connection as the idle timeout does: the calls that wait do not run, the transaction aborts and releases its locks, and the client gets no reply. A call of the transaction that runs, such as a `tpc_finish`, runs whole. Heartbeats and other calls do not reset the time, and the transaction timeout closes no connection without a voted transaction.

A listen address that holds a `/` is the path of a unix domain socket, as the `address` of ZEO's `<zeo>` section can be. At its start, the server removes a stale socket file at the path, as runzeo does, and fails with 1 when a process accepts on it or when the path is not a socket. At a stop, it removes its socket file when the file at the path is still the socket that it bound. TLS does not apply: `--tls-cert` with a socket path is a usage error. The log lines name a client on a socket by the path and the process id of the peer.

### Process shape

The server is a single static binary with no Python inside and no Plone eggs beside it: conflict resolution runs in Rust (see "Conflict resolution dispatch") and the long tail is resolved by the client. `zoe serve` is the only entry point, and the same binary is the Tier 3 front.

### Memory and startup (N6, N7)

The open of a store reads the free-space map of redb, about 128 bytes for each MB of the file, then a fixed number of pages: the format, the transaction index table, the last tid, the last transaction row and the next oid. It rebuilds no index, so `/readyz` gives 200 soon after the start on a store of any size (N7, after a clean close). After a clean close, the open of the write-ahead log reads 32 bytes of each segment. After a crash, it replays the entries after the folded tid, at most `backlog_bytes` and one entry, and reads the headers of the folded entries of the segments in use: about 0.4 s for a full backlog of 256 MiB (ADR 0056). After a killed writer, the first open repairs the file and can take longer, because redb rebuilds the free-space map from every page of the file (ADR 0028).

The size of the stores adds only the free-space map to the resident memory of the server (N6); the configuration and the clients bound the rest: the page cache of each store (`cache-size`); at most 64 MiB of held writes of the database file of each store; the runtime threads, one per core, and at most 512 blocking threads of at most 2 MiB of stack (the compression pool, the read pool, and for each connection the thread of its transaction and at most 4 calls); for each connection, at most 5 decoded calls of at most `max-frame-size` each, the session queue of 4 replies and the hub queue of at most `client-queue-size` frames, and neither the replies nor the hub frames have a bound in bytes; for each open transaction, about three times `staging-memory`: the pickles, their copies in the compression queue and their encoded payloads. For each writable store, the write-ahead log holds at most `backlog_bytes` of entries and their indexes in memory, 256 MiB by default, plus the entry that the leader of a commit batch writes (ADR 0056). `crates/zoe-server/tests/large_store.rs` checks N6 and N7 with a store larger than the bound, read at random from 16 clients; the reference machine runs it with a store of 100 GB, a cache of 1 GB and a bound of 2 GB.

### Named storages

One process serves any number of stores, as ZEO does: `zoe serve --storage main=/var/zoe/main --storage catalog=/var/zoe/catalog`, or a `[storages]` table in the configuration file, and the client's `register(storage_id, read_only)` selects one; `register` with a name that the server does not serve fails with ZEO's `ValueError`. Each store has its own path or backend, blob store, lock manager, invalidations, status, pack schedule, read-only flag, quotas, and a `storage` label on every metric and log line; commits on different stores never wait for each other. Plone mount points therefore work unchanged: one `<zeoclient>` per mount, same server. In-process mode is the same thing with one `<zoe>` stanza per mount.

### Configuration file

`--config FILE` reads a TOML file. Its top-level keys are the options of `zoe serve` without `--`, except `config` and `storage`, each with a string, an integer or a boolean in the syntax of its option. Each `[storages.NAME]` table adds a store under the storage name `NAME`, with the keys `path` (necessary), `blob-dir` (`<path>/blobs` by default), `read-only` and `pack-gc`:

```toml
listen = "0.0.0.0:8100"
lock-timeout = "10s"

[storages.main]
path = "/var/zoe/main"

[storages.catalog]
path = "/var/zoe/catalog"
blob-dir = "/var/zoe/catalog-blobs"
```

The stores of the file add to the stores of `--path` and `--storage`, and a relative path is taken from the working directory. A file that does not read or parse, an unknown key, a value of the wrong type, a store without a path and a storage name that comes twice are usage errors (exit code 2), before the command opens or creates anything.

### The `<zoe-server>` section

`python -m zoe.serve -C FILE` reads the `<zoe-server>` section of a ZConfig file, which `%import zoe` declares, and runs `zoe serve` with its settings, for buildout users (ADR 0028):

```
%import zoe
<zoe-server>
  listen 0.0.0.0:8100
  lock-timeout 10s
  <storage main>
    path /var/zoe/main
  </storage>
  <storage catalog>
    path /var/zoe/catalog
    blob-dir /var/zoe/catalog-blobs
  </storage>
</zoe-server>
```

The keys of the section are the top-level keys of the configuration file and `binary`. Each `<storage NAME>` subsection is a `[storages.NAME]` table, with its name in lower case, as for `runzeo`. A leading `~` in a path key is the home directory. The section wins over the twins: `zoe.serve` removes from the environment of the server the twin of each key that the section sets, and an empty value counts as not set. The binary is the key `binary`, else `ZOE_BINARY`, else the `zoe` binary on the PATH that is not a script, because the wheel ships no server. `zoe.serve` writes the settings as a configuration file that has no name on disk, and replaces itself with `zoe serve --config` on that file (`execve`). So no Python stays in the process of the server, a supervisor stops it with SIGTERM, and no value of the section goes into the arguments of the process. An unknown key, a bad boolean, a storage without a path and a storage name that comes twice are usage errors (exit code 2) before anything starts; a missing binary exits with 1.

### Modes

`--read-only`, or `read-only = true` in a `[storages.NAME]` table, makes every store or one store read-only. The server opens a read-only store as `zoe verify` does (ADR 0028): the store must exist, a store that a killed writer left open gets its repair first, with one WARN line that holds `repaired the store`, and the server holds the lock of the store, so no writer opens it while the server runs. `register(storage_id, false)` on a read-only store fails with `ReadOnlyError` and the connection stays open, so a client with `read_only_fallback` registers again read-only. On a read-only store, a vote, `new_oids` and `pack` fail with `ReadOnlyError`. A follower being promoted serves read-only until it holds the lease, so reads continue through a failover. Maintenance mode (`zoe admin drain`) stops accepting new transactions, lets in-flight `tpc_finish` complete, sends every client a clean close and reports when the store is quiet, for a pack with a full stop, a format migration or a restore.

### Connection handling

The calls of one connection run concurrently, and each reply carries the message id of its call and goes out when its call ends, so `prefetch` and pipelined loads return out of order; the replies of the calls of one transaction keep the order of their calls. `register` runs first, alone, and so do `set_client_label` and `iterator_gc`: the server starts no later call of the connection before they end. The calls of the transaction (`tpc_begin` to `tpc_finish` or `tpc_abort`, the stores and the three upload calls) run in their order on one thread, which drives the core transaction. The calls that read run on a read pool of `--blocking-threads` threads that all connections share, because the core is synchronous; `sendBlob` and `pack` run on a thread of their own. So a vote that waits for a lock holds no thread of the read pool, and a connection with no call that runs and no open transaction holds no thread.

`storea` and `restorea` stage the pickle, queue a job of a shared compression pool that encodes it, and reply at once; the first vote waits for the jobs of its transaction before it takes a lock, encodes itself a job that no thread took yet, and fails with `StorageError` when a job failed. The reply of a load holds the bytes of the record as the core gives them, with no copy.

Each call takes, before it starts, one of the 4 slots of its connection and room for its reply in the session queue of 4 replies, and starts only while at most 1 MiB of replies waits for the client. A call of the read pool also takes a turn in the window of its connection: 1 call for a new connection, opened by 1 call up to 4 for each reply written to the socket while at most 1 MiB of other replies waited, and closed to 1 call by a reply that goes into the session queue while more than 1 MiB waits. So a client that reads promptly runs up to 4 calls of the read pool at once, and a client that does not read its large replies runs them one at a time. The calls of the transaction, `sendBlob` and `pack` take no turn. A download keeps its slot until it ends.

### Wire contract

A frame is a 4-byte big-endian length and a payload. The server sends `M5` first, as raw bytes; the client answers `M5`, or `ruok` for a JSON status and a close. Every other payload is a msgpack array `[id, flags, method, args]`, encoded with bin types and decoded with str keys and arrays as tuples. A connection that got the extension `trace_context` can add a fifth element to a message, its trace context (see "Traces"); a message with five elements closes any other connection. A call that waits has an int id (or `[oid, tid]` for `loadBefore`) and flags false; an asynchronous call, in either direction, has id 0 and flags true and gets no reply. An oid or a tid is 8 bytes. A serial (of `storea`, `storeBlobEnd`, `storeBlobShared`, `checkCurrentSerialInTransaction` and `deleteObject`) can also be a str whose UTF-8 bytes are 8 bytes, as ZEO's tests send `'\0' * 8`; any other str for a serial, an oid or a tid fails with `TypeError`. The server always sends bytes. A reply echoes the id with `.reply` and flags 0, or flags 2 and `[class, __dict__ or args]` for an error. The method shapes are those of `docs/spikes/zeo-wire.md`, and the traces in `docs/spikes/zeo-wire/` are the reference for the protocol tests.

An unknown method, a call before `register`, an error in an asynchronous call, a frame that is cut or is not a message, and a frame longer than `--max-frame-size` close the connection; the bytes of a client close only their own connection. The decode of a frame stops at a depth of about 60 levels and at 100,000 msgpack values, before the server builds the values, so one frame costs at most about twice its size plus 16.2 MiB. Before such a close, after the handshake, the server ends the calls of the connection, aborts its transaction, and drops the bytes of the client until the client sends nothing for 50 ms, or for 500 ms at most: so the calls that the client sent before it saw the close arrive before the FIN, and the close is not a reset, as with ZEO's server.

The server ignores id -1, the heartbeat that a stock client sends every 60 s, except that it is a frame for `--idle-timeout`. The idle time counts from the accept, then from the later of the last whole frame read and the end of the last call of the connection, so one frame that takes longer than the timeout to arrive is cut. It does not count while a call of the connection runs, from its start until it queues its reply, nor while 4 calls run or wait: a client that waits for the reply of its own call is not idle. It counts while the next call waits for room or for a turn and no call runs.

At most 4 decoded calls of a connection run or wait; then the server reads no more bytes of that connection, so TCP makes the client wait. A call starts, and a download sends its next chunk, only while at most 1 MiB of replies waits to be written to the socket, a constant (N6); a larger reply goes out whole, and the invalidations do not count. So the replies that wait for one client hold at most 1 MiB plus one reply for each call of its window. Limit: small replies open the window also for a client that does not read, so such a client can hold one large reply for each call of its window, once. Nothing bounds the memory of many connections together.

### End of a connection

A connection ends when its client closes or resets it, when its hub queue overflows, when it sends no frame for `--idle-timeout`, when its transaction stays open past `--transaction-timeout` after its vote, or when the server stops. The calls that arrived before the end run, the calls of the transaction in order, as ZEO does: a `tpc_finish` that arrived commits whole, unless it waits behind a vote whose lock wait the end cancelled. The calls that did not start stop when a call closes the connection or when the client is gone. The client gets no reply when it, the hub or a timeout closed the connection; at a stop, it gets the replies (see "Stop"). Then the open transaction aborts at any state, between the two votes too, which releases its locks and removes its upload file, and the iterators of the connection go. A server killed during a vote commits nothing of that transaction.

Each end of a connection but a stop of the server also ends the lock wait of its session: a vote that waits leaves the queue, releases the locks that it took and fails with `ConflictError`, and a `tpc_finish` queued behind it does not commit. So a client that disconnects during its vote holds no lock after its disconnect, whatever `--lock-timeout`. At a stop, a vote that waits goes on waiting: the other connections abort their transactions, so the vote gets its lock, and a `tpc_finish` that arrived behind it commits.

The server sets no TCP keepalive, so a host that dies without a FIN or a reset, or a client that stalls during a commit, keeps its connection, its transaction and its locks until `--idle-timeout` closes the connection (for ever with 0), or, after its vote, until `--transaction-timeout` closes it. The idle time counts from the end of the last call: a host that dies while its vote waits keeps its locks for `--lock-timeout` at most; one that dies while its `pack` runs keeps the locks of its voted transaction for the pack plus the idle timeout; a `sendBlob` that waits for room for a chunk stops the idle timer, so a client that reads nothing keeps its download threads and its locks until it reads or closes. While the server waits for room for a call and no call runs, it reads no frame, heartbeats included, and the idle time counts. So a client that does not free 1 MiB within `--idle-timeout` is closed while it sends heartbeats: with 4 large replies of about 32 MiB in its window, a client that reads under about 110 KB/s is closed at the default of 300 s. The server keeps this behaviour on purpose.

### Invalidations

After each `tpc_finish`, every other client of the storage gets one `invalidateTransaction(tid, [oids])`, with the oids from the transaction index, also an empty list, as ZEO 6.2 does; the client that committed gets `info {length, size}`, then its reply, and no invalidation. Each client gets its replies and the invalidations in commit order, because the cache of a stock client refuses a tid that goes back: the commits pass through one hub per storage, which orders them by tid. A commit waits in the hub, never on a thread, and a finish that fails publishes nothing. `register` and `lastTransaction` give the last published tid, and `register` joins the hub at that tid.

Each connection has two queues for its outgoing frames: the session queue of at most 4 replies, and the hub queue of at most `client-queue-size` messages. An invalidation is one message, and so are the `info` after a pack and, for the client that committed, its `info` and reply together, so a hub queue of one message lets a client commit. The hub never waits: on overflow the server closes that connection, and the client's reconnect path replays through `getInvalidations`. The writer sends the frames of both queues in the order in which they went in, so an invalidation can come between `receiveBlobStart` and `receiveBlobStop`, where a stock server never sends one; the stock client handles each message on its own, and a commit never waits for a download. A `loadBefore` reply shows only the commits that the hub published, and comes before the invalidation of any later commit, because the stock client caches a record without a next serial as current. The replies of `register`, `lastTransaction` and `getInvalidations` come after the invalidations of the commits up to their tid. This is the contract that ZEO keeps.

### Change feed

The same broadcast, made public and resumable: `zoe feed --from TID` on the admin port (a gRPC stream, and a WebSocket for browsers) delivers one message per committed transaction with its tid, user, description, extension and the `(oid, class)` pairs it touched, in commit order, exactly once from the requested tid, replayed from the transaction log for any tid still in the store. Consumers acknowledge by tid, so a restarted consumer resumes where it stopped. External indexers, cache purgers, webhook bridges, Loupe's live tail and MCP notifications read it, with no hook in Plone. Class names come from the class pickle, never from unpickling state.

### Blob streaming

A client without a shared blob directory uploads a blob in chunks. `storeBlobStart` needs an open transaction, and creates one upload file in the blob temp directory of the store; `storeBlobChunk` appends to it, and `storeBlobEnd` stages it in the transaction, which takes the file by rename. An error of a blob upload call closes the connection, as in ZEO. Each end of the transaction removes a file that the transaction did not take, and the next writer open of the store removes a file that a crash left. `sendBlob` first reads the whole file and checks its size and its BLAKE3 hash, then streams it in chunks of 64 KiB: `receiveBlobStart`, one `receiveBlobChunk` per chunk, `receiveBlobStop`, then the reply. A blob that fails the check goes out as an error reply with no chunk, because a stock client keeps a partial file after a download that stops. A missing blob is a `POSKeyError`. An upload or a download holds a few chunks in memory, whatever the size of the blob. S3-backed stores upload at `tpc_finish` and keep a local cache for `sendBlob`.

### Health, metrics, shutdown

#### Health and readiness

`--admin-listen HOST:PORT` opens the admin port, a small HTTP/1.1 server that binds with the ZEO port, before the stores open; a port that does not bind fails the start and creates no store. `GET /healthz` gives 200 while every store is open, and 503 before. `GET /readyz` gives 200 when every store is open, loaded its last tid, and held no lock after its open, and, with Tier 2, when the replica is caught up; it gives 503 before, and from the stop signal on. It also gives 503 when the lock table of a store held entries at the open. The body is plain text with one line per storage, `NAME: open`, `NAME: ready` or `NAME: not ready: the lock table held entries at the open`, or the line `starting` or `stopping`; `HEAD` gives the reply without the body, another method 405, another path 404. The port serves one request per connection, with a head of at most 8 KiB that must arrive within 2 s, and at most 64 connections at once, so it belongs on a private address. It never speaks ZEO, and it answers until the end of a stop.

#### Metrics

`GET /metrics` on the admin port gives the metrics in the Prometheus text format once every store is open, and 503 before. Each metric is named `zoe_*` and has the label `storage`; a duration is a histogram in seconds and a counter ends in `_total`. The server counts a call before its reply goes out.

- `zoe_loads_total`, `zoe_load_latency_seconds`: the `loadBefore` calls; `zoe_commits_total`: the commits; `zoe_vote_latency_seconds`: each `vote`, its lock wait included; `zoe_finish_latency_seconds`: each `tpc_finish`, until the commit is durable.
- `zoe_fsync_batch_size`: the commits that one sync makes durable; `zoe_lock_wait_seconds`: the time of each vote to take its locks; `zoe_lock_handoffs_total`; `zoe_intent_locks_total` and `zoe_intent_lock_wait_seconds`.
- `zoe_fold_seconds`: each slice of the fold of the write-ahead log; `zoe_fold_commits_total`: the commits that the fold wrote into the tables; `zoe_backlog_wait_seconds`: each wait of a commit batch for the fold; `zoe_backlog_bytes`: the bytes of the backlog of the log, read at each scrape (ADR 0056). After the open of each store, the server logs the entry that the open cut, with the name of the storage, at ERROR.
- `zoe_conflicts_resolved_total{path}`: `path="python"` counts the oids in conflict that a second vote passes after the client resolved them, `path="native"` the oids that tier 1 or tier 2 merged in a vote that passed. `zoe_structural_merges_total{tier, mode, outcome}`: each result of tier 1 and tier 2, `merged`, `refused` or `undecided`, in mode `on` or `shadow`. `zoe_shadow_verifications_total{tier, same}`: each check of a merge of shadow mode against the record of the client. `zoe_conflicts_raised_total`: each vote that fails with a conflict, and each transaction that ends between the two votes, which the client then raises as `ConflictError`.
- `zoe_writes_on_get_total{class}`: the writes-on-GET report of F32, the records that the transactions of GET and HEAD requests commit, new objects included; `zoe.plone` marks the transaction of each request with the key `zoe.request_method` of its transaction extension, which reaches the server also from a stock `ZEO.ClientStorage`. A deletion, a pickle whose class does not decode and a write of a KV namespace count nothing.
- `zoe_clients_connected`: the registered connections; `zoe_invalidation_queue_depth`: the messages in the deepest hub queue of the storage.

#### Logs

The logs go to stderr from the level INFO on, as text, or with `--log-format json` as one JSON object per line, with the fields of the event and of its spans. Each line of a connection has `client`, the label of `set_client_label` or else the address, and once it registered `storage`. A text that a client sends goes only into a quoted field, never into the message, so it cannot add a log line. `--lock-warn` and `--transaction-warn`, in whole seconds, set `lock-warn` and `transaction-warn` of each store: a lock held longer is logged when it is released, with its `oid`, `client` and `storage`, and a transaction open longer with its client and storage. A log line holds no pickle bytes, user or description.

#### Stop

SIGTERM and SIGINT stop the server within `--shutdown-timeout`, and the command exits with 0. `zoe serve` handles both signals before it creates anything on disk, and a signal during the start stops the server when the start ends, so a signal never leaves a store directory without a store. A SIGKILL or a power loss during the first open can leave one, and so can a first open that fails for another reason, such as a full disk; a later writer open makes a store in such a directory. At a stop, each connection reads no more calls, and the calls already received run, so a received `tpc_finish` commits and gets its reply; then the open transaction aborts, the connection sends what waits and closes, and the stores close cleanly. At the timeout less one second (less half the timeout when that is shorter), the connections that remain close at once. A running pack stops between two batches, with `StorageError` to the packing client, and a later pack at the same time removes what it left (ADR 0025); a stop during the mark waits for the mark and the first batch. A call that runs past the timeout keeps the store of its session open: the process exits at the timeout, that store does not close cleanly, and its next open repairs it (ADR 0028).

After the stop, a connection drops the bytes that its client sends, ends its last frame with a FIN, and closes when the client acknowledged every frame and the FIN, or closed its side, and never later than the forced close. So a client that sends bytes after the stop gets every frame and the reply of its `tpc_finish`, then a clean close, not a reset. Where the server cannot read the send queue of the socket (outside Linux, and in the simulator), a connection closes at most 500 ms after the FIN, and a byte that the client sends after that, while the kernel still sends the last frames, can still reset the connection.

### Traces

Every request, lock wait, fsync and pack step is an OpenTelemetry span, exported over OTLP when the variable `ZOE_OTLP_ENDPOINT` is set, with the protocol of `OTEL_EXPORTER_OTLP_PROTOCOL` (`grpc` to the endpoint, or `http/protobuf`, the default, or `http/json` to `<endpoint>/v1/traces`), over plain HTTP; `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` and `OTEL_EXPORTER_OTLP_TRACES_PROTOCOL` change nothing, but the exporter still reads the headers (`OTEL_EXPORTER_OTLP_TRACES_HEADERS`, else `OTEL_EXPORTER_OTLP_HEADERS`) and the timeout (`OTEL_EXPORTER_OTLP_TRACES_TIMEOUT`, else `OTEL_EXPORTER_OTLP_TIMEOUT`), so a header that the host sets for another collector also goes to `ZOE_OTLP_ENDPOINT`. Each call is a span named after its method; a lock wait is a span `lock_wait` (with `oid`), the write and sync of a commit batch a span `fsync` (with `commits`) and each batch of a pack a span `pack_batch` (with `records`), each inside the span of the call that caused it, with the attribute `zoe.storage`. The traces take only the spans of the zoe crates, and no attribute holds pickle bytes, user or description. The server flushes its spans when it stops. The service name is `zoe`, unless `OTEL_SERVICE_NAME` gives one.

A client that negotiated the extension `trace_context` sends its W3C traceparent with each request, as the fifth element of the message: a msgpack map whose key `traceparent` holds it; the server ignores its other keys. The span of that call takes the trace id of the traceparent and the span of the client as its parent, so a slow Plone request and the server work it caused, the core included, appear in one trace. A call without a valid traceparent is the root of its trace. A fifth element on a connection that did not get `trace_context`, or that is not a map, closes that connection. With the default sampler, the server samples a call as the client sampled its trace. `zoe.zeo.ClientStorage` declares `trace_context` when the package `opentelemetry` is installed, and each call made inside a span carries its traceparent. The client exports no span of its own: the application configures OpenTelemetry.

### TLS

TLS uses rustls; ZEO's `ssl` client option works against it. `--tls-cert FILE` and `--tls-key FILE` (PEM, each needs the other) make the ZEO port speak TLS; the admin port stays plain HTTP. `--tls-client-ca FILE` requires a client certificate that chains to one of its CA certificates, as the `authenticate` key of ZEO's `<ssl>` section does; a client certificate that is byte for byte one of the certificates of that file is accepted too, also a CA certificate, within its validity period and with the proof of its key in the handshake, as OpenSSL accepts it for `authenticate`; no other CA certificate is accepted as a client certificate, and a certificate of `--tls-read-only-client-ca` never matches by its bytes. `--tls-read-only-client-ca FILE` also accepts the certificates of a second CA, whose holders can only register read-only, as on a read-only store, and get `ReadOnlyError` from `pack`, because a pack deletes data; a connection that registers read-only by its own choice still packs, as in ZEO. With either CA, a client certificate is necessary, and a certificate that chains to both CAs is read-write. This is how Loupe and the MCP server hold a read-write or a read-only certificate. Both CA options need `--tls-cert`. The handshake must end within the idle timeout, and a failed handshake closes only its connection. The server reads the files once, at its start, so a file that does not read fails the start with 1 and creates no store.

### Extension negotiation

A client declares the extensions that it wants as a third argument of `register`, a list of names: `register(storage_id, read_only, ["lock_intent"])`. The server accepts the names that it serves, once each, in order, and leaves out the others without an error; `get_info` gives the accepted names back under the key `extensions`. A third argument that is not a list of strings fails `register` with `TypeError`, and the connection stays open and unregistered. A declaration holds for its connection only. A stock ZEO client declares nothing, so its `get_info` has no `extensions` key, and it gets vote-time locking. A call of an extension that the connection did not declare fails with `ValueError`, and the connection stays open. The extensions are `sequences`, `lock_intent`, `kv`, `trace_context` and `server_writes`.

`server_writes` adds no method (ADR 0048, section B4): a connection that declares it promises that, when the reply of its `vote` lists an oid that its transaction did not store, the client ends the current entry of that oid in its cache and gives every Connection of its process one invalidation with every oid of the commit, before `lastTransaction()` gives the tid. Only then can the split merge write in its vote the new bucket of the other side (see "Conflict resolution dispatch"). The native mode of `zoe.zeo.ClientStorage` declares it, and takes the oids of its own commit from the invalidation of its listener; its asyncio mode and a stock client do not. `zoe.zeo.ClientStorage` declares `lock_intent`; the Plone-side piece is `zoe.zodb` (see "Lever 3: early write-intent locks (ADR 0044)").

### Sequences over the protocol (F29)

The extension `sequences` adds `sequence_next(name)`: the next value of the sequence `name` of the store, an int, with the rules of the in-process primitive. The values are unique and strictly increasing per store and per name, from 1, and consecutive within one open store across the connections. A restart of the server skips at most 100 values of a name. The call is outside the two-phase commit: it runs while a transaction is open, and an abort keeps its values. A name that is not a str fails with `TypeError`, and a read-only connection or store with `ReadOnlyError`.

### KV namespaces over the protocol (F31, ADR 0043)

The extension `kv` adds five calls. `flavour` is the str `"ephemeral"` or `"durable"`, `name` a str, and `key`, `start`, `stop` and `value` are bin. `kv_get(flavour, name, key)` gives the value or nil, `kv_scan(flavour, name, start, stop, limit)` gives `[[key, value], ...]` in key order from `start` (included) to `stop` (excluded), nil for an open end, at most `limit` and at most 1,000 pairs, and `kv_generation(name)` gives the generation of a durable namespace as 8 bytes. These three run on the read pool, outside the transaction of the connection. `kv_set(flavour, name, key, value, ttl)` and `kv_delete(flavour, name, key)` have no reply: they run in the lane of the open transaction of the connection, and an error fails the vote, as an error of `storea` does; without an open transaction, the call fails with `StorageTransactionError`, which closes the connection. `ttl` is an int or a float of seconds for `"ephemeral"`, and nil for `"durable"`. A read-only connection or store fails them at the vote with `ReadOnlyError`. A bad argument of a read fails it with `TypeError` or `ValueError`, and the connection stays open. A stock client sees no key, and sees a namespace-only commit as a transaction without records.

### `zoe.zeo.ClientStorage`

A Python subclass of `ZEO.ClientStorage.ClientStorage`, with the same arguments and `native`. By default the native client of F28 runs inside; with `native=False`, or `native false` in `<zoeclient>`, the asyncio client of ZEO runs inside, and so it does by default in a subclass, which can change its methods (`native=True` there raises `TypeError`). Each connection declares `sequences`, `kv` and `lock_intent` in `register`, and `trace_context` when `opentelemetry` is installed; a stock ZEO server refuses the third argument with `TypeError` and logs it, and the connection registers again with two. `sequence(name).next()` and the `kv_*` methods of `zoe.Storage` raise `Unsupported` when the server did not accept their extension.

`%import zoe` gives the ZConfig section `<zoeclient>`, which opens it: it takes every key of `<zeoclient>`, with the same values, `wait-timeout`, as ZEO's `<clientstorage>` has it, `native`, `early-locks` and `early-lock-classes` (ADR 0044, part B; `early-locks on` needs `native true`), and an `<ssl>` section with the keys of the `<ssl>` section of `<clientstorage>` (`certificate`, `key`, `password-function`, `authenticate`, `check-hostname`, `server-hostname`). ZEO's client gets the context that ZEO makes from that section; the native client reads its files. ZEO's component also declares a section type `ssl`, so a configuration cannot import `zoe` and `ZEO` together; it uses `<zoeclient>` with `native false` and `<ssl>` in place of `<clientstorage>`, which opens ZEO's client with the same TLS.

### The native client (F28)

`zoe.zeo.ClientStorage(...)`, the section `<zoeclient>`, and `zoe.testing.native_client(address, **kw)` run the client on `zoe-client`, inside the extension `zoe._zoe` (ADR 0001), and not on the asyncio client of ZEO. It is the default; `native=False` and `native false` keep the asyncio client of ZEO. The instance is still a `ZEO.ClientStorage.ClientStorage`, and no thread of ZEO's client starts. It serves the whole storage API of `ZEO.ClientStorage`. `crates/zoe-py/CLAUDE.md` and `crates/zoe-client/CLAUDE.md` hold the invariants of its parts.

#### The open, the addresses and TLS

An address is a `(host, port)` tuple or the path of a unix domain socket as a `str`, or a list of them. With several addresses, the client connects to all of them at once, keeps the first server that registers, a writable server before a read-only one with `read_only_fallback`, and closes the other connections. With `read_only_fallback`, the open keeps a read-only server only when every other address ended, so an address that never answers delays it until the end of `wait_timeout`; after the open, the client goes on trying a writable server (see "Reconnects"). The open registers with the declaration of its extensions, falls back to two arguments, and reads `get_info` and the last tid. The arguments of `ZEO.ClientStorage` whose feature is not built are the keys of `zoe.zeo._NOT_BUILT`, each with the value that leaves it off; another value fails the open with `Unsupported`, which names the argument, and the gate checks that the dict is empty. The arguments that ZEO 6 ignores are ignored, but `disconnect_poll`: the time between two attempts to connect again, 1 second by default.

The client builds its TLS in Rust on rustls, from the files of the `<ssl>` section of `<zoeclient>` and the argument `ssl_server_hostname`. It checks the chain of the server certificate against the CA certificates of `authenticate`, a PEM file or a directory whose every file it reads, else against the CA certificates of the system, as ZEO's `ssl.create_default_context()` does (`SSL_CERT_FILE` and `SSL_CERT_DIR`, else the default paths of OpenSSL), and, with `check-hostname` (true by default), that the certificate is valid for the server name (`server-hostname`, else the host of the address). A store of CA certificates without one fails the open with `ValueError`. The client sends the certificate of `certificate`, with its key from `key` or from the certificate file, and no certificate when the section has no `certificate`, as `ZEO.zconfig.ssl_config` does: the client then ignores `key` and `password-function`. A server certificate that is byte for byte one of the certificates of `authenticate` is valid without a chain, within its validity period, as OpenSSL accepts it; with `check-hostname` it must name the server by its subjectAltName, or by a common name when it has none. A failed check fails the connection, and the open raises `ClientDisconnected` at the end of `wait_timeout`; the client never falls back to a connection without TLS. An `ssl` context, which does not give back its files, fails the open with `Unsupported`, and so does `password-function` (an encrypted key) in a section with `certificate`. A v1 server certificate is refused.

The client speaks `M5` only, so a stock ZEO server needs `msgpack true`; there it declares nothing. The native client is a drop-in, never a requirement, so the default falls back: when the caller gives no `native` and the open with `wait` finds a server that speaks the pickle protocol `Z5`, the instance becomes a `zoe.zeo.ClientStorage` with the asyncio client of ZEO inside, opened with the same arguments, with a warning under the logger `zoe.zeo`. `native=True` asks for the native client: there, and at a reconnect, a server that answers with another protocol is a failed connection, as for ZEO: the client logs it under `ZEO.asyncio.client`, tries again after 9 seconds, and the open raises `ClientDisconnected` at the end of `wait_timeout`; for `Z5`, the text says that the server needs `msgpack true`, or the client `native=False`.

#### Several transactions at once (ADR 0036)

The open opens one connection, the listener, which never commits. Each transaction takes a free connection of a pool from `tpc_begin` to the end of `tpc_finish` or `tpc_abort`, opens one when it finds none free, up to 64 connections that commit (a constant), and waits for a free one beyond. Loads use any connection; `new_oid` and `sequence(name).next()` use the listener. The server sends the listener the invalidation of each commit of the other connections, the pool's own commits included, in tid order, as a stock ZEO 6 server does too, and one dispatcher delivers each tid of that stream in turn: a tid of another client goes to the DB as `invalidate(tid, oids)`, once; a tid of the pool goes to no DB invalidation: its `tpc_finish` returns at that place and runs its callback `f(tid)` before the dispatcher goes on.

`lastTransaction()` is the last tid that the dispatcher delivered; a call from another thread waits for the delivery that runs, so it gives a tid only after the DB got its invalidations or `f(tid)` ran. While a finish waits for its reply, the dispatcher holds a tid that it does not know, until each finish that was in flight when the tid came has its reply or failed; a finish that fails leaves the hold, so the dispatcher then delivers its tid, if the server committed it, as a tid of another client. A lost or lagged listener is a lost connection: the DB gets `invalidateCache()`, a new transaction fails with `ClientDisconnected`, a finish that had its reply runs `f(tid)` after `invalidateCache()`, a finish without its reply fails, and the client connects again (see "Reconnects"). Each load reply carries the position of its connection, the last tid that the connection read from its own stream, for the client cache.

The calls wait without the GIL. The tokio runtime of the native clients has 2 worker threads for the process, and starts when the first client opens. A client opened before `os.fork()` raises `RuntimeError` in the child at its next call. `zoe.testing.NATIVE_LAYER` runs ZEO's tests and ZODB's mixins on the native client. The client logs as ZEO's client does, under the loggers `ZEO.ClientStorage` and `ZEO.asyncio.client`, with the words of ZEO.

#### The client cache (ADR 0034, stages 1 and 2)

The pool holds one cache, in an anonymous mapping of the process or in a cache file, in the layout of ADR 0034: a header page, an index of slots with linear probes, and a ring of entries, each with its position, oid, start and end tids, the position of the older entry of its oid, its lengths, its codec and two checksums, of its data and of its head. `cache_size` (`cache-size` of `<zoeclient>`, 20 MB by default, as for ZEO) is the size of the ring; 0 turns the cache off. The semantics are those of `ZEO.cache.ClientCache`: an entry is one revision of an oid, with its start tid and its end tid, and a current entry has no end. `loadBefore(oid, before)` hits an entry with `start < before` and either `end ≥ before` or no end: a current entry serves any `before`, because the pool applies each tid to the cache before it delivers it. After a commit of the pool that a stale turn delivered without the cache, a current entry serves only `before ≤ applied + 1` until `applied`, the tid up to which the cache applied the commits, reaches that tid; `load(oid)` hits the current entry whatever `applied` is.

A hit takes no lock and sends nothing: it reads `applied`, the slot and the entry, copies the entry, checks both checksums and checks that the head of the ring stayed within one ring of the entry; a doubt is a miss. The writers take one mutex of the process. The ring is FIFO; an entry larger than half of the ring is never cached; a hit of a current entry in the oldest fifth of the ring copies it to the head when the writer mutex is free. The dispatcher applies each tid to the cache before the DB gets it: a tid of another client ends the current entry of each of its oids; a commit of the client ends the entries of its oids and adds a current entry with the committed data, the pickle that the client resolved included, except for an oid that the server resolved; an oid that the client wrote and that the invalidation does not list, as the node and the new bucket that the split merge resolves without a record, loses its current entry. A load reply with an end always goes in; a current reply goes in only when `applied` is not above the position of the connection that carried it (ADR 0036), so a reply that arrived before a commit is refused after the cache applied that commit (the race of ZEO issue 166). A `ConflictError` or a `ReadConflictError` of a vote drops the current entry of its oid, as ZEO does. `_cache.clear()` drops every entry and keeps `applied`. The entries are raw (ADR 0034).

#### The cache file (ADR 0034, stage 2)

With `client` (the key `client` of `<zoeclient>`), the cache is the file `<client>-<storage>.zoec` in `var` (the current directory by default), so the native client never touches the `.zec` file of a stock client; a `str` as `cache` is the path of ZEO's file, whose `.zec` becomes `.zoec` (a path without either extension gets `.zoec`), and a cache object raises `Unsupported`. The open raises `ValueError` on a file that is not a cache file of ZOE, and changes nothing. The file is mapped in memory, shared, with its disk space reserved and its length fixed while it is open. The header names the version of the layout, the storage, the size and `applied`, with the boot id of the kernel, a clean flag and a checksum. The open takes an exclusive `flock` of the file without a wait: a second open of the file raises `zc.lockfile.LockError`, as ZEO's cache does; several processes on one file are F38.

The open keeps the entries of a file of the same version, storage and size, with a good header, when its last close was clean or when no restart of the kernel came since it was open; else it drops every entry. A kept file serves nothing until its verification against the server, as at a reconnect (see "Reconnects"), with one more check: below the last tid of the server, the server must hold a commit at exactly `applied`, else its history is another one and every entry goes. A file ahead of the server is dropped, where ZEO refuses the server; a failed `getInvalidations` drops the file, where ZEO tries again; and the verification ends before the open returns only with `wait`. `applied` moves only after the entries of its tid ended. The file is marked not clean on disk before the first write to the mapping, so an open that writes nothing pays no sync. The close of a marked file writes the mapping to the disk, then marks the file clean, then frees the lock. The file holds only what the server gave or confirmed, so dropping it is always correct.

#### Conflict resolution

`tpc_vote` resolves in the client the conflicts that the vote reply lists, as `tpc_vote` of `ZEO.ClientStorage` does (F5): for each map `{oid, serials: [committed, read], data}`, it runs `tryToResolveConflict(oid, committed, read, data)` on the thread of the transaction, with no lock of the client held, sends the result with `storea` over the committed serial and votes again, for at most nine rounds; after the ninth it raises `ConflictError`, where ZEO goes on to the finish. `tpc_vote` returns the oids that the server or the client resolved, so the DB loads them again. The client cache keeps the pickle that the client resolved, and never the pickle of an oid that the server resolved. A conflict that does not resolve raises the `ConflictError` of `tryToResolveConflict`, and another error of the resolver raises unchanged; either error drops the current cache entry of the oid and leaves the transaction open for the `tpc_abort` of ZODB. A conflict that the server does not list fails the vote with `ConflictError` or `ReadConflictError`.

#### Reconnects

With `wait` (true by default), the open waits at most `wait_timeout` seconds for a server; without it, the client connects in the background. When the client loses its listener, the DB gets `invalidateCache()` and the client closes every connection of the pool: a transaction that began before the loss fails at its next step with `ClientDisconnected`, never commits on a later connection, and leaves no lock on the server. While the client has no listener, a call that needs the server waits for one at most `wait_timeout` seconds, or the `timeout` of `_call`, then raises `ClientDisconnected`; a hit of the cache answers at once. The dispatcher opens a new listener at once, then every `disconnect_poll` seconds, each attempt one round over the addresses as at the open.

Before the client takes the new server, it verifies its cache as `verify` of ZEO's client does, once for each reconnect. The base is `applied` of the cache, or `lastTransaction()` without a cache. A server whose last tid is the base keeps the cache. A last tid below the base, or below `lastTransaction()`, refuses the server, which the client logs as critical, and it tries again after 9 seconds. A higher last tid asks `getInvalidations(base)`: the cache drops the current entry of each oid of the reply, `applied` moves to the tid of the reply, and the DB gets `invalidate(tid, oids)` before `lastTransaction()` moves to that tid, also when that tid is `lastTransaction()` itself; the invalidations of the new listener at or below that tid are skipped. When the server answers `None`, the client notifies ZEO's `StaleCache` event, the cache drops every entry, the DB gets `invalidateCache()`, and `lastTransaction()` moves to the last tid of the server. After a read-only fallback, the client tries a writable server every `disconnect_poll` seconds and moves to the first one that registers. `min_disconnect_poll`, `max_disconnect_poll` and `drop_cache_rather_verify` change nothing, as for ZEO 6. The departures from ZEO: the DB gets `invalidateCache()` at the loss, where ZEO calls it at each connection; an empty cache verifies through `getInvalidations` as a full one does; and `disconnect_poll` sets the time between two attempts.

#### Blobs

The native client has the two modes of `ZEO.ClientStorage`, with its code for the blob directory, and declares `IBlobStorage` when `get_info` lists it. With `blob_dir` and without `shared_blob_dir`, `blob_dir` is a blob cache in ZEO's layout `zeocache`, so a cache directory works with either client. `loadBlob` returns the file of the cache, and downloads it first when it is missing, under the file lock of the directory of the blob, so the threads and processes of a machine download a blob once, on a connection of the pool other than the listener when one is open. The file gets its name, read-only, only after the reply and when it holds every byte that came, so a reader never opens a partial file. `storeBlob` takes the file into the directory of its oid in the cache and uploads it from there in chunks of 59,000 bytes; `tpc_finish` gives the file its name under the new tid, and `tpc_abort` removes it. `blob_cache_size` and `blob_cache_size_check` prune the cache as ZEO does. With `shared_blob_dir`, the client and the server share `blob_dir`: `storeBlob` puts the file in the directory of its oid there and sends `storeBlobShared` with its name; `loadBlob` returns the file at its BushyLayout path, or raises `POSKeyError`.

#### The rest of the storage API

The other calls of `ZEO.ClientStorage` go through its `_call` and `_async`, which the native client sends on the listener, as on the one connection of ZEO; so `iterator`, `history`, `record_iternext`, `pack`, `undoInfo`, `undoLog`, `server_status`, `getName`, `sortKey`, `supportsUndo` and `copyTransactionsFrom` are the methods of `ZEO.ClientStorage`. A reply converts and an error reply raises as in ZEO. `_call` or `_async` of a call of a transaction raises `StorageTransactionError`; `_call(..., wait=False)` returns a `concurrent.futures.Future`, as ZEO's does. An iterator lives on the listener and is released with `iterator_gc` at the next `tpc_finish` or `tpc_abort` after its drop; the loss of the listener forgets every iterator, and an id of a lost listener raises the `KeyError` of an unknown iterator. `undo` sends `undoa` on the connection of its transaction.

`deleteObject` and `restore` go on the connection of their transaction; at the commit, the cache ends the current entry of each of their oids and adds nothing (where `restore` of ZEO leaves its cache as it is), and so it does for an oid that the vote lists as resolved by the server without a store, as the oids of an undo. `prefetch(oids, tid)` sends one `loadBefore` for each oid that the cache does not hold for `tid`, on the connections of the pool in turn, and returns before the replies, which go into the cache with the position of their connection; without a cache it sends nothing. `sync()` does nothing unless `server_sync` is true: then it pings the listener and returns when the DB got each commit that the listener read before the reply. `client_label` goes in `set_client_label` on each connection of the pool. `new_addr(addr)` gives the addresses of the next attempt to connect. `len()` and `getSize()` read the `length` and `size` of the last `info` call that the server sent, else of `get_info`, as ZEO does.

### `zoe.plone` and the sequences (F29)

In Plone 6.1, one shared counter gives ids to new content: `portal_uidgenerator`, the `UniqueIdGeneratorTool` of Products.CMFUid, whose `__call__` adds 1 to the int `_uid_counter` of the tool. CMFEditions calls it through `portal_historyidhandler` for the history id of each object that it versions, and plone.app.versioningbehavior versions each new Document, Event, Link and News Item. So two editors who create content at the same time write the tool, and one of them gets a `ConflictError`. When the storage of the tool is `zoe.Storage` or `zoe.zeo.ClientStorage` and gives sequences, `zoe.plone` gives the tool its ids from a sequence of the store and never writes the tool in the transaction that asks for the id; the ids stay unique and above the ids that the stock counter gave. Otherwise the tool works as stock. The ZCTextIndex lexicon, the intid utility, the catalog and `BTreeFolder2.generateId` take new ids from a volatile counter with a random start, and the `Length` objects of Plone 6.1 are counts or change counters, so `zoe.plone` leaves them alone.

Plone loads `zoe.plone` through the plone.autoinclude entry point of zoedb, in every instance that has zoedb, with the extra or without; on `IDatabaseOpenedWithRoot`, it replaces `UniqueIdGeneratorTool.__call__`. The test layers of plone.testing do not send that event, so the Plone suites run without the wiring. Each tool has its own sequence, named `zoe.plone.portal_uidgenerator:` and the oid of the tool in hex, so two sites in one root do not share one. The id is `base + value`, where `value` comes from that sequence. The tool keeps the range of the wiring in its attribute `_zoe_ids`, a tuple `(base, floor, mark, end)`: `floor` is the first id of the range, `mark` the largest value that a reservation of the range took, `end` the last id. An id is valid when `value > mark`, `floor < base + value <= end` and `_uid_counter` equals `end`. So `_uid_counter` is always the end of the ids that the wiring reserved, and the stock counter never gives an id that the wiring gave, also after zoe.plone is removed or the site moves to another storage.

When an id is not valid, a reservation reads the tool on a connection of its own and writes it in a transaction of its own, with the note `zoe.plone: reserve ids of portal_uidgenerator`. Within a range, a reservation raises `end` and `_uid_counter` to the id plus 99, and `mark` to the value, so the tool gets one write for each 100 ids. In one store, the value of a caller is always above the `mark` that its snapshot shows. A value at or below it therefore comes from another store, whose sequences start again at 1: a copy through `iterator` and `restore`, which does not copy the sequences, or a zexp import, which gives the tool a new oid. A reservation starts a new range at `max(_uid_counter, end) + 1` for the first id of a site, for such a value, and when `_uid_counter` is not `end`; a new range takes 100 more values of the sequence and makes the last one its `mark`, which is so at least 101. So in one store, the ids of a site are unique and above every id that the stock counter gave; after a copy into a new store, the copy is detected and gives no id again, unless more than `mark` values of the sequence are taken there before the first reservation commits. A copy into a store that already gave values of that sequence is not detected. The reservations of one process wait for each other; two processes that reserve at the same time conflict on the tool, and the reservation reads the tool again and retries, at most 100 times. A new range costs at least 100 ids and 100 calls of `sequence_next`. A storage without sequences, a tool that is new or changed in the transaction of the caller, and a storage that wraps a ZOE storage keep the stock counter.

### `zoe.plone` and queued indexing (ADR 0047)

The indexing queue of Products.CMFCore gives the catalog operations of a transaction (index, reindex with its indexes, unindex), before the commit and before each search, to each `IIndexQueueProcessor` utility; the utility `portal-catalog` writes the catalog in the transaction of the save. So a save writes many objects of the catalog (`docs/spikes/queued-indexing.md`), and two saves of different objects conflict on its buckets. The opt-in backend `indexing` of `zoe.plone` (`zoe.plone:indexing.zcml`, or `indexing` in `ZOE_PLONE_BACKENDS`) changes that:

- `zoe.plone.indexing.install()` registers its queue processor as the global utility `portal-catalog` and keeps the stock one; `uninstall()` gives the stock one back, and `installed()` tells. When the storage of the catalog has KV namespaces, the processor writes, in the transaction of the save, one key for each operation in the durable namespace `zoe.plone.indexing:` followed by the oid of the catalog in 16 hex digits, and writes no object of the catalog. The key is 20 bytes: the time in microseconds, 8 random bytes of the processing of the queue, and the number of the operation; the value is JSON with the operation, the path (the old path for the unindex of a move), the indexes and the metadata flag. A storage without namespaces keeps the stock processor, with one WARN event for each process and storage.
- `zoe.plone.indexing.Indexer(site, batch_size=100)` applies the queue on a connection of its own, under the system user. Each batch scans at most `batch_size` keys, reads the generation of the namespace and waits, at most 10 s, until its storage saw that tid. It coalesces the operations of each path, adds the paths below a path whose operation reindexes only `allowedRolesAndUsers`, resolves each path against its snapshot without acquisition, applies the removals first (a path without an object, a path whose object has another UID, and a path that the UID index holds for the UID of an object of the batch and that no longer holds that object), then indexes or reindexes the other paths with the calls of the stock processor, deletes the keys of the batch, and commits, with the note `zoe.plone: indexing queue`. `run()` applies batches until the queue is empty and calls `after_batch(indexer, keys)` after each commit. A `TransientError` gives the batch 5 tries, then `run()` raises it; another error on one path, a read error of the store included, counts a failure in its keys, and a key with 5 failures moves to the durable namespace `zoe.plone.indexing.failed:` followed by the oid, with an ERROR event; so does a value that is not an operation. Only a missing path (`KeyError` but not `POSKeyError`, `AttributeError`, `NotFound`) makes a path one without an object. A failed search of a subtree is a failure of the path that reindexes its security. A path without keys whose application fails (a stale path of the UID index, a path of a security subtree) logs an ERROR event, and the run skips it. Each path resolves against the newest state, so the catalog converges to a reindex from scratch in any order of the batches, and the keys go in the transaction that applies them, so a crash between two batches loses no operation and applies none twice.
- When the backend is installed, each Zope process starts at `IDatabaseOpenedWithRoot` a daemon thread for each of its databases with KV namespaces, the root database and each mounted database (a database that joins later gets its thread at its first key). The thread of a database runs the indexer of each site whose catalog is in that database while it holds the lease of the site: a key of the ephemeral namespace `zoe.plone.indexing.lease` in that database, with a TTL of 30 s, which each batch writes again and the exit of the process deletes. Each thread finds the sites of its own database, at its start and every minute, at the top of the Zope root or at and just below each mount point of its database, so the thread of a mounted ZOE store under a root without namespaces still finds its sites and applies the keys that a restart left (ADR 0047). The thread and the indexer of a mounted site open a connection on the root database and find the site through the mount point; the catalog, the queue and its keys are in the mounted store, so a batch commits them in one transaction of that store. A commit that wrote keys wakes the thread of each database that it wrote to; each thread also scans its queues every 0.2 s. A run stops at a batch when the lease holds the token of another thread. After a failure of the queue of a site, the thread waits before it serves that site again, from 0.4 s doubled up to 30 s, and the other sites of the thread stay served. `Indexer.run()` alone takes no lease, and the test layers of plone.testing start no thread.
- The window from a save to its batch is the wake and the batch: meanwhile the navigation, the folder views, the collections, the searches and `uuidToObject` show the site before the save, and a page that reads the object itself shows the save. A request that queued operations sets the session cookie `zoe.indexing` (the oid of the catalog, its last key, the name of its database and the path of the site; `HttpOnly`, `SameSite=Lax`). A later request with it waits at `PubStart`, at most 2 s, until the queue holds no key at or below that key and the storage saw the generation, then begins its transaction again and marks it again for the writes-on-GET report, and expires the cookie, also after a wait that ran out, with a WARN event. A cookie that does not parse, or whose key is more than 60 s in the future, is expired at once. Searches in the transaction of a save do not see its own operations; direct calls of the catalog API (`catalog_object`, `uncatalog_object`, `clearFindAndRebuild`, upgrade steps) still write the catalog in their own transaction.
- `@@zoe-indexing` on a site, for `Manage portal`, gives JSON: the keys in the queue, the age of the oldest, the failed keys, whether a thread holds the lease, and the count, p50, p95 and maximum of the delays of the keys that the indexers of the process applied, since a time that the form value `since` gives.
- The way back: run the indexer until the queues are empty, then remove the backend from every instance. A copy through the ZODB iterator or `zoe convert` to a `Data.fs` leaves the queue out, so the catalog of the copy needs a rebuild unless the queue was empty; `zoe backup` and `zoe restore` keep it. An undo of a save gives back no catalog write and no key: reindex the objects after it. plone.protect does not see the keys; a save writes its content object, which it checks as before.

### `zoe.plone` and the registry (F31, ADR 0043)

`portal_registry` keeps its records in two `OOBTree`s, `_fields` and `_values`, in the `_records` of the registry; each field is a record of its own. The registry backend (ADR 0043, part B) moves them, on an explicit step, to a durable namespace of their own, so a write of the registry writes a small registry object and the rows that change, and a request reads the records from a cache of the process.

- `zoe.plone.registry.install()`, through `ZOE_PLONE_BACKENDS=registry` or `zoe.plone:registry.zcml`, lets `move`, `copy_rows` and `reset` run; `uninstall()` stops them and drops the cache; `installed()` tells. A moved registry reads and writes in every process that has zoedb, with or without the option. Each one changes the current transaction of the connection of its registry; the caller commits.
- `move(registry)` draws an id of 16 random bytes and writes the namespace `zoe.plone.registry:` followed by the id in 32 hex digits: a row `f` followed by the name of each record (the pickle of its field), a row `v` followed by the name (the pickle of its value), and the marker `m` (the version 1 of the layout, the oid of the registry, the write counter, 8 bytes big-endian). The registry then holds a `zoe.plone.registry.MovedRecords`: the id, the counter, and views of the rows with the methods of an `OOBTree` that plone.registry calls. Its trees stay in the store until a garbage-collecting pack. A storage without namespaces raises `Unsupported`. The pickles are protocol 3, by value; a persistent object that is not a field of plone.registry is refused, and a broken field is kept.
- A read checks the rows once in each transaction. A registry in no database or in a storage without namespaces, a namespace without a marker, a marker of another oid, and a marker whose counter is below the counter of the registry raise `Unsupported`: the registry is a copy without its rows (the ZODB iterator, zodbconvert, `zoe convert`, a zexp, an OFS copy). When the store holds a newer serial of the registry, a move back committed after the snapshot, and the read raises `ReadConflictError`. Then a read takes the writes of the transaction, then the rows of a cache of the process: the rows of each namespace as bytes, labelled with the counter of their marker, filled by a scan that reads the generation before and after it, at most 16 namespaces for each storage, a fixed limit. The rows are never older than the snapshot of the registry, but they can be newer. A transaction decodes a row once; a rollback to a savepoint drops the decoded rows. A view finds the ends of a key range with a bisect of the sorted names.
- The first write of a transaction sets the counter of the registry and of the marker to 1 more than the highest of the counter of the registry, the counter of the staged marker and the counter of the stored marker, so a counter never repeats after an undo, and it writes the registry object: plone.protect sees the write, and two writes of one registry conflict and retry. A field changed in place is staged again before the commit and before each savepoint: the transaction keeps the bytes of the row of each field that it decoded and pickles the field once, at the check; a pickle equal to the bytes, or to a new pickle of the decoded bytes, is no change, so a read never writes a row. A rollback to a savepoint can keep the staged rows and give back the old counter, so before the commit a registry with staged rows whose counter the transaction did not raise, and whose staged marker holds another counter, gets its counter raised the same way; a move stages a marker with the counter of the registry, 1.
- The guard: in every instance where `zoe.plone` loads, a stock registry in a store with namespaces calls `readCurrent` on the roots of its two trees when code reads its records, and the move empties those roots, so a write that began before a move conflicts at its vote, also with the split merge on; a write of an attribute of the registry object does not. For a root that keeps its keys in its own state (an empty tree, or a tree of one bucket), which the move leaves as it is, the guard also calls `readCurrent` on the registry object, which the move writes. The guard returns at once when it checked the same roots in the current transaction, they are still read current and unchanged, and the registry object is still read current or changed, if the check read it; a rollback past a savepoint that stored a root or the registry object makes it check again. The guard marks only the roots and writes no key, and the move stores each root that it empties, so the argument of the split merge holds (ADR 0048; ADR 0043, section B1).
- `move_back(registry)` puts the records back into new `OOBTree`s and deletes the rows. `copy_rows(source, copy)` gives a copy of a moved registry that fails the check, with the id of its source, the rows of the source under a new id, and deletes stale rows of the copy itself. `reset(registry)` gives a copy whose source is gone empty `OOBTree`s; the import of the step `plone.app.registry` of each profile of the site then gives back the records with their default values. On a ZEO client without namespaces, also under a wrapper that keeps its storage in `base`, `storage` or `_storage`, `reset` raises `Unsupported` and changes nothing, because the client cannot tell a live `zoe serve`, whose rows are intact, from a ZEO server of a FileStorage; the message says to stop the ZEO server and open the storage directly.
- The way back: `move_back(site.portal_registry)` and a commit, for example in a script of `bin/instance run`, then remove the option; nothing is lost. Move the registry back before leaving ZOE (`zoe convert`, which refuses a store with a moved registry unless `--force`; zodbconvert; a zexp into another database), before a downgrade of zoedb, before an OFS copy of the site, and before the delete of the site. `zoe backup` and `zoe restore` keep the rows. Pack never reads them. An undo gives back no row: the undo of a write of a moved registry changes no record; never undo a move back, nor the undo of a move.

## Async and free-threading

Async lives in the server and in the client's ability to overlap I/O; the persistent-object model stays synchronous because a ghost loads inside `__getattribute__`, where nothing can await. Free-threading is what makes one Zope process commit in parallel.

### What is asynchronous

| Layer | Today | In this design |
| --- | --- | --- |
| ZEO client | asyncio loop on a helper thread, synchronous facade to ZODB | unchanged for `ZEO.ClientStorage` and for `zoe.zeo.ClientStorage` with `native=False`; the native client of F28: `zoe-client` on a tokio runtime of 2 threads inside the extension, a synchronous facade whose calls wait without the GIL, and several transactions at once on a pool of connections (ADR 0036); the dispatcher and the pool take no lock that a load waits for, beyond the short pick of a connection, and a hit of the client cache runs on the calling thread and takes no lock |
| ZEO server | asyncio in Python, one loop, GIL-bound | tokio, work-stealing runtime, blocking pool for storage calls, no GIL on the request path |
| Request pipelining | message ids, concurrent calls | handled concurrently; replies out of order; `prefetch` becomes a real batch |
| Storage core | — | synchronous by design; async wrappers around it, never inside |
| Object loading in Zope | synchronous on attribute access | unchanged |

### Async storage interface for new clients

The server exposes the same methods as `async fn` in a Rust client crate (`zoe-client`) and, through PyO3, as awaitables (`await storage.aload_before(oid, tid)`, `await storage.aprefetch(oids)`, `await tm.acommit()`). This is what an async web layer such as collective.starlette uses for things that are not Plone page requests: streaming, WebSocket handlers, background jobs. A Plone request itself keeps running on a worker thread with a synchronous Connection.

`zoe-client` speaks the ZEO 6 msgpack protocol as `ZEO.ClientStorage` does: it registers, declares its extensions and falls back to two arguments for a stock server, loads, runs one transaction at a time, gets the invalidations of the other clients, and sends the heartbeat of a stock client every 60 seconds. Each reply goes to its call by its message id, in any order. It resolves no conflict: a conflict that the vote lists is an error of the call. A single client does not reconnect; the pool of the native client does. It reaches the network, its tasks and the time only through a `Runtime` trait, so the simulator of N18 runs it (`crates/zoe-client/CLAUDE.md`).

### Prefetch-then-touch

The one pattern that lets async code use persistent objects safely: `await conn.aprefetch(oids)` warms the cache, then synchronous traversal hits only the cache. The server supports it with batch loads; the ZEO client already issues `prefetch` as concurrent calls.

### Transaction managers

Async code uses an explicit `TransactionManager` per task (`db.open(transaction_manager=tm)`), never the thread-local default. `zoe.asyncio.transaction()` is a small context manager that does this and runs commit on the pool.

### Free-threading in one process

- The extension declares `Py_mod_gil_not_used`; on 3.14t the GIL stays off when `zoe` loads.
- The core is `Send + Sync`; the lock manager, group commit, the pack state and the sequence counters are its only shared mutable state, behind mutexes sized for disk latency.
- Two worker threads in `tpc_finish` at once hold their per-OID locks, join one commit batch and share one fsync, where `FileStorage` takes one storage-wide commit lock. With the GIL off, two threads can also resolve conflicts at the same time.

### Thread-safety invariants the core enforces

1. The thread that calls `tpc_begin` drives the transaction: the core records the thread id and refuses `store`, `restore` (and `storeBlob`), `checkCurrentSerialInTransaction` and `vote` from another thread with `WrongThread`, which turns a class of silent corruption into an exception. A refused call changes nothing. `tpc_finish` and `tpc_abort` may come from any thread, as ZODB lets them.
2. Locks are acquired in oid order; a request out of order is refused, never granted.
3. A backend write transaction is opened only by the commit-batch leader, a pack batch, a sequence reservation and a restore of a sequence end. The leader and a pack batch open it under the commit sequencer; a sequence reservation and a restore of a sequence end open it outside the sequencer and write only the row of their sequence. Readers use snapshots and never block them.
4. Every shared structure is covered by a ThreadSanitizer CI job and by `loom`-style interleaving tests on the lock manager.

### What stays on persistent and BTrees

With `zoe` loaded but `persistent`, `BTrees` and `zodbpickle` undeclared, CPython re-enables the GIL at import and the parallel-commit benefit disappears, so those packages need `Py_mod_gil_not_used` and a thread-safety audit upstream. On 3.14t the `persistent` fork takes the critical section of the pickle cache on each change of its LRU ring, because a sweep from another thread otherwise corrupts the ring, at about 6 ns per attribute access on 3.14t and nothing on the GIL builds. A sweep from another thread of a Connection in use stays unsupported. With the stock `persistent` on 3.14t, a multi-thread stress of ZODB's `test_race_loadopen_vs_local_invalidate` fails on every storage measured, so ZOE's tests skip it on free-threaded builds until the fork is in use. A Rust port of `persistent` and `BTrees` is a separate project; it would share the native merge code of the core.

## ConflictError strategy

ConflictError is optimistic concurrency at pickle granularity: two transactions write the same object and the second to vote loses. A storage cannot abolish that; it can resolve more conflicts, shrink the window, or serialise writers on the hot object so they wait instead of failing. The design does all three, in that order of cost.

### Step 0: measure before building

Zope logs the oid and class on every ConflictError it retries or raises. The conflicts of the Plone end-to-end benchmark (B5) and of the log replay (B6), ranked by class and by oid, decide which merges go native first. Both run on a synthetic site: the repository and CI hold no production data. B5 ranks first the posting dicts in the `_wordinfo` buckets of ZCTextIndex, then the shared `BTrees.Length` counters that every save writes (`docs/findings/plone-end-to-end.md`).

### Lever 1: resolve in Rust, never in Python on the server

A ZEO server resolves a conflict in Python, with every Plone egg installed. The tiers of "Conflict resolution dispatch" replace that, so two editors who change different fields of one item no longer conflict; the policy is strict by default, and loosened per class only after shadow mode has shown that the merge would have been right.

The posting dicts of ZCTextIndex (ADR 0042, `docs/spikes/posting-dicts.md`): ZCTextIndex keeps the postings of a word that 10 documents or fewer hold as a dict of document id to score, a value of the IOBTree `_wordinfo`, and ZODB's resolver refuses every bucket in which it must compare two dicts. With `posting-dicts on`, tier 1 compares posting dicts entry by entry and merges two changes of one dict against the old dict. It refuses an entry that both sides changed differently, or that one side changed and the other deleted, a dict against a tree, a dict of more than 10 entries on one side, and a merged dict of more than 10 entries or of none. A word that both sides add or that one side deletes stays a refusal of BTrees, so the `Length` of the words of an index stays exact. A word of more than 10 documents keeps its postings in an `IIBTree` of its own, which mostly holds its one bucket inline, and BTrees refuses the delete of the first key of a bucket (reason 13). The first-key rule, under the same key, lets that delete through when the committed transaction made it in the bucket that the tree holds inline and that bucket has no next bucket; a delete by the new transaction stays a refusal. ADR 0042 gives the reasons.

### Lever 2: shrink the window

Faster votes and finishes shorten the time in which a second writer can read a serial that is about to be stale: fewer conflicts, not none.

### Lever 3: early write-intent locks (ADR 0044)

This is the one mechanism that avoids conflicts on an object that cannot merge. The lock comes before the read: an object of a hot class takes its intent lock when its state loads, so a second writer waits before it reads, then reads the commit of the first one, and its vote has no conflict. The wasted work of the retries becomes one wait. ADR 0044, section B1, says why a lock at the first change of the object is not enough.

On the Plone side, `early-locks on` and `early-lock-classes` in `<zoe>` or `<zoeclient>` name the hot classes, by the `module.name` that ZODB pickles. The storage then puts the methods of `zoe.zodb.LockingConnection` on the `Connection` of ZODB, once per process; each patched method does what the replaced method does for a storage without hot classes and for a historical connection, which takes no lock. `setstate` of an object of a hot class calls `lock_intent([oid])` with the owner of the connection, waits for the grant, and loads the record of the serial that the grant returned, past the snapshot of the transaction, or the savepoint of the transaction that holds a change of the oid. At the end of each transaction, and at the close of a connection that no transaction joined, the connection turns the hot objects of its cache into ghosts, so the next access loads them again with the lock. `tpc_begin` binds the owner of the connection to its thread, so the transaction adopts the locks of the connection; its end releases them, also when it did not commit.

A load of a hot object below a hot object that the transaction holds gets `LockOrder`; the connection then releases its intent locks and takes them again with the new oid in one `lock_intent`, in oid order, goes on when the serial of each hot object that it read is unchanged, and raises `ConflictError` otherwise. The transaction manager keeps the hot oids of that attempt as a retry hint: the first load of a hot object in the next transaction takes them all with its own oid in one `lock_intent`, so a retry of Zope on another connection does not fail the same way; the next transaction uses the hint or drops it at its end. There is no batch: a load waits for its own lock. A class of tier 1 is never hot: tier 1 and the lock hand-off serve it. A read-only storage or client has no hot class. A client whose server did not accept `lock_intent`, as a stock ZEO 6 server, takes no early lock and logs one WARN event at each connection, and so does a `<zoeclient>` that runs the client of ZEO inside because its server does not speak M5. `<zoeclient>` with `native false` refuses `early-locks on` with `ValueError`: the client of ZEO has one session and one commit lock for every thread.

Costs and controls:

- A transaction sees a hot object at a state newer than its snapshot: a read skew against the other objects. A hot class is one whose invariants do not span other objects (a counter, a queue head, a lock record).
- Every transaction that reads a hot object waits for its lock, also one that does not write it. A hot class is one that its readers nearly always write.
- A hot class must be a leaf record, whose state refers to no other persistent object: a hot object read past the snapshot can name a child that the snapshot does not hold, or holds at an older state, and the load of that child can raise `ReadConflictError`.
- Long transactions hold locks longer: `lock-timeout` (default 10 s) turns a wait into a `ConflictError`, which Zope retries as today. Through `zoe serve`, a session that holds intent locks 60 s without a `tpc_begin` loses them.
- Deadlocks are prevented by oid ordering; a request out of order is refused, and the connection asks again for the full set in order.
- `readCurrent` takes its shared lock at the vote, as without early locks.
- Under a free-threaded Zope with many worker threads, a waiting thread costs nothing; under a four-thread instance a hot object can stall all four, so early locks stay off by default.

### Lever 4: structural, in Plone

Counters as `Length`, queued indexing, shorter transactions in batch jobs, splitting hot BTrees by key range. Most of these stay application work; the metrics tell where. Queued indexing is the opt-in backend `indexing` of `zoe.plone` (ADR 0047, see "`zoe.plone` and queued indexing"): a save writes its catalog operations to a durable namespace, one key each, instead of the 85 objects of the catalog that an edit of the B5 fixture writes (163 for a creation), and one indexer for each site applies them in transactions of its own. The page after a save waits for its indexing, so the median latency of an operation rises while its p95 falls.

The evidence, on the small fixture of B5, three repetitions of each stack in turn on one machine:

- With queued indexing (`zoe-native-qi`), `edit` at 4 and 16 users had 100 % first-attempt successes and no conflict, against 80 to 85 % and 280 to 290 conflicts per 1,000 operations on `zeo`; the indexer applied each key within 0.53 s of its save. What `create-spread` still conflicted on were the splits of shared trees (`docs/spikes/concurrent-creations.md`), which the split merge targets.
- The gate of phase 4, with the split merge on: `zoe-native-qi` raised 0 %, 0 %, 2.7 % and 3.0 % of the `ConflictError`s per 1,000 operations of `zeo` in `edit` and `create-spread` at 4 and 16 users, each under 10 %.
- B6, on the logs of two B5 runs of `edit` replayed at 1×, 4× and 16× with the posting-dict rule on: the log of `zoe-native-qi` raised 9 `ConflictError`s at each speed on both stacks (6.7 per 1,000), on buckets and on the locks of plone.locking; the log of `zoe-native-qi-kv` (queued indexing, the locking backend and `PrincipalProperties`, ADR 0046, section 9) raised 0 at each speed.

### What remains

Two transactions that write the same object that cannot merge, with early locks off, still conflict, which is correct: the alternative is lost updates. The success criterion comes from levers 1 and 3 together.

## Catalog acceleration and search

The Plone catalog is where write amplification, ConflictErrors, cold starts and memory meet, so ZOE treats it in three steps: the storage-level relief already specified (native merges, early locks, a shared hot cache); `zoe-catalog`, a mirror of ZCatalog's indexes in memory that answers queries in Rust behind the unchanged ZCatalog API, with a native BM25 text index on tantivy; and a projection that replaces bucket writes with commutative deltas. The fallback is the correctness guarantee: anything the mirror does not cover takes the path Plone has always taken.

### Where the catalog hurts today

One content change reindexes 20 to 40 indexes, which makes most of the pickle volume and most of the ConflictErrors of a Plone site. Each query loads bucket pickles into the cache of its process, so each Zope process holds its own copy and is slow until warm. `ZCTextIndex` scores with BM25 in Python, with a splitter that knows no language, so sites add Solr or Elasticsearch and its consistency lag.

### Step 2: the mirror, `zoe-catalog`

- Scope: `FieldIndex`, `KeywordIndex`, `DateIndex`, `DateRangeIndex`, `BooleanIndex`, `UUIDIndex`, `ExtendedPathIndex`, `GopipIndex` (sort), plus the `data` metadata table, `uids` and `paths`. `ZCTextIndex` is not mirrored; the native text index below replaces it.
- Representation: per index a map from key to a roaring bitmap of rids and the reverse map from rid to keys; sorted rid arrays for sort indexes; a trie for the path index; metadata rows in a columnar table so brains need no bucket at all.
- Discovery and build: catalog roots are found by class (`Products.ZCatalog.Catalog.Catalog`) at startup, each index's BTree roots are traversed once in a background job (readiness metric `zoe_catalog_mirror_ready`), then the mirror is maintained at `tpc_finish`, before invalidations go out, from every committed bucket of a mirrored index, decoded by `zoe-pickle`.
- MVCC: the mirror is versioned per tid with structurally shared maps and copy-on-write bitmaps, kept for a window (default 10,000 tids or 10 minutes). A query is answered as of the client's snapshot tid, so a result never names an object the Connection cannot load; outside the window it falls back to the Python path.
- Protocol extension `catalog_query(catalog_oid, tid, plan)`: the plan is ZCatalog's query normalised (index, operator, values or range, `sort_on`, `sort_order`, `sort_limit`, `b_start`, `b_size`, requested metadata). The reply is the ordered rids, the metadata rows and the total count. In-process mode calls the same function through PyO3 with no wire.
- Plone side, `zoe.plone.catalog`: a hook on `Catalog.search`, as `collective.solr` hooks in, routes a query to the mirror when every index and operator in it is supported and builds a `LazyMap` of brains from the returned rows; otherwise the whole query takes the Python path. Security stays in Plone: `allowedRolesAndUsers` is a `KeywordIndex` like any other.
- Correctness is a differential test: every query of the Plone test suites and a recorded production query log run through both paths, and rids, order and counts must be identical, with ties broken by rid as ZCatalog does.
- Memory: a one-million-object catalog with thirty indexes takes the low hundreds of megabytes, once for the whole cluster instead of once per process.

### Native BM25 text index

Plone already scores with BM25; what it lacks is everything around the formula, so the native index is tantivy with BM25 (`k1`, `b` tunable), Snowball stemmers for the site's languages, ASCII folding, stop words, phrase, prefix and fuzzy queries, per-field boosts (`Title^3`, `Description^1.5`, `SearchableText^1`) and snippet generation. One tantivy index per catalog, a field per text index, and a field per language when `plone.app.multilingual` is installed, chosen from the object's `Language`.

- `ZoeTextIndex`, a ZCatalog index class of `zoe.plone`: its `index_object` sends `(rid, index, text)` to the core as a delta record inside the same transaction, because text-index buckets hold word ids, not text, and its `_apply_index` queries tantivy. It pilots the delta mechanism of step 3.
- Consistency: tantivy commits in batches a few hundred milliseconds behind the tid; hits are filtered by the mirror's bitmap of rids existing at the query's snapshot tid; snapshots older than the window fall back to the Python index.
- Durability: the deltas are records in the ZOE transaction, so the tantivy directory beside the store is a cache that `zoe catalog rebuild-text` recreates without Plone.
- Compatibility: a translator maps ZCTextIndex query syntax (`AND`, `OR`, `NOT`, quoted phrases, trailing `*`) to tantivy's; `sort_on='relevance'` keeps meaning BM25; a compatibility switch reproduces the old ranking for sites whose tests pin it. Enhanced mode is the default; fuzzy matching, field boosts and snippets reach new interfaces through the `@search` restapi extension.

### Step 3: the catalog as a projection

Plone keeps computing index values in Python at commit, but emits deltas, `(catalog, rid, index, old value, new value)`, as a record type in the same ZOE transaction, instead of writing buckets. The core applies them to the mirror and appends them to a persisted delta log per catalog with periodic snapshots. Deltas on different rids commute, so two editors indexing different documents never conflict on a shared bucket; the only true conflict left is the same rid and index in two concurrent transactions. Catalog BTrees and `Length` counters leave the store. ZCatalog objects stay as thin proxy index classes, so `plone.app.querystring`, collections and navigation never notice; migration is one rebuild. ACID holds because the deltas ride the transaction that changed the content, and in-process mode works the same way. The projection starts only after the mirror has answered production queries identically.

### Metrics of the catalog

`zoe_catalog_queries_total{path=native|python}`, `zoe_catalog_query_latency_seconds`, `zoe_catalog_mirror_lag_tids`, `zoe_catalog_mirror_build_seconds`, `zoe_text_commit_lag_seconds`, `zoe_catalog_fallbacks_total{reason}`.

### Testing of the catalog

The differential suite above; `zoe-bench catalog` with a query mix replayed from production logs at concurrency, warm and cold; text relevance checked against a labelled set of queries from a real site, in that site's language. Acceptance: identical results on every differential run; a five-index intersection with a sort on a one-million-object catalog under 5 ms at p99 warm; mirror ready within 60 s of a cold start on that catalog; a text query under 20 ms at p99.

## AI-native: MCP server and retrieval

ZOE exposes its store to agents through an MCP server and gives Plone content native retrieval, on pieces of the catalog work: the delta pipeline carries the text, the mirror holds the `allowedRolesAndUsers` of every object as a bitmap, and `zoe-pickle` turns any object into JSON.

### MCP server, `zoe mcp`

A Rust MCP server on the official `rmcp` SDK (crate `zoe-mcp`), inside `zoe serve` or standalone against a server or a store folder, with stdio for local agents and streamable HTTP for remote ones. `zoe mcp --path STORE` (`ZOE_PATH`) opens a store folder read-only through Loupe's folder mode, with `--blob-dir DIR` (`ZOE_BLOB_DIR`, `<path>/blobs` by default), and serves MCP over stdio. It opens the store as `zoe verify` does, with a repair line on stderr, never on stdout, and holds the lock of the store while it runs. It runs as the ops principal of the local operator, with the read-only role, so it offers no tool that writes.

The ops tools are `object_get`, `history`, `diff`, `references` and `space`, which give Loupe's JSON (`space` gives the newest 100 transactions of the growth with the count of all of them); `verify`, which gives the keys of `zoe verify --format json`, with at most 100 findings in each list and the full counts in `totals`, and fails as `zoe verify` does on a blob directory without a layout file; and `explain_conflict(tid)`. The resolution log is a file outside the store, so `explain_conflict` reads the history only: each oid that the transaction wrote (at most 100, with the count), with its class and its size, and the revisions of that oid just before and just after the transaction, with their user and description. Each prompt gives one user message with a request and the JSON of its tools: `explain_transaction(tid)` the result of `explain_conflict`, `why_conflict(oid)` the class and the newest 32 revisions of the object, `summarise_changes(since)` at most 50 transactions after `since`, each with its records counted by class and at most 16 of its objects. Oids and tids are in ZODB form, and no result gives pickle bytes; an error of a tool is a result with `isError`, and the session goes on. stdout carries only MCP messages. The command ends with 0 when the client closes stdin, and with 1 when the store does not open. The console script of the wheel has no MCP server: `zoe mcp` there fails with 1 and names the `zoe` binary.

| Family | Tools and resources |
| --- | --- |
| ops and dev | `object_get(path or oid, as_of)` as decoded JSON, `history`, `diff(oid, tid_a, tid_b)`, `references(oid)`, `tail` as a resource with notifications, `space`, `verify`, `explain_conflict(tid)`; `pack` and `backup` behind the read-write role. They are Loupe's functions with an agent face, and the builder agents use them on the store they are building |
| content | `search(query, mode, filters, as_of, k)` returning passages with path, title, modified, portal type and a citation; `get_document(path)`; `list_children(path)`; `similar(path)` |
| prompts | "explain this transaction", "why did this object conflict", "summarise what changed since tid" |

Security: the MCP server runs as a principal, and every content result is filtered by intersecting the caller's roles with the `allowedRolesAndUsers` bitmap before ranking; objects outside the catalog are visible to the ops role only. Transport security is the server's TLS with read-only or read-write certificates, as for Loupe; a Plone-authenticated gateway (`@mcp` in the restapi, so site users' agents inherit Plone's login and permissions) is a later addition on top, not a replacement.

### Retrieval, `zoe-vectors`

1. Chunking: the `(rid, index, text)` delta that feeds tantivy is split into passages with offsets, stored in the core and versioned by tid, so retrieval returns text and not pointers. One default policy (passage size, overlap, which text indexes) with overrides per `portal_type`.
2. Embedding: asynchronous, like tantivy commits, with `zoe_vectors_lag_tids` as the metric and the as-of-tid bitmap filter so a deleted page never returns. Providers are pluggable. The default build calls an embedding endpoint; a local multilingual model through ONNX, in the server process, is behind a build flag (F37); a remote provider is opt-in per site and logged, so a site's content leaves the site owner's server only by a decision.
3. Vector backend behind one trait, `VectorIndex` (`upsert`, `delete`, `search(vector, k, prefilter)`, `rebuild`), chosen in the stanza:

| Backend | What it is | When |
| --- | --- | --- |
| `builtin` | vectors stored in the ZOE store itself, in a `vectors` key space keyed `(catalog, rid, chunk, tid)`; brute-force SIMD search under a configurable size, an HNSW graph above it, the graph cached beside the store and rebuilt from the vectors when missing | the simple deployment: no extra service, vectors in the backup, and `search(as_of=tid)` answers what the index knew at that tid because the vectors are versioned like everything else |
| `qdrant` | a Qdrant collection per catalog over gRPC; payload carries rid, portal type and roles for pre-filtering; the as-of bitmap is applied after an over-fetch | sites that already run Qdrant or want vector search scaled separately |
| others | the trait is small enough for pgvector or Milvus later | not planned |

4. Hybrid search: BM25 from tantivy and vectors from the backend fused by reciprocal rank, behind the same `catalog_query` extension, the `@search` restapi extension (`mode=bm25|vector|hybrid`, `return=passages`) and the MCP `search` tool. Security filtering happens before ranking in every mode.
5. Rebuild: `zoe catalog rebuild-vectors` re-embeds from the stored passages with no Plone involved; switching backend is a rebuild.

### Metrics of retrieval

`zoe_mcp_requests_total{tool}`, `zoe_mcp_denied_total{reason}`, `zoe_vectors_lag_tids`, `zoe_embed_latency_seconds{provider}`, `zoe_vector_search_latency_seconds{backend}`, `zoe_vectors_remote_bytes_total` (what left the server, by provider).

### Testing of retrieval

MCP conformance with the reference client; a security suite that asserts an anonymous principal never receives a restricted passage across every mode and backend; backend equivalence (`builtin` and `qdrant` return the same top-k on a fixed corpus within a tolerance); retrieval quality on the same labelled query set against BM25 alone; lag and as-of correctness under a write load.

## Deployment

The same wheel and binary cover a laptop, a single server and a Kubernetes cluster; what changes is who opens the store directory.

### Simple

One Zope instance with `<zoe>` in `zope.conf`. No server, no extra process, one directory to back up.

### Clustered, bare metal or VMs

`zoe serve` on the storage host, instances with `<zeoclient>` as today. The repository holds a supervisor unit and a systemd unit (`deploy/`); the server is a single static binary, no Python and no Plone eggs on the storage host.

### Kubernetes

| Tier | Shape | What you get | What you give up |
| --- | --- | --- | --- |
| 0 | one Plone pod, in-process storage, PVC, `Recreate` strategy | simplest possible site, no server | no horizontal scaling of Plone |
| 1 | StatefulSet ×1 for the server, one PVC (redb + blobs), Plone as a stateless Deployment | horizontal Plone scaling, seconds of downtime on a reschedule, full observability | a single point of failure for writes |
| 2 | leader + follower StatefulSet ×2, two PVCs, log shipping, leader election through the Lease API, a Service that follows the lease | automatic failover in seconds, read-only clients served by the follower at a lagged tid | more disk, a replication lag to watch |
| 3 | server Deployment ×N, FoundationDB or TiKV cluster as backend, S3 for blobs | stateless fronts, no PVC on the server, durability and failover owned by the KV cluster | an extra network hop per operation; the FDB transaction limits |

### Tier 1 manifest essentials

- `StatefulSet` with `replicas: 1`, `podManagementPolicy: OrderedReady`, a `volumeClaimTemplate` on an SSD storage class; `fsync` latency of the class decides write throughput, so benchmark the class before choosing it.
- `readinessProbe` on `/readyz`, `livenessProbe` on `/healthz`, `terminationGracePeriodSeconds` above `shutdown-timeout`.
- A `Service` on the ZEO port and a second on the admin port; a `ServiceMonitor` for Prometheus.
- `PodDisruptionBudget` with `maxUnavailable: 0` so a node drain waits for a manual window until Tier 2 exists.
- Backups: a `CronJob` running `zoe backup` into a backup directory or a bucket (incremental, by tid range, through the iterator) and `zoe verify --backup`. Both open the store read-only and take its lock, so they cannot run on a store that a running instance or a server holds.

### Tier 2 mechanics

The follower streams transactions from the leader's log (`iterator_start` from its own last tid, kept open) and applies them with `restore`; it is read-only to clients. Both pods renew a `coordination.k8s.io/Lease`; the holder serves writes. On lease loss the old leader closes client connections, and clients reconnect through the Service, which selects by the `zoe/role=leader` label that a sidecar sets from the lease. Promotion requires the follower to be at the leader's last acknowledged tid; with `replication acks=1`, a leader acknowledges a commit only after the follower confirmed it, which also replaces fsync on slow cloud disks.

### Backup and point-in-time recovery

Continuous shipping comes after the roadmap; the repozo-style dumps of `zoe backup` through the iterator are the backup until then, and stay available for sites without a bucket. The log shipping that feeds a follower feeds a bucket too: `backup.target = s3://bucket/zoe/main` makes the leader ship every committed transaction and every new blob to object storage, with a full snapshot on a schedule (`backup.snapshot = daily`), so a restore reads one snapshot plus the log after it. `zoe restore --from s3://... --to-tid TID` (or `--to-time`) rebuilds a store at any transaction still in the bucket, and `zoe backup verify` restores the latest snapshot plus log into a scratch directory and checks it against the live store's checksums, as a CronJob whose result is a metric. The recovery point is the last shipped transaction, seconds behind the leader. Encryption keys are never in the bucket: a restore needs the wrapping key from its file, environment or KMS, the one secret an operator keeps outside the cluster.

### Tier 3 mechanics

The backend trait maps onto an ordered KV: records under `(oid, tid)` keys, the tid sequencer under one key updated inside the same transaction, invalidations read from a tid-ordered change log that every front tails. Any front can take any client; clients see one Service. Blobs go to S3 with a per-front LRU cache. The FDB limits (5 s, 10 MB per transaction) are met by staging locally and committing in one short write; a commit larger than 10 MB is split by oid range inside one logical tid using FDB's atomic versionstamp ordering.

### Configuration and observability, all tiers

Flags and `ZOE_*` variables, a `ConfigMap` for the server stanza, secrets for TLS and S3. Metrics as listed in "Health, metrics, shutdown", with a Grafana dashboard in the repository (`deploy/grafana/`): commit latency, fsync batch size, lock wait, conflicts resolved by path, invalidation queue depth, replication lag (Tier 2), backend latency (Tier 3).

## Loupe: desktop inspector and editor

Loupe is a Tauri 2 desktop application for ops people and developers that opens a ZOE store or connects to a ZOE server, browses, edits, creates and deletes objects without a Python interpreter, travels in time, tails live commits and runs operations. It never opens a `Data.fs`; it converts one. Crate `zoe-loupe`, product name Loupe. Everything it touches already exists in the design, except the reverse-reference index that it keeps for itself and the reindex queue that it leaves for Plone.

### Two ways in, same screens

A store folder (exclusive, instance stopped, `zoe-core` in-process) or a running server (`zoe-client` over the ZEO protocol with TLS, read and write through the same two-phase commit as any client, so running Plone instances see Loupe's writes through invalidations). A folder opens as `zoe verify` opens a store: a store that a writer left open gets its repair at the open, and the window shows `<path>: the store was not closed cleanly: repaired the store`; a store that was closed cleanly gets no byte changed. Because the wire protocol is ZEO's, Loupe also browses a classic ZEO server, read-only, which is how a site gets inspected before it is converted.

### Pickle layer, `zoe-pickle`

A ZODB record is two pickles, class reference and state, written with one memo. The crate decodes both into a generic tree (class path, attributes, persistent references, blob references, primitives, containers), from the opcodes of protocols 0 to 3, so the records that Python 2 wrote decode too. Each node keeps the opcode form that wrote it, and the encoder writes that form back; new values use protocol 3 with ZODB's `persistent_id` convention. Constructs it does not model (custom `__reduce__` callables, extension codes, Python 2 instances) become opaque nodes that re-emit their original bytes, and editing inside one is refused. Decode then encode must reproduce every record of the conformance corpus and of a production copy byte for byte.

The decoder refuses what Python's unpickler refuses as malformed, for example an unknown protocol or a BINSTRING or LONG4 length of 2³¹ or more. It is stricter than Python in a few places: it refuses the opcodes of protocols 4 and 5, PROTO after the start of a pickle, values or a mark left on the stack at STOP, bytes after the state pickle, and text arguments that no pickler writes (for example a memo index with leading zeros, or an INT in octal or hexadecimal). No operation on the tree recurses once per nesting level, so a deep value cannot overflow the stack. Each record has a node budget, a parameter of each call: online readers such as Loupe use the default of 2²⁰ nodes, and pack and the converters pass the length of the record, which refuses nothing the input can hold. For pack and the converters a refusal is a hard error, never a record without references.

### Full CRUD, and what each operation really does

| Operation | Mechanics | Guard |
| --- | --- | --- |
| Create | allocate an oid with `new_oids`; class by dotted name, picked from the classes seen in the store or typed; initial state built in a typed form; linked from a container (raw attribute, or a Plone-aware insert into `_tree`, `_count` and `_mt_index`) | an unlinked object is reported as garbage-to-be |
| Read | decoded state and both directions of references; inbound references come from a reverse-reference index Loupe builds on first open as a background job, stores beside the store as `loupe-index`, and keeps current from the live tail | — |

Every Loupe write is one ZODB transaction: user `loupe:<operating-system user>`, a description the operator must type, and extension data `{"tool": "loupe", "version": …}` so history and the live tail show which changes came from Loupe. It passes vote like any transaction, so it can lose a conflict and retry. The time-travel view also offers "undo this transaction", which calls the storage's `undo`, shows per object whether the record is current or goes through a merge, and commits with a `loupe:undo` note like any other edit.

### Application invariants

Raw edits bypass Plone: the catalog, `ObjectModifiedEvent` handlers, workflow, `modified` dates, the UUID index. Loupe is a scalpel, not a content editor, and the design says so in four ways:

1. Writes need an explicit expert mode per session.
2. Objects that are catalogued carry a badge, and the commit dialog lists which indexes will be stale.
3. An optional Plone integration in `zoe.plone` provides a reindex queue: Loupe appends the touched oids to a persistent `IOTreeSet` at a known path in the same transaction; the add-on drains the queue on the next request (or a clock tick), reindexes those objects and optionally fires `ObjectModifiedEvent`. With it installed, a Loupe edit is reindexed within seconds; without it, Loupe lists the touched oids and the operator reindexes by hand.
4. Every commit is preceded by a dry run that shows the pickle diff and the list of transactions it would conflict with if any client has them in flight.

### Converters, `zoe convert` and a Loupe screen

The goal is to replace `Data.fs`, so conversion is first-class and runs in Rust without a Python environment:

| Direction | Reader or writer | Notes |
| --- | --- | --- |
| `Data.fs` → ZOE | streaming `FileStorage` reader: transaction records, data records, back pointers, `BushyLayout` and `LawnLayout` blob directories | the migration path for every existing site; resumable by tid |
| RelStorage → ZOE | PostgreSQL via `sqlx`, history-preserving and history-free schemas, blobs from the blob directory or from `blob_chunk` | the second migration path |
| ZOE → `Data.fs` | `FileStorage` writer | the exit path, so nobody is locked in |
| ZOE → ZOE | iterator to a different backend | backend change, Tier 1 to Tier 3 |

Every conversion verifies transaction counts, last tid and a sample of records byte for byte, and writes a report: the number of problems on its line `problems`, one line for each kind of problem with its count, then the problems, the lines about the whole source first, then at most 100 others and a line that counts the rest. The kinds tell a copy without its blob files from a store whose pickles differ: a stop before the end of the file, blob records without a blob directory, a missing transaction, transaction metadata that differs, a missing or different record, a missing blob file, a blob that the store does not have, does not read or holds different, and a failed read of the store. The `Data.fs` converter restores each transaction as a deferred restore (see "Tids"), and calls `Store::sync` after each batch of at most 1,000 transactions or 64 MiB, after the copy pass and after an error of the copy pass. So the copy runs at the rate of its reads, a crash loses only the restores of the open batch, and the next conversion resumes after the last durable tid. The Python route, `zodbconvert` with the `zoe` storage, stays available.

`zoe convert --from-data-fs FILE --path STORE` and `zoe convert --to-data-fs FILE --data-fs-blob-dir DIR --path STORE` run the first and the third direction (ADR 0028). `--data-fs-blob-dir` (`ZOE_DATA_FS_BLOB_DIR`) is the blob directory of the `Data.fs`. `--blob-dir` (`ZOE_BLOB_DIR`) is the blob directory of the store, `<path>/blobs` by default, in both directions. `--to-data-fs` opens the store as `zoe verify` does, and refuses, with 1 and before it writes anything:

- a store with blob records whose blob directory has no layout file: the message names the blob directory and `--blob-dir`;
- a store that holds a moved registry of `zoe.plone` (ADR 0043, part B), a durable namespace whose name starts with `zoe.plone.registry:` and that holds the marker row `m`, because a `Data.fs` holds no namespace and the registry of the copy would raise `Unsupported` on each request. The message names each registry by its oid and its namespace, and the way out: `move_back`, a commit, then the conversion. A marker of a layout other than 1 refuses too;
- a store with a current record of `zoe.plone.properties.PrincipalProperties` or `zoe.plone.history.WorkflowHistory`, which a client without `zoedb` loads as a broken object (ADR 0046, section 9), but for a record that the uninstall of `zoe.plone` retired (a state of one item, the int key 0). The message names each class, its count and its first five oids, and the way back: import the profile `zoe.plone:uninstall` on each site, then `zoe pack` with its GC at a time after the uninstall, then convert.

`--force` (`ZOE_FORCE`) converts anyway, with a warning on stderr and in the report; `--force=false` refuses also when `ZOE_FORCE` forces. With `--from-data-fs`, `--force` has no effect.

### `zoe verify`

`zoe verify --path STORE` checks a store without Python. It opens the store read-only, so it changes no byte of a store that was closed cleanly; a store that a writer left open gets its repair first (ADR 0028): the command writes only `zoe.redb`, and one line to stderr that holds `repaired the store`, or fails with 1 when the repair cannot write the file. The repair also folds the write-ahead log into `zoe.redb` when the log holds a commit after the folded tid, and writes no other file. When the log is damaged, the open of the tools fails with `CorruptTxn`: `zoe verify` then reports the damage as a finding under the key `log`, with the tid and the text of the error, opens the tables alone with `Store::open_read_only_tables`, verifies them and exits with 1 (ADR 0056). `zoe convert --to-data-fs`, `zoe pack --dry-run`, `zoe backup` and `zoe mcp` open a store the same way, and refuse a damaged log. `--blob-dir DIR` (`ZOE_BLOB_DIR`) gives the blob directory, `<path>/blobs` by default, in which the open creates nothing; a store with blob records whose blob directory has no layout file fails the command with 1 before the walk, with a message that names the blob directory and `--blob-dir` (ADR 0023).

The walk checks every record frame, deletions too, and every blob record against its checksum, and each blob file against the size and the BLAKE3 hash of its blob record. It reads each transaction row, each sequence row and every KV namespace row (ADR 0043). Of each oid, the newest record is the current record: its class comes from the class pickle, and its persistent references from `zoe-pickle`, never from an unpickler; a reference to an oid without a current record is dangling, as `referencesf` would find it. The walk counts the oids that have a record, deletions included, and compares them with `object_count` (ADR 0033). `--classes FILE` (`ZOE_CLASSES`) names the classes that the application provides, one `module.name` per line; each other class of the store is a finding. A record that does not decode is a finding, not a crash. A blob record without its record is not checked.

`--format json` (`ZOE_FORMAT`) prints one JSON document with oids and tids as integers and the keys `checksums` (the frames that do not read, each `{oid, tid, error}`), `blobs` (the missing or damaged blob files), `references` (the dangling references, each `{oid, tid, missing}`), `pickles` (the current records whose references cannot be read), `classes` (each class with its count), `unknown_classes`, `object_count` (`null` for a store without a count), `namespaces` (`{ephemeral_keys, durable_keys, expired_keys}`, where `expired_keys` counts the ephemeral keys that wait for a sweep step) and `count` (`{stored, counted}` when the count differs, else `null`). The command exits with 0 when it finds nothing, 1 when it finds something, and 2 on a usage error. The walk keeps 8 bytes for each oid with a current record, and about 24 bytes for each reference to a later oid until it ends. The library is `zoe_convert::verify`, which the `verify` tool of `zoe mcp` calls too.

### `zoe backup` and `zoe restore`: dumps (N15)

`zoe backup --path STORE --to DIR` (`ZOE_PATH`, `ZOE_TO`) opens the store as `zoe verify` does and writes one dump file into the backup directory `DIR`: the full dump the first time, then a dump of the transactions after the last tid of the dumps, read through the iterator. A dump holds each transaction with its tid, user, description, extension and records, deletions included, each blob with its size and BLAKE3 hash, the end of each sequence, and every row of the durable KV namespaces at its last tid (ADR 0043); the ephemeral namespaces stay out. It ends with the BLAKE3 hash of its bytes, and ADR 0030 gives its layout. The backup writes the file under a temporary name, syncs it and renames it, so it never changes a dump, and takes a `flock` on `DIR`. With nothing new, it writes nothing and exits with 0. It refuses, and writes nothing, when the store does not continue the dumps: when their last tid is not a tid of the store, and when the store was packed after that tid; the message asks for a new full dump in a new directory, because one directory holds one chain.

`zoe restore --from DIR --path STORE` (`ZOE_FROM`) refuses a target that holds a store or other files, or a mount point, checks the hash of every dump of the chain before it writes anything, and rebuilds the store in the work directory `STORE.restore`: each transaction under its own tid, with a sync, each blob after a check of its hash, each sequence raised to its end in the dumps, and the durable rows of the last dump in one backend write. A restore reads only the dumps of version 2, and refuses a dump of any other version. Then it renames the work directory to `STORE`, and reports the last tid and its UTC time. A damaged dump, or a missing dump in the middle of the chain, fails the restore with 1 and leaves nothing at the target; a missing newest dump is not seen, as with repozo. A restore to an earlier point restores from a copy of a prefix of the chain. The dumps are not compressed, they keep the history that a later pack removes, and a restored store has a pack watermark of 0.

`zoe verify --path STORE --backup DIR` (`ZOE_BACKUP`) restores the dumps into a throwaway copy in `--scratch SCRATCH` (`ZOE_SCRATCH`, else `TMPDIR`), then opens the store read-only, compares the copy with it up to the last tid of the dumps, and removes the copy, also when the check fails; a copy that a killed check left goes at the next check. Each transaction, record and blob record must be the same, but a record or a transaction that a pack removed at or before the pack watermark is no difference, and a pack watermark after the last tid of the dumps is one. The current record of each oid at the last tid of the dumps must be the same, and each sequence of the store must end at or above its end in the dumps. When the store has no commit after the last tid of the dumps, each durable row must be the same; a difference names the namespace and the xxh3-64 hash of the key. A difference or a damaged dump exits with 1. With `--format json`, the report has the keys `dumps`, `last_tid`, `transactions`, `records`, `blobs`, `sequences`, `durable_rows` and `differences`. The library is `zoe_convert::backup`, `restore` and `verify_backup`.

### Operations tools in Loupe

Each operations feature of the core and the server has a screen: a fork of the current store at any tid; the last scrub and its findings; a pack dry-run as a treemap of what would go, and the retention window; `verify` findings with a jump to each broken reference; `rename-class` with a preview; the change feed as the live tail; a Parquet export dialog; the backup state and, with continuous backup, a point-in-time restore into a fork.

### Stack

Tauri 2; the Rust side links `zoe-core`, `zoe-client`, `zoe-pickle` and `zoe-convert`, exposed to the window as IPC commands; frontend React and TypeScript with Vite, since that is what the Plone frontend world already writes; d3 for the treemap and timelines, a virtualised tree for the browser; UI strings in a translation catalog from the first release. Packages for Linux first, macOS in a later phase, with Tauri's updater and code signing.

### Security of Loupe

Loupe carries production credentials, so the server distinguishes read-only from read-write client certificates and Loupe shows which it holds; read-only mode hides the editor and operations. Credentials live in the operating-system keychain through Tauri's store plugin, never in a config file.

### Testing of Loupe

Pickle round-trip property tests over the corpus; CRUD invariants against a Plone 6 site (edit in Loupe, assert Plone shows the change after invalidation and the `zoe.plone` reindex); reverse-index correctness against a brute-force scan; converter equivalence (`Data.fs` → ZOE → `Data.fs` byte-identical pickles and tids); end-to-end Tauri tests with `tauri-driver`.

### B. Performance

1. `zodbshootout` (RelStorage's harness) is the public scoreboard. Scenarios: add, update, read cold, warm and hot, object sizes 1 KB and 100 KB, concurrency 1, 4, 16, 64 with threads and with processes, against `FileStorage`, ZEO 6, RelStorage on PostgreSQL 17 with history and without, ZOE in-process and ZOE server, on one documented reference machine, each value on a fresh store after its warmup. Results as p50, p99 and operations per second, with the state of the GIL in each worker process. ZOE server is `zoe serve` with its defaults behind a stock `<zeoclient>` (`zoe-server`) and behind the native client (`zoe-native`); a `read_cold` value of `zoe-native` counts only when the server counted a load for each object that it read. `just bench gate DIR` checks N4 against ZEO 6 on the last result of each storage per machine, Python build and set: it fails when a cell of ZEO 6 has no counterpart or a ratio of operations per second is below 1, in every cell but `read_hot`, which with the stock client reads only from the cache of `ZEO.ClientStorage`.
   The phase 3 gate is the native gate, `just bench native` (ADR 0039): `zoe serve` through the native client against ZEO 6 through `ZEO.ClientStorage`, in the 5 scenarios of `zodbshootout` with its objects and data, threads at concurrency 1 and 16 and processes at 16, objects of 1 KB (100 per transaction) and 100 KB (10 per transaction). For each cell, each storage gets one server on a fresh store with its defaults, one populate and one set of worker processes. A scenario runs in pairs of batches, `zeo` then `zoe-native`, with the first storage swapped from one pair to the next and one warmup pair; a batch runs the same number of transactions in a row in each worker, about 20 ms of them and at most 20. The ratio of a pair is the time of the slowest worker for one transaction of ZEO 6 over the one of ZOE. After at least 10 pairs, a cell passes when the 99 % confidence interval of the mean of the log of its ratios is above 0, and fails when it is below 0; it stops at its first verdict, and a cell with no verdict at 100 pairs or after 10 s of pairs fails. The run fails when the server counted fewer loads than the objects that the `read_cold` batches of `zoe-native` read.
2. `zoe-bench`, a Rust load generator that speaks the ZEO protocol: N clients, pipelining depth, read/write mix, Zipf-skewed hot set, transaction size. It measures the two things `zodbshootout` cannot: contention (ConflictErrors per 1,000 commits, lock wait, retries) with vote-time versus early locks, and server saturation (loads per second at a p99 ceiling).
3. `criterion` microbenchmarks in the core: `load_before`, `vote`, `finish`, group-commit batching, lock manager acquire/release, native merge per bucket size, msgpack frame decode.
4. Fsync-class benchmark: the same write workload on NVMe, on a cloud PD or EBS class, and with Tier 2 replication acknowledgement instead of fsync; this is the number that sizes Kubernetes storage classes.
5. Plone end-to-end (B5): `just bench plone`, Locust against a synthetic Plone 6.1 site that one `Data.fs` and its `zoe convert` copy hold, checked equivalent by a logical digest of the site. The fixtures are the presets `small`, `medium` and `large`, and `xlarge`, about 250,000 items in the shape of a real Plone site, so that an edit reindexes as many indexes as on the real site; `xlarge-mini` has its shape at about 1/100. The stacks: ZEO 6 with `ZEO.ClientStorage`, and `zoe serve` with the native client and `zoe.plone`, with ZEO's asyncio client and the ZOE extensions, and with a stock `ZEO.ClientStorage`; and the native client with backends of `zoe.plone`: `zoe-native-kv` (locking), `zoe-native-qi` (queued indexing) and `zoe-native-qi-kv` (both, and `PrincipalProperties`). Scenarios: browsing, catalog searches and collections, the edit and add forms, workflow transitions, a weighted mix, the mix beside a reindex and a REST import, and three controlled contentions. Each run checks the site against a ledger of its logical operations after the run (acknowledged writes present, no phantom, refused writes absent, versions, workflow history, permissions, catalog entries and search tokens). A probe in each Zope process counts the attempts, each `ConflictError` with its class, the resolutions and the storage calls; the result holds successful operations per second, p50, p95 and p99, first-attempt and eventual success, conflicts per 1,000 operations, CPU per operation, and the bytes that the server writes per operation. `just bench plone report --json` writes the summary of a campaign, valid against `bench/schema/plone.schema.json`, with no host name, user name, path or password. The gate of phase 4 is B5: in `edit` and in `create-spread`, at 4 and at 16 users, `zoe-native-qi` raises at most 10 % of the `ConflictError`s that `zeo` raises to Zope per 1,000 operations, in each scenario.
6. Transaction-log replay (B6): replay the transactions of a log at 1×, 4× and 16× speed with their original concurrency grouping, over a read load, and count conflicts raised, resolved natively and resolved in Python. It measures the success criterion and gates no phase, because it replays the records of a log and so cannot show a mechanism that changes what a save writes. The log is synthetic: the transactions of a store that a B5 run on `zeo` kept, timed by the probe records of the run (`docs/spikes/log-replay.md`). `just bench replay RUN` restores them into a new store for each run, then plays them in time order through `ZEO.ClientStorage` to ZEO 6 and through the native client to `zoe serve`, in alternating runs, beside a client that loads the oids of the log. A transaction reads the serials of its oids at the start of its request and stores at its commit its own change applied to the state that it read; a batch of the indexer starts at its commit. A commit that raises `ConflictError` is not retried. Each run counts the conflicts per 1,000 transactions by class and by path, then loads every acknowledged record; a run in which one does not load does not count. `just bench replay report FILE` gives the ratio of the success criterion.
7. The client benchmark (B7, F28): `ZEO.ClientStorage` against the native client on the same server, through the storage API and without ZODB. Shapes: one process with 1 and with 16 threads, and 16 processes; records of 1 KB and 100 KB. Workloads: `cold`, loads of distinct oids from a client with no cache; `warm`, the same loads from a client that reopens the cache file of its `cold` round; `commit`, commits of 100 new records. Servers: `zoe serve` and a ZEO 6 server with msgpack, each client against each, with the same calls on the same server state. Each row runs in at least three interleaved rounds, each in its own process, and reports calls per second, p50 and p99, client CPU per object and the spread; against `zoe serve`, each load of a `cold` round must reach the server and none of a `warm` round. `just bench client report FILE` gives the verdict: in every row against `zoe serve`, a higher rate and a lower client CPU per object.

### C. Durability and crash consistency

1. Simulated filesystem in the core tests: a `Vfs` trait with an in-memory implementation that records every write and fsync, then replays prefixes, reorders unsynced writes and truncates the tail; after every replay the store must open, `verify` must pass, and every acknowledged tid must load. Deterministic, thousands of cases per minute, runs on every PR.
2. Process kill loop (`python/zoedb/tests/crash/test_kill_loop.py`): four writers commit objects and blobs through stock `ZEO.ClientStorage` clients to `zoe serve`; each round kills the server with `SIGKILL` at a random point, restarts it, stops it with `SIGTERM`, runs `zoe verify` on the store, and loads every acknowledged commit and its blobs. `just crash RUNS SEED` runs it and prints the seed; a failure names its round. The Dagger function `crash` runs 10,000 rounds with a new seed, nightly.
3. Power-loss emulation: the same loop on a `dm-flakey` device or a QEMU guest that is force-stopped, so lost page-cache writes are real, weekly.
4. Blob atomicity: kill between blob rename and record commit, verify neither a dangling blob nor a record without its blob.
5. Pack under load: pack during the write benchmark; readers must see consistent snapshots, no `POSKeyError`, and the store size must drop.
6. Deterministic simulation (N18): `zoe_server::sim` runs the production code of the server, its sessions, the core and `zoe-client` in one process on a simulated network and clock, with the store in memory; the crates reach their tasks, threads, timers and lock waits through runtime and clock traits, and one thread runs at a time. A seed decides the whole run: the order of the tasks and threads, the delays and losses of frames, the partitions, the connections that close, and the crashes of the server at a phase of a commit (staged, locked, finishing or acknowledged). A crash is a power loss by default, in which the disk keeps the synced writes and a seeded part of the others, some of them torn, or a kill of the process; the store then opens again from that image. Every commit that a client saw acknowledged must load, its blobs included, no load may give a serial older than an acknowledged commit of its oid, and the store must pass the checks of `zoe verify`. The same seed gives the same trace; `ZOE_SIM_SEED` runs one seed. The runs: the kill loop with blobs; writers of a hot `Length` with slow syncs, where each record holds the value before it plus 1 and the hand-off makes batches of more than 2 commits on average; and split writers of one `IIBTree` with the split merge and `server_writes`, where the tree must hold every acknowledged key after each recovery and a finish hands off no more locks than its commit has records (ADR 0048). `ZOE_SIM_SEEDS` sets the number of seeds; by default, as in `just test`, 200 for the kill loop, 100 for the hot `Length` and 50 for the split writers. `just crash` runs the kill loop and the split writers in release, 200 seeds each by default, and the Dagger function `crash` runs them with 10,000 and 1,000 seeds. Not covered yet: a graceful stop, blob downloads, pack, named storages and read-only mode.

### D. Concurrency and free-threading

- ThreadSanitizer builds of the tests of `zoe-core`, and of the tests of `zoe-server` that a filter names (`just tsan`); `loom` interleaving tests on the lock manager and the commit batch. `just tsan` runs at the end of each phase.
- Free-threaded stress: on 3.14t, 32 threads committing on overlapping and disjoint oid sets through the in-process storage, with invariants checked after every round (serial monotonicity, no lost update, lock table empty).
- Lock-order and deadlock tests: adversarial clients requesting oids out of order; every run must end with `LockOrder` or timeout, never a hang.

### E. Protocol and input fuzzing

- `cargo-fuzz` targets: msgpack frame decoder, `register`/`get_info` handshake, pickle header parser, native merge inputs. One hour per nightly. The repository keeps only the seeds of each target and the script that makes them; the corpus that the nightly runs grow stays in a cache volume of CI. The targets of `crates/zoe-server/fuzz` are `frame`, `handshake`, `merge` and `fields`; `just fuzz` builds and runs them, and a fuzz smoke of the server runs in each `just test`.
- Fault injection on the wire: client disconnect at each 2PC state, server restart during vote, invalidation queue overflow, interrupted blob upload; the client must end in `ClientDisconnected` or a clean retry, the server must hold no stale locks.

### F. Replication and Kubernetes (Tier 2 and 3)

- A `kind` cluster in CI: leader kill during commit, follower promotion, split-brain attempt with two lease holders, rolling restart; acknowledged commits are never lost, clients reconnect within 10 s.
- Tier 3 against a single-node FoundationDB in CI, the same conformance suites.

### G. Operations

- Bit-flip injection: flip random bits in records, blobs and the dictionary on a copy of the corpus; every read must raise `CorruptRecord`, never return data; `zoe scrub` must list every injected fault and nothing else. The frames of the KV namespaces are in the gate too: every bit of an ephemeral row, a durable row and a generation row, flipped, makes each read and scan raise `CorruptKv`, never an absent, expired or other value (`crates/zoe-core/tests/kv_namespaces.rs`).
- Backup round trip: continuous shipping to a local S3-compatible bucket under the write benchmark, then `restore --to-tid` at ten random tids compared record by record against `loadBefore` on the live store; `backup verify` as a scheduled job.
- Feed exactness: an external consumer counts commits through the kill loop and reconnects from its last acknowledged tid; the count must equal the server's, with no duplicate.
- Forks: a fork of the corpus runs the Plone upgrade suite; the base store's checksums are unchanged afterwards; `plone.app.testing` layers stacked on forks run the Plone suites.
- Encrypted store: the whole conformance suite on an encrypted store; a scan of the files finds no plaintext record or blob; a wrong key fails to open with a clear error.
- Named storages: a two-mount Plone site on one server, the ZEO multi-storage tests, commits on one store under load while the other is packed.
- Pack safety: dry-run report compared to the actual removal set; revert inside the window restores every record; incremental pack under the read benchmark keeps p99 inside budget.

| gate of phase 4 | ConflictErrors reaching Zope in B5 versus ZEO: per 1,000 operations of `edit` and `create-spread` at 4 and 16 users, `zoe-native-qi` against `zeo`, in each scenario | ≤ 10% |

| regression gate | p99 or ops/s change on B1 quick scenarios, per PR | within 5% |

### Regression tracking

The results repository, `adeweb-be/zoe-bench-results`, holds the published results of every family: `zodbshootout` (B1), the native gate, the client benchmark (B7) and the summary of each B5 campaign, in one layout with an index of version 2 (ADR 0054; `bench/README.md` gives the layout and the steps). `just bench publish` copies into a checkout of it only a document valid against the schema of its family, of a full run, at a commit of `main`, from a tree that held no change beside its commit, and for B5 with every run verified. It never commits and never pushes: a push needs the approval of the human. The dashboard is the Pages site of that repository, built from `bench/dashboard/`: per machine and Python build, the latest document of each family as plain tables with no headline section, with the earlier ones a selector away, and the charts of `zodbshootout` over every run. It computes no number that a document does not hold, but the ratio of two numbers of one B5 step. The PR gate reads the last ten nightly runs to compute the baseline.

### The publishable set

`just bench showcase` runs, on one machine and in one repetition, the set that the results repository publishes (ADR 0054): the builds; B5 on the fixtures `small` and `medium`, on `zeo` and `zoe-native-qi-kv`, with `edit` and `create-spread` at 1, 4, 8, 16 and 32 users on `small` and every other scenario of the set at 4 and 16 users; one B5 summary per fixture; and the native gate and the client benchmark on CPython 3.13 and 3.14t. A run of `zoe-native-qi-kv` imports the profile `zoe.plone:default` into its copy of the store before the instances start, so the stack runs with the merge policy of a new site. The server, each Zope instance and Locust run on separate physical cores. One run goes at a time, under the bench lock and a load average below 8. A directory belongs to one commit and one set of options, and a start resumes it.

## Risks and open questions

The largest risks are not in Rust; they are in matching ZEO's exact semantics and in the Plone-side hook for early locks.

### Risks

| Risk | Impact | Mitigation |
| --- | --- | --- |
| ZEO protocol edge cases (cache verification after a long disconnect, `getInvalidations` gaps, blob shared-dir modes) differ from the source reading | a Plone cluster sees stale objects | run the full `ZEO.tests` suite from the start of phase 2; keep the invalidation queue large; treat every ZEO test skip as a bug |
| redb write amplification caps commit throughput below RelStorage on write-heavy loads | N4 fails on update scenarios | the append-only log backend is designed in from day one behind the trait; the decision is made on phase 2 numbers |
| Early locks stall a four-thread Zope instance on a hot object | worse latency than ConflictError retries | default stays vote-time locking; early locks are opt-in per instance and documented for free-threaded Zope first |
| The patch of `ZODB.Connection.Connection` for early locks reads ZODB internals that can change between releases | breakage on ZODB upgrades | keep the patch in one small module, `zoe.zodb`, with tests on each version of ZODB that the lock files install (ADR 0044, section B9); propose an upstream hook once it is proven |
| Native merges drift from `BTrees` semantics after a BTrees release | silent data differences | differential tests pin the BTrees version; CI runs against the latest BTrees on a schedule |
| `persistent`, `BTrees`, `zodbpickle` do not declare `Py_mod_gil_not_used` upstream | free-threaded parallelism in Zope stays off | phase 0 opens the PRs; a vendored build with the declaration is the fallback for the first production site |
| Tier 3 on FoundationDB: the 5 s / 10 MB transaction limits and the extra hop | large commits need splitting; p99 rises | stage locally, commit in one short write; Tier 3 is for clusters that need HA more than the last 100 µs |
| Single maintainer | bus factor | the spec, the harness and the conformance suites are the handover; keep the core small |
| Pickle-level assumptions (class paths, `zodbpickle.binary`) break on py2-migrated stores | migration failures | the round-trip test runs on a production copy before any release |
| Loupe edits bypass Plone invariants (catalog, events, workflow) | stale catalog, surprised editors | the four guards of "Application invariants" |
| zoe-pickle cannot round-trip an exotic construct byte for byte | an edit rewrites more than the operator changed | opaque nodes are not editable; the round-trip property test runs on a production copy before each release |
| RelStorage schema changes between versions | the converter misreads a site | pin the supported RelStorage versions, detect the schema version at start, refuse unknown ones |
| Production data or credentials leak into a public repository or a CI log | a data breach, and the adopting site's trust | synthetic corpora in public CI; private runner for production copies; secret scanning on every push; builders have no access to production data |
| The catalog mirror answers a query differently from ZCatalog | wrong search results, silently | the differential suite on every PR and a nightly replay of a production query log; an index or operator that the differential suite does not cover takes the Python path |
| Text index lags the tid or diverges from ZCTextIndex ranking | a just-saved page missing from search; tests that pin ranking break | the snapshot bitmap, the lag metric with an alert, and the compatibility switch of "Native BM25 text index" |
| A remote embedding provider sends content off the site owner's server | GDPR exposure without anyone deciding it | remote providers opt-in per site, logged, and counted by zoe\_vectors\_remote\_bytes\_total |
| An agent reaches content through MCP that Plone would have hidden | a permissions bypass | the security of "MCP server, `zoe mcp`"; the security suite runs on every PR that touches zoe-mcp or zoe-vectors |
| A field-level merge combines two valid saves into an invalid object because an invariant was never declared | silent data inconsistency | policy derived from schemas with strict as the default; merging enabled per class only after shadow mode on production conflicts, but for the stock container classes, whose evidence covers creations only (ADR 0046, section 9); every merge logged with the keys it merged and reversible from history |
| An encryption key is lost | the store and every backup are unreadable | encryption is off by default; the wrapping key lives outside the cluster and is the one secret the runbook makes an operator keep; `zoe backup verify` fails as soon as a snapshot cannot be opened |
| The operations features dilute the core | the storage core gets less review | each tool is its own card with its own acceptance test, and none of them touches the commit path |

### Open questions

- [ ] Is the reference machine a developer workstation, an on-premise server or a cloud VM? The benchmark numbers only mean something on one fixed box.
- [ ] Should the async Python client (`aload_before`, `aprefetch`, `acommit`) ship for collective.starlette before the end of the roadmap, or after it?
