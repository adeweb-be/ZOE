# ZOE — technical specification

@Antoine Duchêne

This document is the technical specification: what ZOE is and how it works. The way of working, the units of work, the sessions, the roadmap and the project organisation are in ZOE — working methods and roadmap.

## Summary

ZOE (Zope Object Engine) is a ZODB storage written in Rust that Plone can use unchanged: in-process for a single Zope instance, or behind a tokio server that speaks the existing ZEO wire protocol for a cluster. It aims to be the fastest storage backend available for Plone while staying ACID, and it attacks ConflictError at the storage layer with per-object locking and native conflict resolution.

**Goals**

1. Drop-in for Plone 6: the only configuration change is the storage stanza in `zope.conf` (`<zoe>` or a `<zeoclient>` pointed at the Rust server). No change to application code, `persistent`, `BTrees` or `transaction`. A `<zeoclient>` against `zoe serve` needs the `msgpack` package, because the server speaks only the msgpack protocol `M5` (F2); `zoedb[plone]` installs it.
2. Fastest measured Plone storage: beats `FileStorage`, ZEO and RelStorage on Postgres on the same `zodbshootout` harness, cold, warm and hot.
3. Async where it pays: the server is fully asynchronous (tokio), handles pipelined requests per connection, and exposes an async storage interface for future async clients. The ZODB object model stays synchronous.
4. ACID by construction: atomic two-phase commit, durable on `tpc_finish` (fsync or replicated acknowledgement; the one exception is the deferred restore of the `Data.fs` converter, durable at its next batch sync, see **Tids**), snapshot isolation through MVCC keyed by `(oid, tid)`, and crash recovery without a repair step of ZOE: the last durable commit is the state. After a killed writer, the first writer open repairs the file and can take longer, because redb rebuilds its free-space map.
5. Fewer ConflictErrors under heavy writes: per-OID commit locks, optional early write-intent locks, and conflict resolution in Rust for structures and for fields, with Python only on the client for the long tail.
6. Two deployment shapes from one crate: in-process (no server) and clustered (server), same on-disk format, switchable by restarting.
7. Cloud-native on Kubernetes in three tiers: single-replica StatefulSet, leader/follower with automatic failover, stateless fronts over FoundationDB or TiKV.
8. Free-threading ready: the Python extension declares `Py_mod_gil_not_used` and commits in parallel inside one free-threaded Zope process.
9. Loupe, a Tauri desktop inspector and editor for ops and developers: browse, time-travel, tail live commits, full CRUD without Python, and converters from `Data.fs` and RelStorage, so ZOE replaces `Data.fs` entirely.
10. A faster catalog behind the unchanged ZCatalog API: an in-memory mirror answering queries in Rust as of the client's snapshot, a native BM25 text index on tantivy with real multilingual handling, and later a delta-based projection that ends bucket conflicts.
11. AI-native: an MCP server for ops and content agents with Plone's permissions enforced before ranking, and native retrieval with chunked passages, local-by-default embeddings, hybrid BM25 and vector search, and a choice of vector backend, ZOE's own index stored in the DB or Qdrant.
12. Operations as a feature: a checksum on every record, compression and encryption at rest, repozo-style dumps (continuous backup with point-in-time recovery comes after the roadmap), copy-on-write forks, a public change feed, named storages for mount points, and the data tools (verify, rename-class, export) in Rust.

**Non-goals**

- Rewriting `persistent` and `BTrees` in Rust. That is a separate, client-side project (section 8 says what is left there).
- An asynchronous persistent-object API (`await obj.load()`). It would break every Plone add-on; the design keeps lazy loading synchronous.
- ZODB 5 and ZEO 5. ZOE targets ZODB ≥ 6.0 and ZEO ≥ 6.0, which means Plone 6.1 and later; older clients are not supported.
- Requiring a new client. `ZEO.ClientStorage` stays supported for the life of the project; the native Rust client of F28 ships in phase 3 as a drop-in, never a requirement; the server replaces `runzeo`.
- Multi-tenancy inside one server. Isolation is by process and by named storage (F22); per-storage quotas are the only shared-server feature.
- The sixteen features triaged as Won't in the roadmap's Feature triage section, among them agent branches with merge-back, actor-tagged transactions, read replicas with session tokens, WASM plugins, server-side subtree clone and blocks as CRDT documents. Everything else from that triage has a requirement above (F29 to F38, N18, N19) or waits after the roadmap.

**Success criteria**

- Plone 6 test suites (`Products.CMFPlone`, `plone.app.contenttypes`, `plone.restapi`) pass against both modes with no skips attributed to the storage.
- `ZODB.tests` conformance suites and the ZEO client test suite pass against the server.
- On the reference benchmark machine, `zodbshootout` shows lower latency and higher throughput than ZEO and RelStorage/Postgres in every scenario, by a margin recorded in section 11.
- A crash test (`kill -9` or power cut at any point of `tpc_finish`) never loses an acknowledged transaction and never needs manual repair.
- On a write-heavy replay of production traffic, ConflictErrors raised to Zope drop by at least an order of magnitude against ZEO with the same data.

## Naming

ZOE, the Zope Object Engine, is the project name: an anagram of ZEO, a first name, and an acronym in the ZODB/ZEO/ZRS tradition. The stem for every identifier is `zoe`, written ZOE in prose. The PyPI name `ZOE` is held by an abandoned OpenGL toy and the crates.io name `zoe` by an active CDC genomics crate, so the distribution ships as `zoedb` while a PEP 541 transfer of `ZOE` is requested, and no bare `zoe` crate is published.

## Context

The ZODB stack is mostly Python; the C lives in three client-side packages, and the upstream projects have started free-threading work. Line counts are from fresh clones made during the analysis (tests excluded).

| Package | Language | Size | Role | Free-threading status |
| --- | --- | --- | --- | --- |
| [ZODB](https://github.com/zopefoundation/ZODB) | Python | 17.6k lines | Connection, DB, FileStorage, MVCC adapter, 2PC | pure Python; thread model is one Connection per thread |
| [ZEO](https://github.com/zopefoundation/ZEO) 6.3.dev0 | Python + 2 optional Cython modules | 10.3k lines | asyncio client and server, msgpack wire protocol | pure Python |
| [persistent](https://pypi.org/project/persistent/) 6.8 | C + Python reference impl | 4.1k lines C | `Persistent` base class, pickle cache, LRU ring | compiles on 3.14t, cp314t wheels, `Per_dealloc` crash fixed in 6.6; does not declare `Py_mod_gil_not_used` |
| [BTrees](https://github.com/zopefoundation/BTrees) | C templates + Python reference impl | 10.7k lines C, 21 instantiations | persistent containers, bucket conflict resolution | no free-threading work; uses persistent's C capsule |
| [zodbpickle](https://github.com/zopefoundation/zodbpickle) | C (fork of CPython `_pickle.c`) | 7.2k lines | `noload`, `binary` shim for py2 data | compiles on 3.14t; does not declare `Py_mod_gil_not_used` |
| [zope.interface](https://pypi.org/project/zope-interface/) 8.6 | C + Python | — | component architecture | 8.3 declares `Py_mod_gil_not_used`, 8.5 ships cp314t/cp315t wheels; cache races found ([#384](https://github.com/zopefoundation/zope.interface/issues/384)) |

What this means for the design:

- A storage server or in-process storage touches none of the C above. It plugs in through `ZODB.interfaces.IStorage`, the same seam `FileStorage` and `RelStorage` use.
- Any extension loaded on 3.14t without `Py_mod_gil_not_used` silently re-enables the GIL. Today `persistent`, `BTrees` and `zodbpickle` all do, so free-threaded parallelism in Zope needs those three declared before ZOE's own declaration matters.
- `persistent` and `BTrees` ship pure-Python reference implementations with full test suites, which makes a later Rust port of them a differential-testing job rather than a rewrite in the dark.

**Python free-threading timeline.** 3.13 (Oct 2024) experimental; 3.14 (Oct 2025) officially supported under [PEP 779](https://peps.python.org/pep-0779/); 3.15 (Oct 2026) adds the free-threaded stable ABI `abi3t` under [PEP 803](https://peps.python.org/pep-0803). Making it the default is left to a future PEP. PyO3 supports free-threaded builds since 0.23 and assumes modules are thread-safe since 0.28 ([guide](https://pyo3.rs/latest/free-threading.html)).

**Targets.** CPython 3.12, 3.13 and 3.14, with 3.14t as the free-threaded build; 3.13t is not a target and 3.15 joins when it ships. Linux x86-64 and macOS on Apple silicon, and a run on either is evidence (ADR 0038). The release builds for macOS and Windows come later, for the wheels, the server binary and Loupe alike.

**Prior art**

| Project | What it is | What ZOE takes from it |
| --- | --- | --- |
| [byteserver](https://github.com/jimfulton/byteserver) (Jim Fulton, 2016–2021) | 3,043 lines of Rust; synchronous `std::net`, two OS threads per client; implements 10 of ZEO's \~35 server methods; no blobs, pack, undo, `checkCurrentSerialInTransaction` or invalidation replay; data treated as opaque; dependencies frozen in 2016 | the per-OID lock manager at vote time; the append-only segment design; the opaque-data server. Not the code. |
| [filestorage2](https://github.com/jimfulton/filestorage2) (2015–2016) | 11 commits, a format document: aligned segments, `PPPP`→`TTTT` marker flip after fsync, per-segment index, crc32 per record | the crash-safety pattern; candidate for the "fast log" backend |
| RelStorage on PostgreSQL | mature ZODB storage over SQL, history-preserving or history-free, row locks at vote | the `(zoid, tid)` data model; `zodbshootout`, its benchmark harness; the HA story it gets from Postgres operators |
| NEO (Nexedi) | distributed ZODB with replication and master election | proof that a global tid sequencer with replicated storage nodes works; its complexity is the warning |
| ZEO 5 | asyncio client, msgpack protocol, `prefetch`, server-side conflict resolution with Plone eggs installed | the wire protocol and the client, unchanged; the deployment model of "a Python process that hosts the server" |

Jim Fulton said in 2016 that the ZODB API is synchronous and that prefetch is the way to overlap I/O ([talk notes](https://2016.ploneconf.org/maurits.vanrees.org/weblog/archive/2016/10/jim-fulton-the-zodb.html)); by 2019 byteserver had been idle for three years ([thread](https://groups.google.com/g/zodb/c/u_QWRSRR14A)). `Connection.prefetch()` exists in ZODB and `ClientStorage.prefetch()` in ZEO today.

## Architecture overview

One Rust crate implements the storage; two thin skins expose it, in-process and over the ZEO wire. Everything above the storage seam is today's Plone, untouched.

&#91;embedded content: architecture · two deployment modes over one storage core\]

The two grey containers are deployment choices; only the tinted core is new code, and both doors call it the same way.

**Layers, top to bottom**

1. **Plone / Zope, unchanged.** Worker threads, one `ZODB.Connection` and pickle cache each, `persistent` and `BTrees` as they are, `transaction` as it is. Lazy loading stays synchronous.
2. **Storage seam.** In simple mode, `zoe.Storage` implements `IStorage` and friends and is wrapped by ZODB's own `MVCCAdapter`, exactly like `FileStorage`. In clustered mode, the unmodified `ZEO.ClientStorage` talks msgpack to the server.
3. **Server skin (clustered mode only).** A tokio process: one task per client connection, pipelined requests with out-of-order replies, invalidation fan-out, blob streaming, health and metrics. A single static binary: no Python inside, conflict resolution in Rust, the long tail resolved by the client.
4. **Storage core (the crate).** Synchronous, no tokio inside, no Python inside. Transaction coordinator (2PC state machine), per-OID lock manager, conflict detection, resolution dispatch (structural, then field-level by policy, the long tail to the client), pack, blob store, and the `Storage` trait that backends implement.
5. **Durable store.** A backend behind the trait: redb first (embedded, ACID, single writer, MVCC), an append-only log with in-memory index as the speed option, FoundationDB or TiKV for Tier 3. Blobs are files beside the store, or an S3-compatible bucket with a local cache.

**Two modes from one core.** `zoe.Storage(path)` and `zoe serve --path …` open the same directory with the same format: `zoe.redb` (the database), `lock` (the single-writer lock, an exclusive `flock` held while the store is open) and the blob store. A new database is written as `zoe.redb.new`, synced, renamed to `zoe.redb` and the directory synced, so a crash during the creation leaves no store or a complete empty one. Moving from one Zope instance to a cluster is: stop the instance, start the server on the directory, point the instances at it.

**One write, clustered mode**

1. A worker thread changes objects; on commit, `ClientStorage` sends `tpc_begin`, one `storea` per changed pickle, then `vote`.
2. The protocol layer decodes each frame and hands it to the coordinator, which stages the pickles for that transaction in a per-transaction buffer.
3. On `vote`, the lock manager acquires per-OID locks for the written oids in oid order. A second transaction on the same oids queues; transactions on disjoint oids proceed in parallel.
4. For each staged oid whose current serial is newer than the serial the client saw, resolution runs in Rust: a structural merge for BTree buckets, sets and `Length`, then a field-level three-way merge where the merge policy allows it. What neither tier resolves goes back in the vote reply, as ZEO 6 lists a conflict for the client to resolve; the client runs the class's own `_p_resolveConflict` locally, re-stores and votes again, with the locks still held; a class that does not resolve raises `ConflictError` in the client.
5. On `tpc_finish`, the coordinator allocates the tid, writes all records under one backend transaction, fsyncs (group commit coalesces concurrent finishers), releases the locks, acknowledges the client, and broadcasts one invalidation message per other client with the oid list. A lock of an oid that tier 1 merges passes to the vote that waits for it when the finish starts, before the fsync ("The lock hand-off").

**One read.** `loadBefore(oid, tid)` → protocol layer → core → backend range lookup on `(oid, < tid)` → the pickle and its serial, written to the socket without an intermediate copy. In simple mode the same call is a Python method into the core with no wire.

**Where async lives.** In the server skin, and in the crates that talk to a network or to an agent: `zoe-client`, `zoe-bench`, `zoe-mcp` and the server mode of Loupe. The core is synchronous. The extension module `zoe._zoe` links tokio only through `zoe-client`, for the native client of F28, and starts its threads when the first native client opens, never at import (ADR 0035); it never links rmcp. The ZODB side of a client is synchronous; `prefetch` is how a client overlaps I/O, and the server answers prefetched loads out of order on the same connection.

## Storage core

The core is a synchronous Rust library, `zoe-core`, with no Python and no tokio inside; both skins call it. It owns correctness: the data model, 2PC, locking, conflict handling, pack and blobs. Backends own bytes.

**Data model**

| Key space | Key | Value | Notes |
| --- | --- | --- | --- |
| `records` | `(oid: u64, tid: u64)` big-endian, 16 bytes | a record frame, checksum tag 1; its header carries the serial of the previous record, its payload the pickle bytes or their zstd frame, as the codec byte says | one row per object version; a 0-length payload marks a deletion by `deleteObject`; pack removes rows and writes no deletion |
| `txn_oids` | `(tid: u64, oid: u64)` big-endian, 16 bytes | empty, not a frame, so no checksum tag | the transaction index: one key per record, deletions included, written in the same backend transaction as the record; a range scan over one tid gives the oids of that transaction in oid order; the iterator reads the oids of its range only from it; pack removes a key with its record; a store without the table does not open; ADR 0026 |
| `txns` | `tid: u64` big-endian, 8 bytes | a frame, checksum tag 3, whose payload is the status byte, the oid count as a `u64`, then user, description and extension, each with a `u32` length; the oid count and the three lengths are little-endian | the transaction log; status is `committing` until the finish record lands; pack lowers the oid count to the records that remain and removes a row that keeps none |
| `blobs` | `(oid: u64, tid: u64)` big-endian, 16 bytes | a frame, checksum tag 2, with previous serial 0 whose payload is the BLAKE3 hash of the blob file (32 bytes), then the size of the file in bytes as a little-endian `u64` | one row per blob revision, written in the same backend transaction as its record; the file lives in the blob store, at the BushyLayout path of `(oid, tid)`; a store without the table has no blobs |
| `sequences` | the sequence name, UTF-8 text | a frame, checksum tag 5, with codec 0 and previous serial 0 whose payload is the end of the reserved values as a little-endian `u64`: the first value that the store has not reserved; the checksum covers the name | one row per sequence; a reservation writes it in a backend write transaction of its own, durable before any value of the block is given; a restore raises it with `Sequence::restore_end`, which never lowers it; values are reserved in blocks of 100, so each reopen, after a crash or not, skips at most 100 values of a name and never repeats one; the skips of reopens in a row add up, so a caller can see a larger gap; not transactional: an abort keeps its values; pack never touches it; a store without the table has no sequence yet; ADR 0024 |
| `meta` | fixed text keys | `format` (`ZOE format 2`), `last_tid`, `next_oid`, `pack_watermark`, `object_count`; numbers are 8-byte big-endian; not frames, so no checksum tag | one row each; pack writes `pack_watermark`, the tid of the last pack, with its first batch, and a store that was never packed has no such row; `object_count` is the number of distinct oids that have at least one record, a deletion included, in every snapshot: each commit batch and each pack batch updates it in its own backend write, a new store starts at 0, and a store of format 2 without it fails to open with `Format`; a writer open of a store of `ZOE format 1` counts the oids of `records` once and writes the count and the name `ZOE format 2` in one write with a sync, and a read-only open of such a store writes nothing and has no count (ADR 0033) |

`loadBefore(oid, tid)` is a reverse range scan from `(oid, tid - 1)`; `load(oid)` is `loadBefore(oid, MAX)`; `loadSerial` is a point read. This is the RelStorage history-preserving layout, which is what makes MVCC and `history()` free.

**Tids.** A tid is ZODB's 8-byte `TimeStamp`, strictly increasing. The core allocates it at `tpc_finish` under the commit sequencer: `max(now, last_tid + 1 tick)`. Clients may pass a tid only through `restore` (copy and replication paths), never through normal commits: `tpc_begin` with a tid starts a restore transaction, which takes both `store` and `restore`, and its `tpc_finish` commits under that tid. The tid must be after the last tid, both at `tpc_begin` and at `tpc_finish`, and it must not be `MAX`. Otherwise the call is refused, and a refusal at `tpc_finish` does not halt the store. A restore transaction that begins with `Store::tpc_begin_restore_deferred` (or `Txn::begin_restore_deferred`) is a deferred restore: its `tpc_finish` runs the same commit path, the tid check, the locks and the placement of the blobs with all their syncs, but its backend commit has no sync (redb `Durability::None`). The commit is visible to readers and sets the last tid when `tpc_finish` returns; it becomes durable with the next durable commit, which is `Store::sync` or any other finish or batch. A crash loses every deferred commit after the last durable commit, and the store then ends at a whole commit. `Store::sync` is one backend write transaction under the commit sequencer that writes no record, no transaction row and no last tid, committed with a sync; it fails with `ReadOnly` on a read-only store and with `Halted` on a halted store, and its own error halts the store as a failed finish does. Only the converter of `Data.fs` uses deferred restores; `tpc_begin`, `tpc_begin_restore`, `zoe serve`, `zoe.Storage` and `zoe restore` keep a durable finish. A normal commit never gets `MAX`; when no tid below it is left, `tpc_finish` is refused. In Tier 3 the sequencer is one key updated inside the backend transaction (or an FDB versionstamp).

**Two-phase commit, per transaction**

```
Begin ──storea*──▶ Staged ──vote──▶ Locked ──tpc_finish──▶ Durable ──▶ Invalidated
   │                 │                │
   └── tpc_abort ────┴── tpc_abort ───┴── tpc_abort (locks released, staging dropped)
```

- `Staged`: pickles sit in a per-transaction buffer: in memory up to `staging-memory` bytes (default 16 MiB), and beyond it in a spill file of the transaction under `staging/` in the store directory, as byteserver does. A spill file is never durable data: nothing syncs it, the transaction removes it at finish or abort, and a writer open removes the spill files that a crash left. Nothing is visible. A staged record can hold its payload, encoded before the finish on another thread (`Encoded::encode`) and attached with `Txn::set_encoded`; the core attaches it only when the length and the xxh3-64 hash of the pickle and the compression of the store match, and a later store of the oid drops it. The server attaches the payloads of its compression pool this way (see "Connection handling").
- `Locked`: per-OID locks held for every written oid and every oid passed to `checkCurrentSerialInTransaction` (shared lock). Conflict detection and resolution happen here, so a failed vote releases locks before any disk write.
- `Durable`: one backend write transaction holds the records, their keys in the transaction index, the txn row with status `committed`, and the meta update; it is fsynced before the client is acknowledged, except for a deferred restore (see **Tids**), which a later durable commit makes durable. A crash before the fsync leaves nothing; a crash after it leaves a complete transaction. No repair step of ZOE exists because there is nothing half-written to find. After a killed writer, the first writer open repairs the file and can take longer, because redb rebuilds its free-space map (see "Memory and startup").
- `Invalidated`: after acknowledgement, the oid list is pushed to every other client (server skin) or applied to the in-process invalidation queue.

**Lock manager.** A `HashMap<oid, LockState>` with a wait queue per oid, protected by one mutex (contention on the map is negligible against disk time; a sharded map is a later optimisation). Locks are acquired in ascending oid order, so two transactions cannot deadlock on each other; a transaction that must wait releases nothing and queues once. Shared locks (readCurrent) and exclusive locks (writes) follow the usual compatibility matrix. A lock-wait timeout (default 10 s) turns a wait into a `ConflictError`, so a stuck client cannot stall the store.

**Early write-intent locks (extension, ADR 0045).** An intent owner takes exclusive locks before the vote of its transaction, before the transaction reads the oids: `lock_intent(oids)` takes the lock of each oid, in ascending order, and returns the current serial of each one when it holds them all. A competing request on the same oid waits in its queue, as a vote waits, within `lock-timeout`; a longer wait, or the end of the connection, fails it with `ConflictError`, and the call keeps no lock that it took. An intent request never takes a lock hand-off: it waits until the store holds the last commit of the oid, so the serial that it returns is the serial of that commit. Deadlock avoidance: intent locks come in oid order, so a request for an oid at or below an oid that the owner holds fails with `LockOrder` (`StorageTransactionError` for the client) and takes nothing, and the client releases and asks again for the whole set in order. The next transaction of the owner adopts its locks (`Txn::adopt_intents`): the vote counts them as its own, and takes its other locks in oid order. When it must wait for an oid below an intent lock that it holds, it first releases the intent locks above that oid, then takes them again in order, and the serial check catches a commit that came in between. The locks are advisory: the vote still checks every serial, so a dropped intent lock makes nothing wrong. Through `zoe serve`, the session owns them: `lock_intent` and `unlock_intent()` run on the thread of the transaction of the session, from the first `lock_intent`, the next `tpc_begin` adopts them, a session that holds them 60 s without a `tpc_begin` loses them, with one WARN event, and a `tpc_begin` that fails releases them. `zoe_intent_locks_total` and `zoe_intent_lock_wait_seconds` count and time them. In-process mode calls the same core. Section 9 explains how the client uses them, and why this is the one mechanism that avoids conflicts instead of resolving them.

**Conflict resolution dispatch**

1. Detect: for each staged `(oid, serial_seen)`, compare with the current serial; equal means no conflict.
2. Tier 1, structural, in Rust: BTree buckets, sets and `Length` whose keys Rust can order (ints, floats, strings, bytes and tuples of those) merge with the rules of `BTrees._base` and `Length._p_resolveConflict` and are re-encoded by `zoe-pickle`. Object keys that need Python ordering fall through. Built (`zoe_core::merge`, ZOE-203): the vote that takes the locks, in both modes, runs tier 1 on each stale written oid that the client could resolve and whose class, read from the class pickle alone, is a bucket, a set, a BTree or a tree set of a family of BTrees but `fs`, or `BTrees.Length.Length`. The merge follows `bucket_merge` of `MergeTemplate.c` step by step; a BTree or a tree set merges only when it holds one bucket inline, as in BTrees. `zoe_pickle::python` keeps the identity of each object as Python's unpickler gives it and pickles as zodbpickle does with protocol 3, so the merged record is the record of ZODB's resolver, byte for byte, when that resolver imports each class of the record under the name that the record gives (an alias of a module, or a class that it cannot import, gives other bytes there; `crates/zoe-pickle/CLAUDE.md`). A merge is stored over the committed serial under the locks of the vote, and the reply of `vote` gives the oid as a bare oid, as a ZEO 6 server does for a conflict that it resolved; `tpc_vote` of `zoe.Storage` returns it. A refusal of BTrees fails the vote with `ConflictError` at once, without a resolution in the client. Tier 1 never guesses: a comparison that Rust cannot make (values of mixed types, a dict, an int against a float; two lists compare as in Python), a record that does not decode, or a state that holds a construct that the model does not hold, leaves the conflict to the client as before. The posting-dict rule (ADR 0042, off by default) also merges the posting dicts of ZCTextIndex, dicts of int to int in a bucket with integer keys, entry by entry against the old dict, and the first-key rule, under the same key, lets a delete of the first key by the committed transaction through in the bucket that a BTree or a tree set holds inline: the two merges where ZODB's resolver refuses (see "Lever 1").
3. Tier 2, field-level, in Rust: for any persistent object whose class the merge policy marks mergeable, decode the old, committed and new states, compute the two changed-key sets, merge when they are disjoint or agree, and apply the per-field strategies the policy names (`lww`, `sum`, `max`, `union`, `append`, or a named native merge such as an append-only `workflow_history`). Fields the policy marks coupled stay strict.
4. Tier 3, the long tail: classes with their own `_p_resolveConflict` and no policy. The core keeps the locks of the vote and returns the committed states (`vote_resolving`). In server mode, the reply of `vote` lists each such conflict as a ZEO 6 server with `client-conflict-resolution` does: `{oid, serials: [committed, read], data}`, where `data` is the pickle that the client stored. Every stock `ZEO.ClientStorage` accepts this reply, with no negotiation: it loads the read and the committed states with `loadSerial`, runs the method locally, where the class already lives, re-stores the resolved state over the committed serial with `storea` and votes again. The locks stay held between the two votes; a stock ZEO server releases its commit lock there. The second vote takes no lock, checks every serial again, and replies `[]` or fails. A class that does not resolve raises `ConflictError` in the client, which aborts; a client that disconnects between the two votes releases the locks. In-process mode calls the method directly through the `ConflictResolvingStorage` mixin, with the same vote: the storage re-stores the resolved states and votes again. A stale read-current serial is never resolved, nor is a new object, a deletion or a deleted object: the vote fails at once.
5. Unresolved: the vote fails with `ConflictError`, or the client raises it when the class does not resolve. No tier ever runs Python on the server.

The structural merges have a mode, `on`, `shadow` or `off`, for all their classes (`structural-merges`, `on` by default) and for each class (`structural-merge-class CLASS MODE`); `posting-dicts` is the mode of the posting-dict rule and of the first-key rule (`off` by default), and `resolution-log FILE` names the resolution log, a file of JSON lines outside the store, one for each result of tier 1 with the user and the description of both transactions (ADR 0042). The keys are the same in `<zoe>` and in `zoe serve`. In shadow mode, tier 1 writes its result to the log and the conflict goes on as without it, so the client resolves it; the rules of ADR 0042 in shadow mode write their result in the field `shadow` of the line, and the conflict then ends as with the rules off. A shadow mode without `resolution-log` raises `ValueError` at the open in-process, and is a usage error of `zoe serve`. ZOE-205 moves these switches into the merge policy.

The merge policy is a versioned object in the store, so it is transactional and the server reloads it on change. `zoe.plone` generates it from Dexterity schemas (a type whose schema declares no `@invariant` is mergeable field by field; fields named in an invariant are coupled) plus a short overrides file, and Loupe shows and edits it. Shadow mode runs tiers 1 and 2 on every conflict but leaves the outcome of the conflict as without them (the client resolves it or raises), recording what would have been merged by class, tier and field; merging is switched on per class once a production run shows it would have been right, judged by replaying the merged states through the differential suite. Every resolution, merged or raised, is logged with oid, class, tier, the keys merged and both transactions' user and description; built for tier 1 (the resolution log of ADR 0042). Tier 1 and 2 merges are replayed through the Python resolvers in the test suite and must produce identical pickles.

**Pack.** Pack at tid T keeps what a reader at T or later needs; T is the lower of the requested tid and the last tid. It keeps every record after T and, for each object that such a reader can reach, the newest record at or before T, a deletion included; it removes every other record at or before T with its blob record, then its blob file. It removes rows and writes no deletion record. The roots of the mark are the root object and every object that a record after T refers to, so an object that a later record links again stays; from each root the mark follows the newest record at or before T. References come from `zoe-pickle`, which reads the persistent id of every BINPERSID of a record, opaque parts included, as ZODB's `referencesf` does, and never unpickles; weak references and references into another database keep nothing. A reachable record that does not decode fails the pack before it removes anything. Pack runs in batches, in key order, the oldest record of an object first. Each batch is one backend write transaction that removes records with their keys in the transaction index and their blob records, lowers the oid count of their transaction rows and removes a row that keeps no record, so `history` and the iterator stay consistent. Readers never wait. A finish waits for at most one batch: while a pack runs, each finish notes its oids, and before each batch the pack holds the commit sequencer, marks what the noted records refer to and commits the batch, so a record committed during the pack that links an object again keeps it. The first batch writes `pack_watermark`; nothing is undoable past it, and a pack at an earlier tid does nothing. Blob files are deleted after the removal of their blob records is durable: before the commit, an intent file in `blobs/tmp/` names them, so a crash leaves no blob file that the next open does not remove. A client that links an object from a reference read before T can still link an object that a batch removed, as with ZODB's own pack. A failed batch write halts the store as a failed finish does; a record that fails its checksum stops the pack, which never deletes the evidence of a corruption; a read-only store refuses a pack. ADR 0025 records these decisions. `pack` is exposed on both skins and as a CLI (`zoe pack --days 7`). With `pack-gc` false (`Options::pack_gc`, true by default), a pack collects no garbage, as the `pack-gc` of FileStorage and RelStorage does: a site with mount points has references across databases, and a pack that collects garbage in one database can delete an object that another database still uses. Such a pack has no mark and reads no reference, so a record that does not decode does not stop it. It keeps every record after T and, of each object, the newest record at or before T, whether a reader can reach the object or not, except when that record is a deletion: then the object goes, with each of its records at or before T, their blob records and their blob files, as FileStorage's pack without garbage collection does. The batches, the watermark, the intent files of the blob files and the stop between batches stay the same, and a dry run of such a store reports what such a pack removes. `pack-gc` is an option of the open store, not a record of the store, so a store packed both ways stays valid: `zoe.Storage(path, pack_gc=False)`, the key `pack-gc` of `<zoe>`, `zoe serve --pack-gc=false` and the key `pack-gc` of a `[storages.NAME]` table, and `zoe pack --pack-gc=false` (`ZOE_PACK_GC`) set it.

**Blobs.** The blob store is a trait with two implementations: a directory tree beside the store, and an S3-compatible store with a local LRU cache. The directory tree is `blobs/` in ZODB's `BushyLayout`, or the directory of the `blob-dir` option (ADR 0027), so existing tools understand it: `blobs/.layout` holds `bushy`, and the file of `(oid, tid)` is one directory per big-endian byte of the oid, then the tid as ZODB's `tid_repr` writes it, for example `blobs/0x00/0x00/0x00/0x00/0x00/0x00/0x12/0x34/0x03f6db4f24444444.blob`. A committed blob file is read-only and immutable per `(oid, tid)`. `storeBlob` writes into a temp file in `blobs/tmp/`, computes its BLAKE3 hash on the way, and syncs it. `tpc_finish` places the files before the backend commit: it writes and syncs an intent file in `blobs/tmp/` that names the tid and the oids, renames each file into place and syncs its directory. The backend write transaction then holds each blob record (hash and size) next to its record, and the intent file is removed. The intent file of a deferred restore stays in `blobs/tmp/` after its backend commit, until a durable commit covers it: a durable batch or `Store::sync` removes it. So a crash never leaves a blob record without its file, and a lost deferred restore leaves no blob file. A crash can leave a file without its record: the next open reads only `blobs/tmp/`, never the whole tree, and removes the files that an intent file names and that have no blob record. In `blobs/tmp/` a writer open then removes only the files whose names the server owns: `<digits>.tmp`, the intent files, `layout.tmp` and `upload-<digits>`. Every other file stays. With a shared blob directory, `blobs/tmp/` is the `temporaryDirectory()` of each ZEO client, so a restart of the server keeps the uncommitted and savepoint files of the clients; the files of a client that crashed stay, as with ZEO's server. Every read through the core checks the size and the hash at the end of the file; a mismatch is a distinct `CorruptBlob` error with the oid and tid. `loadBlob` returns a path (simple mode) or streams chunks (server mode). ADR 0023 records the blob record and the crash order.

**Undo.** Every `(oid, tid)` record stays until pack, so undoing a transaction T is a read and a write: for each oid in T, the undo transaction stores the state the oid had before T (`loadBefore(oid, T)`), or a delete record when T created it. When the oid's current record is T's, that is the whole job; when later transactions changed it, the write goes through the resolution tiers as a three-way merge, with T's state as the base, the current state as ours and the pre-T state as theirs, and fails with `UndoError` when no tier resolves it. A blob record points at the earlier blob file, immutable per `(oid, tid)`. `undoLog` and `undoInfo` read the transaction index; nothing is undoable past the last pack. In server mode `undoa` queues the undo into the running transaction and `vote` does the work, as ZEO's own server does.

**Record framing: checksums, compression, encryption.** Every record, blob record, transaction row, sequence row and intent file is a frame: a 32-byte little-endian header, then the typed-field slots, then the payload. The header holds the frame version (byte 0), the flags (1), the codec (2), a reserved byte (3), the branch id as a `u32` (4 to 7), the previous serial (8 to 15), the payload length as a `u32` (16 to 19), the length of the typed-field slots as a `u16` (20 and 21), two reserved bytes (22 and 23) and the checksum (24 to 31): xxh3-64 with seed 0 over a one-byte tag of the key space, then the key that the frame is stored under (the 16-byte big-endian `(oid, tid)` key of a record or a blob record, the 8-byte big-endian tid key of a transaction row or an intent file, the UTF-8 name of a sequence row), then bytes 0 to 23, the slots and the payload, so a frame under the wrong key or in the wrong key space fails it. The tags are 1 for `records`, 2 for `blobs`, 3 for `txns`, 4 for the intent files and 5 for `sequences`; 0 is never a tag, 6 is reserved for `vectors`, and a tag never changes and is never reused (ADR 0029). The tag is not stored: a reader checks with the tag of the table or file that it reads. The checksum (xxh3-64, CRC32C on backends that already keep one) is verified on every read and a mismatch surfaces as a distinct `CorruptRecord` error with the oid and tid (`CorruptBlob` with the oid and tid for a blob record, `CorruptTxn` with the tid for a transaction row, `CorruptSequence` with the name for a sequence row), never as a `POSKeyError`. The codec byte says how the payload holds the data: 0 is the data as it is, 1 is one zstd frame that states the data length in its own frame header, and a codec that a build does not know is refused as a newer format. By default, the store writes each record as it is, with codec 0 (the setting `compression` is `none`, ADR 0041). With `zstd`, it compresses each record with zstd at a configured level, 3 when the setting gives none, and keeps the result only when it is smaller than the data; otherwise it writes the data as it is with codec 0. Transaction rows, blob records and intent files use codec 0. A store reads every codec whatever its own setting, so the setting can change between opens. The payload length in the header and the checksum cover the stored bytes, so a read verifies them before it decompresses. Decompression is bounded: the zstd payload is exactly one standard zstd frame (its magic number is checked, so no skippable or legacy frame passes), the length that it states is at least 1 (empty data marks a deletion, so it is never compressed) and at most `u32::MAX` and at most 32,768 times the stored length (a zstd writer puts at most 128 KiB in a block of at least 4 bytes; libzstd accepts larger blocks, so the reader enforces this ratio itself), and it must decode to exactly that length; any other payload is a `CorruptRecord`. A later codec adds a dictionary trained on a sample of the store's own records, kept in the store header and versioned, so a pickle-heavy Plone store shrinks three to five times and the page cache holds proportionally more objects. With encryption on, the frame is sealed with AES-256-GCM under a per-store data key, itself wrapped by a key from a file, the environment or a KMS; the tid and oid are the nonce material, so no two records share a nonce. `zoe scrub` reads every frame at low priority, in the background or on a schedule, and reports mismatches to the metrics and the admin log; Loupe's integrity screen shows the last scrub.

**Forks.** A fork is an overlay store: reads fall through to the base at a fixed tid, writes land in the overlay, and the overlay has its own tids, pack and blobs. `zoe fork base sandbox --at <tid>` opens one without copying the base; discarding it is deleting a directory. It is ZODB's `DemoStorage` done natively, so `plone.app.testing` layers stack forks instead of DemoStorages, an upgrade is rehearsed on a fork of a production copy before it touches the real store, and Loupe opens a fork as it opens any store. A fork is never merged back; what is kept is reapplied as a normal transaction.

**Pack safety.** `zoe pack --dry-run` prints what a pack would remove, by class and by size, without touching the store. A pack never deletes at once: removed records move into a retention window (`pack-retention`, a number of days) during which `zoe pack --revert` restores them, and physical deletion happens when the window closes. Pack is incremental by default, a bounded slice of oids per step interleaved with normal traffic, so there is no pack weekend; a full pack remains available for migrations. Until the retention window and incremental pack ship in phase 7, a pack removes records at once and every pack is a full pack.

**Guardrails.** `max-record-size`, `max-transaction-size` and `max-blob-size` refuse a `store` with a clear error before anything is written; a lock held longer than `lock-warn` and a transaction open longer than `transaction-warn` are logged with their oid, client and duration, and counted in the metrics (the log lines are built; the counters in the metrics are not built yet). The record size is the length of the pickle, the transaction size is the sum of the pickles of the transaction, and the blob size is the length of the blob file; blob bytes do not count toward the transaction size. A size equal to a limit passes, and no limit is set by default. A restore transaction checks no size limit, blobs included, so a copy such as `zodbconvert` never refuses what its source took. Over the wire, `--max-frame-size` of `zoe serve` (256 MiB by default) also bounds one record, because a `storea` or `restorea` frame holds it whole: a copy through the server needs a limit above the largest record of its source. The error is `TooLarge`, which names the configuration key of the limit and holds no pickle bytes.

**The storage trait**

```rust
pub trait Backend: Send + Sync {
    fn load_before(&self, oid: Oid, tid: Tid) -> Result<Option<Record>>;
    fn load_serial(&self, oid: Oid, tid: Tid) -> Result<Option<Bytes>>;
    fn load_blob(&self, oid: Oid, tid: Tid) -> Result<Option<BlobRecord>>;
    fn last_tid(&self) -> Tid;
    fn begin_write(&self) -> Result<WriteTxn<'_>>;      // one per tpc_finish or pack batch
    fn iter_txns(&self, from: Tid, to: Tid) -> TxnIter<'_>;                                // reads the rows as it goes, from one snapshot
    fn history(&self, oid: Oid, limit: usize) -> Result<Vec<RecordMeta>>;
    fn load_before_next(&self, oid: Oid, tid: Tid) -> Result<(Option<Record>, Option<Tid>)>; // loadBefore and the next serial, one snapshot
    fn txn_oids(&self, from: Tid, to: Tid) -> Result<BTreeMap<Tid, Vec<Oid>>>;              // the oids of each transaction of a range
    fn indexed_tids(&self, from: Tid, to: Tid, limit: usize) -> Result<Vec<Tid>>;           // a slice of the tids of the index, for the iterator
    fn current_from(&self, from: Oid) -> Result<Option<(Oid, Record)>>;                     // the current record of the first oid ≥ from
    fn pack(&self, before: Tid, reachable: &dyn Fn(Oid, Tid) -> bool) -> Result<PackStats>; // not used: pack goes through the methods below
    fn pack_watermark(&self) -> Result<Tid>;                                                 // the tid of the last pack, 0 before the first
    fn record_keys(&self, from: Oid, limit: usize) -> Result<Vec<(Oid, Tid)>>;              // the record keys of whole oids from `from`, for the pack scan
    fn txn_records(&self, tid: Tid) -> Result<Option<TxnRecords>>;                          // a transaction row, its index keys and their records, one snapshot
    fn sync(&self) -> Result<()>;                         // fsync barrier: makes deferred commits durable; Store::sync calls it
    fn sequence_end(&self, name: &str) -> Result<Option<u64>>;                               // the first value that the sequence has not reserved
    fn sequence_names(&self) -> Result<Vec<String>>;                                         // the names of the sequences that have a row
}

pub trait WriteTxn {
    fn put_record(&mut self, oid: Oid, tid: Tid, prev: Tid, data: &[u8]) -> Result<()>;
    fn put_blob(&mut self, oid: Oid, tid: Tid, blob: &BlobRecord) -> Result<()>;
    fn put_txn(&mut self, meta: &TxnMeta) -> Result<()>;
    fn remove_record(&mut self, oid: Oid, tid: Tid) -> Result<()>;  // pack
    fn remove_blob(&mut self, oid: Oid, tid: Tid) -> Result<()>;    // pack
    fn replace_txn(&mut self, meta: &TxnMeta) -> Result<()>;        // pack: a lower oid count, the last tid unchanged
    fn remove_txn(&mut self, tid: Tid) -> Result<()>;               // pack: a row that keeps no record
    fn put_pack_watermark(&mut self, tid: Tid) -> Result<()>;       // pack
    fn put_sequence_end(&mut self, name: &str, end: u64) -> Result<()>; // a sequence reservation, alone in its write transaction
    fn commit(self) -> Result<()>;                        // durable on return
    fn commit_deferred(self) -> Result<()> { self.commit() } // visible on return, durable with the next commit
}
```

The core, not the backend, implements locking, 2PC, resolution, invalidations and blobs, so a backend is a few hundred lines.

**Backends**

| Backend | When | Durability | Trade-off |
| --- | --- | --- | --- |
| redb (embedded, pure Rust, MVCC, single writer) | first release, both modes | ACID per write transaction, fsync on commit | copy-on-write B-tree: write amplification; simplest to get right |
| append-only log + in-memory oid→offset index (filestorage2 design) | when `zodbshootout` shows redb's write path is the bottleneck | sequential appends, one fsync per group, marker flip | custom format: own backup, verify and index-rebuild tools |
| FoundationDB or TiKV | Tier 3 | replicated before acknowledgement | network hop per operation; FDB caps a transaction at 5 s and 10 MB, so large commits stage locally and write in one short transaction |

**The database file.** The core opens the redb file through its `Vfs`. On a disk (`OsVfs`), the file holds the page writes that redb makes for a commit, and makes them before the sync, in the order of their offsets, each run of adjacent pages as one write; a read, a change of the length and the close make them first too, so the sync makes durable the same bytes as before. A growth of the file of at most 64 MiB gets zeros, so a commit that later writes into the new space syncs no allocation of blocks; redb doubles the file up to 4 GiB, so a store gets them while it is small. The zeros move a cost and do not remove it: the sync after a growth writes them, up to 64 MiB once. The gain of 2.6 ms to 1.0 ms for the finish of a commit of a young store was measured on APFS (macOS); ext4 and XFS are not measured. On macOS, a sync is `fsync(2)`, as for FileStorage, and not `F_FULLFSYNC`: macOS is a platform for development (ADR 0038, ADR 0040). On Linux, a sync is `fdatasync` for the database file and `fsync` for the other files and the directories.

**Group commit.** `tpc_finish` calls join a commit batch; the batch leader writes all members under one backend transaction, fsyncs once, and wakes every member. The leader writes an attached payload into its frame as it is (`WriteTxn::put_payloads`) and encodes inline only the records without one, so the frames are the same either way and an attached payload takes its compression out of the batch. A batch whose members are all deferred restores commits with `WriteTxn::commit_deferred`, without the fsync and without a call of `Observer::batch_synced`; a batch with any other member fsyncs, which makes the deferred commits before it durable too. A finish that waits for the end of a batch waits on a waiter of the store clock, so the simulator runs other threads meanwhile. On a 10 ms fsync device this is the difference between 100 and several thousand commits per second.

**The lock hand-off (ADR 0044).** A lock passes from a commit whose finish started to the vote that merges onto it, and the merge commits after it. Once its member is in the queue of group commit, a finish cannot abort, and its staged records are the records that its batch writes. So it hands the lock of each oid that it writes, of a class that tier 1 merges in mode `on`, to the exclusive vote at the head of the queue of the oid, with a copy of its staged record. That vote merges onto the copy at once. A refusal fails it at once. When tier 1 does not decide, the vote keeps the lock and waits until the commit of the holder is durable, within `lock-timeout`, then goes on as without the hand-off, so the client resolves the conflict against the committed record. The finish of the new owner starts after the finish of the holder, so its commit is in the batch of the holder after it, or in a later batch, and the batch writes the tid of the holder as the previous serial of the merged record. A failed write or sync halts the store, so no commit is durable before the commit that it merged onto, and an acknowledged commit stays durable (N1). The lock table keeps the hand-off until the store holds the last commit of the oid: until then, a new owner that aborts or fails passes the lock with the same hand-off to the next exclusive vote, and a shared request (`readCurrent`) waits, so no vote reads a state that the store does not hold. The commits of a hot `Length` then share a batch: A, then B merged onto A, then C merged onto B, each one taking the lock when the finish before it starts. `zoe_lock_handoffs_total` counts the hand-offs. A restore never hands off a lock, and a commit that writes no hot object takes the same path as before.

## In-process mode

`zoe.Storage` is a PyO3 extension class that implements ZODB's storage interfaces directly over the core, so one Zope instance runs without any server, the way it runs on `FileStorage` today.

ZODB 5 wraps any storage that does not implement `IMVCCStorage` in `ZODB.mvccadapter.MVCCAdapter`, which builds per-connection snapshots from `loadBefore`. ZOE relies on that rather than implementing MVCC twice; `IMVCCStorage` is a later optimisation if profiling shows the adapter in the way.

**Opening.** `zoe.Storage(path, *, read_only=False, lock_timeout=None, blob_dir=None, pack_gc=True)` opens the store in the directory `path` and creates the directory when it is missing. `pack_gc=False` packs without garbage collection (see "Pack"); the core takes it as `Options::pack_gc`, and the store does not record it. `lock_timeout` is the lock-wait timeout in seconds; `None` keeps the default of the store. `blob_dir` is the blob directory, `path/blobs` when it is `None`; the core takes it as `Options::blob_dir` (ADR 0027). The store does not record its blob directory, so each open gives the same one: a store with blobs refuses a blob directory without a layout file with `StorageError`, because the option is missing or wrong or the directory is not mounted. A `blob_dir` that is not a directory raises `OSError` before anything is created. A blob directory without a layout file that holds other files, or that another open store holds, raises `StorageError` and keeps its files. A read-only storage refuses `tpc_begin`, `new_oid`, `store`, `deleteObject`, `pack`, `restore`, `storeBlob`, `restoreBlob` and `temporaryDirectory` with `ReadOnlyError`, and a missing directory, or a missing parent of `blob_dir`, with `FileNotFoundError`: it creates nothing. It does not use the read-only open of the core yet: it opens the store for writes and takes the exclusive lock, so it also upgrades a store of `ZOE format 1` to `ZOE format 2` (ADR 0033). `close` aborts the open transactions, and the storage then refuses every call, a `tpc_begin` that races the close included; a call in progress keeps the store open until it returns. `zoe.Storage` is `zoe.storage.Storage`, a Python subclass of the extension class `zoe._zoe.Storage` and of ZODB's `ConflictResolvingStorage` that declares `IStorage`, `IBlobStorage`, `IStorageIteration`, `IStorageCurrentRecordIteration`, `IBlobStorageRestoreable` and `IExternalGC`, and adds `tpc_vote` with the conflict resolution, `history`, `iterator`, `copyTransactionsFrom`, `pack`, `registerDB` and `supportsUndo`. `import zoe` does not import ZODB: `zoe.Storage` loads `zoe.storage` at first use.

**Thread model.** `Storage` is thread-safe and shared by all Connections of a process. Per-connection state lives in ZODB; per-transaction state is a core transaction in a table of the storage, keyed by the identity of the ZODB transaction object. A second `tpc_begin` of the same transaction, or a call with a transaction that the storage did not begin, raises `StorageTransactionError`; `tpc_abort` of an unknown transaction does nothing. The thread that calls `tpc_begin` drives the transaction: `store`, `deleteObject`, `restore`, `storeBlob`, `checkCurrentSerialInTransaction` and `tpc_vote` from another thread raise `zoe.WrongThread`, a subclass of `StorageTransactionError`, and change nothing. `tpc_finish` and `tpc_abort` may run on any thread, as ZODB's own `BasicStorage.test_tid_ordering_w_commit` does. On a free-threaded build, two worker threads can be inside `tpc_finish` at the same time; the core's lock manager and group commit sort them out. No mutex of the core or of the extension is held while Python code runs. The per-OID locks of a vote are not mutexes: they stay held while `_p_resolveConflict` runs, until the second vote ends, the transaction aborts or the storage closes. The module declares `Py_mod_gil_not_used` (PyO3 0.28 default), so loading it does not re-enable the GIL.

**Commit publication.** The core makes a commit durable and visible before `tpc_finish` calls its callback, which hands the invalidations to the other Connections. A commit is published when its callback has run, and `lastTransaction` gives only a published tid: it waits for the callback of the last commit, so a Connection never starts a snapshot after a commit whose invalidations it did not get. Callbacks run in commit order: the core gives each commit the tid of the commit before it, and a commit waits until that one is published. A callback that calls `lastTransaction` gets the tid before its own commit. A callback cannot commit in its own storage, because that commit would wait for the callback: its `tpc_finish` raises `StorageTransactionError` and commits nothing.

**Stop by a signal.** Zope and waitress install no handler of SIGTERM or SIGHUP, so without help the default action ends the process before Python finalizes, and each stop of an instance leaves its stores unclean for a read-only open. So when `zoe.Storage` opens a store, read-only too, the extension installs a handler of SIGTERM and one of SIGHUP, each only when `signal.getsignal` gives `signal.SIG_DFL` for that signal and the extension has no handler of it yet. An ignored signal, as `nohup` sets SIGHUP, and a handler of the application keep their action; a handler that the application sets later replaces the handler of the extension, which never comes back. The handler only wakes the watcher thread of the extension, one per process, which runs no Python code and takes no GIL. The watcher closes each open storage of the process as `close` does: the storage refuses each later call, the transactions that no call uses abort, and when no call holds the store, the watcher drops it, so the database closes cleanly and Loupe, `zoe mcp` and `zoe verify` open it with no repair. A `tpc_finish` whose commit started before the signal commits, durably. The wait lasts at most 5 seconds from the signal for all the storages together; a store that a call still holds then, such as a running pack, stays open, and the others close. Then the watcher restores the default action of the signal and raises it again, so the process ends with the status of the signal, -15 or -1, also when no storage is open. A child of `os.fork()` has no watcher: an at-fork hook gives it the default action back where Python sees `SIG_DFL`. SIGINT needs no handler, because `KeyboardInterrupt` ends the interpreter, whose drop closes the store. ADR 0031 records the design.

**Errors.** Core errors arrive as the exceptions of ZODB: `NotFound` as `POSKeyError(oid)`; `Conflict` as `ConflictError` and `ReadConflict` as `ReadConflictError`, both with `oid` and, for a stale serial, `serials == (current, read)` (a lock-wait timeout gives no serials); a `ConflictError` on a stored object also gets the stored pickle as `data`, from which ZODB reads the class name; a conflict that `_p_resolveConflict` does not resolve raises the `ConflictError` of `tryToResolveConflict`, which also gives `class_name`, and the failed vote releases its locks; `Protocol` and `LockOrder` as `StorageTransactionError`; `WrongThread` as `zoe.WrongThread`; `Halted`, `CorruptRecord`, `CorruptTxn` and `Backend` as `StorageSystemError`; `Locked`, `Closed`, `Format`, `TooLarge` and a call on a closed storage as `StorageError`; `Io` as `OSError`.

| `early-lock-classes` | `ZOE_EARLY_LOCK_CLASSES` | the hot classes of `early-locks`, each as `module.name`, separated by spaces or commas; each must be a leaf record, whose state refers to no other persistent object; a class of tier 1 raises `ValueError` | none: `early-locks on` takes no lock |
| `read-only` | `ZOE_READ_ONLY` | a boolean, as in `<filestorage>` | `false` |
| `pack-gc` | `ZOE_PACK_GC` | a boolean, as in `<filestorage>`: `false` packs without garbage collection (see "Pack") | `true` |
| `compression` | `ZOE_COMPRESSION` | the compression of the records that the store writes: `none`, `zstd` or `zstd:LEVEL`, as `--compression` of `zoe serve`; a store reads every compression, so the key can change between opens; another value raises `ValueError` | `none` |
| `structural-merges` | `ZOE_STRUCTURAL_MERGES` | the mode of the structural merges (tier 1) of each class that `structural-merge-class` does not name: `on`, `shadow` or `off` (ADR 0042) | `on` |
| `structural-merge-class` | `ZOE_STRUCTURAL_MERGE_CLASSES` | the mode of one class, as `CLASS MODE`, such as `BTrees.IOBTree.IOBucket shadow`; the key comes once for each class, and the twin takes `CLASS=MODE` pairs separated by commas | none |
| `posting-dicts` | `ZOE_POSTING_DICTS` | the mode of the posting-dict rule and the first-key rule of ADR 0042: `on`, `shadow` or `off` | `off` |
| `resolution-log` | `ZOE_RESOLUTION_LOG` | a file of JSON lines, one for each result of tier 1, opened in append mode and never synced; a leading `~` is the home directory | none: no line is written |

A key of the stanza wins over its twin: the twin gives the value only when the stanza does not set the key, with the same syntax. An empty value of any key counts as not set, so the key takes its twin, then its default.

With the `uri` extra, `zoedb[uri]`, the same storage is reachable through `zodburi` as `zoe:///var/zoe?backend=redb` for scripts, `zodbverify` and `zodbconvert`. The path of the URI is `path`, and it is absolute. The query takes the other keys of the table, with the same names and values, each at most once but `structural-merge-class`, which comes once for each class, and the URI does not read the twins. The query also takes the database keys of zodburi, such as `database_name` and `connection_cache_size`; zodburi refuses any other key.

In a buildout, `plone.recipe.zope2instance` knows only filestorage, ZEO client and RelStorage, so an instance part points `zope-conf-template` at a template carrying the stanza above; the Plone extra ships that template, and a `zoe` option for the recipe is a later contribution upstream.

**Migration from `Data.fs`**

1. `zodbconvert` from `<filestorage>` to `<zoe>`: uses `iterator` on the source and `restore` on the target; tids, oids and pickles are copied unchanged, blobs are copied by `restoreBlob`.
2. Verify with `zodbverify` on the new store, then compare `lastTransaction()` and a random sample of `loadSerial` results between the two.
3. Swap the stanza, start the instance.
4. The reverse direction works the same way, which is the exit path if something goes wrong.

**What the instance gains without a server.** No wire, so a cache miss costs a redb lookup and an unpickle. With free-threaded Zope, commits on disjoint objects run in parallel inside one process; today a single instance on `FileStorage` serialises every commit behind one lock.

## Server mode

`zoe serve` runs a tokio server that speaks ZEO's msgpack protocol so that `ZEO.ClientStorage` connects unchanged; it replaces `runzeo`, not the client.

**Command line.** `zoe serve --path STORE --listen HOST:PORT` serves one store under the storage name `1`, the default of ZEO; the options have the twins `ZOE_PATH` and `ZOE_LISTEN`, and `--listen` defaults to `127.0.0.1:8100`. `--listen PATH` listens on a unix domain socket, as the `address` of the `<zeo>` section of ZEO can be a path: a value of `--listen` (of `ZOE_LISTEN`, and of the key `listen` of the configuration file and of `<zoe-server>`) that holds a `/` is the path of a unix domain socket, and any other value is `HOST:PORT`. The server binds the path as it is, so a relative path is relative to its current directory, and the limit of 108 bytes of a socket address applies to the path as given. At its start, it connects to a socket file at the path: when a process accepts the connection, the start fails with 1, names the path and leaves the file; otherwise the file is stale, and the server removes it, as runzeo does. A path that exists and is not a socket fails the start with 1 and stays. At a stop by SIGTERM or SIGINT, and when a later step of the start fails, the server removes its socket file, but only when the file at the path is still the socket that it bound. The line on stdout is then `listening PATH`. TLS does not apply to a unix domain socket: `--tls-cert` with a path for `--listen` is a usage error that names both options. The log lines name a client on a socket `PATH pid PID`, with the process id that the kernel gives for the peer (`SO_PEERCRED`), or `PATH` without it; the metrics have no label of a client. The idle timeout, the stop and the limits of a connection apply on a socket as on TCP, and so does the lingering close: on a socket, the send queue holds the bytes that the client did not read. A stock `ZEO.ClientStorage` connects with the path as its address. `--storage NAME=PATH` (`ZOE_STORAGE`, which gives one store) adds a store under the storage name `NAME` and repeats, and `--config FILE` (`ZOE_CONFIG`) reads the configuration file below; one store at least is necessary, and a storage name that comes twice, `1` from `--path` and from `--storage` too, is a usage error. `--invalidation-queue-size` (`ZOE_INVALIDATION_QUEUE_SIZE`, 100,000 transactions by default) bounds the gap that `getInvalidations` covers, and `--client-queue-size` (`ZOE_CLIENT_QUEUE_SIZE`, 1,000 messages by default, at least 1) bounds the hub queue of one client, the invalidations and the frames of its commits that wait for it (see "Invalidations"); it does not set the session queue of a connection, which holds 4 replies. A store that does not exist is created, except a read-only store, which must exist. `--admin-listen HOST:PORT` (`ZOE_ADMIN_LISTEN`, the key `admin-listen` of the configuration file) opens the admin port, an HTTP port for the probes (see "Health, metrics, shutdown"); without it, the server opens no admin port. stdout carries only the lines `admin <address>` and `listening <address>`; the server writes `listening` once it accepts connections, and `admin` just before it when it has an admin port, so a port of 0 gives a free port, and the logs go to stderr. The listening TCP socket takes `SO_REUSEADDR`, so a restarted server binds the same port at once. The server announces `M5` and takes only `M5`. `--max-frame-size` (`ZOE_MAX_FRAME_SIZE`) is the longest frame that a client can send, 256 MiB by default: a `storea` or `restorea` frame holds a whole record, so the default stays far above the 16 MiB at which ZODB warns about a large record, and above a blob chunk. A copy through the server, as `zodbconvert` to a ZEO client does, fails on a record of its source that is longer than the limit, so such a copy needs a larger limit. `--shutdown-timeout` (`ZOE_SHUTDOWN_TIMEOUT`, 30 seconds by default, in whole seconds with the syntax of `--lock-timeout`) bounds the stop on SIGTERM or SIGINT (see "Health, metrics, shutdown"). `--idle-timeout` (`ZOE_IDLE_TIMEOUT`, 300 seconds by default, in whole seconds with the syntax of `--lock-timeout`; 0 turns it off) closes a connection that sends no frame for that time while no call of the connection runs (requirement N20, see "End of a connection"). The time counts from the last whole frame, so one frame that takes longer than the timeout to arrive is cut. `--read-only` (`ZOE_READ_ONLY`, a boolean, `false` by default) serves every store for reads only (see "Modes"). `--pack-gc` (`ZOE_PACK_GC`, a boolean, `true` by default, the top-level key `pack-gc` of the configuration file) gives `pack-gc` to every store: `--pack-gc=false` packs every store without garbage collection (see "Pack"), and the key `pack-gc = false` of a `[storages.NAME]` table packs one store so; a store packs with garbage collection only when both are true (`ServeOptions::pack_gc` and `StorageOptions::pack_gc` in Rust). `--cache-size` (`ZOE_CACHE_SIZE`, the key `cache-size` of the configuration file) is the most bytes that the page cache of each store holds, as a whole number with the suffix `KB`, `MB` or `GB` (powers of 1024, as ZConfig's `byte-size`) or none for bytes; the default is the default of the store, 1 GiB (see "Memory and startup"). `--compression` (`ZOE_COMPRESSION`, the key `compression` of the configuration file) is the compression of the records that each store writes: `none`, `zstd` or `zstd:LEVEL`; the default is the default of the store, `none` (see "Record framing"), and a store reads every compression, whatever this option. `tpc_finish` replies only after the commit is durable, so a SIGKILL at any point loses no acknowledged commit. `--blocking-threads` (`ZOE_BLOCKING_THREADS`, the number of cores by default, at least 1) is the number of threads of the read pool, which runs the calls that read for all the connections together (see "Connection handling"). The extension of `tpc_begin` comes as a msgpack map: an empty map stores empty extension bytes, and another map stores its pickle in protocol 3, as `zoe.Storage` stores `extension_bytes`. The console script of the wheel has no server: `zoe serve` there fails with 1 and names the `zoe` binary. `zoe_server::serve::Server` runs the same server in the process of a Rust test, and `zoe.testing.ZoeServer` runs the binary for a Python test.

**Process shape.** The server is a single static binary with no Python inside and no Plone eggs beside it: conflict resolution runs in Rust (section 5) and the long tail is resolved by the client. `zoe serve` is the only entry point, and the same binary is the Tier 3 front.

**Memory and startup (N6, N7).** The open of a store reads the free-space map of redb, about 128 bytes for each MB of the file, then a fixed number of pages: the format, the transaction index table, the last tid, the last transaction row and the next oid. It rebuilds no index. So `zoe serve` writes `listening`, and `/readyz` gives 200, soon after its start on a store of any size. N7 holds after a clean close. After a killed writer, the first writer open repairs the file and can take longer: redb rebuilds the free-space map of the database, and that reads every page of the file. The first read-only open of a tool repairs the file the same way, and takes as long (ADR 0032). The resident memory of the server depends on its configuration and its clients; the size of its stores adds only the free-space map of redb, about 128 bytes for each MB of the file. The resident memory is at most the sum of these terms:

- the page cache of each store, at most `cache-size` bytes: the pages that the reads keep and the pages that a write buffers;
- the held writes of the database file of each store, at most 64 MiB: the page writes of a commit until its sync (see "The database file");
- the threads: the runtime threads, one for each core, and the blocking threads: the compression pool runs at most one job for each core at once, the read pool runs at most `blocking-threads` calls at once, and each connection holds at most 5 more threads, the thread of its transaction and 4 calls that run, downloads and packs included (see "Connection handling"). All the blocking threads come from the 512 threads of the blocking pool of tokio, each with a stack of at most 2 MiB;
- the client queues: for each connection, at most 5 decoded calls, the 4 that took a slot and the 1 that the reader holds, each from a frame of at most `max-frame-size` (see "Wire contract"), the session queue of 4 replies, and the hub queue of at most `client-queue-size` frames; the replies and the hub frames have no bound in bytes;
- the staging memory: for each open transaction, at most `staging-memory` bytes of pickles (16 MiB, the default of the store), and the index of its oids; the compression pool holds a copy of a pickle in memory until its job runs, and its payload until the vote, only for a pickle that the transaction keeps in memory, so at most `staging-memory` bytes more of each kind: about three times `staging-memory` for one transaction in all;
- the free-space map of each store, which redb keeps in memory: about 128 bytes for each MB of the file, so about 13 MB for a file of 100 GB;
- the base of the process: the binary, the runtime, the hubs and the open iterators of each connection.

Only the page cache fills up with the reads of a large store, and only the free-space map grows with the size of the file; the other terms grow with the clients and their transactions. `crates/zoe-server/tests/large_store.rs` checks both requirements: it reads a store larger than the bound at random from 16 clients and checks the peak resident memory of the server. Its defaults are small, so that `just test` runs it; the reference machine runs it with a store of 100 GB, a cache of 1 GB and a bound of 2 GB.

**Named storages.** One process serves any number of stores, as ZEO does: `zoe serve --storage main=/var/zoe/main --storage catalog=/var/zoe/catalog`, or a `[storages]` table in the config, and the client's `register(storage_id, read_only)` selects one. Each store has its own path or backend, blob store, lock manager, pack schedule, read-only flag, quotas and a `storage` label on every metric and log line; commits on different stores never wait for each other. Plone mount points therefore work unchanged: one `<zeoclient>` per mount, same server. In-process mode is the same thing with one `<zoe>` stanza per mount. Built so far: the path, the blob directory, the lock manager, the invalidations, the status and the read-only flag of each store (see "Modes"); `register` with a name that the server does not serve fails with ZEO's `ValueError`, and `ruok` gives the status of every store. The quotas and the metric labels come later.

**Configuration file.** `--config FILE` (`ZOE_CONFIG`) reads a TOML file. Its top-level keys are the options of `zoe serve` without `--`, except `config` and `storage`, each with a string, an integer or a boolean in the syntax of its option. Each `[storages.NAME]` table adds a store under the storage name `NAME`, with the keys `path` (necessary), `blob-dir` (the blob directory, `<path>/blobs` by default), `read-only` (`true` serves that store for reads only, see "Modes"; `false` by default) and `pack-gc` (`false` packs that store without garbage collection, see "Pack"; `true` by default). The top-level key `read-only` serves every store for reads only, as `--read-only` does:

```toml
listen = "0.0.0.0:8100"
lock-timeout = "10s"

[storages.main]
path = "/var/zoe/main"

[storages.catalog]
path = "/var/zoe/catalog"
blob-dir = "/var/zoe/catalog-blobs"
```

An option on the command line wins over its twin, and both win over the file. The stores of the file add to the stores of `--path` and `--storage`, and a relative path is taken from the working directory, as on the command line. A file that does not read or does not parse, an unknown key, a value of the wrong type, a store without a path and a storage name that comes twice are usage errors (exit code 2): the command reads the file before it opens anything, so it creates nothing.

**The `<zoe-server>` section.** Buildout users configure the server in ZConfig too. `python -m zoe.serve -C FILE` reads the `<zoe-server>` section of the file, which `%import zoe` declares, and runs `zoe serve` with its settings:

```
%import zoe
<zoe-server>
  listen 0.0.0.0:8100
  lock-timeout 10s
  <storage main>
    path /var/zoe/main
  </storage>
  <storage catalog>
    path /var/zoe/catalog
    blob-dir /var/zoe/catalog-blobs
  </storage>
</zoe-server>
```

The keys of the section are the top-level keys of the configuration file, with the syntax of their options, and `binary`. Each `<storage NAME>` subsection is a `[storages.NAME]` table, with the keys `path` (necessary), `blob-dir`, `read-only` and `pack-gc`; ZConfig gives the name of a section in lower case, as for `runzeo`. A leading `~` in `path`, `blob-dir`, `tls-cert`, `tls-key`, `tls-client-ca` and `tls-read-only-client-ca` is the home directory. The section wins over the twins, as the `<zoe>` section does: `zoe.serve` removes from the environment of the server the twin of each key that the section sets, and an empty value counts as not set. The wheel ships no server, because the extension is built without the server (the feature `serve` of `zoe-server`): the binary is the key `binary`, else `ZOE_BINARY`, else the `zoe` binary on the PATH, and the search on the PATH skips a script, such as the console script `zoe` of the wheel. `zoe.serve` writes the settings as a configuration file into a file that has no name on disk, and replaces itself with `zoe serve` on that file (`execve`). On Linux, the file is a memory file (`memfd_create`), and the command is `zoe serve --config /proc/self/fd/N`. macOS has no memory file: there, the file is a temporary file of mode 0600 in a private temporary directory, whose name and directory `zoe.serve` removes at once, and the command is `zoe serve --config /dev/fd/N`. An open of `/dev/fd/N` on macOS shares the offset of the descriptor. So `zoe.serve` sets the offset to 0 before the `execve`, and `zoe serve` reads its configuration file once. So no Python stays in the process of the server, a supervisor stops it with SIGTERM, and no value of the section goes into the arguments of the process. An unknown key, a bad boolean, a storage without a path and a storage name that comes twice are usage errors (exit code 2) before anything starts; `zoe serve` checks the other values and refuses a bad one with 2 too. A missing binary exits with 1. ADR 0028 records the choice.

**Modes.** `--read-only` serves reads and refuses `tpc_begin` with ZEO's `ReadOnlyError`. Built so far: `--read-only` (`ZOE_READ_ONLY`, the top-level key `read-only`) makes every store read-only, and `read-only = true` in a `[storages.NAME]` table makes one store read-only (`ServeOptions::read_only` and `StorageOptions::read_only` in Rust). The server opens a read-only store with the repairing read-only open of the core (`Store::open_read_only_repairing`, ADR 0032): the store must exist, the server changes no byte of a store that was closed cleanly, and it holds the lock of the store, so no writer opens the store while the server runs. The open takes the blob directory of the store, the `blob-dir` of its `[storages.NAME]` table, and the server checks it as `zoe verify` does: a store with blobs whose blob directory has no layout file does not start, and the message names that directory. A read-only store that a killed writer left open gets its repair first, under its lock: redb repairs the database file through an open for writes, and the server writes only `zoe.redb`. The server then logs one WARN line that names the storage and holds `repaired the store`, for example `/srv/store: the store was not closed cleanly: repaired the store`. When the repair cannot write the file, as on a read-only file system, the start fails with 1 and a message that says that the store was not closed cleanly and gives the error of the system (`RepairFailed`), and the store does not change. `register(storage_id, false)` on a read-only store fails with `ReadOnlyError` and the connection stays open, so a client with `read_only_fallback` registers again read-only, and a client without it does not connect. On a read-only store, `tpc_begin` fails the vote with `ReadOnlyError`, `new_oids` and `pack` fail at once with `ReadOnlyError`, and the reads work as on another store. A follower being promoted serves read-only until it holds the lease, so reads continue through a failover (ZEO's `read_only_fallback` on the client side works as today). Maintenance mode (`zoe admin drain`) stops accepting new transactions, lets in-flight `tpc_finish` complete, sends every client a clean close and reports when the store is quiet, which is how a pack with a full stop, a format migration or a restore is run.

**Connection handling.** One tokio task per client reads its frames and starts its calls, and one task writes its frames; frames are length-prefixed msgpack as ZEO 5 defines them (`[message_id, async_flag, method, args]`). The calls of one connection run concurrently, and each reply carries the message id of its call and goes out when its call ends, so `prefetch` and pipelined loads return out of order. `register` runs first, alone: the server starts no other call of the connection before it ends. So does `set_client_label`, so that each later call logs with the label, and so does `iterator_gc`, which a stock client sends with no reply: a later call of the connection for an iterator that it removed fails with `KeyError`. The calls that started before these two still run. The calls of the transaction (`tpc_begin`, `storea`, `restorea`, `checkCurrentSerialInTransaction`, `deleteObject`, `vote`, `tpc_finish`, `tpc_abort` and the three upload calls) run in their order on one thread, from `tpc_begin` to the end of the transaction, so that thread drives the core transaction: `storea` comes before `vote`, and the core never answers `WrongThread`. The calls that read (`loadBefore`, `loadSerial`, `history`, `new_oids`, the iterators and the other short calls) run on the read pool of `--blocking-threads` threads, shared by all the connections, because the core is synchronous. `sendBlob` and `pack` run on a thread of their own, because a download waits for its client and a pack runs long. So a vote that waits for a lock holds no thread of the read pool, and the loads of its connection and of the others go on. The compression of the staged pickles runs off the path of the transaction, on the compression pool, which all the connections share: one queue of jobs and at most one thread for each core, threads of the blocking pool of tokio that run the jobs of the queue in order, each with the zstd context of its thread, and end when the queue is empty; a job starts a thread only when it waits behind the jobs that the threads run. `storea` and `restorea` stage the pickle, queue a job that encodes it with the compression of the store and reply at once, so the `storea` of a large record does not wait for its compression. No job is queued for a deletion, a pickle in the spill file, a store without compression, or a store after a vote that listed conflicts: the finish encodes these. The first vote waits for each job of its transaction before it takes a lock, so a vote that waits for its jobs holds no lock, then attaches each payload; it encodes itself each job that no thread of the pool took yet, so it never waits for a thread that cannot start, as when the blocking pool of tokio is full or the runtime stops; a job that failed fails the vote with `StorageError` and ends the transaction. An abort, a failed vote and a lost connection drop the jobs of the transaction: a job that waits does not encode, and a job that encodes ends unread. `tests/commit_cpu.rs` measures the server CPU per committed object. A load passes between threads only three times: the reader starts it at once on a free thread of the read pool (a task waits for a thread only when the pool is busy), that thread makes the reply and puts it in the queue of the connection, which wakes the writer, and the reader wakes again only for the next frame. The end of a call does not wake the reader: the idle timer reads the end of the last call when it fires. The reply of a load that finds a record holds the buffer that the core gives for the record: the server encodes only the bytes before and after it, and the writer sends the length of the frame and its parts in one vectored write. So the bytes of the record are not copied between the core and the socket, and a stock client gets the same frame byte for byte. `tests/load_cpu.rs` measures the server CPU per load of 1 KB and of 100 KB. A connection with no call that runs and no open transaction holds no thread, so idle clients, many more than the threads of the blocking pool of tokio, never stop a new client. Each call takes, before it starts, one of the 4 slots of its connection and room for its reply in the session queue of its connection, 4 replies: so at most 4 calls of a connection run or wait at once, and a call never waits to put its reply. A call starts only while at most 1 MiB of replies wait for the client (see "Wire contract"). A call of the read pool also takes a turn in the window of its connection: the window of a new connection holds 1 call, each reply that the server has written to the socket while at most 1 MiB of other replies waited opens it by 1 call up to 4, and a reply that goes into the session queue while more than 1 MiB waits closes it to 1 call. So a client that reads promptly runs up to 4 calls of the read pool at once, and a client that does not read its large replies runs them one at a time. The calls of the transaction, `sendBlob` and `pack` take no turn, so a vote that waits for a lock does not stop the loads of its connection. A call waits for its slot, its turn and its room in the reader, never on a thread of the read pool. A download keeps its slot until it ends, and gives back its room after its first frame. So a client that reads nothing keeps at most 4 download threads and the thread of its transaction, while the server reads no more of its calls; the threads of the transactions, the downloads, the packs and the read pool all come from the 512 threads of the blocking pool of tokio. The `ruok` status runs on the read pool, so a busy read pool delays it. A stock client sends the calls of one thread in order and waits for the reply of each call that has one, so concurrency comes from its threads and from `prefetch`. Writes from one client are serialised per transaction by the coordinator.

**Wire contract.** A frame is a 4-byte big-endian length and a payload. The server sends `M5` first, as raw bytes; the client answers `M5`, or `ruok` for a JSON status and a close. Every other payload is a msgpack array `[id, flags, method, args]`, encoded with bin types and decoded with str keys and arrays as tuples. A connection that got the extension `trace_context` can add a fifth element to a message, its trace context (see "Traces"); a message with five elements closes any other connection. A call that waits has an int id (or `[oid, tid]` for `loadBefore`) and flags false; an asynchronous call, in either direction, has id 0 and flags true and gets no reply. An oid or a tid is 8 bytes. A serial (of `storea`, `storeBlobEnd`, `storeBlobShared`, `checkCurrentSerialInTransaction` and `deleteObject`) can also be a str whose UTF-8 bytes are 8 bytes, as ZEO's tests send `'\0' * 8`: it reads as those 8 bytes, as ZEO's server takes it, so `'\0' * 8` is the serial of a new object. A str serial of another length, and an oid or a tid as a str, fail with `TypeError`. The server always sends bytes. A reply echoes the id with `.reply` and flags 0, or flags 2 and `[class, __dict__ or args]` for an error. The server ignores id -1, the heartbeat of the client, except that it is a frame for `--idle-timeout`: the idle time counts from the accept until the protocol of the client, then from the later of the last frame that the server read and the end of the last call of the connection, and a stock client sends a heartbeat every 60 s, busy or idle. The time while a call of the connection runs does not count: a client that waits for the reply of its own call is not idle. A call runs from the time that the server starts it until it queues its reply, or until it ends when it has no reply; a heartbeat starts no call. The time while 4 calls of the connection run or wait does not count either, because a call runs then. The time counts while the next call waits for more than 1 MiB of replies to go out or for a turn of the read pool and no call runs: so a client that does not read one large reply and sends one more call is closed after the timeout, and its open transaction aborts and releases its locks. An unknown method, a call before `register`, and an error in an asynchronous call close the connection. A frame longer than `--max-frame-size` closes the connection before the server reserves memory for it. The decode of a frame has two bounds, checked before the server builds the values: a depth of about 60 levels of arrays or maps, and 100,000 msgpack values (a message of a stock client has fewer than 20, because a record is one `bin` value); a frame over a bound closes the connection. So one frame costs at most about twice its size plus 16.2 MiB. A frame that is cut or is not a message closes the connection too; the bytes of a client close only their own connection. After the handshake, before a close that the bytes of the client cause (a frame longer than `--max-frame-size`, a frame that is not a call, a trace context that the connection did not declare, an unknown method, a call before `register`, an error in an asynchronous call), the server ends the calls of the connection and aborts its transaction, reads and drops the bytes of the client until the client sends nothing for 50 ms, or for 500 ms at most, then closes: so the calls that the client sent before it saw the close arrive before the FIN, and the close is not a reset, as with ZEO's server (a reset makes the asyncio of CPython 3.12 lose the next connection of a stock client). A reply carries the message id of its call and goes out when its call ends, so the replies of one connection can go out in another order than their calls; the replies of the calls of one transaction keep the order of their calls. At most 4 decoded calls of a connection run or wait; then the server reads no more bytes of that connection, so TCP makes the client wait, and the connection stays open, until `--idle-timeout` when no call of the connection runs. A reply counts from the time it goes into the session queue until the server has written it to the socket; a call starts only while at most 1 MiB of replies waits for the client, a constant with no option (requirement N6), and a download sends its next chunk only then. A reply larger than 1 MiB goes out whole. The invalidations do not count; `--client-queue-size` bounds them. The size of a reply is known only after its call ran, so the window of the read pool (see "Connection handling") limits the calls that can add a large reply at once. So the replies that wait for one client, the one that the server writes included, hold at most 1 MiB plus one reply for each call of its window. The socket takes a reply whether the client reads or not. A large reply is larger than the buffers of the socket, and a small reply is smaller: a large reply fills the buffers, so large replies open the window only for a client that reads; small replies fit in the buffers, so they open the window also for a client that does not read. Limit: a client that got small replies and then stops reading can hold one large reply for each call of its window, up to 4, once, until the window closes; the reply of `register` is small, so a new client that sends loads of large records and reads nothing holds about 2 large replies. These bounds hold per frame and per connection: nothing bounds the memory of many connections together. The method shapes are those of `docs/spikes/zeo-wire.md`, and the traces in `docs/spikes/zeo-wire/` are the reference for the protocol tests of `zoe serve`.

**End of a connection.** A connection ends when its client closes or resets it, when its hub queue overflows, when it sends no frame for `--idle-timeout`, or when the server stops. The calls that arrived before the end run, the calls of the transaction in order, as ZEO does: a `tpc_finish` that arrived commits whole, unless it waits behind a vote whose lock wait the end cancelled (see below). A call that closes the connection, an error of an asynchronous call or a reply that the server cannot queue because the client is gone, stops the calls that did not start. When the client, the hub or the idle timeout closed the connection, the client gets no reply; at a stop of the server, the connection stays open until its calls end, so the client gets the reply, and it drops the bytes that the client sends after the stop, so its close is a FIN, not a reset (see "Health, metrics, shutdown"). Then the thread of the transaction aborts the open transaction at any state, after `tpc_begin`, after a store, after the vote or between the two votes; the abort releases its locks and removes its upload file. The end of a connection also removes its iterators. A server killed during a vote commits nothing of that transaction, because nothing is durable before `tpc_finish`. Each end of a connection but a stop of the server also ends the lock wait of its session: the core ends the wait through a cancel handle (`LockCancel`) that the session gives to each of its transactions, so a vote that waits for the lock of an object leaves the queue, releases the locks that it took and fails with `ConflictError`, a vote that must wait after the end fails at once, and a `tpc_finish` queued behind such a vote does not commit. A client that closes or resets its connection during its vote holds no lock after its disconnect, whatever `--lock-timeout`. The idle timeout never ends such a wait, because the idle timer does not count while the vote runs (see below). At a stop, a vote that waits goes on waiting, because its client is still connected: the other connections abort their transactions, so the vote gets its lock, and a `tpc_finish` that arrived behind it commits. One limit remains. The server sets no TCP keepalive, so a host that dies without a FIN or a reset, or a client that stalls during a commit, keeps its connection, its transaction and its locks until `--idle-timeout` closes the connection (for ever with 0). The idle timer does not count while a call of the connection runs, so a slow `tpc_finish`, a vote that waits for a lock or a long `pack` keeps its connection without a heartbeat; a transaction that waits for its next call runs no call, so a client that stalls after its vote is closed after the timeout. So the bound of `--idle-timeout` counts from the end of the last call: a host that dies without a FIN or a reset while its vote waits for a lock keeps its locks for `--lock-timeout` at most, when the vote fails and releases them, and its connection for `--lock-timeout` plus the idle timeout, a host that dies while its `pack` runs keeps the locks of its voted transaction for the whole pack plus the idle timeout, and a host that dies with a `sendBlob` in flight keeps them until the kernel gives up on its socket, plus the idle timeout. A `sendBlob` runs until it ends, after its last chunk: while it waits for room for a chunk because its client reads nothing, the idle timer does not count, so the threads of such a client, and the locks of a transaction that it voted, stay until it reads or closes. While the server waits for room for a call of a client that reads nothing and no call runs, the idle timer counts, so such a client loses its connection and its locks after the timeout. Limit: while the server waits for room for a call, it reads no frame, heartbeats included. So a connection closes when, for the whole idle timeout, more than 1 MiB of its replies is not yet written to the socket and no call runs, and a client that reads very slowly can be closed while it sends heartbeats. The server keeps this behaviour on purpose. During the wait it reads no frame, so a client must free 1 MiB within `--idle-timeout`. With up to 4 large replies in the window, about 32 MiB, a client that reads under about 110 KB/s is closed at the default of 300 s.

**Invalidations.** After each `tpc_finish`, every other client of the storage gets one `invalidateTransaction(tid, [oids])`, with the oids from the transaction index; the client that committed gets `info {length, size}`, then its reply, and no invalidation, as from ZEO. A commit that wrote no oid sends `invalidateTransaction(tid, [])` to the other clients, as ZEO 6.2 does. Each client gets its own replies and the invalidations in commit order, because the cache of a stock client refuses a tid that goes back: the commits pass through one hub per storage, which orders them by the tid before each commit that `finish_after` gives. A commit waits in the hub, never on a thread, and a finish that fails publishes nothing. `register` and `lastTransaction` give the last published tid, and `register` joins the hub at that tid, so a client gets the invalidation of every later commit. Each connection has two queues for the frames that go out: the session queue, which holds at most 4 replies of the calls (`QUEUE`), and the hub queue, which holds at most `client-queue-size` messages (default 1,000). An invalidation is one message, and so is the `info` after a pack; the `info` and the reply of a commit, for the client that committed, are one message too, and go in together, so a hub queue of one message lets a client commit. A call takes room for its reply before it starts, and a download waits for room for each chunk; the hub never waits: on overflow the server closes that connection, and the client's reconnect path replays through `getInvalidations`. A counter per connection places each frame when it goes into either queue, and the writer sends the frames in that order. The chunks of a `sendBlob` download go through the session queue, so the invalidation of a commit that finishes during a download takes its place between two chunks: an `invalidateTransaction` can come between `receiveBlobStart` and `receiveBlobStop`, where a stock server never sends one. The stock client handles each message on its own, and a commit never waits for a client that downloads. A `loadBefore` reply shows only the commits that the hub published (the store makes a commit visible before that), and it takes its place before the invalidation of any later commit, because the stock client caches a record without a next serial as current. The replies of `register`, `lastTransaction` and `getInvalidations` come after the invalidations of the commits up to their tid; the invalidation of a later commit can come before them, and a stock client applies only the invalidations after that tid. This is the same contract ZEO keeps.

**Change feed.** The same broadcast, made public and resumable: `zoe feed --from <tid>` on the admin port (a gRPC stream, and a WebSocket for browsers) delivers one message per committed transaction with its tid, user, description, extension and the list of `(oid, class)` it touched, in commit order, exactly once from the requested tid, replayed from the transaction log for any tid still in the store. Consumers acknowledge by tid, so a restarted consumer resumes where it stopped. It is what an external indexer (OpenSearch, Solr), a cache purger (Varnish), a webhook bridge, Loupe's live tail and MCP notifications read; nothing in Plone has to be hooked for them. Class names come from `zoe-pickle` reading the class pickle, never from unpickling state.

**Blob streaming.** A client without a shared blob directory uploads a blob in chunks. `storeBlobStart` needs an open transaction, and creates one upload file in the blob temp directory of the store; `storeBlobChunk` appends to it, and `storeBlobEnd` stages it in the transaction, which takes the file by rename. An error of a blob upload call (`storeBlobStart`, `storeBlobChunk` or `storeBlobEnd`) closes the connection, as in ZEO. The upload belongs to the open transaction: each end of the transaction (finish, abort, a failed vote, the end of the connection) removes a file that the transaction did not take, and the next open of the store for writes removes a file that a crash left. `sendBlob` reads each blob twice. First it reads the whole file and checks its size and its BLAKE3 hash; then it streams the file in chunks of 64 KiB: `receiveBlobStart`, one `receiveBlobChunk` per chunk, `receiveBlobStop`, then the reply. A blob that fails the check goes out as an error reply with no chunk, because a stock client keeps a partial file after a download that stops, and its next download of that blob then fails. A missing blob is a `POSKeyError`. At most 4 calls of a connection run or wait, and the session queue holds 4 frames, so an upload or a download holds a few chunks in memory, whatever the size of the blob. S3-backed stores upload at `tpc_finish` and keep a local cache for `sendBlob`.

**Health, metrics, shutdown**

- `GET /healthz` on the admin port returns 200 when the store is open; `GET /readyz` when the last tid is loaded, the lock manager is empty of stale entries and (Tier 2) the replica is caught up.
  Built: `--admin-listen HOST:PORT` (`ZOE_ADMIN_LISTEN`) opens the admin port, a small HTTP/1.1 server on the runtime of the server. It binds with the ZEO port, before the stores open, so a port that does not bind creates no store. `GET /healthz` gives 200 while every store is open, and 503 before. `GET /readyz` gives 200 when every store is open, its open loaded its last tid, and its lock table held no entry after the open; it gives 503 before, and from the stop signal on, while the stop runs. The lock table of a store that the process just opened is empty, so the check of stale entries holds at once; a running transaction holds locks, and these are not stale. The body is plain text with one line for each storage, `NAME: open` or `NAME: ready`, or the single line `starting` or `stopping`. `HEAD` gives the same reply without the body, whatever the status; another method on a known path gives 405, and another path gives 404. A query string does not count. A request head ends with an empty line, `\r\n\r\n` or `\n\n`. The port takes one request on each connection and closes it after the reply; a request head longer than 8 KiB, its empty line included, gives 431, a head that does not end within 2 seconds closes the connection without a reply, and at most 64 connections are served at once. So 64 clients that send nothing hold the probes for up to 2 seconds: put the admin port on a private address, never on a public one. A port that does not bind fails the start with a message that names the admin address. It never speaks ZEO: it sends nothing before a request, so a ZEO client that waits for the protocol of the server gets nothing, and its connection closes after 2 seconds. The admin port is not one of the tasks that a stop waits for: it stays open, and answers, until the end of the stop, then closes before the stores close. The readiness of a replica comes in phase 5.
- `GET /metrics` exposes Prometheus counters and histograms: `loads_total`, `load_latency_seconds`, `commits_total`, `vote_latency_seconds`, `finish_latency_seconds`, `fsync_batch_size`, `lock_wait_seconds`, `conflicts_resolved_total{path=native|python}`, `conflicts_raised_total`, `clients_connected`, `invalidation_queue_depth`.
  Built: `GET /metrics` on the admin port gives these metrics in the Prometheus text format (`text/plain; version=0.0.4`), each named `zoe_*` and with the label `storage`, once every store is open, and 503 before. A duration is a histogram in seconds, and a counter ends in `_total`. `zoe_loads_total` and `zoe_load_latency_seconds` count and time the `loadBefore` calls; `zoe_commits_total` counts the commits of `tpc_finish`; `zoe_vote_latency_seconds` times each `vote`, its lock wait included, and `zoe_finish_latency_seconds` each `tpc_finish` that ends a transaction, until the commit is durable and published. `zoe_fsync_batch_size` is the number of commits that one sync of a commit batch makes durable, `zoe_lock_wait_seconds` the time of each vote to take its locks, a wait past `--lock-timeout` included, and `zoe_lock_handoffs_total` the locks that a finish handed to the vote at the head of their queues: the core reports them through its observer trait, and has no metrics dependency. `zoe_conflicts_resolved_total{path="python"}` counts the oids in conflict that a second vote passes after the client resolved them, and `path="native"` the oids that tier 1 merged in a vote that passed; `zoe_structural_merges_total{mode, outcome}` counts each result of tier 1, `merged`, `refused` or `undecided`, in mode `on` or `shadow`. `zoe_conflicts_raised_total` counts transactions: each vote that fails with a conflict, and each transaction that ends between the two votes, which the client then raises as `ConflictError`. `zoe_clients_connected` is the number of registered connections, and `zoe_invalidation_queue_depth` the messages that wait in the deepest hub queue among the connections of the storage, the queue that `--client-queue-size` bounds. Each help text gives the unit of its metric. The locks and the transactions past `lock-warn` and `transaction-warn` are logged, and not counted in the metrics yet.
- Logs. Built: the logs of `zoe serve` go to stderr from the level INFO on, as text, or with `--log-format json` (`ZOE_LOG_FORMAT`, the key `log-format` of the configuration file) as one JSON object for each line, with the fields of the event and of its spans. Each log line of a connection has `client`, the label that the client gave with `set_client_label` (an empty label gives the address back) or else its address, and once it registered `storage`. A text that a client sends, such as a method name or a label, goes only into a field, never into the message: the text format quotes and escapes a field of text, so a line feed cannot add a log line. `--lock-warn` (`ZOE_LOCK_WARN`) and `--transaction-warn` (`ZOE_TRANSACTION_WARN`), in whole seconds, set `lock-warn` and `transaction-warn` of each store: a lock held longer is logged when it is released, with its `oid`, its `client` and its `storage`, and a transaction open longer with its client and its storage. Without them, or with 0, nothing is logged. A log line holds no pickle bytes, user or description.
- SIGTERM: stop accepting connections, let in-flight `tpc_finish` calls complete, abort transactions still in `Staged` or `Locked`, send a close to each client, exit. Bounded by `shutdown-timeout` (default 30 s). Built: SIGINT does what SIGTERM does, and the command exits with 0. `zoe serve` handles both signals before it creates anything on disk. A signal during the start stops the server when the start ends: each store open ends, the stores close, and the command exits with 0, also when the signal came before the line `listening`. So a signal never leaves a store directory without a store. A SIGKILL or a power loss during the first open can leave one, and so can a first open that fails for another reason, such as a full disk; a later writer open makes a store in such a directory. Each connection reads no more calls, and the calls that the server already received run, so a `tpc_finish` that the server received commits and gets its reply before the close; then the transaction of the connection ends, which aborts it if it is open, and the connection sends what waits and closes; then the stores close, so the strict read-only open of the core (`Store::open_read_only`) accepts them. A client that does not answer the protocol does not hold the stop. At the timeout less one second (less half the timeout when that is shorter), the connections that remain close at once, so a client that does not read its replies holds the stop only until then. A running pack stops between two of its batches: the packing client normally gets `StorageError` before the close (no test checks it over the wire), the store keeps the records that the pack did not remove, and a later pack at the same time removes them (ADR 0025). The pack checks the stop only after a batch, and its mark reads every reachable record before the first batch, so a stop during the mark waits for the mark and the first batch: at most one batch of removals runs after the stop. A call that runs past the timeout, a long mark in particular, keeps the store of that session open: the process exits at the timeout, and that store does not close cleanly, so the strict read-only open refuses it with `NotClosedCleanly`, and the next writer open, or the next tool that reads the store, rebuilds the free-space map of its database (ADR 0032); the other stores close, because a session keeps only the store that `register` selected. After the stop, each connection reads the bytes that its client sends and drops them, never as calls, and its writer ends the last frame with a FIN; the connection closes when the send queue of its socket is empty (the client acknowledged every frame and the FIN), or when the client closes its side, and never later than the forced close. The connection reads the queue every 50 ms at most. So a client that sends bytes after the stop, as a client that shares one connection between threads does, gets every frame and the reply of a `tpc_finish` that the server received, then a clean close, not a reset, also when its replies drain slowly. A client that reads nothing keeps its connection until the forced close. Reading the queue takes one `unsafe` call (`ioctl` `SIOCOUTQ`), Linux only. A stream without a socket, as in the simulator, and a read of the queue that fails, close at most 500 ms after the FIN; a byte that the client sends after that, while the kernel still sends the last frames, can still reset the connection.

**Traces.** Every request, lock wait, fsync and pack step is an OpenTelemetry span, exported over OTLP when `ZOE_OTLP_ENDPOINT` is set. A client that negotiated the `trace_context` extension sends its W3C traceparent with each request, so a slow Plone request and the server work it caused appear in one trace in Jaeger or Tempo; the `zoe.zeo` client sends it when `opentelemetry` is installed in the Zope process. Built: with `ZOE_OTLP_ENDPOINT` set, `zoe serve` exports its spans over OTLP with the protocol of `OTEL_EXPORTER_OTLP_PROTOCOL`: `grpc` (to the endpoint itself), `http/protobuf` (the default) or `http/json` (both to `<endpoint>/v1/traces`), over plain HTTP, without TLS. The signal variables `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` and `OTEL_EXPORTER_OTLP_TRACES_PROTOCOL` change neither the endpoint nor the protocol. `ZOE_OTLP_ENDPOINT` is a variable only, as the `OTEL_*` variables are, not an option of `zoe serve`. Without it, no exporter starts, also when `OTEL_EXPORTER_OTLP_ENDPOINT` is set. Each call of a connection is a span named after its method, a wait for a per-OID lock is a span `lock_wait` (with `oid`), the write and sync of a commit batch a span `fsync` (with `commits`) and each batch of a pack a span `pack_batch` (with `records`), each inside the span of the call that caused it: the sync of a batch is inside the `tpc_finish` of its leader. Every span has the attribute `zoe.storage`. The core emits `tracing` spans only, and the server gives them the storage through the OpenTelemetry context of the call. The traces take only the spans of the zoe crates, never an event, and no attribute holds pickle bytes, user or description. The log lines do not show these spans. The server flushes its spans when it stops, after the stop of the connections. A connection that declared `trace_context` in `register`, and got it, can add a fifth element to each message: the trace context, a msgpack map whose key `traceparent` holds a W3C traceparent (`00-<trace id>-<parent id>-<flags>`); the server ignores its other keys. The span of that call takes the trace id of the traceparent, and the span of the client as its parent, so the spans under it, those of the core included, join the trace of the client. A call without a fifth element, or whose traceparent is missing or not valid, is the root of its trace. A message with five elements on a connection that did not get `trace_context` is a protocol error: the server closes that connection, as it does with any frame that is not a message, and serves the others. So does a fifth element that is not a map. With the default sampler of OpenTelemetry (`parentbased_always_on`), the server samples a call as the client sampled its trace: the call of a trace that the client did not sample exports no span. `zoe.zeo.ClientStorage` declares `trace_context` when the package `opentelemetry` is installed in its process, with `native` true or false; then, on a connection that got it, each call made inside a span carries the traceparent of that span, and a call outside a span has four elements. The native client reads the traceparent on the calling thread when the call starts. The client exports no span of its own: the application configures OpenTelemetry. The service name is `zoe`, unless `OTEL_SERVICE_NAME` gives one.

**Configuration** is flags or environment variables (`ZOE_PATH`, `ZOE_BLOB_DIR`, `ZOE_SHARED_BLOB_DIR`, `ZOE_STORAGE`, `ZOE_CONFIG`, `ZOE_LISTEN`, `ZOE_MAX_FRAME_SIZE`, `ZOE_INVALIDATION_AGE`, `ZOE_SHUTDOWN_TIMEOUT`, `ZOE_IDLE_TIMEOUT`, `ZOE_BLOCKING_THREADS`, `ZOE_CACHE_SIZE`, `ZOE_ADMIN_LISTEN`, `ZOE_LOG_FORMAT`, `ZOE_OTLP_ENDPOINT`, `ZOE_LOCK_WARN`, `ZOE_TRANSACTION_WARN`, `ZOE_BACKEND`, `ZOE_BLOB_STORE`, `ZOE_LOCK_TIMEOUT`, `ZOE_EARLY_LOCKS`, `ZOE_STRUCTURAL_MERGES`, `ZOE_STRUCTURAL_MERGE_CLASSES`, `ZOE_POSTING_DICTS`, `ZOE_RESOLUTION_LOG`, `ZOE_TLS_CERT`, `ZOE_TLS_KEY`, `ZOE_TLS_CLIENT_CA`, `ZOE_TLS_READ_ONLY_CLIENT_CA`), the TOML configuration file of `--config`, plus a ZConfig `<zoe-server>` section for buildout users, which `python -m zoe.serve` runs (see "The `<zoe-server>` section"). TLS uses rustls with its ring provider; ZEO's `ssl` client option works against it. `--tls-cert FILE` and `--tls-key FILE` (`ZOE_TLS_CERT`, `ZOE_TLS_KEY`, PEM, each needs the other) make the ZEO port speak TLS; the admin port stays plain HTTP. `--tls-client-ca FILE` (`ZOE_TLS_CLIENT_CA`) requires a client certificate that chains to one of its CA certificates, as the `authenticate` key of ZEO's `<ssl>` section does, and the handshake refuses another client. A client certificate that is byte for byte one of the certificates of that file is accepted too, also when it is a CA certificate, within its validity period and with the proof of its key in the handshake, as OpenSSL accepts it for `authenticate` (ZEO's tests use such a certificate); no other CA certificate is accepted as a client certificate, and a certificate of `--tls-read-only-client-ca` never matches by its bytes. `--tls-read-only-client-ca FILE` (`ZOE_TLS_READ_ONLY_CLIENT_CA`) also accepts the certificates of a second CA, and their holders register read-only only: `register(storage_id, false)` fails with `ReadOnlyError` and the connection stays open, so a client with `read_only_fallback` registers again read-only, as on a read-only store (see "Modes"). A read-only client also gets `ReadOnlyError` from `pack`, because a pack deletes data; `zeopack` needs a read-write certificate, and a connection that registers read-only by its own choice still packs, as in ZEO. This is how Loupe and the MCP server hold a read-write or a read-only certificate. With either CA, a client certificate is necessary; a certificate that chains to both CAs is read-write. Both CA options need `--tls-cert`. The handshake must end within the idle timeout, a stop ends it at once, and a failed handshake closes only its connection. The server reads the files once, at its start and before it listens, so a file that does not read fails the start with 1 and creates no store; the reload of a certificate is not built.

**Extension negotiation.** A client declares the extensions that it wants as a third argument of `register`, a list of names: `register(storage_id, read_only, ["lock_intent"])`. The server accepts the names that it serves, once each, in the order of the declaration, and leaves out a name that it does not know or serve, without an error. `get_info` gives the accepted names back under the key `extensions`, an empty list when it accepted none. A third argument that is not a list of strings fails `register` with `TypeError`, and the connection stays open and unregistered. A declaration holds for its connection only. A stock ZEO client declares nothing: its `get_info` has no `extensions` key, and it gets vote-time locking. A call to a method of an extension that the connection did not declare fails with `ValueError`, and the connection stays open. Built so far: the negotiation, and the extensions `sequences`, `lock_intent` and `trace_context` (see "Traces"). `zoe.zeo.ClientStorage` declares `lock_intent`; the Plone-side piece is `zoe.zodb` (section 9).

**Sequences over the protocol (F29).** The extension `sequences` adds `sequence_next(name)`: the next value of the sequence `name` of the store, an int, with the rules of the in-process primitive. The values are unique and strictly increasing per store and per name, from 1, and consecutive within one open store across the connections. A restart of the server skips at most 100 values of a name. The call is outside the two-phase commit: it runs while a transaction is open, and an abort keeps its values. A name that is not a str fails with `TypeError`, and a read-only connection or store with `ReadOnlyError`.

**`zoe.zeo.ClientStorage`.** A Python subclass of `ZEO.ClientStorage.ClientStorage`, with the same arguments and `native`. By default the native client of F28 runs inside (see "The native client (F28)"). With `native=False`, or the key `native false` of `<zoeclient>`, the asyncio client of ZEO runs inside, as described here. A subclass of `zoe.zeo.ClientStorage` keeps the asyncio client of ZEO by default, because it can change its methods; `native=True` on it raises `TypeError`. Each connection declares `sequences` and `lock_intent` in `register`, and `trace_context` too when the package `opentelemetry` is installed (see "Traces"). Against a stock ZEO server, which refuses a third argument of `register` with `TypeError` and keeps the connection open, the connection registers again with two arguments, and the client works as `ZEO.ClientStorage` does. The stock server logs that `TypeError` with a traceback once for each connection, and the client has no key to turn the declaration off. `sequence(name).next()` calls `sequence_next` when the server accepted `sequences` on the connection, and raises `ZODB.POSException.Unsupported` otherwise. `%import zoe` gives the ZConfig section `<zoeclient>`, which opens it: it takes every key of `<zeoclient>`, with the same values, `wait-timeout`, as ZEO's `<clientstorage>` has it, `native`, `early-locks` and `early-lock-classes` (ADR 0045; `early-locks on` needs `native true`), and an `<ssl>` section with the keys of the `<ssl>` section of `<clientstorage>` (`certificate`, `key`, `password-function`, `authenticate`, `check-hostname`, `server-hostname`). ZEO's client gets the context that ZEO makes from that section; the native client reads its files. Because ZEO's component also declares a section type `ssl`, a configuration cannot import `zoe` and `ZEO` together; such a configuration uses `<zoeclient>` with `native false` and `<ssl>` in place of `<clientstorage>`, which opens ZEO's client with the same TLS.

**The native client (F28).** `zoe.zeo.ClientStorage(...)`, the section `<zoeclient>`, and `zoe.testing.native_client(address, **kw)` run the client on `zoe-client`, inside the extension `zoe._zoe` (ADR 0035), and not on the asyncio client of ZEO. It is the default; `native=False` and `native false` keep the asyncio client of ZEO. The instance is still a `ZEO.ClientStorage.ClientStorage`, and no thread of ZEO's client starts. Built so far: a pool of connections (ADR 0036; see below); the open (`register` with the declaration of `sequences`, and of `trace_context` when the package `opentelemetry` is installed, and the fallback to two arguments, `get_info`, the last tid), the traceparent of each call as with `native` false (see "Traces"), `new_oid`, `load`, `loadBefore`, `loadSerial`, `getTid`, ZODB's two-phase commit with `checkCurrentSerialInTransaction` and a `tpc_begin` with a tid, several transactions at once, the invalidations of the other clients to the DB, `sequence(name).next()`, `close`, a client cache with `cache_size` and `_cache.clear()`, in memory or in a file with `client`, `var` and `cache`, blobs with `blob_dir`, `shared_blob_dir`, `blob_cache_size` and `blob_cache_size_check` (see below), conflict resolution in the client (see below), and the rest of the storage API (see below). It connects as ZEO does: an address is a `(host, port)` tuple or the path of a unix domain socket as a `str`, or a list of them. With several addresses, the client connects to all of them at once, keeps the first server that registers, a writable server before a read-only one with `read_only_fallback`, and closes the other connections. TLS comes from the files of the `<ssl>` section of `<zoeclient>` and from the argument `ssl_server_hostname`: the client builds its TLS in Rust on rustls, the TLS stack of `zoe serve`, checks the chain of the server certificate against the CA certificates of `authenticate` and, with `check-hostname` (true by default), that the certificate is valid for the server name (`server-hostname`, else the host of the address). `authenticate` is a PEM file or a directory; in a directory, the client reads every file, a superset of OpenSSL, which reads only the hashed names that `openssl rehash` makes. Without `authenticate`, or with `DYNAMIC` that is not a directory, the client checks the server against the CA certificates of the system, as ZEO's `ssl.create_default_context()` does: the files of `SSL_CERT_FILE` and `SSL_CERT_DIR` when one of them is set, else the default paths of OpenSSL, read with `rustls-native-certs` at the open. A directory or a system store without a CA certificate fails the open with `ValueError`. The client sends the certificate of `certificate`, with its key from `key` or from the certificate file. A section object without `certificate` gives a client without a certificate, as `ZEO.zconfig.ssl_config` does: the client then ignores `key` and `password-function`, and a server that requires a client certificate refuses it. The section type `ssl` of `<zoeclient>` requires `certificate`, as ZEO's section type does. The tag of the `<ssl>` section is the tag of ZEO, so one ZConfig file cannot `%import zoe` and `%import ZEO` together (see "`zoe.zeo.ClientStorage`"). A failed check fails the connection, and the open raises `ClientDisconnected` at the end of `wait_timeout`; the client never falls back to a connection without TLS. An `ssl` context, as `ZEO.ClientStorage` takes it, fails the open with `Unsupported`, which names `ssl`: a context does not give back the files of its certificate and key. So ZEO's `<clientstorage>` with `<ssl>`, which makes a context, does not open the native client, and the two tests of `ZEO.tests.testssl` that open it are out of its conformance run. Without `check-hostname`, the client runs the chain check of rustls alone and never the name check. A host that does not resolve leaves the round of the open, and the other addresses still open. Known limits of the native TLS, not in `_NOT_BUILT`: it refuses `password-function` (an encrypted key) with `Unsupported`; and it refuses a v1 server certificate, which webpki does not read. A server certificate that is byte for byte one of the certificates of `authenticate` (a file or a directory, not the system store) is valid without a chain, within its validity period, also when it is a CA certificate, as OpenSSL accepts the self-signed certificate of the server given as `authenticate` (ZEO's tests do so). With `check-hostname`, such a pinned certificate must be valid for the server name by its subjectAltName, or, when it has none, by a common name of its subject that is the DNS name, as OpenSSL checks it for Python's `ssl`; a certificate that a CA signed never matches by its common name. With `read_only_fallback`, the open keeps a read-only server only when every other address ended, so an address that never answers delays it until the end of `wait_timeout`; after the open, the client goes on trying a writable server (see "Reconnects"). It speaks `M5` only, so a stock ZEO server needs `msgpack true`; there it declares nothing. The native client is a drop-in, never a requirement, so the default falls back: when the caller gives no `native` (and `<zoeclient>` has no key `native`), and the open with `wait` finds a server that speaks the pickle protocol `Z5` of a stock ZEO server without `msgpack true`, the open stops the native client at once and the instance becomes a `zoe.zeo.ClientStorage` with the asyncio client of ZEO inside, opened with the same arguments: it logs a warning under the logger `zoe.zeo` that names the protocol, and works as with `native=False`. Without `wait`, the open does not connect, so it cannot see the protocol and the client stays native. `native=True` (`native true`) asks for the native client: there, and at a reconnect of a native client, a server that answers with another protocol (`Z4`, or `Z5` without `msgpack true`) is a failed connection, as for ZEO: the client logs "Registration or cache validation failed, b'Z4'" at error level under `ZEO.asyncio.client`, tries again after 9 seconds, ZEO's `register_failed_poll`, and the open raises `ClientDisconnected` ("timed out waiting for connection") at the end of `wait_timeout`; for `Z5`, the text goes on to say that the native client speaks only `M5` and that the server needs `msgpack true`, or the client `native=False`. The arguments of `ZEO.ClientStorage` whose feature is not built are the keys of `zoe.zeo._NOT_BUILT`, each with the value that leaves it off; another value fails the open with `Unsupported`, which names the argument, and the gate checks that the dict is empty. The arguments that ZEO 6 ignores are ignored, but `disconnect_poll`: the time between two attempts to connect again, 1 second by default, the `connect_poll` of ZEO's client. **Several transactions at once (ADR 0036).** The open opens one connection, the listener, which never commits. Each transaction takes a free connection of a pool from `tpc_begin` to the end of `tpc_finish` or `tpc_abort`, with one transaction of the server on it; it opens a connection only when it finds none free, up to `zoe.zeo._POOL_BOUND` (64) connections that commit, and waits for a free one when all are busy. The bound is a constant, not a key. Loads use any connection, the listener included; `new_oid` and `sequence(name).next()` use the listener. The server sends the listener the invalidation of each commit of the other connections, the pool's own commits included, in tid order, and one dispatcher in Rust delivers each tid of that stream in turn: a tid of another client goes to the DB as `invalidate(tid, oids)`, once, through a thread of the client; a tid of the pool never goes to the DB as an invalidation: its `tpc_finish` returns at that place and runs its callback `f(tid)` before the dispatcher goes on. `lastTransaction()` is the last tid that the dispatcher delivered, from the `register` tid of the listener on, and after `close` the last tid before the close; a call from another thread than the one that delivers waits for the delivery that runs, so it gives a tid only after the DB got its invalidations or `f(tid)` ran. While a finish waits for its reply, the dispatcher holds a tid that it does not know, until each finish that counted as in flight when the tid came has its reply or failed; a finish counts from before its frame goes out, and a finish that fails, loses its connection or drops leaves the hold, so the dispatcher then delivers its tid, if the server committed it, as a tid of another client. A lost or lagged listener is a lost connection, and a lost listener also ends a hold: the DB gets `invalidateCache()`, the client counts as disconnected, and a new transaction fails with `ClientDisconnected`; a finish that had its reply then runs `f(tid)` after `invalidateCache()` and returns its tid, and a finish without its reply fails. Then the client connects again (see "Reconnects"). Each load reply carries the position of its connection, the last tid that the connection read from its own stream, for the cache of ADR 0034. It works with no change against a stock ZEO 6 server, which also sends the listener the invalidations of the other connections in tid order. The calls wait without the GIL, and the extension declares that it runs without the GIL. The tokio runtime of the native clients has 2 worker threads for the process, and starts when the first client opens. A client opened before `os.fork()` raises `RuntimeError` in the child at its next call, before it takes any lock. `zoe.testing.NATIVE_LAYER` makes `ZEO.ClientStorage.ClientStorage` and `<zoeclient>` open the native client, and gives the native class as base to each class of a loaded module that derives from the class of ZEO (`TestClientStorage` of ZEO's `ConnectionTests`, `ServerManagingClientStorage` of `testZEO`), so ZEO's tests and ZODB's mixins run on it. The private names of `ZEO.ClientStorage` that ZEO's tests read give the same things: `_server` is the part of ZEO's client thread that needs no asyncio (`call`, `async_`, `is_connected`, `is_read_only`, and `timeout`, the wait for a server), and its `client` is the current connection, whose `verify_result` tells how the verification of the cache ended, in the words of ZEO (`empty cache`, `Cache up to date`, `quick verification`, `cache too old, clearing`, `Cache newer than server`); each connection calls `notify_connected(conn, info)` with that connection, and each loss `notify_disconnected()`, as ZEO does, so a subclass that overrides them sees each connection; `_cache` gives `maxsize`, `path` (the `.zoec` file or `None`), `len()` (the entries of the cache, current or not), `contents()` (the oid and the tid of each current entry) and `clear()`; `_wait(timeout)` waits for a server. The client logs its connections, its losses, a dropped cache and a refused server under the logger `ZEO.ClientStorage`, with the words of ZEO, and an error of the server that ZEO logs, under `ZEO.asyncio.client`, as "<address> from server: <class>:<args>". **The client cache (ADR 0034, stages 1 and 2).** The pool holds one cache, in an anonymous mapping of the process or in a cache file (below), in the layout of ADR 0034: a header page, an index of slots `(oid + 1, position)` with linear probes, and a ring of entries, each with its logical position, oid, start and end tids, the position of the older entry of its oid, its lengths, its codec, a checksum of its data and a checksum of its head. `cache_size` (the key `cache-size` of `<zoeclient>`, 20 MB by default, as for ZEO) is the size of the ring; the header and the index come on top; 0 turns the cache off. The semantics are those of `ZEO.cache.ClientCache`: an entry is one revision of an oid, with its start tid and its end tid, and a current entry has no end. `loadBefore(oid, before)` hits an entry with `start < before` and either `end ≥ before`, or no end, where `applied` is the tid up to which the cache applied the commits: a current entry serves any `before`, `maxtid` included, as the cache of ZEO does, because the pool applies each tid to the cache before it delivers it. After a commit of the pool that a stale turn delivered without the cache, a current entry serves only `before ≤ applied + 1` until `applied` reaches that tid (ADR 0034); `load(oid)` hits the current entry whatever `applied` is, as `ZEO.ClientStorage.load` does. A hit takes no lock, writes nothing (but the copy below) and sends nothing to the server: it reads `applied`, the slot, then the entry, copies it, checks both checksums and checks that the head of the ring stayed within one ring of the entry; a doubt is a miss. Every word of the mapping is an atomic. The writers take one mutex of the process. The ring is FIFO: a new entry overwrites the oldest bytes; an entry larger than half of the ring is never cached; a hit of a current entry in the oldest fifth of the ring copies it to the head when the writer mutex is free. The dispatcher applies each tid to the cache before the DB gets it and before `lastTransaction()` gives it: a tid of another client ends the current entry of each of its oids at the tid; a commit of the client ends the entries of its oids and adds a current entry with the committed data, the pickle that the client resolved included, except for an oid that the server resolved; then `applied` moves to the tid. A load reply with an end always goes in; a current reply goes in only when `applied` is not above the position of the connection that carried it, taken by the reader when the reply arrived (ADR 0036, "Loads and the client cache"), so a reply that arrived before a commit and is stored after the cache applied that commit is refused (the race of ZEO issue 166). A newer current reply drops an older current entry of its oid. A `ConflictError` or a `ReadConflictError` of a vote drops the current entry of its oid, as `tpc_vote` of `ZEO.ClientStorage` does. `_cache.clear()` drops every entry and keeps `applied`: the head of the ring moves two rings forward. After `close`, the cache serves and stores nothing more; `close` of a cache in memory drops every entry. A lost or lagged listener keeps the cache for the verification of the next connection (see "Reconnects"); a turn that comes after the loss only drops the current entry of each oid that its commit wrote, and the cache records its tid as skipped (see `loadBefore` above). The entries are raw, with the codec field of each entry at "none" (ADR 0034: raw by default; zstd per entry is a later setting). **The cache file (ADR 0034, stage 2).** With `client` (the key `client` of `<zoeclient>`), the cache is the file `<client>-<storage>.zoec` in `var` (the current directory by default), the name of ZEO's file with its own extension, so the native client never reads or writes the `.zec` file of a stock client; a `str` as `cache` is the path of ZEO's file, whose `.zec` becomes `.zoec` (a path without either extension gets `.zoec`), and a cache object raises `Unsupported`. The open never changes a file that is not a cache file of ZOE: it raises `ValueError`. The file is mapped in memory, shared, and holds the header page, the index and the ring: its length never changes while it is open, and the open reserves its disk space when its blocks do not cover its length. The header names the version of the layout (in the magic), the storage, the size and `applied`, the last tid of the cache; it also holds the boot id of the kernel, a clean flag and a checksum of its state. The open takes an exclusive `flock` of the file without a wait: a second open of the same file, in the same process or in another, raises `zc.lockfile.LockError`, as ZEO's cache does with its `.lock` file; several processes on one file are F38. The open keeps the entries of a file of the same version, storage and size, with a good header, when its last close was clean or when no restart of the kernel came since it was open (a process that dies leaves its writes in the page cache); else it drops every entry. A file that the open keeps serves nothing until its verification against the server, which follows the verification of a reconnect: `applied` equal to the last tid of the server keeps the entries; below it, the server must hold a commit at exactly `applied` (`iterator_start(applied, applied)` and `iterator_next`), else its history is another one, as for a server restored from an older copy, and every entry goes; then `getInvalidations(applied)` drops the current entry of each oid of the reply, and `None` drops every entry; above it, the open drops every entry. The client logs a dropped file as ZEO logs a stale cache (the `StaleCache` event and "dropping stale cache", before the drop), and a file ahead of the server, or of another history, as critical. With `wait`, the connect and that verification share one `wait_timeout`. The departures from ZEO at the open: a file ahead of the server is dropped, where ZEO refuses the server; a failed `getInvalidations` drops the file, where ZEO tries again; and the verification ends before the open returns only with `wait`. Every entry carries a checksum of its head and of its data, so an entry whose check fails is dropped, never served, and the next load stores it again. `applied` moves only after the entries of its tid ended, so a process that dies leaves a file whose `applied` is not newer than its entries. The file is marked not clean, and that mark is on the disk, before the first write to the mapping: an open that keeps the file and writes nothing pays no sync, as ZEO's open, and a crash then leaves the clean file of the last close; a quick verification writes, so it pays the sync at the open. A mark that fails disables the cache, and the open does not wait for it. The close of a marked file writes the mapping to the disk, then marks the file clean, then frees the lock; the close of a file that nothing wrote only frees the lock. The file holds only what the server gave or confirmed, so dropping it is always correct. **Conflict resolution.** `tpc_vote` resolves in the client the conflicts that the vote reply lists, as `tpc_vote` of `ZEO.ClientStorage` does (F5): for each map `{oid, serials: [committed, read], data}` of the reply, it runs `tryToResolveConflict(oid, committed, read, data)` on the thread of the transaction, with no lock of the client held and, on a free-threaded build, no GIL; it sends the result with `storea` over the committed serial and votes again, for at most nine rounds. A vote that still lists a conflict after the ninth round raises `ConflictError`, where ZEO goes on to the finish, which a stock server then refuses; `zoe serve` never lists a conflict twice. `tpc_vote` returns the oids that the server or the client resolved, so the DB loads them again. The client cache keeps the pickle that the client resolved, as the cache of `ZEO.ClientStorage` does: the server stores those bytes unchanged. It never holds the pickle of an oid that the server resolved. A conflict that does not resolve raises the `ConflictError` of `tryToResolveConflict`, with the oid and the serials; another error of the resolver, such as a result that is not `bytes`, raises unchanged. Either error drops the current cache entry of the oid and leaves the transaction open: the `tpc_abort` of ZODB releases its locks on the server. A conflict that the server does not list (a new object, a deletion, a read-current serial) fails the vote with `ConflictError` or `ReadConflictError`. **Reconnects.** With `wait` (true by default), the open waits at most `wait_timeout` seconds for a server; without it, the open returns at once, and the client connects in the background. When the client loses its listener, the DB gets `invalidateCache()` and the client closes every connection of the pool: a transaction that began before the loss fails at its next step with `ClientDisconnected`, never commits on a later connection, and leaves no lock on the server. While the client has no listener, a call that needs the server waits for one at most `wait_timeout` seconds, or the `timeout` of `_call`, as ZEO does, then raises `ClientDisconnected`; after `close` it raises at once. A hit of the cache answers without a wait, and a call of a transaction that began before the loss raises at once. The dispatcher of the pool opens a new listener at once, then every `disconnect_poll` seconds, in the background: no thread that calls a method runs it, and `close` stops it. Each attempt is one round over the addresses, as at the open, for at most `wait_timeout` seconds, with the read-only fallback; the lookup of a host name runs on a blocking thread, never on a thread that serves the connections. Before the client takes the new server, it verifies its cache as `verify` of `ZEO/asyncio/client.py` does, once for each reconnect of the client, not for each connection of the pool. The base is `applied` of the cache, or `lastTransaction()` without a cache. A server whose last tid is the base keeps the cache. A last tid below the base, or below `lastTransaction()`, refuses the server: the client logs it as critical, stays disconnected and tries again after 9 seconds, the `register_failed_poll` of ZEO. A higher last tid asks `getInvalidations(base)`: the cache drops the current entry of each oid of the reply and keeps the other entries, `applied` moves to the tid of the reply, and the DB gets `invalidate(tid, oids)`, as ZEO calls `invalidateTransaction` after `getInvalidations`, before `lastTransaction()` moves to that tid. The invalidations of the new listener at or below that tid are skipped, so the DB never gets a tid twice. The tid of the reply can be `lastTransaction()` itself: a commit of the client that had its reply when the listener was lost ran its callback after `invalidateCache()` and moved `lastTransaction()` past `applied`. The commits of other clients between `applied` and that tid never reached the DB, and a connection that polled while the DB handled `invalidateCache()` can hold their objects from before them. So the DB still gets `invalidate(tid, oids)`, and `lastTransaction()` stays. When the server answers `None`, the client notifies ZEO's `StaleCache` event and logs the dropped cache as critical, then the cache drops every entry, as ZEO does, so a handler of the event still sees the entries; then the DB gets `invalidateCache()`, and `lastTransaction()` moves to the last tid of the server. Then the connections of the new server serve the calls, and the client logs the reconnect. On a read-only server after a fallback, the client tries a writable server every `disconnect_poll` seconds; when one registers, the client leaves the read-only server as after a loss, and takes the writable one. `min_disconnect_poll`, `max_disconnect_poll` and `drop_cache_rather_verify` change nothing, as for ZEO 6. The departures from ZEO: the DB gets `invalidateCache()` at the loss, where ZEO calls it at each connection; an empty cache verifies through `getInvalidations` as a full one does, where ZEO skips the verification; and `disconnect_poll` sets the time between two attempts, where ZEO waits 1 to 2 seconds. **Blobs.** The native client has the two modes of `ZEO.ClientStorage`, with its code for the blob directory: `loadBlob`, `openCommittedBlobFile` and `temporaryDirectory` are those of ZEO, and the storage keeps `fshelper`, ZODB's `FilesystemHelper`. It declares `IBlobStorage` when `get_info` of the server lists it, as ZEO does (see "The rest of the storage API"). With `blob_dir` and without `shared_blob_dir`, `blob_dir` is a blob cache in ZEO's layout `zeocache` (`ZEO.ClientStorage.BlobCacheLayout`, marker `.layout`), so a cache directory works with either client. `loadBlob` returns the file of the cache, and downloads it first when it is missing: it takes the file lock of the directory of the blob (`.lock`, ZEO's `_lock_blob`), so the threads and the processes of a machine download a blob once, and calls `sendBlob` on a connection of the pool other than the listener when one is open, so the delivery of the invalidations never waits for a download. The server sends `receiveBlobStart`, one `receiveBlobChunk` per chunk and `receiveBlobStop` on that connection, then the reply; the reader of the connection gives them to the download of their oid and serial, which writes `<blob>.dl`. The file gets its name, read-only (`S_IREAD`), only after the reply and `receiveBlobStop`, and only when it holds as many bytes as came, so a reader never opens a partial file; a failed download removes `<blob>.dl`, and a download removes a `<blob>.dl` that a stopped download or a crash left before it writes its own. A connection runs one download of a blob at a time, also when the first one stopped before its reply. A second `loadBlob` finds the file and downloads nothing; it sets the time of access, as ZEO does. `storeBlob` takes the file at once into the directory of its oid in the cache, under a name that ends in `.tmp-`, by rename or by copy, and uploads it from there with `storea`, `storeBlobStart`, one `storeBlobChunk` per chunk of 59,000 bytes and `storeBlobEnd`, one chunk in memory at a time; `tpc_finish` gives the file its name under the new tid, under the lock of the blob, also when its callback raises, and `tpc_abort` or a finish that gives no tid removes it. `blob_cache_size` and `blob_cache_size_check` prune the cache as ZEO does: when the bytes downloaded or committed since the last check pass `blob_cache_size_check` percent of `blob_cache_size`, a thread runs ZEO's `_check_blob_cache_size`, which removes the files of the least recent access until the cache holds `blob_cache_size` less that check size, and skips a file whose directory lock is held; `close` waits for the last such thread. A file that a reader holds open stays readable after the pruning removes it, and `openCommittedBlobFile` downloads a file that the pruning removed before its open again. With `shared_blob_dir`, the client and the server share `blob_dir` (`zoe serve --shared-blob-dir`): `storeBlob` puts the file in the directory of its oid there, sends `storea` and `storeBlobShared` with the name of the file, and the server takes it by rename; `loadBlob` returns the file of the shared directory, at its BushyLayout path, and raises `POSKeyError` when it is missing. **The rest of the storage API.** The other calls of `ZEO.ClientStorage` go through its `_call` and `_async`, which the native client sends on the listener, as on the one connection of ZEO; so `iterator`, `history`, `record_iternext`, `pack`, `undoInfo`, `undoLog`, `server_status`, `getName`, `sortKey`, `supportsUndo` and `copyTransactionsFrom` are the methods of `ZEO.ClientStorage`. A reply is converted as ZEO's msgpack decoder does (an array becomes a tuple), and an error reply raises what ZEO raises for it: the exception that the `exc_factories` of `ZEO.asyncio.client` make from its value, so a `POSKeyError` keeps its oid as bytes, or else `ServerException(class, value)`; `loadSerial` raises the same way. The listener never sends a call of a transaction: `_call` or `_async` of one raises `StorageTransactionError` and sends nothing. As ZEO's, `_call` waits at most its `timeout`, `wait_timeout` by default, for a server. `_call(..., wait=False)` returns a `concurrent.futures.Future` of the reply, as ZEO's does; a thread of the client waits for the reply, in the context of the caller. An iterator lives on the listener, with its id in `_iterator_ids` and its Python iterator in `_iterators`, as in ZEO; after the drop of the Python iterator, the next `tpc_finish` or `tpc_abort` releases it with `iterator_gc`, the loss of the listener forgets every iterator (a later `next()` raises `ClientDisconnected`), and `close` releases them with the connections. An iterator id carries the generation of the listener that gave it, which changes at each loss of the listener: the server of a new listener numbers its iterators from 0 again, so a call with an id goes only to the listener of its generation. An id of a lost listener, which a thread can register after the loss, raises the `KeyError` of an unknown iterator and sends nothing, and `iterator_gc` sends each id only to the listener of its generation. `undo` sends `undoa` on the connection of its transaction, and `undoInfo` and `undoLog` call the server on the listener; the server answers as it does for `ZEO.ClientStorage`. Until phase 4 (F11), `zoe serve` closes the connection of an unknown call. For `undoInfo` and `undoLog`, that is the listener: the whole pool is lost, the DB gets `invalidateCache()`, each open transaction of the process fails, and the client connects again, as a stock client does on its one connection. For `undo`, only the connection of its transaction closes: its vote fails with `ClientDisconnected`, and the pool keeps its server. `deleteObject` and `restore` (`restorea`, with `None` data for a deletion) go on the connection of their transaction; at the turn of the commit, the cache ends the current entry of each of their oids and adds nothing (a departure for `restore`: ZEO's `restore` leaves its cache as it is), and so it does for an oid that the vote lists as resolved by the server without a store, as the oids of an undo, as `TransactionBuffer` of ZEO gives them. The serial of `store`, `deleteObject` and `checkCurrentSerialInTransaction` can be a str whose UTF-8 bytes are 8 bytes, as ZEO's tests give `'\0' * 8` and ZEO's server takes it. `prefetch(oids, tid)` sends one `loadBefore` for each oid that the cache does not hold for `tid`, once for an oid that comes twice, all at once, on the connections of the pool in turn, and returns before the replies; each reply goes into the cache with the position of its connection, so a current record that an invalidation ended while its reply was on its way does not go in, and a failed load changes nothing. Without a cache it sends nothing, and without a server it raises `ClientDisconnected`. `sync()` does nothing, as in ZEO, unless `server_sync` is true: then it calls `ping` on the listener and returns when the DB got each commit that the listener read before the reply, or when the client lost that listener (a thread that runs a delivery or the callback of `tpc_finish` returns at the reply). `client_label` goes in `set_client_label`, without a reply, on each connection of the pool after its `get_info`, so the log lines of the server name every connection. `new_addr(addr)` gives the addresses of the next attempt to connect and sets `_addr`, as ZEO's does; the client keeps its server until it loses it, then connects to the new addresses and verifies its cache there. The client declares each interface of `get_info` that ZEO declares (`IStorageRestoreable`, `IStorageIteration`, `IStorageUndoable`, `IStorageCurrentRecordIteration`, `IBlobStorage`, `IExternalGC`). `len()` and `getSize()` read the `length` and `size` of the last `info` call that the server sent on a connection of the pool, after a commit or a pack, also on a connection that left the pool since, else of `get_info` of the listener, as `_info` of ZEO holds them; a new server starts again from its `get_info`.

**`zoe.plone` and the sequences (F29).** In Plone 6.1, one shared counter gives ids to new content: `portal_uidgenerator`, the `UniqueIdGeneratorTool` of Products.CMFUid. Its `__call__` adds 1 to the int `_uid_counter` of the tool. CMFEditions calls it through `portal_historyidhandler` for the history id of each object that it versions, and plone.app.versioningbehavior versions each new Document, Event, Link and News Item. So two editors who create content at the same time write the tool, and one of them gets a `ConflictError`. When the storage of the tool is `zoe.Storage` or `zoe.zeo.ClientStorage` and gives sequences, `zoe.plone` gives the tool its ids from a sequence of the store and never writes the tool in the transaction that asks for the id; the ids stay unique and above the ids that the stock counter gave. Otherwise the tool works as stock. The ZCTextIndex lexicon, the intid utility, the catalog and `BTreeFolder2.generateId` take new ids from a volatile counter with a random start and write no shared counter, and the `Length` objects of Plone 6.1 are counts or change counters. `zoe.plone` leaves them alone.

The mechanics. Plone loads `zoe.plone` through the plone.autoinclude entry point of zoedb, in every instance that has zoedb, with the extra or without; on `IDatabaseOpenedWithRoot`, it replaces `UniqueIdGeneratorTool.__call__`. The test layers of plone.testing do not send that event, so the Plone suites run without the wiring. Each tool has its own sequence, named `zoe.plone.portal_uidgenerator:` and the oid of the tool in hex, so two sites in one root do not share one. The id is `base + value`, where `value` comes from that sequence. The tool keeps the range of the wiring in its attribute `_zoe_ids`, a tuple `(base, floor, mark, end)`: `floor` is the first id of the range, `mark` the largest value that a reservation of the range took, `end` the last id. An id is valid when `value > mark`, `floor < base + value <= end` and `_uid_counter` equals `end`. So `_uid_counter` is always the end of the ids that the wiring reserved, and the stock counter never gives an id that the wiring gave, also after zoe.plone is removed or the site moves to another storage. When an id is not valid, a reservation reads the tool on a connection of its own and writes it in a transaction of its own, with the note `zoe.plone: reserve ids of portal_uidgenerator`, never in the transaction of the caller. Within a range, a reservation raises `end` and `_uid_counter` to the id plus 99, and `mark` to the value, so the tool gets one write for each 100 ids. In one store, the value of a caller is always above the `mark` that its snapshot shows: the values strictly increase, and the caller takes its value after its snapshot starts. A value at or below that `mark` therefore comes from another store, whose sequences start again at 1: a copy through `iterator` and `restore` (zodbconvert), which does not copy the sequences, or a zexp import, which gives the tool a new oid and so a new sequence. A reservation starts a new range at `max(_uid_counter, end) + 1`, above every id of the site, for the first id of a site, for such a value, and when `_uid_counter` is not `end` (the stock counter gave ids meanwhile, or is an old `Length`). A new range then takes 100 more values of the sequence and makes the last one its `mark`, so `mark` is always at least 101. What is guaranteed: in one store, the ids of a site are unique and above every id that the stock counter gave; after a copy into a new store, the copy is detected and gives no id again, unless more than `mark` values of the sequence of the tool are taken in the new store before the first reservation there commits, which takes more than 100 reservations that fail after they took their value. A copy into a store that already gave values of the sequence of the tool is not detected. The reservations of one process wait for each other; two processes that reserve at the same time conflict on the tool in the reservation transaction, which reads the tool again and retries, at most 100 times. A new range costs at least 100 ids and 100 calls of `sequence_next`. A storage that does not give sequences (`Unsupported`), a tool that is new or changed in the transaction of the caller, and a storage that wraps a ZOE storage keep the stock counter.

## Async and free-threading

Async lives in the server and in the client's ability to overlap I/O; the persistent-object model stays synchronous because a ghost loads inside `__getattribute__`, where nothing can await. Free-threading is what makes one Zope process commit in parallel.

**What is asynchronous**

| Layer | Today | In this design |
| --- | --- | --- |
| ZEO client | asyncio loop on a helper thread, synchronous facade to ZODB | unchanged for `ZEO.ClientStorage` and for `zoe.zeo.ClientStorage` with `native=False`; the native client of F28, the default of `zoe.zeo.ClientStorage`: `zoe-client` on a tokio runtime of 2 threads inside the extension, which start at the first open; a synchronous facade to ZODB whose calls wait without the GIL; several transactions at once on a pool of connections, with one dispatcher task that orders the tids of the listener (ADR 0036); the dispatcher and the pool take no lock that a load waits for, beyond the short pick of a connection; a hit of the client cache (ADR 0034) runs on the calling thread, takes no lock and keeps the GIL |
| ZEO server | asyncio in Python, one loop, GIL-bound | tokio, work-stealing runtime, blocking pool for storage calls, no GIL on the request path |
| Request pipelining | message ids, concurrent calls | handled concurrently; replies out of order; `prefetch` becomes a real batch |
| Storage core | — | synchronous by design; async wrappers around it, never inside |
| Object loading in Zope | synchronous on attribute access | unchanged |

**Async storage interface for new clients.** The server exposes the same methods as `async fn` in a Rust client crate (`zoe-client`) and, through PyO3, as awaitables (`await storage.aload_before(oid, tid)`, `await storage.aprefetch(oids)`, `await tm.acommit()`). This is what an async web layer such as collective.starlette uses for things that are not Plone page requests: streaming, WebSocket handlers, background jobs. A Plone request itself keeps running on a worker thread with a synchronous Connection. Built so far: `zoe-client` speaks the ZEO 6 msgpack protocol as `ZEO.ClientStorage` does. `Client::connect(addr, storage)` sends `M5` and `register`. The client then gives `last_transaction`, `new_oids`, `load`, `load_before`, `history`, a transaction (`begin`, then `store`, `vote`, and `finish` or `abort`), the invalidations of the other clients, and `close`. Each reply goes to its call by its message id, in any order. One transaction runs at a time on a client, as with the commit lock of `ZEO.ClientStorage`. The client sends the heartbeat of a stock client every 60 seconds, so an `--idle-timeout` above 60 seconds, as the default of 300 is, never closes it. It resolves no conflict: a conflict that the vote lists, or a `ConflictError`, is `Error::Conflict`, and a vote that fails sends `tpc_abort` and waits for its reply. A lost connection fails every pending call and every later call with `Error::Disconnected`; a `Client` does not reconnect, a `Pool` of `Pool::with_reconnect` does (see F28). The client reaches the network, its tasks and the time only through the trait `Runtime` (connect, spawn, sleep), with `Tokio` in production, and every `select!` is `biased;`, so the simulator of N18 can run it. A transaction uploads a blob as a stock client does without a shared blob directory (`store_blob`: `storea`, `storeBlobStart`, chunks of 59,000 bytes, `storeBlobEnd`). `Client::open(runtime, addr, storage, options)` registers read-only when `Options::read_only` says so, declares `Options::extensions` in a third argument of `register`, registers again with two arguments when a stock server refuses the third with `TypeError`, and calls `get_info`; the client then uses an extension only when the server accepted it, as `sequence_next` does with `sequences`. `Client::begin_with` sends the tid and the status of `tpc_begin`. A transaction also has `check_current_serial`, whose stale serial fails the vote with `Error::ReadConflict`, and `vote_resolved`, which gives the oids that the server resolved. `load_serial` loads one revision. `Client::call` and `Client::notify` send any call of the server, with and without a reply, `Client::ping` calls `ping`, and an error reply keeps its value (`Error::Server::value`), so a bytes argument stays bytes. A transaction has `delete_object`, `restore` and `undo` (`deleteObject`, `restorea`, `undoa`). `Options::client_label` sends `set_client_label` after `get_info`. `Client::pushed_info` gives the map of the `info` calls of the server, merged, with a stamp of the process. A `Pool` sends `call` and `notify` on its listener, and refuses a call of a transaction there; `Pool::prefetch` loads oids into its cache at once, `Pool::sync` pings the listener and waits for the delivery of what it read, and `Pool::info` gives `get_info` with the last sizes that the server sent. Call timeouts are not built in `zoe-client`, and the awaitables of the Python side are not built.

**Prefetch-then-touch.** The one pattern that lets async code use persistent objects safely: `await conn.aprefetch(oids)` warms the cache, then synchronous traversal hits only the cache. The server supports it with batch loads; the ZEO client already issues `prefetch` as concurrent calls.

**Transaction managers.** Async code uses an explicit `TransactionManager` per task (`db.open(transaction_manager=tm)`), never the thread-local default. `zoe.asyncio.transaction()` is a small context manager that does this and runs commit on the pool.

**Free-threading in one process**

- The extension declares `Py_mod_gil_not_used`; on 3.14t the GIL stays off when `zoe` loads.
- ZODB's contract already is one Connection per thread, nothing shared but the DB. The core is `Send + Sync`; the lock manager, group commit, the pack state and the sequence counters are the only shared mutable state, and all are behind mutexes sized for disk latency, not instruction latency.
- Two worker threads in `tpc_finish` at once: both hold their per-OID locks, both join the same commit batch, one fsync, both acknowledged. Today `FileStorage` takes one storage-wide `_commit_lock` from `tpc_begin` to `tpc_finish`.
- `tpc_vote` runs conflict resolution on the caller's thread; with the GIL off, two threads can resolve at the same time, and native merges need no Python at all.

**Thread-safety invariants the core enforces**

1. The thread that calls `tpc_begin` drives the transaction: the core records the thread id and refuses `store`, `restore` (and `storeBlob`), `checkCurrentSerialInTransaction` and `vote` from another thread with `WrongThread`, which turns a class of silent corruption into an exception. A refused call changes nothing. `tpc_finish` and `tpc_abort` may come from any thread, as ZODB lets them.
2. Locks are acquired in oid order; a request out of order is refused, never granted.
3. A backend write transaction is opened only by the commit-batch leader, a pack batch, a sequence reservation and a restore of a sequence end (`Sequence::restore_end`). The leader and a pack batch open it under the commit sequencer; a sequence reservation and a restore of a sequence end open it outside the sequencer and write only the row of their sequence, never a record, a transaction row or a `meta` row. Readers use snapshots and never block them.
4. Every shared structure is covered by a ThreadSanitizer CI job and by `loom`-style interleaving tests on the lock manager.

**What stays on persistent and BTrees.** With `zoe` loaded but `persistent`, `BTrees` and `zodbpickle` undeclared, CPython re-enables the GIL at import and the parallel-commit benefit disappears. The first step of the roadmap is therefore upstream: `Py_mod_gil_not_used` plus a thread-safety audit in those three packages (zope.interface already did it in 8.3). The LRU ring in `cPersistence.c` changes on nearly every attribute access. On 3.14t the `persistent` fork takes the cache's critical section there too, because a sweep from another thread (`DB.cacheMinimize()`, `cacheGC()`) otherwise corrupts the ring; this costs about 6 ns per attribute access on 3.14t and nothing on the GIL builds. The one-Connection-per-thread rule still holds for the objects: a sweep from another thread of a Connection in use stays unsupported, because the thread that uses it can get spurious `AttributeError`s or read an instance dict that is being freed. With the stock `persistent` on 3.14t, a multi-thread stress of the pattern of ZODB's `test_race_loadopen_vs_local_invalidate` fails on every storage that was measured: on `zoe.Storage` and on `FileStorage` with a `SystemError` in `ZODB.serialize` or a spurious `AttributeError`, and on `MappingStorage` with a crash of the interpreter. The test itself passes most runs. ZOE's tests skip it on free-threaded builds until the fork is in use. A Rust port of `persistent` and `BTrees` is a separate project; it would share the native merge code from section 5.

## ConflictError strategy

ConflictError is optimistic concurrency at pickle granularity: two transactions write the same object and the second to vote loses. A storage cannot abolish that; it can resolve more conflicts, shrink the window, or serialise writers on the hot object so they wait instead of failing. The design does all three, in that order of cost.

**Step 0: measure before building.** Zope logs the oid and class on every ConflictError it retries or raises. Before the native-merge list is final, rank the conflicts of the Plone end-to-end benchmark (B5) and of the log replay (B6) by class and by oid; the top ten classes decide which merges go native first. Both run on a synthetic site, and their logs replace a sample of production logs: the repository and CI hold no production data. B5 ranks first the posting dicts in the `_wordinfo` buckets of ZCTextIndex, then the shared `BTrees.Length` counters that every save writes (`docs/findings/plone-end-to-end.md`). Expected suspects in Plone: catalog index buckets (`IOBTree`, `OOBTree`, `IITreeSet`), `BTrees.Length.Length` in indexes and BTreeFolder2, the BTrees of the ZCTextIndex lexicon (`_wids`, `_words`), the `portal_uidgenerator` counter of CMFUid, and annotations on shared objects such as the site root and the registry.

**Lever 1: resolve in Rust, never in Python on the server.** Today a conflict on a bucket costs three unpickles and one pickle in Python on the ZEO server, per object, per retry, and the server must carry every Plone egg to do it. Section 5 replaces that with three tiers: structural merges for buckets, sets and `Length`; field-level three-way merges for any object whose merge policy allows it, so two editors changing different fields of the same item no longer conflict; and, for classes with their own `_p_resolveConflict`, resolution on the client, where the class already lives. The policy is derived from Dexterity schemas by `zoe.plone`, strict by default, and loosened per class only after shadow mode has shown on production conflicts that the merge would have been right.

The posting dicts of ZCTextIndex (ADR 0042, `docs/spikes/posting-dicts.md`). ZCTextIndex keeps the postings of a word that 10 documents or fewer hold as a dict of document id to score, a value of the IOBTree `_wordinfo`. BTrees compares two values with `<`, which raises for two dicts, so ZODB's resolver refuses every bucket in which it must compare two dicts, and these refusals are most of the saves of B5 that fail at their first attempt. A store whose postings are all trees changes almost nothing, because ZCTextIndex makes a new dict for each word that enters an index. With `posting-dicts on`, tier 1 compares posting dicts entry by entry and merges two changes of one dict against the old dict; it refuses an entry that both sides changed differently, or that one side changed and the other deleted, a dict against a tree, a dict of more than 10 entries on one side, and a merged dict of more than 10 entries or of none. A word that both sides add or that one side deletes stays a refusal of BTrees, so the `Length` of the words of an index stays exact. The entry of a document is only written by a transaction that indexes or unindexes that document, and two such transactions collide on `_docwords` anyway, so a merge only joins the entries of different documents. A word of more than 10 documents keeps its postings in an `IIBTree` of its own, which mostly holds its one bucket inline; when a reindex removes the document of the lowest id, BTrees refuses the delete of the first key of that bucket (reason 13), which protects a parent node that the root of a tree of one inline bucket does not have. The first-key rule, under the same key, lets that delete through there, when the committed transaction made it and the inline bucket has no next bucket; ADR 0042 says why a delete by the new transaction stays a refusal (a node inside a tree that a record cannot tell from a root).

**Lever 2: shrink the window.** Faster vote and finish (group commit, no Python on the server path) shorten the interval during which a second writer can read a serial that is about to be stale. This reduces the probability of conflict, not its possibility.

**Lever 3: early write-intent locks (ADR 0045).** This is the one mechanism that avoids conflicts on an object that cannot merge. A lock taken when the transaction first marks an object changed is not enough: ZODB reads every object at the snapshot of the start of the transaction, and `register` comes after the load, so a writer that waits there holds a stale state when it gets the lock, and its vote fails as without the lock (`docs/spikes/early-lock-hook.md`). So the lock comes before the read: an object of a hot class takes its intent lock when its state loads. A second writer waits before it reads, then reads the commit of the first one, and its vote has no conflict. The wasted work of the retries becomes one wait.

Mechanics on the Plone side: `early-locks on` and `early-lock-classes` in `<zoe>` or `<zoeclient>` name the hot classes, by the `module.name` that ZODB pickles. The storage then puts the methods of `zoe.zodb.LockingConnection` on the `Connection` of ZODB, once per process, and keeps the methods that it replaces as `Connection` has them then; each patched method checks the storage of the database of the connection first, and does what the replaced method does for a storage without hot classes and for a historical connection, which takes no lock. `setstate` of an object of a hot class calls `lock_intent([oid])` with the owner of the connection, waits for the grant, and loads the record of the serial that the grant returned, past the snapshot of the transaction; when a savepoint of the transaction holds a change of the oid, it loads the savepoint, under the lock. At the end of each transaction, with an implicit or an explicit transaction manager, and at the close of a connection that no transaction joined, the connection turns the hot objects of its cache into ghosts, so the next access loads them again with the lock. `tpc_begin` binds the owner of the connection to its thread, also when the connection took no lock, so the transaction of the storage adopts the locks of the connection and never those of the default owner of the storage; the end of the transaction releases them, also when it did not commit. A load of a hot object below a hot object that the transaction holds gets `LockOrder`; the connection then releases its intent locks and takes them again with the new oid in one `lock_intent`, in oid order, goes on when the serial of each hot object that it read is unchanged, and raises `ConflictError` otherwise. Then the transaction manager of the connection keeps the hot oids of the attempt as a retry hint: the first load of a hot object in its next transaction takes them all with its own oid, in oid order, in one `lock_intent`. The hint is on the manager, so it serves a retry of Zope on another connection; the next transaction uses it or drops it at its end. There is no batch: a load waits for its own lock. A class of tier 1 is never hot: tier 1 and the lock hand-off serve it. A read-only storage or client has no hot class. The locks are advisory, so a client whose server did not accept `lock_intent`, as a stock ZEO 6 server, takes no early lock and logs one WARN event at each connection, and so does a `<zoeclient>` that runs the client of ZEO inside because its server does not speak M5. `<zoeclient>` with `native false` refuses `early-locks on` with `ValueError`: the client of ZEO has one session and one commit lock for every thread.

Costs and controls:

- A transaction sees a hot object at a state newer than its snapshot: a read skew against the other objects. A hot class is one whose invariants do not span other objects (a counter, a queue head, a lock record).
- Every transaction that reads a hot object waits for its lock, also one that does not write it. A hot class is one that its readers nearly always write.
- A hot class must be a leaf record, whose state refers to no other persistent object: a hot object read past the snapshot can name a child that the snapshot does not hold, or holds at an older state, and the load of that child can raise `ReadConflictError`.
- Long transactions hold locks longer: `lock-timeout` (default 10 s) turns a wait into a `ConflictError`, which Zope retries as today. Through `zoe serve`, a session that holds intent locks 60 s without a `tpc_begin` loses them.
- Deadlocks are prevented by oid ordering; a request out of order is refused, and the connection asks again for the full set in order.
- `readCurrent` takes its shared lock at the vote, as without early locks.
- Under a free-threaded Zope with many worker threads, a waiting thread costs nothing; under a four-thread instance a hot object can stall all four, so early locks stay off by default.

**Lever 4: structural, in Plone.** Counters as `Length`, queued indexing (Plone's `CMFCore` indexing queue already defers catalog writes to the end of the transaction), shorter transactions in batch jobs, splitting hot BTrees by key range. These stay application work; the metrics from section 7 tell you where.

**What remains.** Two transactions writing the same non-mergeable object with early locks off still conflict, and that is correct: the alternative is lost updates. The target in the success criteria (an order of magnitude fewer ConflictErrors reaching Zope on a production replay) comes from levers 1 and 3 together; the harness in section 11 measures each separately.

## Catalog acceleration and search

The Plone catalog is where write amplification, ConflictErrors, cold starts and memory meet, so ZOE treats it as a first-class target in three steps: the storage-level relief already specified (native merges, early locks, a shared hot cache); a read-side accelerator, `zoe-catalog`, that mirrors ZCatalog's indexes in memory and answers queries in Rust behind the unchanged ZCatalog API; and a write-side projection that replaces bucket writes with commutative deltas. A native BM25 text index on tantivy ships with the accelerator as the first ZOE-native index.

&#91;embedded content: catalog query path · mirror or Python, same brains\]

The fallback is the correctness guarantee: anything the mirror does not cover takes the path Plone has always taken.

**Where the catalog hurts today**

| Path | What happens | Cost |
| --- | --- | --- |
| write | one content change reindexes 20 to 40 indexes: dozens of bucket pickles and `Length` counters per transaction | most of the pickle volume and most of the ConflictErrors in a Plone site |
| read | each query loads bucket pickles into the process cache, intersects `IISet`s in C, and sorting on `modified` loads the sort index's `_unindex` for every hit | slow until warm, minutes of crawl after every restart |
| memory | every Zope process holds its own copy of the same buckets | N processes, N catalogs |
| text | `ZCTextIndex` scores with Okapi BM25 in Python over word-id buckets, with a splitter that knows no language, no stemming, no accent folding, no snippets | sites bolt on Solr or Elasticsearch and inherit a second system and its consistency lag |

**Step 2: the mirror, `zoe-catalog`**

- Scope: `FieldIndex`, `KeywordIndex`, `DateIndex`, `DateRangeIndex`, `BooleanIndex`, `UUIDIndex`, `ExtendedPathIndex`, `GopipIndex` (sort), plus the `data` metadata table, `uids` and `paths`. `ZCTextIndex` is not mirrored; the native text index below replaces it.
- Representation: per index a map from key to a roaring bitmap of rids and the reverse map from rid to keys; sorted rid arrays for sort indexes; a trie for the path index; metadata rows in a columnar table so brains need no bucket at all.
- Discovery and build: catalog roots are found by class (`Products.ZCatalog.Catalog.Catalog`) at startup; each index's BTree roots are traversed once in a background job (readiness metric `zoe_catalog_mirror_ready`), then maintained incrementally: at `tpc_finish`, before invalidations go out, every committed bucket of a mirrored index is decoded by `zoe-pickle` and applied.
- MVCC: the mirror is versioned per tid with structurally shared persistent maps and copy-on-write bitmaps, kept for a window (default 10,000 tids or 10 minutes). A query carries the client's snapshot tid and is answered as of that tid, so a result never names an object the Connection cannot load. Outside the window the query falls back to the Python path.
- Protocol extension `catalog_query(catalog_oid, tid, plan)`: the plan is ZCatalog's query normalised (index, operator, values or range, `sort_on`, `sort_order`, `sort_limit`, `b_start`, `b_size`, requested metadata). The reply is the ordered rids, the metadata rows and the total count. In-process mode calls the same function through PyO3 with no wire.
- Plone side, `zoe.plone.catalog`: a hook on `Catalog.search`, the way `collective.solr` hooks in, routes a query to the mirror when every index and operator in it is supported and builds a `LazyMap` of brains from the returned rows; otherwise the whole query takes the Python path. Security stays in Plone: `allowedRolesAndUsers` is a `KeywordIndex` like any other and arrives in the plan as today.
- Correctness is a differential test, not a claim: every query of the Plone test suites and a recorded production query log run through both paths, and rids, order and counts must be identical, with ties broken by rid as ZCatalog does.
- Memory: roaring bitmaps and shared structure put a one-million-object catalog with thirty indexes in the low hundreds of megabytes, once for the whole cluster instead of once per process.

**Native BM25 text index.** Plone already scores with BM25; what it lacks is everything around the formula, so the native index is tantivy with BM25 (`k1`, `b` tunable), Snowball stemmers for the site's languages, ASCII folding, stop words, phrase, prefix and fuzzy queries, per-field boosts (`Title^3`, `Description^1.5`, `SearchableText^1`) and snippet generation. One tantivy index per catalog, a field per text index, and a field per language when `plone.app.multilingual` is installed, chosen from the object's `Language`.

- Why it is the first native index: text-index buckets hold word ids, not text, so a BM25 index cannot be rebuilt from them. `zoe.plone` therefore provides `ZoeTextIndex`, a ZCatalog index class whose `index_object` sends `(rid, index, text)` to the core as a delta record inside the same transaction and whose `_apply_index` queries tantivy. This pilots the delta mechanism of step 3 on the one index with the largest quality gain.
- Consistency: tantivy commits in batches a few hundred milliseconds behind the tid; hits are filtered by the mirror's bitmap of rids existing at the query's snapshot tid; snapshots older than the window fall back to the Python index.
- Durability: the deltas are records in the ZOE transaction, so the tantivy directory beside the store is a cache that `zoe catalog rebuild-text` recreates without Plone.
- Compatibility: a translator maps ZCTextIndex query syntax (`AND`, `OR`, `NOT`, quoted phrases, trailing `*`) to tantivy's; `sort_on='relevance'` keeps meaning BM25; a compatibility switch reproduces the old ranking for sites whose tests pin it. Enhanced mode is the default; fuzzy matching, field boosts and snippets reach new interfaces through the `@search` restapi extension.

**Step 3: the catalog as a projection (phase 10, design only here).** Plone keeps computing index values in Python at commit, but instead of writing buckets it emits deltas, `(catalog, rid, index, old value, new value)`, as a record type in the same ZOE transaction. The core applies them to the mirror and appends them to a persisted delta log per catalog with periodic snapshots. Deltas on different rids commute, so two editors indexing different documents never conflict on a shared bucket again; the only true conflict left is the same rid and index in two concurrent transactions, which is raised as today. Catalog BTrees and `Length` counters leave the store, which removes most of the write amplification. ZCatalog objects stay as thin proxy index classes, so `plone.app.querystring`, collections and navigation never notice; migration is one rebuild. ACID holds because the deltas ride the transaction that changed the content, and in-process mode works the same way.

**Metrics.** `zoe_catalog_queries_total{path=native|python}`, `zoe_catalog_query_latency_seconds`, `zoe_catalog_mirror_lag_tids`, `zoe_catalog_mirror_build_seconds`, `zoe_text_commit_lag_seconds`, `zoe_catalog_fallbacks_total{reason}`.

**Testing, on top of section 11.** The differential suite above; `zoe-bench catalog` with a query mix replayed from production logs at concurrency, warm and cold; text relevance checked against a labelled set of queries from a real site, in that site's language. Acceptance: identical results on every differential run; a five-index intersection with a sort on a one-million-object catalog under 5 ms at p99 warm; mirror ready within 60 s of a cold start on that catalog; a text query under 20 ms at p99.

**Roadmap placement.** Phase 6: the mirror, the native text index and the `zoe.plone.catalog` hook. Operations and data tools are phase 7, AI-native retrieval phase 8; Tier 3 is phase 9. The projection is phase 10, started only after the mirror has answered a long enough run of production queries identically.

## AI-native: MCP server and retrieval

ZOE exposes its store to agents through an MCP server and gives Plone content native retrieval, built on pieces the catalog work already provides: the delta pipeline carries the text, the mirror holds every object's `allowedRolesAndUsers` as a bitmap, and `zoe-pickle` turns any object into JSON. The vector backend is a choice: ZOE's own index stored in the DB for simple deployments, or Qdrant for sites that want a dedicated vector service.

**MCP server, `zoe mcp`.** A Rust MCP server on the official `rmcp` SDK, running inside `zoe serve` or standalone against a server, with stdio for local agents (Claude Code on an ops laptop) and streamable HTTP for remote ones. Crate `zoe-mcp`. Built so far: `zoe mcp --path STORE` (`ZOE_PATH`) opens a store folder read-only through Loupe's `Folder`, with `--blob-dir DIR` (`ZOE_BLOB_DIR`) as the blob directory of the store, `<path>/blobs` by default, as in `zoe verify` and `zoe convert`: the store does not record its blob directory (ADR 0027), and the open creates nothing in it or in its parent. On a store that was closed cleanly, the open changes no byte. A store that a writer left open gets its repair first, as in `zoe verify` (ADR 0032): the command writes only `zoe.redb`, and one line to stderr that holds `repaired the store`, never to stdout; a repair that fails ends the command with 1 and a message that gives the error of the system. It holds the lock of the store while it runs, so a running instance and `zoe mcp` never share a store, and serves the read-only ops tools `object_get`, `history`, `diff`, `references`, `space`, `verify` and `explain_conflict`, and the prompts `explain_transaction`, `why_conflict` and `summarise_changes`, over stdio. It runs as the ops principal of the local operator, with the read-only role, so it offers no tool that writes. `object_get`, `history`, `diff`, `references` and `space` call Loupe's function and give Loupe's JSON; `space` gives the newest 100 transactions of the growth with the count of all of them. `verify` calls `zoe_convert::verify` on the store of the folder (`Folder::store`) and gives the keys of `zoe verify --format json`, with at most 100 findings in each list, the full count of each in `totals`, and their sum in `findings`; a store with blob records whose blob directory has no layout file is a tool error, as for `zoe verify`, whose text names the blob directory and `--blob-dir`. `space` reads the sizes of the blob files in the same blob directory. The store keeps no record of conflicts until the resolution log of phase 4, so `explain_conflict(tid)` reads the history only: each oid that the transaction wrote (at most 100, with the count), with its class from the class pickle and its size, and the revisions of that oid just before and just after the transaction, with their user and description. Each prompt gives one user message with a request and the JSON that its tools give: `explain_transaction(tid)` the result of `explain_conflict`, `why_conflict(oid)` the class and the newest 32 revisions of the object, `summarise_changes(since)` at most 50 transactions after `since`, each with its records counted by class and at most 16 of its objects. Oids and tids are in ZODB form, and no result gives pickle bytes; an error of a tool is a result with `isError`, and the session goes on. stdout carries only MCP messages. The command ends with 0 when the client closes stdin, and with 1 when the store does not open. The console script of the wheel has no MCP server: `zoe mcp` there fails with 1 and names the `zoe` binary. The modes inside `zoe serve` and against a server, the `tail` resource and streamable HTTP come in phase 7.

| Family | Tools and resources | Ships |
| --- | --- | --- |
| ops and dev | `object_get(path or oid, as_of)` as decoded JSON, `history`, `diff(oid, tid_a, tid_b)`, `references(oid)`, `tail` as a resource with notifications, `space`, `verify`, `explain_conflict(tid)`; `pack` and `backup` behind the read-write role | phase 2, read-only, on a store folder; `tail` and the modes inside `zoe serve` and against a server in phase 7; they are Loupe's functions with an agent face, and the builder agents use them on the store they are building |
| content | `search(query, mode, filters, as_of, k)` returning passages with path, title, modified, portal type and a citation; `get_document(path)`; `list_children(path)`; `similar(path)` | phase 8 |
| prompts | "explain this transaction", "why did this object conflict", "summarise what changed since tid" | phase 2 on a store folder; on a server in phase 7 |

Security: the MCP server runs as a principal, and every content result is filtered by intersecting the caller's roles with the `allowedRolesAndUsers` bitmap before ranking; objects outside the catalog are visible to the ops role only. Transport security is the server's TLS with read-only or read-write certificates, as for Loupe; a Plone-authenticated gateway (`@mcp` in the restapi, so site users' agents inherit Plone's login and permissions) is a later addition on top, not a replacement.

**Retrieval, `zoe-vectors`**

1. Chunking: the `(rid, index, text)` delta that feeds tantivy is split into passages with offsets; passages are stored in the core, versioned by tid, so retrieval returns text and not pointers. One default policy (passage size, overlap, which text indexes) with overrides per `portal_type`, because minutes and decisions chunk differently from news items.
2. Embedding: asynchronous, like tantivy commits, with `zoe_vectors_lag_tids` as the metric and the as-of-tid bitmap filter so a deleted page never returns. Providers are pluggable: a local multilingual model through ONNX in the server process is the default, because a site's content should not leave the site owner's server by default; remote providers (Mistral, Voyage, OpenAI) are opt-in per site and logged as such.
3. Vector backend behind one trait, `VectorIndex` (`upsert`, `delete`, `search(vector, k, prefilter)`, `rebuild`), chosen in the stanza:

| Backend | What it is | When |
| --- | --- | --- |
| `builtin` | vectors stored in the ZOE store itself, in a `vectors` key space keyed `(catalog, rid, chunk, tid)`; brute-force SIMD search under a configurable size, an HNSW graph above it, the graph cached beside the store and rebuilt from the vectors when missing | the KISS deployment: no extra service, vectors in the backup, and `search(as_of=tid)` answers what the index knew at that tid because the vectors are versioned like everything else |
| `qdrant` | a Qdrant collection per catalog over gRPC; payload carries rid, portal type and roles for pre-filtering; the as-of bitmap is applied after an over-fetch | sites that already run Qdrant or want vector search scaled separately |
| others | the trait is small enough for pgvector or Milvus later | not planned |

4. Hybrid search: BM25 from tantivy and vectors from the backend fused by reciprocal rank, behind the same `catalog_query` extension, the `@search` restapi extension (`mode=bm25|vector|hybrid`, `return=passages`) and the MCP `search` tool. Security filtering happens before ranking in every mode.
5. Rebuild: `zoe catalog rebuild-vectors` re-embeds from the stored passages with no Plone involved; switching backend is a rebuild.

**Metrics.** `zoe_mcp_requests_total{tool}`, `zoe_mcp_denied_total{reason}`, `zoe_vectors_lag_tids`, `zoe_embed_latency_seconds{provider}`, `zoe_vector_search_latency_seconds{backend}`, `zoe_vectors_remote_bytes_total` (what left the server, by provider).

**Testing, on top of section 11.** MCP conformance with the reference client; a security suite that asserts an anonymous principal never receives a restricted passage across every mode and backend; backend equivalence (`builtin` and `qdrant` return the same top-k on a fixed corpus within a tolerance); retrieval quality on the same labelled query set against BM25 alone; lag and as-of correctness under a write load.

**Roadmap placement.** MCP ops tools and prompts on a store folder in phase 2, a thin layer; the modes inside `zoe serve` and against a server, the `tail` resource and streamable HTTP in phase 7, with Loupe's server mode. Content tools, chunking, embeddings, both vector backends and hybrid search are phase 8, AI-native; Scale-out is phase 9 and the catalog projection phase 10.

## Deployment

The same wheel and binary cover a laptop, a single server and a Kubernetes cluster; what changes is who opens the store directory.

**Simple.** One Zope instance with `<zoe>` in `zope.conf`. No server, no extra process, one directory to back up. With free-threaded Zope this instance commits in parallel on its own.

**Clustered, bare metal or VMs.** `zoe serve` on the storage host, instances with `<zeoclient>` as today. Supervisor or systemd unit shipped in the package; the server is a single static binary, no Python and no Plone eggs on the storage host.

**Kubernetes**

| Tier | Shape | What you get | What you give up |
| --- | --- | --- | --- |
| 0 | one Plone pod, in-process storage, PVC, `Recreate` strategy | simplest possible site, no server | no horizontal scaling of Plone |
| 1 | StatefulSet ×1 for the server, one PVC (redb + blobs), Plone as a stateless Deployment | horizontal Plone scaling, seconds of downtime on a reschedule, full observability | a single point of failure for writes |
| 2 | leader + follower StatefulSet ×2, two PVCs, log shipping, leader election through the Lease API, a Service that follows the lease | automatic failover in seconds, read-only clients served by the follower at a lagged tid | more disk, a replication lag to watch |
| 3 | server Deployment ×N, FoundationDB or TiKV cluster as backend, S3 for blobs | stateless fronts, no PVC on the server, durability and failover owned by the KV cluster | an extra network hop per operation; the FDB transaction limits |

**Tier 1 manifest essentials**

- `StatefulSet` with `replicas: 1`, `podManagementPolicy: OrderedReady`, a `volumeClaimTemplate` on an SSD storage class; `fsync` latency of the class decides write throughput, so benchmark the class before choosing it.
- `readinessProbe` on `/readyz`, `livenessProbe` on `/healthz`, `terminationGracePeriodSeconds` above `shutdown-timeout`.
- A `Service` on the ZEO port and a second on the admin port; a `ServiceMonitor` for Prometheus.
- `PodDisruptionBudget` with `maxUnavailable: 0` so a node drain waits for a manual window until Tier 2 exists.
- Backups: a `CronJob` running `zoe backup --to s3://…` (incremental, by tid range, through the iterator) and `zoe verify`. Built so far: `zoe backup --to DIR` writes dumps into a local directory, and `zoe verify --backup DIR` checks them (see "`zoe backup` and `zoe restore`: dumps"). Both open the store read-only and take its lock, so they cannot run on a store that a running instance or a server holds. A backup through the server is a card of its own.

**Tier 2 mechanics.** The follower streams transactions from the leader's log (`iterator_start` from its own last tid, kept open) and applies them with `restore`; it is read-only to clients. Leader election: both pods renew a `coordination.k8s.io/Lease`; the holder serves writes. On lease loss the old leader closes client connections; clients reconnect through the Service, which selects by the `zoe/role=leader` label that a sidecar sets from the lease. Promotion requires the follower to be at the leader's last acknowledged tid; a leader acknowledges a commit only after the follower confirmed it when `replication acks=1` is set, which also replaces fsync on slow cloud disks.

**Backup and point-in-time recovery (continuous shipping is post-roadmap; dumps are the phase 2 answer).** The log shipping that feeds a follower feeds a bucket just as well: `backup.target = s3://bucket/zoe/main` makes the leader ship every committed transaction and every new blob to object storage as it commits, with a full snapshot on a schedule (`backup.snapshot = daily`) so a restore reads one snapshot plus the log after it. `zoe restore --from s3://... --to-tid <tid>` (or `--to-time`) rebuilds a store at any transaction still in the bucket, and `zoe backup verify` restores the latest snapshot plus log into a scratch directory and checks it against the live store's checksums; the Tier 1 manifest runs it as a CronJob and its result is a metric. The recovery point is the last shipped transaction, seconds behind the leader; repozo-style dumps through the iterator stay available for sites without a bucket. Encryption keys are never in the bucket: a restore needs the wrapping key from the file, environment or KMS it came from, which is the one secret an operator must keep outside the cluster.

**Tier 3 mechanics.** The backend trait maps onto an ordered KV: records under `(oid, tid)` keys, the tid sequencer under one key updated inside the same transaction, invalidations read from a tid-ordered change log that every front tails. Any front can take any client; clients see one Service. Blobs go to S3 with a per-front LRU cache. The FDB limits (5 s, 10 MB per transaction) are met by staging locally and committing in one short write; a commit larger than 10 MB is split by oid range inside one logical tid using FDB's atomic versionstamp ordering.

**Configuration and observability, all tiers.** Flags and `ZOE_*` variables, a `ConfigMap` for the server stanza, secrets for TLS and S3. Metrics as listed in section 7, with a Grafana dashboard shipped in the repository: commit latency, fsync batch size, lock wait, conflicts resolved by path, invalidation queue depth, replication lag (Tier 2), backend latency (Tier 3).

## Loupe: desktop inspector and editor

Loupe is a Tauri 2 desktop application for ops people and developers that opens a ZOE store or connects to a ZOE server, browses, edits, creates and deletes objects without a Python interpreter, travels in time, tails live commits and runs operations. It never opens a `Data.fs`; it converts one. Crate `zoe-loupe`, product name Loupe.

&#91;embedded content: Loupe · folder mode, server mode, reverse index and reindex hook\]

The tinted box is the app; everything it touches already exists in the design, except the reverse index it keeps for itself and the queue it leaves for Plone.

**Two ways in, same screens.** A store folder (exclusive, instance stopped, `zoe-core` in-process; a store that a writer left open gets its repair at the open, and the window shows `<path>: the store was not closed cleanly: repaired the store`, ADR 0032; a store that was closed cleanly gets no byte changed) or a running server (`zoe-client` over the ZEO protocol with TLS, read and write through the same two-phase commit as any client, so running Plone instances see Loupe's writes through invalidations). Because the wire protocol is ZEO's, Loupe also browses a classic ZEO server, read-only, which is how a site gets inspected before it is converted.

**Pickle layer, `zoe-pickle`.** A ZODB record is two pickles, class reference and state, written with one memo. The crate decodes both into a generic tree (class path, attributes, persistent references, blob references, primitives, containers). It reads the opcodes of protocols 0 to 3, so the records that Python 2 stores wrote in protocols 1 and 2 decode too. Each node keeps the opcode form that wrote it, and the encoder writes that form back: it never picks another one, and new values use protocol 3 with ZODB's `persistent_id` convention. Constructs it does not model (custom `__reduce__` callables, extension codes, Python 2 instances) become opaque nodes that re-emit their original bytes; editing inside one is refused rather than guessed. Fidelity is a tested property: decode then encode must reproduce every record of the conformance corpus and of a production copy byte for byte.

The decoder refuses what Python's unpickler refuses as malformed, for example an unknown protocol or a BINSTRING or LONG4 length of 2³¹ or more. It is stricter than Python in a few places: it refuses the opcodes of protocols 4 and 5, PROTO after the start of a pickle, values or a mark left on the stack at STOP, bytes after the state pickle, and text arguments that no pickler writes (for example a memo index with leading zeros, or an INT in octal or hexadecimal). No operation on the tree recurses once per nesting level, so a deep value cannot overflow the stack. Each record has a node budget, a parameter of each call: online readers such as Loupe use the default of 2²⁰ nodes, and pack and the converters pass the length of the record, which refuses nothing the input can hold. For pack and the converters a refusal is a hard error, never a record without references.

**Application invariants.** Raw edits bypass Plone: the catalog, `ObjectModifiedEvent` handlers, workflow, `modified` dates, the UUID index. Loupe is a scalpel, not a content editor, and the design says so in four ways:

1. Writes need an explicit expert mode per session.
2. Objects that are catalogued carry a badge, and the commit dialog lists which indexes will be stale.
3. Later, not in V1: an optional Plone integration, `zoe.plone`, shipped as the zoedb\[plone\] extra of the wheel, provides a reindex queue: Loupe appends the touched oids to a persistent `IOTreeSet` at a known path in the same transaction; the add-on drains the queue on the next request (or a clock tick), reindexes those objects and optionally fires `ObjectModifiedEvent`. With it installed, a Loupe edit is reindexed within seconds; without it, Loupe lists the touched oids and the operator reindexes by hand, which is the V1 answer.
4. Every commit is preceded by a dry run that shows the pickle diff and the list of transactions it would conflict with if any client has them in flight.

**Converters, `zoe convert` and a Loupe screen.** The goal is to replace `Data.fs`, so conversion is first-class and runs in Rust without a Python environment:

| Direction | Reader or writer | Notes |
| --- | --- | --- |
| `Data.fs` → ZOE | streaming `FileStorage` reader: transaction records, data records, back pointers, `BushyLayout` and `LawnLayout` blob directories | the migration path for every existing site; resumable by tid |
| RelStorage → ZOE | PostgreSQL via `sqlx`, history-preserving and history-free schemas, blobs from the blob directory or from `blob_chunk` | the second migration path |
| ZOE → `Data.fs` | `FileStorage` writer | the exit path, so nobody is locked in |
| ZOE → ZOE | iterator to a different backend | backend change, Tier 1 to Tier 3 |

Every conversion verifies transaction counts, last tid and a sample of records byte for byte, and writes a report. The report of `zoe convert` gives the number of problems on its line `problems`, then one line for each kind of problem with its count and no cap, then the list of problems: first the lines about the whole source, then at most 100 other lines and a last line that counts the others. The kinds are a stop before the end of the file, blob records without a blob directory (one problem), a missing transaction, a user, description or extension that differs, a missing record, a record that differs, a missing blob file, a blob that the store does not have, a blob that differs, a blob that the store does not read, and a failed read of the store. So the counts tell a copy without its blob files from a store whose pickles differ. The `Data.fs` converter restores each transaction as a deferred restore, and calls `Store::sync` after each batch of at most 1,000 transactions or 64 MiB of pickles and blob bytes, whichever comes first, and once after the copy pass, before the verification. After an error of the copy pass it calls `Store::sync` too, and returns the first error. So the copy runs at the rate of its reads, not of the fsyncs, a crash loses only the restores of the open batch, and the next conversion resumes after the last durable tid, which is a tid of the file. A conversion without a problem prints no count line. The library gives the counts with `Report::count` and `Report::problem_count` (`zoe_convert::ProblemKind`). The Python route, `zodbconvert` with the `zoe` storage, stays available for anyone who prefers it.

`zoe convert --from-data-fs FILE --path STORE` and `zoe convert --to-data-fs FILE --data-fs-blob-dir DIR --path STORE` run the first and the third direction (ADR 0028). `--data-fs-blob-dir` (`ZOE_DATA_FS_BLOB_DIR`) is the blob directory of the `Data.fs`. `--blob-dir` (`ZOE_BLOB_DIR`, the twin of the key `blob-dir` of the `<zoe>` section) is the blob directory of the store, `<path>/blobs` by default, in both directions: `--from-data-fs` puts the blobs of the store there and nothing in `<path>/blobs`. The store does not record its blob directory (ADR 0027). So `--to-data-fs` refuses a store with blob records whose blob directory has no layout file: it fails with 1 before it writes anything, and the message names the blob directory and `--blob-dir`.

**`zoe verify`.** `zoe verify --path STORE` checks a store without Python and opens it read-only, so it changes no byte of a store that was closed cleanly. A store that a writer left open gets its repair first (ADR 0032): the command writes only `zoe.redb`, and one line to stderr, for example `zoe verify: /srv/store: the store was not closed cleanly: repaired the store`. When the repair cannot write the file, as on a read-only file system, the command fails with 1, its message says that the store was not closed cleanly and gives the error of the system, and the store does not change. `zoe convert --to-data-fs` and `zoe pack --dry-run` open the store the same way. `--blob-dir DIR` (`ZOE_BLOB_DIR`) gives the blob directory of the store, `<path>/blobs` by default; the read-only open changes no byte and creates nothing in it or in its parent, also when it repairs the store. A store with blob records whose blob directory has no layout file is not the store of that directory (ADR 0027): the command fails with 1 before the walk, prints no report and names the blob directory and `--blob-dir`, instead of one finding for each blob. `zoe verify --backup` opens the store the same way. `Store::open_read_only` itself does not make this check. It walks every record key: each record frame, deletions too, and each blob record passes its checksum, and each blob file has the size and the BLAKE3 hash of its blob record. It reads each transaction row, one at a time, and each sequence row (`Backend::sequence_names` lists the names); a sequence name that is not UTF-8 is one finding in `checksums`, and then no sequence row is read. Of each oid, the newest record is the current record: its class comes from the class pickle, and its persistent references from `zoe-pickle`'s `persistent_ids` with the node budget of the record length, never from an unpickler. A reference to an oid without a current record is dangling, as `referencesf` would find it. The walk counts the oids that have a record, deletions included, and compares them with `object_count` (ADR 0033): a count that differs is one finding; a store of `ZOE format 1` has no count yet, and the report says so in one line, which is no finding. `--classes FILE` (`ZOE_CLASSES`) names the classes that the application provides, one `module.name` per line; each other class of the store is a finding, as the classes that `zodbverify` cannot import. A record that does not decode is a finding, not a crash. `--format json` (`ZOE_FORMAT`) prints one JSON document with oids and tids as integers, and these keys: `checksums`, the frames that do not read, each `{oid, tid, error}`, where a transaction row has `null` as its oid and a sequence row has `null` as its oid and its tid and names the sequence in `error`, except for a name that is not UTF-8, where `error` names the name before it, or the start of the list for the first name; `blobs`, the blob files that are missing or do not match their blob records, each `{oid, tid, error}`, where the `error` of a missing file says "missing" and the `error` of a damaged file does not; `references`, the dangling references, each `{oid, tid, missing}`; `pickles`, the current records whose references zoe-pickle cannot read, or that hold a reference whose oid is not 8 bytes, each `{oid, tid, error}`; `classes`, the class of each current record with its count, `{"module.name": count}`; `unknown_classes`, the classes that `--classes` does not name; `object_count`, the count that the store keeps, or `null` for a store of `ZOE format 1`; `count`, `{stored, counted}` when the count differs from the oids of the records, else `null`. The command exits with 0 when it finds nothing, 1 when it finds something, and 2 on a usage error. The walk keeps 8 bytes for each oid with a current record, and about 24 bytes for each reference to a later oid until it ends; ZODB gives a new object its oid when it pickles the parent, so nearly every reference in a store that ZODB builds points to a later oid. The library is `zoe_convert::verify`. The `verify` tool of `zoe mcp` calls it too; Loupe does not. A blob record without its record is not checked yet: no read of the store lists the blob records.

**`zoe backup` and `zoe restore`: dumps (N15).** `zoe backup --path STORE --to DIR` (`ZOE_PATH`, `ZOE_TO`) opens the store read-only, as `zoe verify` does (it repairs a store that a writer left open, and says so on stderr), and writes one dump file into the backup directory `DIR`: the full dump the first time, then a dump of the transactions after the last tid of the dumps, read through the iterator. A dump holds each transaction with its tid, user, description, extension and records, deletions included, the blob of each blob record with its size and BLAKE3 hash, and the end of each sequence, read after the last tid of the dump. It ends with the BLAKE3 hash of its bytes. ADR 0030 gives the layout. The backup writes the file under a temporary name, syncs it and renames it, so it never changes a dump that `DIR` holds. When the dumps end at the last tid of the store, it writes nothing and exits with 0. It takes a `flock` on `DIR`, so two backups never write into it together. It refuses, and writes nothing, when the store does not continue the dumps: when their last tid is not a tid of the store (the dumps of another store, or of a store restored from a part of the chain), and when the store was packed after that tid. A pack at that tid removes only history that the dumps hold, so the backup continues the dumps. The message asks for a new full dump in a new directory. One directory holds one chain, and `zoe backup` has no option to start a new full dump. `zoe restore --from DIR --path STORE` (`ZOE_FROM`) refuses a target that holds a store or other files, or a mount point, checks the BLAKE3 hash of every dump of the chain in a streaming pass before it writes anything, and rebuilds the store in the work directory `STORE.restore`: each transaction under its own tid, each blob after a check of its hash, and each sequence raised to its end in the dumps with `Sequence::restore_end`, so no value comes twice. Then it renames the work directory to `STORE`, and its report gives the last tid and its UTC time. A damaged dump, or a missing dump in the middle of the chain, fails the restore with 1, and a failed restore leaves nothing at the target. A missing newest dump is not seen: the restore gives the older state and exits with 0, as repozo does. A restore to an earlier point restores from a copy of a prefix of the chain. `zoe verify --path STORE --backup DIR` (`ZOE_BACKUP`) restores the dumps into a copy in its scratch directory, compares the copy with the store up to the last tid of the dumps, and removes the copy; the next paragraph gives the scratch directory and the order of the steps. Each transaction, record and blob record must be the same, but at or before the pack watermark of the store, a record or a transaction that a pack removed is no difference. A pack watermark after the last tid of the dumps is a difference; a pack watermark equal to it is not. Otherwise the current record of each oid at the last tid of the dumps must be the same, so a store whose history diverged differs. Each sequence of the store must end at or above its end in the dumps. A difference is a finding, and the command exits with 1; so does a damaged dump. With `--format json`, the report is one JSON document with the keys `dumps`, `last_tid`, `transactions`, `records`, `blobs`, `sequences` and `differences`. A restore commits each transaction with a sync, and reads each dump twice: once to check its hash, once to restore it. `zoe verify --backup` costs as much as a restore: a full copy of the store in the scratch directory and a sync for each transaction; it holds the lock of the store only for the comparison. The dumps are not compressed, and a restored store has a pack watermark of 0. The dumps keep the history that a later pack removes. The library is `zoe_convert::backup`, `restore` and `verify_backup`.

`zoe verify --path STORE --backup DIR` builds its copy of the dumps before it opens the store, so the store stays free while the copy is built; it opens the store read-only only for the comparison. `--scratch SCRATCH` (`ZOE_SCRATCH`) is the directory of the copy, on a filesystem with room for the whole store; without it, the copy goes to the temporary directory (`TMPDIR`). The copy is a throwaway store: the check builds it with the normal restore and removes it at the end, also when the check fails. A copy that a killed check left goes at the next check in the same scratch directory. A dump that does not restore fails the check with 1 before it opens the store. `--scratch` without `--backup` is a usage error.

**Operations tools in Loupe.** Each operations feature of the core and the server has a screen: open a fork of the current store at any tid and work in it; the last scrub, its findings and a button to run one; a pack dry-run as a treemap of what would go, the retention window with what is still revertible; `verify` findings with a jump to each broken reference; `rename-class` with a preview of affected objects; the change feed as the live tail, with filters by class and user; a Parquet export dialog that picks classes and attributes; the backup state (last shipped tid, last verified snapshot) and a point-in-time restore into a fork once continuous backup ships after the roadmap, which is the safe way to look at what the store held at a given moment.

**B. Performance**

1. `zodbshootout` (RelStorage's harness) is the public scoreboard. Scenarios: add, update, read cold, warm and hot, object sizes 1 KB and 100 KB, concurrency 1, 4, 16, 64 with threads and with processes, against `FileStorage`, ZEO 6, RelStorage on PostgreSQL 17 with history and without (`keep-history false`, on the same PostgreSQL), ZOE in-process and ZOE server, on one documented reference machine (CPU, NVMe, kernel, Python build, free-threaded or not). Results as p50, p99 and operations per second. Each value runs in its own `zodbshootout` run, after its warmup, on a fresh store that the harness removes when the value ends, and a cell fails before it starts when the disk of the work directory has less free space than one value needs. ZOE server is `zoe serve` with its default settings behind a stock `<zeoclient>` (the storage `zoe-server`), in the same cells as ZEO 6, and from phase 3 also behind the native client of F28 (the storage `zoe-native`: `<zoeclient>` with `native true`). A `read_cold` value of `zoe-native` counts only when the server counted at least one load for each object that it read; otherwise the run fails, because a client cache that `_cache.clear()` does not empty would turn it into a cache read. Each scenario entry records, for each worker process, whether the GIL was on at its end and which modules turned it back on. `just bench gate DIR` checks N4 against ZEO 6: it keeps the last result of each storage per machine, Python build and set, prints the ratio of operations per second in each scenario and cell, and fails when a cell of ZEO 6 has no counterpart or a ratio is below the gate. The gate checks `zoe-server` at 1 in every cell but `read_hot` (phase 2): with the stock client, `read_hot` empties ZODB's object cache, then reads from the cache of `ZEO.ClientStorage`, so none of its reads reaches the server; the gate prints the left-out rows and does not count them. `--python` makes only one Python build count and prints the others beside it. The phase 3 gate is the native gate, `just bench native` (ADR 0039), a driver of the harness and not a `zodbshootout` run: `zoe serve` through the native client against ZEO 6 through `ZEO.ClientStorage`, in the 5 scenarios of `zodbshootout` with its objects and data, threads at concurrency 1 and 16 and processes at 16, objects of 1 KB (100 per transaction) and 100 KB (10 per transaction). For each cell, each storage gets one server on a fresh store, one populate and one set of worker processes for the whole cell; `zoe serve` runs with its defaults, which store records raw, as FileStorage does. A scenario runs in pairs of batches: a batch of `zeo`, then of `zoe-native`, with the first storage swapped from one pair to the next and one warmup pair; a batch runs the same number of transactions in a row in each worker, as the inner loops of `zodbshootout` do, about 20 ms of them and at most 20, from the time of the warmup pair. The ratio of a pair is the time of the slowest worker for one transaction of ZEO 6 over the one of ZOE. After at least 10 pairs, a cell passes when the 99 % confidence interval of the mean of the log of its ratios is above 0, and fails when it is below 0; it stops at its first verdict, at 100 pairs or after 10 s of pairs, and a cell with no verdict then is undecided and fails. The run fails when the server counted fewer loads than the objects that the `read_cold` batches of `zoe-native` read. Each cell records the GIL of each worker process. The full set is the comprehensive benchmark of a later phase.
2. `zoe-bench`, a Rust load generator that speaks the ZEO protocol: N clients, pipelining depth, read/write mix, Zipf-skewed hot set, transaction size. It measures the two things `zodbshootout` cannot: contention (ConflictErrors per 1,000 commits, lock wait, retries) with vote-time versus early locks, and server saturation (loads per second at a p99 ceiling).
3. `criterion` microbenchmarks in the core: `load_before`, `vote`, `finish`, group-commit batching, lock manager acquire/release, native merge per bucket size, msgpack frame decode.
4. Fsync-class benchmark: the same write workload on NVMe, on a cloud PD or EBS class, and with Tier 2 replication acknowledgement instead of fsync; this is the number that sizes Kubernetes storage classes.

Four stacks: ZEO 6 with `ZEO.ClientStorage`, and `zoe serve` with the native client and `zoe.plone`, with ZEO's asyncio client and the ZOE extensions, and with a stock `ZEO.ClientStorage`; every other setting is the same. A production copy runs on the private runner of its site, as the corpora rule above says.
6. Transaction-log replay: replay N days of production transactions from the iterator at 1×, 4× and 16× speed with their original concurrency grouping, over a read load, and count conflicts raised, resolved natively and resolved in Python. This is the measurement behind the success criterion on ConflictErrors. In the repository and in CI, the log is synthetic: the transactions of a store that a B5 run on `zeo` kept (`--keep-store`), with the start of each transaction from the probe records of the run (`docs/spikes/log-replay.md`). `just bench replay RUN` (`bench/replay`) runs in the interpreter of the zoeclient Plone instance, so the resolver of ZODB has the classes of the site. Each run starts a new server on a new store and restores the transactions before the first request; then one thread plays the timed transactions in time order, through `ZEO.ClientStorage` to ZEO 6 and through the native client to `zoe serve`, in alternating runs, beside a second client that loads the oids of the log. A transaction starts at the start of its request in the probe records and reads the serials of its oids then, and it stores at its commit; one scale applies to every event, so the same transactions overlap at every speed (an open question on the card asks whether a faster speed should overlap more). It stores its own change applied to the state that it read (through `_p_resolveConflict` of the class; where that refuses on a bucket, a set or a BTree of one bucket, by putting the keys that it added, changed or deleted, with their whole values, into the items that it read; else its own record), and a commit that raises `ConflictError` is not retried. Each run counts the conflicts per 1,000 transactions by class and by path (`native`, `python-client`, `python-server`, `refused`; a vote that fails hides what it resolved before its refusal) and the `ConflictError`s, then loads every record of every acknowledged transaction; a run in which one does not load, or that replays no transaction, does not count. `just bench replay report FILE` gives the verdict of the success criterion, which is the gate of phase 4: the `ConflictError`s per 1,000 transactions of `zoe serve`, over its runs that count, are at most 10 % of ZEO's, and every speed has a run of each stack that counts.

Shapes: one process with 1 and with 16 threads on one client, and 16 processes with one client each. Records of 1 KB and 100 KB. Workloads: `cold`, loads of distinct oids from a client with no cache, each `loadBefore` before the tid after the last transaction, as a ZODB connection loads; `warm`, the same loads from a client that reopens the cache file that its `cold` round wrote, the open and its verification included; `commit`, commits of 100 new records (`new_oid`, `tpc_begin`, `store`, `tpc_vote`, `tpc_finish`). Servers: `zoe serve` and a ZEO 6 server with msgpack (the protocol M5, the only one that the native client speaks), each client against each. Both clients run the same calls in the same order on the same server state: the loads run on one store that no round changes, and each commit round on a fresh store. Each row runs in at least three rounds that interleave the clients, each round in its own process, and reports calls per second, p50 and p99 of a call, client CPU per object, and the spread of the rounds. Against `zoe serve`, the server counts the loads: each load of a `cold` round reaches it, and no load of a `warm` round does. The result names the machine, the Python build, the modules that turned the GIL back on, and the versions of both clients. `just bench client` runs it, and `just bench client report FILE` gives the verdict: the native client beats `ZEO.ClientStorage` when, in every row against `zoe serve`, it has a higher rate and a lower client CPU per object. A row against the ZEO server is printed and does not count.

**C. Durability and crash consistency**

1. Simulated filesystem in the core tests: a `Vfs` trait with an in-memory implementation that records every write and fsync, then replays prefixes, reorders unsynced writes and truncates the tail; after every replay the store must open, `verify` must pass, and every acknowledged tid must load. Deterministic, thousands of cases per minute, runs on every PR.
2. Process kill loop: writers against a real store, `SIGKILL` at random points including inside `tpc_finish`, restart, verify, repeat 10,000 times nightly. The test is `python/zoedb/tests/crash/test_kill_loop.py`: four writers commit objects and blobs through stock `ZEO.ClientStorage` clients to `zoe serve`; each round kills the server, restarts it, stops it with `SIGTERM`, runs `zoe verify` on the store, and loads every acknowledged commit. `zoe verify` checks the size and the hash of every blob file; the test compares the bytes of a blob through the blob cache of its check client, which keeps a blob after its first load. `just crash RUNS SEED` runs it (200 rounds and a random seed by default) and prints the seed. A failure of `zoe verify` or of a load names its round, and pytest shows the local variables of every failure, the round among them. The same two arguments repeat the kill times, not the order of the threads. The Dagger function `crash` runs 10,000 rounds with a new seed by default, and never takes its result from the cache; 10,000 rounds need about 3 GB in `TMPDIR`. `just test` does not collect it.
3. Power-loss emulation: the same loop on a `dm-flakey` device or a QEMU guest that is force-stopped, so lost page-cache writes are real, weekly.
4. Blob atomicity: kill between blob rename and record commit, verify neither a dangling blob nor a record without its blob.
5. Pack under load: pack during the write benchmark; readers must see consistent snapshots, no `POSKeyError`, and the store size must drop.
6. Deterministic simulation (N18): `zoe_server::sim` runs the server and its clients in one process on a simulated network and clock, with the store on the `MemVfs` of the core. It runs the production code: each connection runs the connection code of `zoe serve` (`serve_stream`), its session and the core, and each client is `zoe-client`. The server reaches its tasks, its blocking threads and its timers through a runtime trait, as `zoe-client` reaches its network, tasks and timers, and the core reaches the time and its lock waits through `Clock` (`now`, `monotonic`, `waiter`). The simulator is an executor of its own, not turmoil or madsim: one thread runs at a time, and a blocking thread gives the baton back when it waits for a channel or a lock, when the core syncs the database file, and when it ends. A seed decides the whole run: the order of the tasks and threads, the delays and losses of frames, the partitions between a client and the server, the connections that close, and the crashes of the server. Each crash comes at a phase of a commit that the seed picks: staged (the client stored and did not vote), locked (between the vote and `tpc_finish`), finishing (at the sync of the database file in `tpc_finish`) or acknowledged (the client got the reply of `tpc_finish`). The writes to the database file wait in a cache until the next sync of the file, as in the page cache of the system. A crash is a power loss by default: the disk keeps the synced writes, a seeded prefix of the other operations, and a seeded subset of the cached writes, in any order, some of them torn (only the first half or only the second half lands). A crash can also be a kill of the process (every write lands). The store then opens again from that image. A run ends with a crash too, and every commit that a client saw acknowledged must load, its blobs included; no load may give a serial older than an acknowledged commit of its oid; the store must pass the checks of `zoe verify`, and no blob file may lack its blob record. With `blobs(true)`, the clients also upload blobs as `ZEO.ClientStorage` does (`storeBlobStart`, `storeBlobChunk`, `storeBlobEnd`), and the server writes each upload into a blob file of the core, through the `Vfs` of the store. The same seed gives the same trace, in one process and across processes, debug and release; `ZOE_SIM_SEED` runs one seed, and a failing run prints it. Simulated waits take no real time: a lock timeout of 10 s costs milliseconds. Only test builds have the simulator (the feature `sim`, which only the dev-dependency of `zoe-server` on itself turns on). With `hot_length(true)`, the hot oid of the clients holds a `BTrees.Length.Length` that each transaction increments, so tier 1 merges the writers and the finishes hand off the lock; the check after the run reads the history of the oid, and each record must hold the value of the record before it plus 1. With `slow_syncs(true)`, a sync of the database file takes simulated time, and other tasks and threads run meanwhile, so batches of two or more finishes form and votes merge onto commits that are not durable yet; at a crash, the thread that syncs ends first. `crates/zoe-server/tests/simulated_hot_length.rs` runs eight clients, 200 commits and five power-loss crashes for each of 100 seeds with both, with 0 losses, no stale read, no finding and no break of the history, and hand-offs over the seeds. With a round trip shorter than a sync, sixteen clients and 400 commits over 20 seeds give a mean `zoe_fsync_batch_size` above 2 (2.44 to 2.54 measured; about 1.15 with the hand-off disabled). Not covered yet: a graceful stop, blob downloads, pack, named storages and read-only mode. The kill loop under the simulator is `crates/zoe-server/tests/simulated_kill_loop.rs`: four clients, 200 commits with blobs and five power-loss crashes for each seed, with 0 losses, no stale read and no finding, and the four phases among the crashes of 200 seeds. `ZOE_SIM_SEEDS` sets the number of seeds (200 by default, in `just test`); `just crash RUNS SEED SEEDS` runs it in release after the process kill loop, and the Dagger function `crash` runs it with `ZOE_SIM_SEEDS=10000`.

**D. Concurrency and free-threading**

- ThreadSanitizer build of the core and the extension on every PR; `loom` interleaving tests on the lock manager and the commit batch.
- Free-threaded stress: on 3.14t, 32 threads committing on overlapping and disjoint oid sets through the in-process storage, with invariants checked after every round (serial monotonicity, no lost update, lock table empty).
- Lock-order and deadlock tests: adversarial clients requesting oids out of order; every run must end with `LockOrder` or timeout, never a hang.

**E. Protocol and input fuzzing**

- `cargo-fuzz` targets: msgpack frame decoder, `register`/`get_info` handshake, pickle header parser, native merge inputs. One hour per nightly. The repository keeps only the seeds of each target and the script that makes them; the corpus that the nightly runs grow stays in the `zoe-target` cache volume of CI, so a prune of the volume loses it and the next run starts again from the seeds. The targets of `zoe serve` are `frame` and `handshake` in `crates/zoe-server/fuzz`; `just fuzz` builds them with the pinned toolchain and runs them, and a fuzz smoke of the server (`crates/zoe-server/tests/fuzz_smoke.rs`) runs in each `just test`.
- Fault injection on the wire: client disconnect at each 2PC state, server restart during vote, invalidation queue overflow, interrupted blob upload; the client must end in `ClientDisconnected` or a clean retry, the server must hold no stale locks.

**F. Replication and Kubernetes (Tier 2 and 3)**

- A `kind` cluster in CI: leader kill during commit, follower promotion, split-brain attempt with two lease holders, rolling restart; acknowledged commits are never lost, clients reconnect within 10 s.
- Tier 3 against a single-node FoundationDB in CI, the same conformance suites.

**G. Operations**

- Bit-flip injection: flip random bits in records, blobs and the dictionary on a copy of the corpus; every read must raise `CorruptRecord`, never return data; `zoe scrub` must list every injected fault and nothing else.
- Backup round trip: continuous shipping to a local S3-compatible bucket under the write benchmark, then `restore --to-tid` at ten random tids compared record by record against `loadBefore` on the live store; `backup verify` as a scheduled job.
- Feed exactness: an external consumer counts commits through the kill loop and reconnects from its last acknowledged tid; the count must equal the server's, with no duplicate.
- Forks: a fork of the corpus runs the Plone upgrade suite; the base store's checksums are unchanged afterwards; `plone.app.testing` layers stacked on forks run the Plone suites.
- Encrypted store: the whole conformance suite on an encrypted store; a scan of the files finds no plaintext record or blob; a wrong key fails to open with a clear error.
- Named storages: a two-mount Plone site on one server, the ZEO multi-storage tests, commits on one store under load while the other is packed.
- Pack safety: dry-run report compared to the actual removal set; revert inside the window restores every record; incremental pack under the read benchmark keeps p99 inside budget.

## Risks and open questions

The largest risks are not in Rust; they are in matching ZEO's exact semantics and in the Plone-side hook for early locks.

| Risk | Impact | Mitigation |
| --- | --- | --- |
| ZEO protocol edge cases (cache verification after a long disconnect, `getInvalidations` gaps, blob shared-dir modes) differ from the source reading | a Plone cluster sees stale objects | run the full `ZEO.tests` suite from phase 2 week 1; keep the invalidation queue large; treat every ZEO test skip as a bug |
| redb write amplification caps commit throughput below RelStorage on write-heavy loads | N4 fails on update scenarios | the append-only log backend is designed in from day one behind the trait; the decision is made on phase 2 numbers |
| Early locks stall a four-thread Zope instance on a hot object | worse latency than ConflictError retries | default stays vote-time locking; early locks are opt-in per instance and documented for free-threaded Zope first |
| The `Connection.register` hook for early locks touches ZODB internals that change between releases | breakage on ZODB upgrades | keep the hook in one small module with a test per supported ZODB version; propose an upstream `IStorage` extension hook once it is proven |
| Native merges drift from `BTrees` semantics after a BTrees release | silent data differences | differential tests pin the BTrees version; CI runs against the latest BTrees weekly |
| `persistent`, `BTrees`, `zodbpickle` do not declare `Py_mod_gil_not_used` upstream | free-threaded parallelism in Zope stays off | phase 0 opens the PRs; a vendored build with the declaration is the fallback for the first production site |
| Tier 3 on FoundationDB: the 5 s / 10 MB transaction limits and the extra hop | large commits need splitting; p99 rises | stage locally, commit in one short write; Tier 3 is for clusters that need HA more than the last 100 µs |
| Single maintainer | bus factor | the spec, the harness and the conformance suites are the handover; keep the core small |
| Pickle-level assumptions (class paths, `zodbpickle.binary`) break on py2-migrated stores | migration failures | the round-trip test runs on a production copy before any release |
| Loupe edits bypass Plone invariants (catalog, events, workflow) | stale catalog, surprised editors | expert mode, catalogued-object badges, pickle diff before commit, the optional zoe.plone reindex queue; Loupe is documented as a scalpel, not a content editor |
| zoe-pickle cannot round-trip an exotic construct byte for byte | an edit rewrites more than the operator changed | opaque nodes re-emit original bytes and are not editable; the property test runs on a production copy before every release |
| RelStorage schema changes between versions | the converter misreads a site | pin the supported RelStorage versions, detect the schema version at start, refuse unknown ones |
| Production data or credentials leak into a public repository or a CI log | a data breach, and the adopting site's trust | synthetic corpora in public CI; private runner for production copies; secret scanning on every push; builders have no access to production data at all |
| The catalog mirror answers a query differently from ZCatalog | wrong search results, silently | differential suite on every PR; production query log replay nightly; any index or operator not covered by the suite takes the Python path by construction |
| Text index lags the tid or diverges from ZCTextIndex ranking | a just-saved page missing from search; tests that pin ranking break | hits filtered by the snapshot bitmap; commit lag as a metric with an alert; the compatibility switch for pinned rankings |
| A remote embedding provider sends content off the site owner's server | GDPR exposure without anyone deciding it | local ONNX provider by default; remote providers opt-in per site, logged, and counted by zoe\_vectors\_remote\_bytes\_total |
| An agent reaches content through MCP that Plone would have hidden | a permissions bypass | roles bitmap intersected before ranking in every mode; non-catalogued objects ops-only; the security suite runs on every PR touching zoe-mcp or zoe-vectors |
| A field-level merge combines two valid saves into an invalid object because an invariant was never declared | silent data inconsistency | policy derived from schemas with strict as the default; merging enabled per class only after shadow mode on production conflicts; every merge logged with the keys it merged and reversible from history |
| An encryption key is lost | the store and every backup are unreadable | encryption is off by default; the wrapping key lives outside the cluster (file, environment or KMS) and is the one secret the runbook makes an operator keep; `zoe backup verify` fails loudly as soon as a snapshot cannot be opened |
| The operations features dilute the core | phase 7 grows, the storage core gets less review | phase 7 is a parallel track behind the server gate; each tool is its own card with its own acceptance test; none of them is in the first release and none of them touches the commit path |
