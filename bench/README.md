# Benchmarks

This directory holds the reference baseline: a harness that runs [zodbshootout](https://pypi.org/project/zodbshootout/) against FileStorage, ZEO 6 and RelStorage on PostgreSQL, with history (`relstorage`) and without (`relstorage-hf`), and the JSON schema of its results. The same harness measures ZOE in-process, the storage `zoe`, through the `<zoe>` stanza, and ZOE server twice: the storage `zoe-server`, a stock ZEO client of `zoe serve` through the `<zeoclient>` section, and the storage `zoe-native`, the native client of `zoe serve` through the `<zoeclient>` section with `native true`. The phase 3 gate does not run zodbshootout: it has a driver of its own, the native gate (see [The gate](#the-gate)). `zoe-bench` (contention and server saturation) and the criterion microbenchmarks live in `crates/`.

## Run it

`just bench` is the entry point. Run it inside `devenv shell`.

| Command | What it does |
| --- | --- |
| `just bench` | the full set against every storage; writes to `target/bench/results` |
| `just bench run --quick` | the quick set, the regression gate of a pull request |
| `just bench run --storage zeo --quick` | one storage only |
| `just bench native` | the phase 3 gate (ADR 0039): `zoe-native` against `zeo` in the 30 cells of the gate set, in about a minute; writes `target/bench/native/<started>.json` and prints the report (see [The gate](#the-gate)) |
| `just bench native --cell threads:1:1024 --scenario read_warm` | a part of the phase 3 gate |
| `just bench native report FILE` | the rows of a result of the phase 3 gate and its verdict |
| `just bench test` | the tests of the harness (the acceptance test of the baseline) and of `bench/common` |
| `just bench test FILE...` | the tests of those files only |
| `just bench client` | the client benchmark: `ZEO.ClientStorage` against the native client (see [The client benchmark](#the-client-benchmark)) |
| `just bench client report FILE` | the rows of a result of the client benchmark and its verdict |
| `just bench profile COMMAND` | the load path profile: where one load spends its time between the ghost and the client cache, on a hit and on a miss (see [The load path profile](#the-load-path-profile)) |
| `just bench index DIR` | rewrites `index.json` of a results tree, in version 2 (see [The results repository](#the-results-repository)) |
| `just bench publish [--main REF] SRC... CHECKOUT` | copies the result documents of every family into a checkout of the results repository and rewrites its `index.json`; it never commits and never pushes (see [Publishing](#publishing)) |
| `just bench gate DIR` | the parity gate of phase 2: `zoe-server` against `zeo` in each cell of a results tree but `read_hot` (see [The gate](#the-gate)) |
| `just bench plone COMMAND` | the Plone end-to-end benchmark: Locust against a Plone site on ZEO and on ZOE (see [The Plone end-to-end benchmark](#the-plone-end-to-end-benchmark)) |
| `just bench showcase` | the publishable set in one command: the builds, B5 on `small` and `medium`, a B5 summary per fixture, the native gate and the client benchmark on CPython 3.13 and 3.14t; writes `target/bench/showcase/<started>/` (see [The showcase](#the-showcase)) |
| `just bench showcase --plan` | each run of the set with its estimate; runs nothing |

Every harness of `bench/` (the baseline, the Plone end-to-end benchmark, the log replay, the showcase and `publish`) starts and stops its servers, and records where its numbers come from, through `bench/common`, the package `benchcommon`. It uses the standard library only, so the log replay, which runs in the interpreter of a Plone instance, takes it from `PYTHONPATH`; the other harnesses take it as an editable path source. It holds a free port; the start of a ZEO server, and the start of `zoe serve`, which waits for its line `listening <address>`; the stop of a server: SIGTERM, then a wait, then SIGKILL; the `zoe` binary; the environment of a server, without the `ZOE_*` variables of the caller; the atomic write of a result; the bench lock; and the provenance of a result: the machine, its CPU model, the commit and whether the tree differs from it. `just check` checks that the harnesses that build zoedb pin the forks of `persistent`, `zodbpickle` and `BTrees` that `python/` pins.

**The bench lock.** One benchmark runs at a time. Each benchmark of `just bench` holds an exclusive `flock(2)` on `ZOE_BENCH_LOCK` (`target/bench/bench.lock` by default) from before its build to its end: `run`, `native`, `client`, `load`, `saturate`, `plone prepare`, `plone run`, `plone campaign` and `replay RUN`. When another holds it, the recipe says `wait for the bench lock` and waits. The showcase holds it for each of its runs. A child command of a holder, such as the native gate of a run of the showcase, takes the lock through the open file of its parent, which `ZOE_BENCH_LOCK_FD` names, so it does not wait for its parent. The tests, the reports, `gate`, `index`, `publish` and `--plan` take no lock.

The bench project takes `python/zoedb` as an editable path source, as the uv workspace of the Python tests does. So the harness runs the Python code of the tree. uv builds the extension with maturin in the release profile, and the cache keys in `python/zoedb/pyproject.toml` tell uv to build it again when the Rust code changes.

RelStorage runs when `ZOE_BENCH_PG_DSN` (or `--dsn`) names a PostgreSQL database that the harness may empty. `relstorage` and `relstorage-hf` use the same database. The harness drops every table, sequence, view and function of RelStorage there, so never give it a database that something else uses. Without it, the harness skips both and says so. The Dagger function `bench` starts PostgreSQL 17 as a service and runs the harness tests, then the baseline, and returns the results tree:

```sh
dagger call --mod ci bench --quick export --path target/bench/ci-results
```

Other settings:

- `ZOE_BENCH_MACHINE` or `--machine`: the machine name in the results. The default is the CPU model, for example `intel-core-ultra-7-155h`: on Linux the `model name` of `/proc/cpuinfo`, on macOS `sysctl machdep.cpu.brand_string`, such as `apple-m2-pro`. Every harness gives one machine the same name.
- `ZOE_BENCH_COMMIT`: the commit to record. The default is `git rev-parse HEAD`. Each result also records `run.dirty`: true when `git status --porcelain --untracked-files=no` lists a change, false when it lists none, null when git fails, as in the container of the Dagger function `bench`, which has no `.git`. It is null too when `ZOE_BENCH_COMMIT` names another commit than the tree, which is then no record of that commit.
- `UV_PYTHON`: the interpreter, `3.13` by default. Each interpreter gets its own environment under `target/bench/`.
- `--workdir`: where the storages write their files, `target/bench/work` by default. Keep it on the disk under test, not on a tmpfs. Its disk needs the free space of one value (see [The disk](#the-disk)).
- `ZOE_BINARY`: the `zoe` binary of the storages `zoe-server` and `zoe-native`. Without it, the harness takes `target/release/zoe` of the repository (under `CARGO_TARGET_DIR` when it is set). When the binary is missing, the harness stops with the command that builds it. `just bench run` and `just bench test` build it in release first, so it is never stale.

## What it measures

zodbshootout runs five scenarios: `add`, `update`, `read_cold`, `read_warm` (zodbshootout's write/read: write the objects, then read them back in the next transaction; the time includes both) and `read_hot`. Each runs in a set of cells. A cell is a mode, a concurrency and an object size. Every transaction holds 100 objects.

| Set | Cells | Values per scenario and cell |
| --- | --- | --- |
| quick | threads, concurrency 1 and 16, objects of 1 KB | 5 |
| full | threads at concurrency 1, 4, 16 and 64; processes at 4, 16 and 64; objects of 1 KB and 100 KB | 20 |

- Each value runs in its own zodbshootout run, on a fresh store: one scenario, one pyperf worker process, one warmup, then the value (`--processes 1 --warmups 1 --values 1 --loops 1`). The warmup runs in the same process and on the same store as the value, so the costs of a first call stay out of the value. The other options are the same for every value.
- Only `add` gets `--zap force`: zodbshootout zaps the store before each call of `add`, and it refuses a zap without `add`. For the other scenarios, zodbshootout populates the fresh store before the calls: the tree with 100 objects per worker and the shared mapping of conflicts.
- For each value, the harness makes a new directory under the work directory, starts the ZEO server or `zoe serve` on a new store in it, runs zodbshootout, stops the server and removes the directory: the store, the logs and the pyperf output. For `relstorage` and `relstorage-hf`, it empties the database with RelStorage's `zap_all` before and after each value. RelStorage refuses to open a database that has the schema of the other history mode, so before the first value of each of the two storages, the harness drops the tables, the sequences, the views and the functions of RelStorage in both modes. A value that fails keeps its directory and its logs, and the run stops.
- In the threads mode, one process runs the workers as threads that share one `DB`, as in one Zope process. In the processes mode, each worker is a process with its own `DB`, as in several Zope processes.
- FileStorage and `zoe` run only in the threads mode: only one process can open a FileStorage file or a ZOE store. ZEO, both RelStorage storages, `zoe-server` and `zoe-native` run in every cell.
- A sample is the time for the slowest worker to do one transaction. A result reports the mean, the median and the 99th percentile of the values of a scenario and cell. `ops_per_second` is objects per second for all workers together: concurrency × 100 ÷ mean.
- Every storage runs with its default settings. The `<zoe>` stanza sets only `path`. `relstorage` keeps history, like FileStorage and ZEO. `relstorage-hf` is the same `<relstorage>` section with `keep-history false` and nothing else: many sites run RelStorage without history, and it is the faster mode on writes. The ZEO server is a separate process on the same machine.
- `zoe-server` runs `zoe serve --path <value>/store --listen 127.0.0.1:0` in the directory of each value, a separate process on the same machine, as the ZEO server. No `ZOE_*` variable of the environment reaches it, so it runs with its default settings. The client is the `<zeoclient>` section of ZEO with its default settings, as for `zeo`. The result records the version of the server as `zoe` in `software`.
- `zoe-native` runs `zoe serve` as `zoe-server` does, with `--admin-listen 127.0.0.1:0` in addition. The client is the `<zoeclient>` section of `zoe.zeo.ClientStorage`, after `%import zoe`, with `server` and `native true` and no other key: the native inside, with its default settings. The result records the version of the server as `zoe` and the version of `zoedb` in `software`.
- zodbshootout logs the exception of a benchmark and reports a time for it all the same. So when the log of a zodbshootout run holds a record of level `ERROR` or `CRITICAL`, the value fails with that record, and the run stops.
- zodbshootout empties the cache of the client with `_cache.clear()` before each cold read. A cache that this call does not empty would turn `read_cold` into a cache read. So for each `read_cold` value of `zoe-native`, the harness reads `zoe_loads_total` on the admin port before and after the zodbshootout run, and compares the difference with the objects that the run read (the warmup and the value). When the server counted fewer loads than objects read, the run fails with a message that names `read_cold` and the cache.
- Each scenario entry records the GIL of its worker processes, in the list `workers`: one item per Python process of its zodbshootout runs that imported ZODB (the zodbshootout process, its pyperf worker and, in the processes mode, the process of each worker). `gil_enabled` is `sys._is_gil_enabled()` when the process ended, and `gil_enabled_by` lists the modules that turned the GIL back on, from the warnings of CPython. On 3.14t a number means little without it: RelStorage's driver `psycopg2._psycopg` turns the GIL back on, for example. The record comes from `shootout/startup/sitecustomize.py`, which the harness puts first on `PYTHONPATH` of each zodbshootout run, and which pyperf passes to its worker with `--inherit-environ`. It changes no setting of the run: it shows each warning as Python does, removes its directory from `sys.path`, and imports the `sitecustomize` module that it hides, if there is one.

The corpus is synthetic: zodbshootout generates its own objects. Results are numbers, never data.

## The disk

The work directory holds one value at a time. The largest value of the full set, `update` at concurrency 64 with objects of 100 KB, takes about 40 GB on `filestorage` and `zeo`, and about 26 GB on `zoe` and `zoe-server`. A value of the quick set takes at most 0.3 GB.

Before each cell, the harness compares `disk_needed(storage, cell)` with the free space of the disk of the work directory. When the free space is smaller, the cell fails before it starts. The message names the storage, the cell, the bytes needed and the bytes free. The cells before it left nothing, and the harness writes no result for that storage.

`disk_needed` is an upper bound of the bytes of one value: the populate and two calls of `update` (the warmup and the value), at the object size and 8 KiB per record, and 64 MiB for an empty store, the index files and the logs. For `relstorage` and `relstorage-hf` it is 64 MiB, because the data goes to PostgreSQL, whose disk the harness does not see.

| Objects | c=1 | c=4 | c=16 | c=64 |
| --- | --- | --- | --- | --- |
| 1 KB | 0.26 GB | 0.82 GB | 0.98 GB | 3.7 GB |
| 100 KB | 2.3 GB | 9.1 GB | 11.0 GB | 43.7 GB |

So the full set needs about 44 GB of free space, and the quick set about 1 GB.

The populate of a value is one transaction: about 0.67 GB at concurrency 64 with objects of 100 KB. Through `ZEO.ClientStorage`, for `zeo`, `zoe-server` and `zoe-native`, the transaction buffer of the client holds a copy of it in a temporary file under `TMPDIR`, and for `zeo` the commit log of the ZEO server holds a second copy there. These files are outside the work directory and outside the check, so `TMPDIR` needs room for them.

## Results

Each run of one storage gives one JSON document that validates against [`schema/results.schema.json`](schema/results.schema.json). The document names the storage, the machine (CPU, logical CPUs, memory, kernel, the disk that holds the storage files), the Python build (version, free-threaded or not), the versions of every package and server, the commit and whether the tree held changes that the commit does not (`run.dirty`), and one entry per scenario and cell, with the GIL record of its workers. It holds no host name, user name or path.

## The gate

N4 sets two gates against ZEO 6 through `ZEO.ClientStorage`.

### Phase 2: parity

The phase 2 gate is parity: `zoe-server` at least 1× `zeo` in each zodbshootout cell that reaches the server. `python -m shootout gate`, or `just bench gate DIR`, reads the results tree DIR in the layout below and turns the gate into a pass or a fail per cell:

```sh
just bench gate target/bench/results
```

- For each machine, Python build and set (quick or full), it keeps the last result of each storage, by the start of the run. So it compares one machine, one Python build and the same cells, and never a quick run with a full run.
- For each scenario and cell of the baseline, it prints `ops_per_second` of both storages and their ratio.
- It checks parity of `ops_per_second` by default and leaves `read_hot` out: zodbshootout's `read_hot` empties the object cache of the connection, then reads the objects from the cache of `ZEO.ClientStorage`, so no read reaches the server. The report prints each cell that it leaves out with the numbers that exist and the verdict `left out`, and says why in a `left out:` line, such as `left out: read_hot at 1 KB, because ...`. Such a cell counts neither as below nor as missing. The summary line names the cells that it leaves out: `each cell but read_hot`. `read_hot` still runs and stays in the results.
- It exits with 0 when the ratio of each cell that counts is at least the ratio of the gate. It exits with 1 when a ratio is below, when a cell of the baseline has no counterpart in the storage, or when the tree holds no result of the baseline.
- `--storage zoe-server --baseline zeo` are the defaults. `--ratio` takes any positive value in place of parity.
- `--python cp314t` counts only the results of that build. The report prints the groups of the other builds after them, marked `does not count`, with their verdicts in lower case. Without `--python`, every build counts.
- The phase 2 gate counts only the full set of the reference machine. The RelStorage row of N4 counts `relstorage` and `relstorage-hf`.

### Phase 3: the native gate

The phase 3 gate (ADR 0039) asks `zoe-native`, `zoe serve` through the native client, to be faster than `zeo` in every cell of the gate set, and it runs in about a minute. It does not run zodbshootout: `shootout/native.py` drives both storages, and `shootout/nativeworker.py` runs the workers.

```sh
just bench native
just bench native --cell processes:16:102400 --scenario add update
just bench native report target/bench/native/<started>.json
```

- **Cells.** The 5 scenarios of zodbshootout (`add`, `update`, `read_cold`, `read_warm`, `read_hot`) in 3 shapes (threads 1, threads 16, processes 16), at 1 KB and 100 KB: 30 cells. A transaction holds 100 objects at 1 KB and 10 objects at 100 KB.
- **The same work as zodbshootout.** The workers use zodbshootout's `SpeedTestData`: its `PObject`, its data and its mapping per worker. `add` puts new objects in the mapping and commits. `update` changes each object and commits. `read_cold` opens a connection with no cache and reads each object. `read_warm` opens a connection with no cache, changes each object, commits, reads each object and commits. `read_hot` empties the cache of a primed connection and reads each object from the cache of the storage. Before a batch of `read_cold` or `read_warm`, each process empties the cache of its connections and of its storage, and that work is not timed.
- **Start once.** For each cell, each storage gets one server on a fresh store (a ZEO 6 server on a FileStorage, and `zoe serve` with its default settings, which store records raw, as FileStorage does), one populate and one set of worker processes, started with `spawn`. In the threads mode, one process runs the workers as threads on one shared `DB`. In the processes mode, each worker is a process with its own `DB`. Both servers run for the whole cell. The cell removes its stores when it ends.
- **Pairs.** A batch runs the same number of transactions in a row in each worker of one storage, as the inner loops of zodbshootout do: the warmup pair sets it, so that a batch lasts about 20 ms, with at most 20 transactions. Its time is the time of the slowest worker for one transaction. A pair is one batch of `zeo` and one of `zoe-native`, and the storage that goes first changes from one pair to the next. Only one storage works at a time. One pair before the first one warms the scenario up and does not count.
- **The rule.** The ratio of a pair is `t_zeo / t_zoe`. After at least 10 pairs, a scenario passes when the 99 % confidence interval (Student's t) of the mean of the log of the ratios is above 0, and fails when it is below 0. It stops at its first verdict, at 100 pairs, or after 10 s of pairs. A scenario without a verdict is `UNDECIDED`, and it fails the gate: a tie is not faster.
- **Checks.** The run of `read_cold` of `zoe-native` fails when `zoe serve` counted fewer loads (`zoe_loads_total` on its admin port) than the objects that the batches read. Each worker checks that it read every object, and that a cold read loaded them.
- **The report.** One row per cell that the result holds: the median times per object of the slowest worker of both storages in µs, the geometric mean of the ratios, its interval, the pairs and the verdict. The summary counts the cells that are slower, undecided and missing. `just bench native` exits with 0 when every cell of the 30 passes, else with 1; `report` exits with 2 when the file is not a result of the gate.
- **The result.** One JSON document that validates against [`schema/native.schema.json`](schema/native.schema.json): the machine, the Python build, the versions, the commit and `run.dirty`, the rule, and for each cell the GIL record of the worker processes of each storage and, for each scenario, its pairs and its outcome: `ratio` (the geometric mean of the ratios), `low` and `high` (its interval), as the rule gives them, null for a value that is not finite (`high` with fewer than 2 pairs), and `verdict` (`pass`, `fail`, or null when undecided). So a reader of the result does not apply the rule again (ADR 0054). The keys are optional, so a result without them stays valid. The report applies the rule to the pairs again, and its verdict agrees with them.
- **Python.** The phase 3 gate counts a run on CPython 3.14t: `UV_PYTHON=3.14t just bench native`. A run on another build is a report, not the gate.

## The client benchmark

F28 asks the native client to beat `ZEO.ClientStorage` on the client benchmark, cold and warm cache, and the phase 3 gate asks for it too. zodbshootout mixes the client with ZODB and the server. The client benchmark isolates the client: it calls the storage API of each client without ZODB, `loadBefore` for the loads and `new_oid`, `tpc_begin`, `store`, `tpc_vote` and `tpc_finish` for the commits. The clients are `ZEO.ClientStorage` and the native client, `zoe.zeo.ClientStorage` with `native=True`, both with their default settings but the cache. `python -m shootout client`, in `shootout/client.py` and `shootout/clientworker.py`, is the benchmark.

```sh
just bench client                                # both servers, 1000 objects per worker
just bench client --server zoe-serve --objects 200
just bench client report target/bench/client/<started>.json
```

- **Shapes.** One process with 1 thread, one process with 16 threads on one client, and 16 processes with one client each.
- **Record sizes.** 1 KB and 100 KB of random bytes.
- **Workloads.** `cold`: each worker loads `--objects` distinct oids (1000 by default), with no cache. Each load is `loadBefore(oid, tid)`, where `tid` follows the last transaction of the client, as the loads of a ZODB connection are. `warm`: the same loads from a client that opens the cache file that its `cold` round wrote; the open of the client and the verification of its cache count in the time and the CPU. `commit`: each worker commits `--commits` transactions of 100 new records (`max(1, objects // 50)` by default, so 20 with 1000 objects). When the spread of a commit row is large, give more commits.
- **Traverse.** One more workload runs through ZODB, as a Connection loads: the harness writes a tree of `PersistentMapping`s through a `DB` on a client of ZEO, the root of the store with 20 children for each node over 3 levels (8,421 objects), whose 8,000 leaves each hold 1 KB of random bytes, and a new client of ZEO walks it once. In each round, a new process opens a `DB` on its client with an empty cache in memory, calls `cacheMinimize()` and walks the tree depth first through attribute access (`values()`); the clock covers the walk. It runs for `ZEO.ClientStorage`, and for the native client with its setting `prefetch-references` on and off, which the harness gives through `ZOE_PREFETCH_REFERENCES`. A row gives the time of one walk (the median of the rounds) and the loads that `zoe serve` counted from the open of the client to its close (the median of the rounds). With the setting on, a miss prefetches the children of its record, but a record that a prefetch brought prefetches nothing, so the misses are the root and the nodes of the second level; a load of a child before the reply of its prefetch joins that load and sends no request of its own. The rows do not count in the verdict.
- **Servers.** `zoe serve` (`zoe-serve`) and a ZEO 6 server on a FileStorage (`zeo`), each client against each. Each server has its default settings, but the ZEO server speaks the msgpack protocol M5 (`ZEO_MSGPACK`): the native client speaks only M5, as `zoe serve` does. So both clients speak M5 to both servers. `--server` takes one or both.
- **The same server state.** For each server and record size, the harness fills one store with the records that the workers load, then no round changes it. After the fill, a new client of ZEO with an empty cache loads each record once, and no round measures it. So the first `cold` round, which is a round of `ZEO.ClientStorage` in two rounds of three, finds the server as warm as the next ones. Each commit round runs on a fresh store. Both clients run the same calls in the same order.
- **Rounds.** Each row runs in at least three rounds (`--rounds`). The rounds of both clients interleave, and the client that goes first changes from one round to the next. Each round runs in a fresh process. The native client imports ZEO too, so the processes of both clients load ZEO and ZODB. Each process imports its client and the modules of its calls before the clock starts. So the clock of a `warm` round covers the open of the client and the verification of its cache, and the clock of no round covers an import: each round fails when a module was imported inside its clock. In the processes shape, that process starts the 16 worker processes (`spawn`), and they start their calls together.
- **The cache.** In the `cold` and `warm` rounds, each client has a cache file: `client` and `var` give `w<worker>-1.zec` to `ZEO.ClientStorage` and `w<worker>-1.zoec` to the native client. The `cold` round starts with no file and writes it. The `warm` round of the same client reopens it, and fails when it is not there. Both clients get the same `cache_size`, large enough to hold every record of the round. Against `zoe serve`, the harness reads `zoe_loads_total` on the admin port before and after each round: a `cold` round fails when the server counted fewer loads than the round made, and a `warm` round fails when the server counted any load. The ZEO server counts no loads, so nothing checks that the cache served the `warm` rows against it. These rows do not count in the verdict.
- **Numbers.** For each row: calls per second (the calls of all workers of a round, divided by the time of the round, the median of the rounds), p50 and p99 of one call (over the calls of all rounds), client CPU per object (the user and system CPU of the client processes of a round, their threads included, divided by the objects loaded or stored, the median of the rounds) and the spread of the rounds (the highest rate minus the lowest, divided by the median). A call is one `loadBefore`, or one commit of 100 records.
- **The result.** One JSON document that validates against [`schema/client.schema.json`](schema/client.schema.json): the machine, the Python build, `gil_enabled_by` (the modules that turned the GIL back on in a process of the run), the versions of both clients (`ZEO` and `zoedb`) and of `zoe serve`, the commit and `run.dirty`, the objects and one row per client, server, shape, workload and record size, and the traverse rows in `traverse`. Each row records the GIL of its processes in `workers`, as the results of zodbshootout do. `--output` names the file; the default is `target/bench/client/<started>.json`. A run that fails keeps its directory under the work directory, with the logs of its servers.

**The verdict.** `just bench client report FILE` prints one row per shape, workload, record size and server, with the rates of both clients, their ratio, their client CPU per object, their p50 and p99, and the spread. It first checks the file against the schema, and exits with 2 when the file does not match. In a row against `zoe serve`, the native client passes when it has a higher rate and a lower client CPU per object than `ZEO.ClientStorage`, and the row says `FAIL` otherwise. A row with the numbers of one client only says `missing`. A row against the ZEO server shows the same comparison in lower case and does not count. Then one traverse row per server gives the time of one walk in ms and the loads of the server for `ZEO.ClientStorage` and for the native client with `prefetch-references` on and off, with the largest spread of the three; it does not count. The report exits with 0 when every row against `zoe serve` passes and no row is missing, and with 1 otherwise.

**The disk.** For each server and record size, the work directory holds the load store, the cache files of both clients for one shape, and one commit store: `disk_needed` in `shootout/client.py` bounds it, and the harness checks the free space before it starts. With 1000 objects and records of 100 KB, and 20 commits per worker, that is about 10.1 GB; with records of 1 KB, about 0.7 GB. The native client allocates its whole cache file at the open.

The full run belongs on the reference machine, on CPython 3.14t with the 3.13 run beside it, as for the gate.

## The load path profile

`just bench profile` measures where one load spends its time between the ghost of a ZODB connection and the client cache: the harness of `docs/spikes/load-path.md`, `shootout/loadpath.py`. It is a measure, not a gate, and it writes no file unless `--out` asks for one.

```sh
just bench profile terms --out target/bench/profile/terms.json     # every row
just bench profile terms --client native --size 1024 --rounds 10
devenv --profile profiling shell -- just bench profile loop --kind miss --size 102400 --py-spy target/bench/profile/miss.txt
just bench profile frames target/bench/profile/miss.txt
just bench profile scan target/bench/plone/fixtures/<name>/store/filestorage/Data.fs
devenv --profile profiling shell -- just bench profile plone --py-spy
```

- **`terms`.** For each client and record size, a new server on a new store: `zoe serve` for the native client (`zoe.zeo.ClientStorage`), a ZEO 6 server on a FileStorage for `ZEO.ClientStorage`. A `DB` on the client writes the corpus of zodbshootout, a `PersistentMapping` of its `PObject`s (1,000 of 1 KB, or 200 of 100 KB). Both clients get a client cache of 256 MB, which holds the corpus; no other setting of a client or a server changes. A hit round calls `cacheMinimize()`, then reads one attribute of each object, as `read_hot` does, then runs each layer of a load alone over the same objects: `MVCCAdapterInstance.load`, `ClientStorage.loadBefore`, the call of the client cache, `ObjectReader.getState` and its parts, `__setstate__` and the lines of `Connection.setstate` after the decode. A miss round empties the client cache before the read and before each layer that reaches it; on the native client, it also times a prefetch of every oid before the read. Each term is the difference of two layers of the same round, per load, in µs: the median and the range of the rounds (30 at 1 KB, 15 at 100 KB). `terms` also counts the Python calls of one load (`sys.setprofile`), the `persistent_load` callbacks of each record and, against `zoe serve`, the loads that the server counted per miss.
- **`loop`.** One round, hit or miss, again and again for `--seconds`, for a profiler: `--py-spy FILE` runs the loop under `py-spy record --native` in its raw format, and `--cprofile FILE` under cProfile. py-spy is in the `profiling` profile of the shell, and it reads a process with a GIL only. `frames FILE` prints the share of each frame of a load in the samples under the timed loop, and the frames with the most own samples.
- **`scan`.** Each current record of a FileStorage, by class: the records, their bytes and their references, which are the `persistent_load` callbacks of one load. It imports only ZODB, so the interpreter of a Plone instance runs the file by path, and `--classes` then says which classes have a `__setstate__` in Python.
- **`plone`.** `plonebench/loadpath.py` copies the store of the `small` fixture of B5, starts `zoe serve` on it with the settings of B5, and runs `plonebench/inzope/loadpath.py` in the interpreter of the zoeclient scenario: one Zope thread that sends anonymous requests of a folder listing and of a document view through the publisher of Zope in its own process, 200 by default, with `cacheMinimize()` before each. For each request it records the time, the objects loaded and the loads that the server counted (the misses of the client cache); then it counts the `persistent_load` callbacks and the Python calls of each load, and the classes loaded. `--py-spy` samples the process, and `frames FILE --root _request_folder` (or `_request_document`) reads the samples of one kind. It needs `just plone zoeclient build` and the fixture (`just bench plone prepare`), and writes into `target/bench/plone/loadpath/`.

## The Plone end-to-end benchmark

B5 of the specification: Locust against a Plone 6.1 site, ZEO against ZOE, same Plone, same hardware. zodbshootout and the client benchmark measure the storage; this benchmark measures what a Plone user gets: completed pages and saves per second, their latency, and what conflicts cost. The harness is the uv project `bench/plone` (package `plonebench`). The findings of the last campaign are in [`docs/findings/plone-end-to-end.md`](../docs/findings/plone-end-to-end.md).

```sh
just plone zeo build && just plone zoeclient build && just plone zeoclient build
just bench plone prepare                       # the small fixture, once
just bench plone run --stack zoe-native --scenario edit --steps 1:60,4:60,16:60
just bench plone campaign --stacks zeo,zoe-native --scenarios browse,edit --reps 3 --list campaign.txt
just bench plone report $(cat campaign.txt) --out report.md --json summary.json   # the runs of one campaign
just bench plone serve --stack zeo             # a stack on a copy of the fixture, for a look
just bench plone test                          # the tests of the harness
```

**The stacks.** Every setting but the storage section is the same: the runner writes `zope.conf` and `wsgi.ini` of each instance from one template (`plonebench/stack/templates.py`), with the eggs of the buildout scenarios of `plone/`.

| Stack | Server | Client | What differs from `zeo` |
| --- | --- | --- | --- |
| `zeo` | ZEO 6 (`runzeo`, FileStorage, pickle protocol Z5) | `<zeoclient>`: `ZEO.ClientStorage` | the baseline; the ZEO server resolves conflicts with ZODB's resolver |
| `zoe-native` | `zoe serve` | `<zoeclient>`: `zoe.zeo.ClientStorage`, native client; `zoedb[plone]` | the production combination: the native client, the `sequences` extension and `zoe.plone`, which gives `portal_uidgenerator` its ids from a store sequence |
| `zoe-native-kv` | `zoe serve` | as `zoe-native`, with `ZOE_PLONE_BACKENDS locking` in the `<environment>` of `zope.conf` | the KV namespaces of ADR 0043: the locks of the edit forms live in the ephemeral namespace of the store, so a lock writes no object |
| `zoe-native-qi` | `zoe serve` | as `zoe-native`, with `ZOE_PLONE_BACKENDS indexing` in the `<environment>` of `zope.conf` | queued indexing (ADR 0047): a save writes its catalog operations to a durable namespace of the store, and the indexer of the site applies them. After the steps, the runner waits for an empty queue through `@@zoe-indexing`, as the maintainer, before the verification, and the result records under `indexing` the time that the queue took to empty and the delays of the indexer of each instance, for the run and from the start of each step |
| `zoe-native-qi-kv` | `zoe serve` | as `zoe-native-qi`, with `ZOE_PLONE_BACKENDS indexing,locking`; before the instances start, the runner runs `inzope/member_properties.py`, which moves the properties of the members and groups of the site into records of `zoe.plone.properties.PrincipalProperties` and writes the tier 2 entry of that class into the merge policy, as the profile `zoe.plone:default` does; the result records the moves under `member_properties` | queued indexing (ADR 0047), the locks in the ephemeral namespace (ADR 0043), and the login times merged at the vote (ADR 0046, section 9): a login writes the record of its member, not the bucket of the property sheet of PAS |
| `zoe-asyncio` | `zoe serve` | `<zoeclient>` with `native false`; `zoedb[plone]` | ZEO's asyncio client with the ZOE extensions: the sequence without the native client |
| `zoe-stock` | `zoe serve` | `<zeoclient>`: stock `ZEO.ClientStorage` over M5, no zoedb | the server alone, with no client extension |

On `zoe serve` every client resolves conflicts through the vote (tier 3), after the structural merges of tier 1 in the server. `--split-merges on` (or `shadow`, `off`) writes the switch `split_merges` of the merge policy (ADR 0048) into the store of a run of a stack of `zoe serve` with zoedb, through a client of its own, before the instances start; the policy keeps its classes and its other switches, and `result.json` records the policy in `merge_policy`. Without the option, the store keeps the policy of the fixture. `--folder-orders on` (or `shadow`, `off`) writes the switch `folder_orders` of the order merge (ADR 0052) the same way, with the tier 2 entry of `plone.app.contenttypes.content.Folder` that merges `modification_date` with `max`; a run of the mechanism of ADR 0052 takes `--split-merges on --folder-orders on`. `--profile zoe.plone:default` imports that profile into each site of the store of a run of a stack of `zoe serve` with zoedb, through a client of its own (`inzope/profile.py`), before the instances start, as the owner of a site does: its import steps write the merge policy of the site and move the properties of the members and groups, so `member_properties.py` does not run. `result.json` records the profile in `profile`, the moves in `member_properties` and the policy in `merge_policy`. A campaign gives the switches and the profile only to the stacks that take them. `zoe serve` writes raw records by default (ADR 0041); `--zoe-compression zstd` (or `zstd:LEVEL`) gives it `--compression`, and the result records it. FileStorage has no compression, so a run with zstd is a compression experiment of its own. The records of the fixture keep the compression of the `zoe convert` that prepared it: raw since ADR 0041, zstd before (see the fixture below).

**The ports.** The instances listen on 18080 and up, the server on 18100 and its admin port on 18199. `--port-offset N` adds N to each of them, so two runs share one machine: an offset of 200 or more keeps the ports of the two runs apart, and the harness refuses to start when one of its ports is in use. The two runs also share the CPUs, so their times do not compare.

**The constants** (`stack.Settings`, recorded in each result): 2 Zope instances with 2 request threads each, a ZODB cache of 30,000 objects per connection and a pool of 7 connections, a storage client cache of 128 MB in memory for each instance (no persistent cache file, for either client), a blob cache per instance, on Linux the server on CPU 0, the instances on CPUs 1 and 2, Locust on CPU 3 (`taskset`). `--zope-cpus` gives one CPU list for each instance, separated by `;`. A list shorter than `--instances`, such as `--zope-cpus "1;3"` with `--instances 4`, is an error: `prepare`, `run`, `campaign` and `serve` exit with 2 before they look for the fixture, and the stack refuses to start its instances. A longer list is valid: the instances take its first lists. Both servers make a commit durable before `tpc_finish` returns: FileStorage calls `fsync` in `_finish_finish`, `zoe serve` syncs its group commit. `zoe serve` keeps the default page cache of its store (1 GiB); `--zoe-cache-size 128MB` gives it `--cache-size 128MB`, and the result records it. The page cache of the store disk is shared and stays warm between runs: the container cannot drop it.

**On macOS.** The harness runs there too, with three differences that each result records under `environment.machine`. macOS has no CPU affinity, so no process is pinned, and the scheduler puts each thread on a performance or an efficiency core (`cpu_pinning`, `core_kinds`). On macOS `fsync(2)` leaves the data in the cache of the drive, and only `F_FULLFSYNC` writes it to the medium. `zoe serve` calls `fsync(2)` there (ADR 0040), as Python's `os.fsync` in FileStorage does, so by default both servers pay for the same durability. `--zeo-fsync full` makes `probe/zeoserver/launch.py` give the ZEO server `F_FULLFSYNC`, a stronger sync than the one of `zoe serve` (`durability`). The macOS runs of the findings before ADR 0040 ran `zoe serve` with `F_FULLFSYNC` and ZEO with `--zeo-fsync full`. The sampler reads `proc_pid_rusage` and psutil instead of `/proc`. The runnable time minus the CPU time stands for the run delay, and steal time, disk flushes and the split of context switches are absent. The store copies are APFS clones (`/bin/cp -c`).

**The fixture.** `prepare` builds a deterministic synthetic site (`plonebench/corpus.py`; presets `small`, `medium`, `large`, `xlarge` and `xlarge-mini`, or `--spec FILE` with any field of `SiteSpec`): sections of nested folders, Documents and News Items with generated text and subjects, Files of 16 KB to 1 MB, collections, users with local roles through groups, three workflow states, and the folders `bench/inbox`, `bench/hot`, `bench/shared` and `bench/import` for the contention scenarios. It builds the site on a ZEO server, converts the `Data.fs` with `zoe convert`, then reads a logical digest of the site through each store (`inzope/digest.py`: every object with its fields, state, UID, local roles, View roles, dates, versions and workflow history; the users and groups; the catalog and fixed queries) and refuses the fixture when they differ. The text is made of generated words, never of a natural language. `equivalence.json` records the commit that converted it (`converted_at`); a fixture from before ADR 0041 holds zstd records, and `prepare --force` makes it again with raw ones. The fixture lives under `target/bench/plone/fixtures/<name>`, with the password of the accounts in a file only the user reads. A run never opens it. It copies the store of its stack in full (`cp -a`, with reflinks where the file system has them, clones on APFS), then syncs the copy to the disk before the server starts (`sync -f`: one syncfs(2) of the file system of the copy, which also writes the dirty pages of other files of that file system). So the kernel writes no page of the copy during the warmup or the steps, where the writes would compete with the syncs of the commits. `result.json` records the bytes of the copy and the seconds of the copy and of the sync under `restore`. On ext4 without reflinks, `cp` returns once the page cache holds the copy, and the sync then waits for the disk: on the reference machine, at 67 to 136 MB/s, about 80 to 160 s for each run of a stack of `zoe serve` on `xlarge` (about 11 GB) and 45 to 90 s for `zeo` (about 6 GB). On `xlarge-mini` (66 MB on `zeo`, 140 MB on `zoe serve`) the copy takes 0.05 s and the sync 0.1 to 5 s, as the other writes of the file system go.

**The targets file.** `prepare` writes `targets.sqlite` beside `manifest.json` (`workload.write_targets`), and a run writes it first when the fixture has none or when `manifest.json` changed. It comes from `manifest.json` and the spec in it only, with no plan of the site and no change to another file of the fixture: so a fixture of an older build runs with no new build. It holds the accounts, the search terms, the subjects and the code words of the titles (words 100 to 1,099 of the vocabulary of the spec, `corpus.site_words`); the browsable Folders, Documents and News Items, and Files, in the order of the manifest, with the slice of the Documents and News Items below each Folder and the Folder of each one (the manifest lists a container before what it holds, so the items below a Folder are one slice); the Collections; and each item with its index in the manifest, its container, its type, title, state, pool, section, size, UID, versions and workflow history, indexed by path, by container and by section. Locust and the verification read it through `workload.TargetsFile` and never load the manifest. A pick of `browse` draws a number, as a choice from a list of the same length does, and reads one row; a user reads the rows of its own section once. So the users of `small` and `medium` do the same operations on the same items as when Locust read the manifest (`tests/test_locust_operations.py`). On the manifest of `xlarge` (249,988 items, 97 MB), `write_targets` takes about 2 s and writes 77 MB; Locust starts in 0.23 to 0.28 s with a peak of 58 to 71 MB, its 64 users start in at most 0.05 s, and a call of `browse` costs 0.03 ms of Locust. When Locust loaded the manifest and planned the site in each of its two processes of a run, the start took 65 to 72 s and 1.08 GB, the users of `edit` 0.9 s, and a call of `browse` 20.6 ms, so `browse` measured Locust, not the stores.

**The site of 250,000 items.** The preset `xlarge` has the shape of a real Plone site of about 300,000 items, scaled to 250,000, with the stock types of Plone 6.1 (a decision of the human). Its sections are the units of the site (`leaf_folders` of `SiteSpec` is not 0), and `depth` and `fanout` do not apply:

| Depth | Items |
| --- | --- |
| 1 | 240 Folders: the units, `section-NN` |
| 2 | 750 Folders: in each unit, about 2 Folders `folder-NN` that hold Folders, and the Folder `news` |
| 3 | 7,200 Folders `folder-NNN`, the leaves, about 30 in each unit; 34,000 News Items, in the Folder `news` of their unit |
| 4 | 177,000 Documents with rich text and 30,500 Files, in the leaves |

Each unit also holds its Collection `recent`, and `bench` holds the folders of the scenarios: the plan has 249,988 items. The units differ in size. The weight of a unit comes from a log-normal spread (`unit_spread` 1.3, from the quantiles of the normal distribution, so the sizes do not depend on the seed), and its News Items and its leaves follow its weight: a unit holds from 38 to 17,221 items. A leaf holds about 25 Documents and 4 Files (`leaf_spread` 0.1). Each count splits by the largest remainder, so the totals are exact. The children of a container (the site or a Folder) have a median of 28, a 90th percentile of 32, a 99th percentile of 112 and a maximum of 1,450 (`largest`), and 4 containers hold more than 1,000. Files are 16 KB each. The states and the pools are those of the other presets: 20 % private, 10 % pending, and the pools `browse`, `edit` and `workflow` take 2, 2 and 1 Document of 5. Each of the 96 editors gets a unit of its own, so up to 96 editors never share one. The 48 shared Documents of `contention-folder` and `contention-fields` lie in `bench/shared/folder-00`, a Folder of depth 3, as a leaf is. The catalog has 56 indexes and 53 metadata columns: the 31 indexes and 32 columns of a stock site, plus 11 `FieldIndex`, 6 `KeywordIndex`, 5 `DateIndex` and 3 `BooleanIndex` on attributes `bench_*` that the build sets on each item, from the seed and the path, and a metadata column on 21 of them. So an edit reindexes as many indexes as on the real site. The other presets keep the stock catalog. `xlarge-mini` has the same shape at about 1/100, for the tests: 8 units, leaves of the same size, and 2,586 items.

**The pack.** The fixtures of `xlarge` and `xlarge-mini` hold no history of their build (`pack_every` of `SiteSpec`). The build packs the FileStorage through ZEO after each 50,000 items, and `prepare` removes the `Data.fs.old` and the `blobstorage.old` that each pack keeps. After the build, `prepare` stops the server and packs the FileStorage once more, before the digest and `zoe convert`. So the records of `Data.fs` are its live objects, and `zoe convert` copies only these. The other presets keep the history of their build. The manifest loop of `inzope/build_site.py` and the walks of `inzope/digest.py` do not commit, so they call `cacheGC` as they go: their object cache stays near its target size. A full build of `xlarge` runs in one process for about 6.5 hours on the reference machine: the build at about 0.08 s per item, then the last pack, the two digests and the conversion in about 40 minutes. At rest the fixture takes about 17 GB: `Data.fs` about 5.5 GB, the blobs 0.5 GB, the ZOE store about 11 GB. Its disk peaks at about 28.5 GB, during the digest of the ZOE store, whose check copy is a full copy on ext4. `build_site.py` takes about 2 GB of memory, 0.8 GB of it for the plan. These numbers are estimates from the builds at 1/100 and 1/10. The build of `xlarge-mini` takes about 4 minutes. During a build, `build/builder/log/build_site.py.out` in the directory of the fixture gets each line of progress, and `prepare` prints each pack.

`ZOE_BENCH_FIXTURE_BUILD=1 just bench plone test bench/plone/tests/test_fixture_build.py` builds `xlarge-mini` and `small` again, as `test-<name>`, on the ports of the defaults plus 400 (`ZOE_BENCH_FIXTURE_PORT_OFFSET` gives another offset), and checks the equivalence, the records of the packed `Data.fs`, the catalog of each, and the object cache of the digest. It takes about 5 minutes and the CPUs of the machine. `just bench plone test` without the variable skips it.

**The scenarios** (`plonebench/workload.py`). Each simulated user has its own session and account: anonymous visitors, members, editors who hold local roles on one section, an importer and a maintainer. The UI scenarios go through the rendered pages and the forms of Plone, with the CSRF token of plone.protect; the REST scenarios go through plone.restapi with a JWT, and the report names the interface of each scenario.

| Scenario | Users do |
| --- | --- |
| `browse` | folders, Documents, News Items, File views and downloads, up the breadcrumbs; anonymous and logged in |
| `catalog` | `@@search` with text, filters, sorting and a second page; collections; REST `@search` with metadata |
| `edit` | the edit form on Documents of their own section, a user per Document |
| `create-spread` / `create-shared` | the add form in folders of their own section / all in `bench/inbox` |
| `workflow` | publish and retract from the workflow menu, then an anonymous request that checks the visibility |
| `mixed` | a weighted mix of the above, weights in the result |
| `mixed-background` | `mixed`, beside one maintainer that reindexes `SearchableText` in a loop and one importer that posts Documents through REST |
| `contention-folder` | the edit form, a Document each, all in one folder |
| `contention-fields` | REST PATCH, two users on each Document: one writes the title, the other the description |
| `contention-same` | REST PATCH, every user writes the title of one of four hot Documents |

A run steps the users of a closed workload (`--steps users:seconds,...`, no think time by default): each user waits for its response before its next operation, so a slower server lowers the offered rate. The first seconds of each step stay out (`--trim`). Locust gets no retry: a write that fails is a failed operation, unless `--client-retries N` gives a bounded retry, whose latency runs from the first request to the final outcome.

**The ledger and the verification.** Locust writes one record for each logical operation (`plonebench/ledger.py`): what it wrote and what the site acknowledged, with the outcome `ok` (the response showed the effect), `failed` (an HTTP error: Zope aborted the transaction), `ambiguous` (no complete answer: the write may have committed) or `rejected`. A write leaves a pending record before its request, so a run that ends during a request leaves an ambiguous one. After the run, the instances stop, and `inzope/observe.py` reads the site through a client of its own, read-only, before any repair. `plonebench/verification.py` then checks: each acknowledged creation exists, no object exists without its operation, a refused write did not commit, UIDs and history ids are unique, each edited field holds the last acknowledged value (with several writers, a value that no later acknowledged write superseded), each acknowledged edit added one CMFEditions version and each transition one workflow history entry, anonymous may View exactly the published objects, each object has one catalog entry with its title, state, date and security, and a search for the token of the current title finds the object while a superseded token does not. The verdict is in each result.

The verification reads what the run wrote and what lies next to it, not the whole site, so its time follows the run. The runner reads the items that it needs from the targets file, and `verify-request.json` names the paths of the ledger, the containers of the creations, the ranges of the manifest within 64 items of each object of the ledger, and a fixed sample of 100 items, drawn with the seed of the spec. The observer reads:

- each object of the ledger and of the sample, as above;
- the children of each container of a creation and of the container of each object of the ledger, against the children of the manifest: a child that the manifest does not hold is a new object, for the checks of creations and phantoms;
- the catalog entry of each item of the ranges and of each of these children: `uids`, `paths`, `data` and the path index agree on its record id, its container holds its object, and its Title and review_state are those of the manifest, unless the run wrote it;
- the 64 entries on each side of the record id of each object of the ledger and of each new object, in `paths`, `data` and the `_unindex` of the path index: each entry is in all three with one path, `uids` gives its record id back, and its container holds its object;
- the UID and the history id of each object that it observes: the `UID` and `cmf_uid` indexes find no other object, and the manifest holds each UID once;
- the length of the catalog: the `catalog_size` of the manifest plus the new objects.

The build gives consecutive record ids in the order of the manifest, and a bucket of an IOBTree holds at most 60 keys, so the items next to an object in the manifest hold the entries of the buckets that a write of the object rewrites; a new object takes a random record id, and the entries next to it hold the rest. The sample has the title, state, versions and workflow history of the manifest (check `sample`; the manifest gives an item without a workflow, a File, the workflow history of its container, so the check leaves that out), and the checks of permissions and of the catalog apply to it. A run writes only the objects of its ledger, the containers of its creations and the catalog buckets of their entries, so a defect that a run makes lies there, or changes the length of the catalog anywhere in the site. What the reads do not see is damage far from every write that keeps the length of the catalog and misses the sample: no write of a run makes it, and `prepare` checks the fixture once. On `xlarge-mini`, after runs with 4 instances and steps `4:5,16:5`, the observer reads 151 to 156 content objects (`mixed`) and 228 to 230 (`edit`, 42 or 43 objects in the ledger) for 2,586 items, where the walk of the whole site read 2,586 to 2,593, and checks 700 to 1,800 entries by path and as many by record id. `ZOE_BENCH_B5_MINI=1 just bench plone test bench/plone/tests/test_b5_mini.py` runs B5 on a copy of `xlarge-mini` with only the files of a fixture of an older build, with 4 instances and steps of 5 s, on the ports of the defaults plus 500 (`ZOE_BENCH_B5_PORT_OFFSET`): runs of `mixed` on `zeo` and `zoe-native-qi-kv` and of `edit` on `zeo` pass, and the verification fails on copies of the store of the edit run where an edited Document lost its edit, where a News Item left the catalog, and where a File beside an edited Document left the catalog while the length of the catalog stayed the same. It takes about 4 minutes, and 4 more when it builds `xlarge-mini`.

**The instrumentation.** A WSGI filter in each Zope process (`probe/plonebench_probe.py`, first in the pipeline of `wsgi.ini`) writes one JSON line per request: the op id and attempt that Locust sends in headers (never a URL or a body), the attempts of the publisher, each `ConflictError` with the class of its object and whether the publisher retried, the commit time, the storage calls of the request (`loadBefore`, `store`, `tpc_vote`, `tpc_finish`, `tpc_abort`) with their time and bytes, the conflicts that ZODB's resolver resolved in the process, the reason of each resolution that failed (for a bucket, the reason that BTrees gives, such as `Conflicting changes`), the resolutions of each attempt that failed after them, and the CPU time of the thread. The same filter runs on every stack. The ZEO server resolves conflicts in its own process, so a probe there (`probe/zeoserver`) counts them, with the same reasons and the resolutions of each vote that failed after them; on `zoe serve` the clients resolve, and the probe of the instances counts them. The runner reads `server_status` of both servers, and the Prometheus metrics of `zoe serve` (lock waits, vote and finish latency, fsync batch sizes), before and after the measured window, and samples the processes once a second (`/proc` on Linux, `proc_pid_rusage` and psutil on macOS): CPU, resident memory, I/O bytes, context switches and run-queue delay of each process, the CPUs (steal included) and the disk of the store (flushes included). For the CPUs of the Zope instances (the CPUs of the lists that the instances run on: the first `--instances` lists of `--zope-cpus`), on Linux, it also reads the clock that the hardware measured over the last milliseconds (`cpufreq/cpuinfo_avg_freq` in sysfs, else `scaling_cur_freq`) and the time that the core of each CPU spent throttled since the boot (`thermal_throttle/core_throttle_total_time_ms`). Sibling CPUs give the same throttle time of their core, so it reads that time for one CPU of each physical core (`topology/physical_package_id` and `topology/core_id`). The kernel adds an episode of throttle to the counter when the episode ends: an episode that crosses the edge of a step counts in the step where it ends, and an episode that is still open after the last step does not count. `result.json` holds `zope_clock_mhz`, the mean clock over the samples of the steps (the trim excluded) and over the Zope CPUs, and `zope_throttle_seconds`, the growth of the throttle time of each physical core of the Zope CPUs during the steps (the trim excluded), summed over the cores; each step holds the same two values in its `resources`. Each is null when the machine does not give it, as on macOS, never 0. The log of the run gives them in a line `zope CPUs 1;3;6;8: clock mean 4183 MHz, throttle 0.0 s during the steps`. An idle CPU reads a low clock, so the mean of a step at few users is lower than the clock of a busy core: compare the clocks of runs at the same users. For the server, on Linux, it also reads the counters of the bytes written to the store: `wchar` of `/proc/<pid>/io` (the bytes given to write calls), the bytes that the process gave to its TCP sockets (`bytes_sent` of `ss -tie` without `bytes_retrans`, plus `notsent`, every port), the summed size of the regular files that the process holds open for writing outside the directory of its store (`server.out`, `zoe-serve.log`, a resolution log), and on `zeo` the size of `Data.fs`. When a connection closes, the sampler keeps the bytes that its last sample saw; the bytes that it sent after that sample are lost, at most one second of one connection. The connections of the instances stay open for the whole run, and the runner reads the admin port of `zoe serve` only outside the measured window. A counter that a stack does not keep is absent from its result, never 0. `--no-probe` runs without the filter, to measure its cost.

**The results.** Each run writes `target/bench/plone/runs/<started>-<scenario>-<stack>-r<n>/`: `result.json` (the machine, with `ZOE_BENCH_MACHINE` as its name when it is set, the software, the commit and whether the tree held changes that the commit does not (null when git fails or when `ZOE_BENCH_COMMIT` names another commit; the report then says `tree unknown`), the stack, the settings, the scenario and its mix, the steps, the fixture and its equivalence, the numbers of each step, the server counters, the resources and the verdict), the ledger, the probe files, the samples, the CSV files of Locust and the logs. The store copy goes at the end. `report` reads run directories and prints one table per scenario: per stack and step, the median rate of successful operations over the repetitions with its range, p50, p95 and p99 pooled over the repetitions (a p99 of fewer than 200 operations is marked `~`), failures, first-attempt successes, server attempts per operation, conflicts per 1,000 operations, exhausted retries, CPU per operation of Zope and of the server, the bytes the server wrote per successful operation in two columns, the CPU of Locust and the verdicts. "store KB written/op" is the bytes that the server gives to the write calls of its store: on `zeo` the growth of `Data.fs`, which FileStorage only appends to (its writes to `Data.fs.tmp` do not count); on `zoe serve` the growth of `wchar` minus the bytes of its TCP sockets and the growth of its other files, which leaves the writes to `zoe.redb` and the wake-ups of the tokio runtime: 8-byte writes to an eventfd, which `wchar` counts and the column keeps (1.5 KB per operation in a run of `edit` on `zoe-native`, under 0.2 % of the column). The sampler reads the write counter and the socket counter one after the other, so on a step that writes almost nothing the value can fall a little below 0. It counts no blob: the scenarios of B5 upload none, and a blob that a scenario uploads would count on `zoe serve` only. It counts what the server asks the kernel to write, not the bytes that reach the device. On macOS the sampler has no `wchar`, so the column shows `–`. "server page cache KB/op" is `write_bytes` of `/proc/<pid>/io`. The kernel charges it a whole page-cache folio, up to 2 MB, when a write dirties a clean one, so on a store that a large copy put in the page cache it is many times the bytes written (`docs/spikes/server-write-volume.md`). A campaign alternates the order of the stacks from one repetition to the next.

**The summary of a campaign.** `report RUN... --json FILE` also writes the summary of the runs, the document of the family `plone` that `just bench publish` publishes (ADR 0054). It validates against [`schema/plone.schema.json`](schema/plone.schema.json) before `report` writes it. It holds the machine, the Python of the instances, the software, the commit and whether the tree was clean (`run.dirty`: true when a run had a dirty tree, null when a run has no record of its tree), the fixture (its name, its preset and its counts of objects and catalog entries), the settings, each stack with its switches and its merge policy, the scenarios, one row per scenario, stack and step with the numbers of the table and the objects loaded and stored per second (the `loadBefore` and `store` calls that the probe counts for the operations of the step, over its seconds, the median of the repetitions), and the verdict of the verification of each run (`not run` for a run without one). When a run of the campaign records `zope_clock_mhz` or `zope_throttle_seconds`, each run of the summary holds the key, null for a run that did not record it; the summary of runs that record neither has neither key. A number that its counter does not give is null. It holds no host name, user name, path or password: no `zope.conf`, no traceback and no message of a check. The machine name is the name that the runs recorded, else `ZOE_BENCH_MACHINE` of the report, else the CPU model of the runs. One summary holds one campaign: when the runs hold more than one fixture, commit, machine name, Python of the instances (implementation, major and minor version, free-threaded or not) or value of a setting (the ports and the switches of a stack may differ), `report` prints the key and its values, exits with 2 and writes no summary. It still writes the Markdown report. So run `report --json` once per campaign, on the run directories of one fixture.

## The log replay

B6 of the specification: the transactions of a store that a B5 run kept, replayed against ZEO and against `zoe serve`, with the conflicts that each stack raises and resolves. It measures the success criterion on `ConflictError`s: the `ConflictError`s that reach Zope on `zoe serve`, as a share of ZEO's, with a target of at most 10 %. It is a measure, not a gate: the gate of phase 4 is B5. The log is synthetic: the store of a B5 run on the synthetic site, never production data.

```sh
just bench plone run --stack zeo --scenario edit --steps 4:60,16:60 --keep-store
just bench replay target/bench/plone/runs/<run>          # 1x, 4x and 16x on both stacks
just bench replay target/bench/plone/runs/<run> --speeds 1 --repetitions 3
just bench replay report target/bench/replay/<started>.json
just bench replay test                                   # the tests of the replay
```

**The log** (`replay/log.py`). The FileStorage of the run, read through its iterator in tid order. The commit of a transaction is the time of its tid. Its start comes from the probe records of the instances (`probe/instance*.jsonl`): a tid belongs to the request that committed, that started before the tid and that ended first after it, and starts at the start of that request, its first attempt: the replay does not retry, and the attempt whose `ConflictError` reaches Zope is the first one. A request that commits several times begins each next transaction at its previous commit. A tid that no request explains starts at its commit. A transaction of a background job starts at its commit too, and takes no request: no request makes it, and the job runs its transactions one after the other. The replay knows such a transaction by its note (`BACKGROUND` in `replay/log.py`): `zoe.plone: indexing queue`, a batch of the indexer of queued indexing. The report of the match counts it as unmatched, and the first line of a run gives their number. The transactions before the first request are the base: the fixture and the start of the instances. Each run restores the base into its new store first, and counts nothing in it.

**The runs** (`replay/runner.py`). For each speed, for each repetition, one run of each stack, on a new server and a new store under `target/bench/work/replay`: `zeo` is `ZEO.ClientStorage` to a ZEO 6 server on a FileStorage, and `zoe-native` is the native client to `zoe serve`. At the speed s, an event that the log puts t seconds after its first start comes t / s seconds after the start of the run. A transaction reads the serials and the states of its oids at its start and stores at its commit. One scale applies to every event, so the same transactions overlap at every speed, and the counts do not change with the speed (`docs/spikes/log-replay.md`). It stores its own change, applied to the state that it read: the change from the record of the oid before it in the log to its own record, through the `_p_resolveConflict` of the class; where that refuses on a bucket, a set or a BTree of one bucket of BTrees, the keys that the transaction added, changed or deleted go into the items that it read, each with its whole value; else it stores its own record. Each run counts how its records came to be (`rebases`). This is not a conflict, and no count holds it. One thread plays the events in time order, so the order of the commits is the order of the log on every machine. A second client loads the oids of the log beside it; the run records its loads and the error that stopped it, if any (`read_load`). A commit that raises `ConflictError` is not retried: the count is of the `ConflictError`s that reach Zope. The replay runs in the interpreter of the zoeclient Plone instance, so the resolver of ZODB, in the replay and in the ZEO server, has the classes of the site. The native client is the package `zoe` of the last `just plone zoeclient build`: build the instance again after a change of the client. `--zoe-serve-arg ARG` gives `zoe serve` one more argument, such as `--zoe-serve-arg=--posting-dicts --zoe-serve-arg=on`. A result records the commit and whether the tree differs from it, the `zoe` binary with its version and its sha256, these arguments, the package `zoe` and the sha256 of its extension, Python and the machine (`software`), before the first run; when they differ at the end, it records them again (`software_after`).

**The counts.** Each run counts the conflicts by class (`module.name` of the record) and by path: `native` (`zoe serve` resolved it), `python-client` (the resolver of ZODB in the replay), `python-server` (the resolver of ZODB in the ZEO server) or `refused` (the commit raised `ConflictError`). A vote that fails hides the conflicts that it resolved before its refusal, on both stacks, so a count by path holds the conflicts of the votes that pass and the refused oid of each vote that fails (`docs/spikes/log-replay.md`). After the run, a new client loads every record of every acknowledged transaction at its tid; a run in which one does not load does not count.

**The measure** (`replay/gate.py`). `ConflictError`s per 1,000 transactions over the runs of each stack that count, and the ratio of the success criterion: the rate of `zoe-native` over the rate of `zeo`. There is no ratio when a stack has no run that counts, or when `zeo` has no `ConflictError`. `just bench replay report FILE` prints one row per run, the conflicts per 1,000 transactions by class and by path, and, as its last line, the rates, the ratio as a percentage of `zeo` and the target of at most 10 %, with each speed that has no run that counts for a stack. It exits with 0 for a result, whatever the ratio, and with 2 when FILE is not a result. `python -m replay run` exits with 0 after its runs, whatever the ratio, and with 2 when it refuses the log: no probe records, probe records that explain no transaction of the store, a merge policy that is not valid, or a timed transaction that writes the root with a policy. `just bench replay RUN` gives these codes, and exits with 1 before the replay when RUN kept no FileStorage, when RUN has no probe records, or when the interpreter of the zoeclient instance is missing. A run that replays no transaction does not count. A result is `target/bench/replay/<started>.json`, valid against `bench/schema/replay.schema.json`.

## The showcase

`just bench showcase` runs the publishable set on one machine, in one repetition, and leaves a directory that `just bench publish` takes (ADR 0054). The set is a decision of the human. Run nothing else beside it.

```sh
just bench showcase --plan                    # each run and its estimate; runs nothing
just bench showcase                           # a new directory target/bench/showcase/<started>/
just bench showcase --set capacity            # the capacity set: xlarge with 4 instances
just bench showcase --dir target/bench/showcase/<started>    # resume it
touch target/bench/showcase/<started>/STOP    # stop after the current run
just bench publish target/bench/showcase/<started> CHECKOUT
```

**The set**, in the order of its runs:

1. The builds: the release `zoe` binary (or the file that `ZOE_BINARY` names), `just plone zeo build` and `just plone zoeclient build`. The recipe builds nothing before the showcase starts, so no build runs between two measurements.
2. For `small`, then `medium`: the fixture, which `prepare` builds only when it is missing; the B5 runs of the fixture; then the B5 summary of the fixture (`report --json`).
   - `small`: `browse`, `catalog` and `mixed` at 4 and 16 users; `edit` and `create-spread` at 1, 4, 8, 16 and 32 users, the curve of the dashboard; `contention-folder`, `contention-fields` and `contention-same` at 4 and 16 users.
   - `medium`: `browse`, `catalog`, `edit`, `create-spread` and `mixed` at 4 and 16 users.

   Each scenario runs on `zeo` and on `zoe-native-qi-kv`, one after the other, and the stack that goes first changes from one scenario to the next. Each run keeps its verification.
3. The native gate (`just bench native`) and the client benchmark (`just bench client`), each on CPython 3.13 and on 3.14t. They run in the environment of `bench/shootout`, not in the one of `bench/plone`, with the `zoe` binary of the build, the commit of the showcase and `ZOE_BENCH_MACHINE`, so every document names the same machine and commit.

**The capacity set** (`--set capacity`, a decision of the human). The default set has 2 instances on 2 cores, and ZOE uses 1.9 of these 2 cores at 8 users and more, so it cannot show more throughput. The capacity set runs B5 on the site of 250,000 items with 4 instances:

1. The builds of the default set.
2. The fixture `xlarge`, which `prepare` builds only when it is missing (about 6.5 hours); the B5 runs of `xlarge` on `zeo` and `zoe-native-qi-kv`, with 4 instances of 2 threads: `edit` and `create-spread` at 4, 8, 16, 32 and 64 users, the curve of the dashboard; `contention-folder`, `contention-fields` and `contention-same` at 8 and 32 users; `browse`, `catalog` and `mixed` at 8 and 32 users. The stack that goes first changes from one scenario to the next, as in the default set, so the heat of the machine favours no stack. Each run keeps its verification.
3. The B5 summary of `xlarge`. No native gate and no client benchmark.

Its layout on the reference machine (6 performance cores of 2 threads, 8 efficiency cores): the server on CPU 0 (core 0), for both stacks; the instances on CPUs 1, 3, 6 and 8, one performance core each, whose sibling CPUs (2, 4, 7 and 9) stay idle; Locust on the efficiency cores 12 and 13; core 5 (CPUs 10 and 11) stays free for the system. `--fixtures xlarge-mini` runs the same set on the shape of `xlarge` at 1/100, for the tests. The directory holds one document, `summary-xlarge.json` (or `summary-xlarge-mini.json`), and its summary records the layout in `settings`: `instances` 4, `threads` 2, `server_cpus` `0`, `zope_cpus` `["1", "3", "6", "8"]`, `locust_cpus` `12,13`.

The plan of the capacity set holds 21 runs: the 3 builds, `prepare-xlarge`, the 16 B5 runs and `summary-xlarge`. Its estimate, with the defaults: about 2 minutes of builds; the load of the 16 runs, 3,600 s of warmups and steps; 1.25 s for each second of load (the drain of the queue and the verification); and a fixed time for each run on `xlarge`, the copy of the store with its sync, the start and the stop: 180 s on `zoe-native-qi-kv`, whose store is about 11 GB, and 120 s on `zeo`, whose `Data.fs` and blobs are about 6 GB. That is about 3 hours with the fixture, and about 9 h 30 min when `prepare` builds it.

**The clock of the Zope CPUs.** A throttled core runs the instance on it slower, and its numbers then do not compare with those of another run. The result of each B5 run holds the mean clock of the Zope CPUs during the steps and the throttle time of their cores (see the instrumentation above). The line `done` of a B5 run in `showcase.log` gives them, such as `done b5-xlarge-edit-zeo in 16 min: verification pass, zope clock 4183 MHz, zope throttle 0.0 s`, and the B5 summary holds them for each run, in `runs[].zope_clock_mhz` and `runs[].zope_throttle_seconds`. So a throttled run shows in the log and in the published numbers.

**The ZOE stack.** Before the instances of a run of `zoe-native-qi-kv` start, a client of the run imports the profile `zoe.plone:default` into the copy of the store (`--profile`, above). So the stack runs with the merge policy that a new site gets from the profile: the split merge and the order merge of a folder on, tier 2 on for `plone.app.contenttypes.content.Folder` and `Products.CMFPlone.Portal.PloneSite` with `modification_date: max`, and for `zoe.plone.properties.PrincipalProperties` and `zoe.plone.history.WorkflowHistory`, and the entries that the profile derives for the other types in shadow mode. The result records the policy in `merge_policy`, and the B5 summary in `stacks[].merge_policy`. The harness writes no switch, so `split_merges` and `folder_orders` of the `switches` of the stack are null: the policy tells what is on. `zeo` imports nothing.

**The options of the set.** `--set default` (also without the option) or `--set capacity`; `--fixtures`, `small,medium` for the default set and `xlarge` for the capacity set, which also takes `xlarge-mini`; `--step-seconds 60`, `--warmup 60` and `--trim 5`, the defaults of `run`; `--client-objects 1000`, the `--objects` of the client benchmark; and the layout of each B5 run, for both stacks: `--instances 2` (4 for the capacity set) and `--threads 2`, `--server-cpus 0`, `--zope-cpus "1;3"` (`"1;3;6;8"` for the capacity set) and `--locust-cpus 6` (`12,13` for the capacity set). Each set gives its own defaults, and an option overrides the default of the set. On the reference machine these CPUs are on separate physical cores, so each Zope instance has a core of its own (a decision of the human); the settings of each result record the layout. A list of Zope CPUs shorter than the instances is an error: the showcase exits with 2, runs nothing and writes nothing. A directory records these options and its commit: `ZOE_BENCH_COMMIT`, else `git rev-parse HEAD`. A start with another commit or other options of the set exits with 2 and runs nothing. `--max-load` and `--port-offset` are not options of the set, so a start with other values resumes the directory.

**A start** runs the runs that are not done, in the order of the plan, one at a time. For each run, it holds the bench lock (see [Run it](#run-it)), so that no other benchmark runs beside it, and it waits while the 1-minute load average is `--max-load` (8) or more. After the run, a file `STOP` in the directory ends the showcase with exit 0; a `STOP` that exists when a start begins goes away. On Linux, `systemd-inhibit` keeps the machine awake until the showcase ends; when it is missing or refuses, the showcase warns and goes on. A tree that differs from its commit gives a warning too: the runs go on, and `publish` refuses their documents.

**Failures.** A failed build or `prepare` stops the showcase at once. A failed B5 run, native gate, client benchmark or summary stays to do, and the showcase goes on with the next run, but not with the summary of a fixture whose B5 runs are not all done. The exit code is 0 when no run failed, 1 when a run failed, and 2 when the directory belongs to another commit or other options. A later start runs only what is to do. A native gate or a client benchmark that writes its result ended well, also when it exits with 1: the report gives the verdict. A B5 run whose verification fails ended well too, and no later start runs it again: the log and the summary give its verdict, and `publish` refuses the summary. The last line of the log counts the runs that failed, the runs to do, the B5 runs whose verdict is not `pass` and the native gates that exit with 1, and it says `to publish` only when every run is done and every B5 verdict is `pass`.

**Interrupts and resumes.** Ctrl-C, SIGTERM and SIGHUP (a terminal that closes) stop the current run, which stays to do. Locust stops with its run, and a child command (a build, a native gate, a client benchmark) runs in a process group of its own, which the showcase stops when the child ends or on an interrupt, so no process of a run survives it. Two starts on one directory never run a run twice: each looks at the state again when it holds the lock. Each build and each `prepare` records in `state/` the sha256 of the `zoe` binary, the sha256 of the zoedb extension of the Plone instances, or the commit that converted the fixture (`converted_at`); a later start warns when one of them changed, because its runs then use another binary or another fixture.

**The directory.**

| Path | Holds |
| --- | --- |
| `showcase.log` | one line for each start and end of a run, with the verdict of each B5 run |
| `summary-<preset>.json`, `native-<python>.json`, `client-<python>.json` | the documents that `just bench publish` takes: only these are `*.json` files directly in the directory |
| `summary-<preset>.md` | the report of the B5 runs of a fixture |
| `logs/<id>.log` | the output of each run |
| `runs/<id>/` | the directory of each B5 run |
| `failed/<id>-<started>/` | the directory of an earlier attempt of a B5 run, without its copy of the store: only the last attempt of a run keeps one |
| `state/` | the commit and the options of the set, and one file for each run that ended well |

**The plan.** `--plan` prints one line for each run: its id, its state (`todo` or `done`), its estimate and what it does, then the total of the runs to do. A line gives the set and its layout, such as `set: capacity, 4 instances of 2 threads; server CPUs 0, Zope CPUs 1;3;6;8, Locust CPUs 12,13`. `--json` prints the same plan as one JSON document: `directory`, `commit`, `dirty`, `options` (with `set`, `instances` and `threads`), `estimate_seconds` and `runs`; each run has `id`, `kind` (`build`, `prepare`, `b5`, `summary`, `native` or `client`), `state`, `estimate_seconds` and the fields of its kind; a `b5` run has `instances` and `threads` beside its `pinning`. The plan runs nothing, writes nothing and takes no lock. The state of a run depends only on the directory, so the plan of a new directory shows every run to do; the run of a `prepare` whose fixture exists only finds it. The default set takes about 4 hours on the reference machine.

**The tests.** `just bench plone test bench/plone/tests/test_showcase.py` checks the plan, the resume, `STOP`, the lock and the failures, with a fake runner, and runs no benchmark. `ZOE_BENCH_SHOWCASE_SMOKE=1 just bench plone test bench/plone/tests/test_showcase_smoke.py` runs the set on `small` alone, with steps of 5 s, no warmup, a trim of 1 s and 50 client objects, from a clean tree, then publishes the directory into an empty checkout and reads it. It takes the CPUs of the machine, and about 21 minutes on the reference machine when the builds and the fixture exist. `just bench plone test bench/plone/tests/test_showcase_capacity.py` checks the plan of the capacity set, the default set, the refusal of a short list of Zope CPUs, the layout that each B5 run gets and the clock in the line `done` and in the summary, and runs no benchmark. `ZOE_BENCH_SHOWCASE_SMOKE=1 just bench plone test bench/plone/tests/test_showcase_capacity_smoke.py` runs the capacity set on `xlarge-mini` with steps of 5 s, no warmup and a trim of 1 s, from a clean tree, then publishes the directory into an empty checkout and reads it: the layout, the scenarios and the users of the set, every run `pass`, and the clock of each run. It takes about 11 minutes on the reference machine when the builds and the fixture exist, about 3 more for the builds and about 4 more when it prepares the fixture. `ZOE_BENCH_SHOWCASE_PORT_OFFSET` gives the B5 runs a `--port-offset`.

## The results repository

The results go to the [`adeweb-be/zoe-bench-results`](https://github.com/adeweb-be/zoe-bench-results) repository. It holds every family of results in one layout (ADR 0054):

```text
index.json
results/shootout/<machine>/<python>/<storage>/<started>-<commit>.json
results/native/<machine>/<python>/<started>-<commit>.json
results/client/<machine>/<python>/<started>-<commit>.json
results/plone/<machine>/<python>/<fixture>/<started>-<commit>.json
```

| Family | Command | Document | Schema | Its key |
| --- | --- | --- | --- | --- |
| `shootout` | `just bench run` | one per storage and run | [`results.schema.json`](schema/results.schema.json) | `storage` |
| `native` | `just bench native` | one per run of the native gate | [`native.schema.json`](schema/native.schema.json) | `cells` |
| `client` | `just bench client` | one per run of the client benchmark | [`client.schema.json`](schema/client.schema.json) | `rows` |
| `plone` | `just bench plone report --json` | one per campaign of B5 | [`plone.schema.json`](schema/plone.schema.json) | `fixture` |

- A document names its family by one key at its top level, the last column. A document with none of these keys, or with more than one, is of no known family.
- `<machine>` is `machine.name`. `<python>` is a short name for the build: `cp313`, or `cp314t` for a free-threaded 3.14; for `plone` it is the Python of the Plone instances. `<started>` is the UTC start of the run, `YYYYMMDDTHHMMSSZ`. `<commit>` is the first 12 characters of the ZOE commit. `<fixture>` is the name of the fixture of the campaign.
- A result in the layout of version 1, `results/<machine>/<python>/<storage>/<started>-<commit>.json`, is a `shootout` document. It keeps its path.
- `index.json` of version 2 lists every document, oldest first (by `started`, then by `path`): its `family`, its `path` under the root of the checkout, `machine`, `python`, `stacks` (`shootout`: the storage; `native`: the storages of its cells, `zeo` and `zoe-native`; `client`: the clients of its rows; `plone`: its stacks), `fixture` (`plone` only, else null), `scenarios` (the scenarios, or the workloads of the client benchmark), `started` and `commit`. `just bench index DIR` rewrites it from each `*.json` file under `results/` of DIR. It does not read the old index, so it reads a tree of either version. An index of version 1 has no family: its documents are `shootout`.

The harness of zodbshootout keeps its own tree under `target/bench/results`: a full run under `results/<machine>/<python>/<storage>/`, and a quick run under `quick/` instead, never published. `just bench gate` reads that tree. Only `publish` writes the layout above.

### Publishing

```sh
just bench publish target/bench/results/results/reference/cp314t/zeo target/bench/native ../zoe-bench-results
just bench publish summary.json ../zoe-bench-results
just bench publish --main HEAD summary.json ../zoe-bench-results    # the runs of a card branch
```

`just bench publish [--main REF] SRC... CHECKOUT` copies result documents into CHECKOUT, an existing checkout of the results repository. A SRC is a document, or a directory: the `*.json` files directly in it are documents, and its subdirectories are not read. A document is publishable when:

1. it is JSON, of a known family, and valid against the schema of its family;
2. it is not a quick run of zodbshootout;
3. its commit is on REF: `git merge-base --is-ancestor COMMIT REF` succeeds in the ZOE repository of the harness. REF is `origin/main`, unless `--main` names another, such as `HEAD` on a card branch;
4. `run.dirty` is false. A run of a dirty tree is refused, and so is a run with no record of its tree (no `run.dirty`, or null, as a run in the container of the Dagger function `bench`);
5. for `plone`, the verification of each run passed;
6. its path in CHECKOUT is free or holds the same bytes, and no other document of the same publish goes there with other bytes. Each part of the path is a name (a letter or a digit, then letters, digits, `.`, `_` or `-`). No part of the path in CHECKOUT is a symbolic link or a file, and the path, when it exists, is a regular file. So a document never writes outside `results/`.

A partial run is publishable as it is: a run of the native gate with `--cell` or `--scenario`, or a client run with other `--objects`, holds fewer cells or rows, and its document shows them.

`publish` checks everything before it writes: every document, the path of each file that it writes, and the new index, from the tree of CHECKOUT and the new documents. A file under `results/` of CHECKOUT that the index cannot read (not JSON, a document of another family than its directory, a symbolic link) stops the publish. When a document is not publishable, it prints one line on stderr for each reason, `publish: SRC: REASON`, then `publish: refused N of M documents; nothing changed in CHECKOUT`; when CHECKOUT or the page stops the publish, it prints `publish: CHECKOUT: REASON` or `publish: FILE: REASON`. Either way it exits with 1, and CHECKOUT stays as it was, byte for byte. Else it copies the bytes of each document to its path in CHECKOUT (a path that holds the same bytes stays as it is), copies the files that git tracks under `bench/dashboard/` to the same path in CHECKOUT when that directory exists (not the dotfiles, `__pycache__` or the symbolic links; a file of the page cannot go under `results/` or to `index.json`), writes `index.json` of version 2, last, prints the path of each document and of the index, and exits with 0. Each file goes to a random temporary name beside it, then replaces its path, so a file holds its old bytes or its new bytes; an interrupt leaves no temporary file. When a write fails after the checks (a read-only directory, a full disk), `publish` removes the temporary file, prints `publish: CHECKOUT: cannot write PATH: ERROR`, a line `publish: wrote FILE` for each file that it wrote, and `publish: wrote N of M files in CHECKOUT; index.json is not written`, and exits with 3. It copies the page from the working tree, so it prints `publish: warning: FILE differs from HEAD; CHECKOUT gets the file of the working tree` for each tracked file of `bench/dashboard/` that differs from the commit, and goes on. A tracked file that the working tree does not hold is not copied, and the warning says so. It exits with 2, and changes nothing, when CHECKOUT is not a directory, a SRC does not exist or holds no document, or REF is not a commit of the repository. It writes nothing outside CHECKOUT, never runs git there, never commits and never pushes. Review the change of the checkout, then commit it; a push to the public repository needs the approval of the human.

## The dashboard

The dashboard is the GitHub Pages site of the results repository, <https://adeweb-be.github.io/zoe-bench-results/>. Its source is [`dashboard/`](dashboard/), and `just bench publish` copies each file that git tracks there into the checkout:

| File | Holds |
| --- | --- |
| `index.html` | the page: one static page with no build step. It renders the tables and the charts, and loads Chart.js from cdnjs at a pinned version |
| `data.js` | a plain ES module with no access to the DOM: `load(read)` reads `index.json` of version 2, then each document of the index, and gives the data of the page |
| `README.md` | the README of the results repository: the layout, `index.json` of version 2 and the page |

The page requests only cdnjs and its own files. A selector of the machine and of the Python build applies to every section. For each family of tables, the page shows the latest document (for B5, the latest of each fixture), and a selector gives the earlier ones:

- **B5.** Each stack with what it turns on, from the summary: the server, the client, the backends of `zoe.plone`, the switches and the merge policy. One table per scenario, with one group of rows per step and one row per stack: the numbers of the step, the verdicts of the verification, and below each number of a stack other than `zeo` its ratio to `zeo` in the same step. For `edit` and `create-spread`, the users against the ok operations per second and against the `ConflictError`s per 1,000 operations.
- **The native gate.** Each cell and scenario with `ratio`, `low`, `high` and `verdict` as the result holds them, and a dash for a result without them.
- **The client benchmark.** Each row.
- **zodbshootout.** For each cell, `ops_per_second`, `p50_seconds` or `p99_seconds` of each scenario against the start of the run, over every run, with one line per storage. A point links to its commit. The quick cells are a subset of the full cells, so a regression gate can compare a quick run with the last ten full runs on the same machine.
- **The method** of each document: the machine, Python, the software, the commit, and for B5 the fixture with its object counts, the settings and the scenarios; and how to reproduce the results with `just bench showcase` and `just bench publish`.

The page computes no number that a document does not hold, except the ratio of a number of a B5 step to the number of `zeo` in the same step. It rounds the numbers to three significant digits and scales their units. `bench/shootout/tests/test_dashboard.py` publishes the samples of `bench/shootout/tests/data/publish` and `bench/shootout/tests/data/dashboard` into an empty checkout, runs `data.js` under node, and compares its data with the documents. It also checks the requests and the dark mode of the page. A test cannot live in `dashboard/`, because `publish` copies each tracked file of that directory.

## The reference machine

The numbers mean something only when they come from one fixed machine. For now the reference machine is a developer workstation; a dedicated runner can replace it later. Every result names its machine, so results from another machine never mix with the baseline on the dashboard.
