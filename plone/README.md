# Plone instances

The Plone instances that the suites and the benchmarks run against. zc.buildout builds them; `just plone` is the entry point. One configuration per scenario:

| File | Storage |
| --- | --- |
| `filestorage.cfg` | FileStorage, the baseline |
| `zeo.cfg` | a ZEO 6 server and a ZEO client, the baseline |
| `zoe.cfg` | the in-process `<zoe>` storage |
| `zeoclient.cfg` | a stock ZEO client of `zoe serve`, without zoedb |
| `zoeclient.cfg` | `zoe.zeo.ClientStorage` (`<zoeclient>`) against `zoe serve`, with `zoedb[plone]` |
| `zeoclient-mount.cfg` | two ZEO clients of one `zoe serve`, the second at the mount point `/content` |

`just plone <scenario>` builds a scenario and starts its instance in the foreground. `just plone <scenario> build` only builds it. `just plone <scenario> check` runs `set_admin.py` and `create_site.py` in the instance, which create the admin user and a Plone site. Then it starts the instance, and `read_site.py` reads the page of the site over HTTP. A new mark in the title of the site tells that the page comes from this instance. The instances listen on 127.0.0.1, on the port `ZOE_PLONE_PORT`, 8080 by default.

The zeoclient scenario runs against `zoe serve`, which is not a buildout part. `just plone zeoclient check` builds the `zoe` binary with cargo, into `CARGO_TARGET_DIR` or `target`. It starts `zoe serve` on the store `target/plone/zeoclient/var/zoe`, on `127.0.0.1:8100`, the `zeo-address` of `zeoclient.cfg`. zoe serve speaks only the msgpack protocol `M5`, so the instance of the scenario has the `msgpack` egg: it installs no zoedb, whose `plone` extra gives `msgpack`. The server gets no `ZOE_*` variable of the caller, and writes its log to `target/plone/zeoclient/var/log/zoe-serve.log`. The recipe waits until the server listens, then runs the check through the ZEO client. At the end, also when a step fails, it stops the instance, then stops the server with SIGTERM, so the store closes cleanly. `just plone zeoclient` and `just plone zeoclient build` do not start a server.

The zoeclient scenario is the zeoclient scenario with the client of zoedb: `zoe.zeo.ClientStorage`, the `<zoeclient>` section, which declares the ZOE extensions to the server, so the instance gets the sequences of the store. The instance has `zoedb[plone]`, so Plone loads `zoe.plone`. plone.recipe.zope2instance cannot write a `<zoeclient>` section, so `zoeclient.cfg` renders `templates/zoeclient.conf.in` into the instance, as `zoe.cfg` does. The client connects to `127.0.0.1:8100` with the storage name `1`. `just plone zoeclient check` starts `zoe serve` on `target/plone/zoeclient/var/zoe`, as the zeoclient check does.

The zoe scenario also has `zoedb[plone]`. The zeoclient scenario stays stock: its instance has no zoedb.

`just plone <scenario> creators THREADS ITEMS SEED` measures the conflicts of new content on `portal_uidgenerator`, on zoe, zeoclient and zoeclient. It runs `set_admin.py` and `create_site.py` in the instance, then `creators.py THREADS ITEMS SEED`. The script sets `_uid_counter` of `portal_uidgenerator` to SEED, adds the folder `creators` with a history id, and runs THREADS threads, each with its own connection, that create ITEMS Documents each, one transaction for each Document, and retry on `ConflictError`. Its last line of stdout is a JSON report: the Documents created, the seed, the history id of each Document, and the `ConflictError`s by class. For zeoclient and zoeclient, the recipe starts `zoe serve` on a new store, `target/plone/<scenario>/var/creators`, on `127.0.0.1:8100`, and stops it at the end. `plone/tests/test_id_allocation.py` runs it with 50 threads, 4 Documents and the seed 100000.

The zeoclient-mount scenario extends zeoclient. Its instance has two databases in `zope.conf`, each a `<zeoclient>` of the same server: `main` at `/`, with the storage name `main`, and `content` at the mount point `/content`, with the storage name `content` and a blob cache of its own. Plone 6.1 does not ship `Products.ZODBMountPoint`, so the scenario adds it, at version 2.0: version 3.0 makes `Products` a native namespace package, which the `Products` eggs of Plone 6.1 hide. `just plone zeoclient-mount check` starts one `zoe serve` with the two named storages, `--storage main=target/plone/zeoclient-mount/var/main` and `--storage content=target/plone/zeoclient-mount/var/content`, on `127.0.0.1:8100`. Its log is `target/plone/zeoclient-mount/var/log/zoe-serve.log`. `create_site.py MARK /content` adds the mount point when it is missing, then adds the site in the folder `/content`, so the site and its catalog go to the store `content`. The check reads the site at `/content/Plone`, then stops the instance and the server as the zeoclient check does. `just plone zeoclient-mount` and `just plone zeoclient-mount build` do not start a server.

`just plone <scenario> suites` runs the test suites of `Products.CMFPlone`, `plone.app.contenttypes` and `plone.restapi` with the `bin/test` of the scenario: zope.testrunner, with the suites unchanged. The script is the part `test` of `base.cfg`, which the recipe adds to the parts of the scenario for this command only. The options that follow the command go to `bin/test`, for example `just plone zoe suites -t test_folder_view`. zope.testrunner prints a summary, `Total: N tests, F failures, E errors`, at the end.

The layer of `zoe.plone.testing` puts ZOE under the fixtures. The `Startup` layer of plone.testing opens a `DemoStorage` without a base, so its base is a `MappingStorage`; the layers of Plone stack their own `DemoStorage` on top. The layer gives that first `DemoStorage` a ZOE storage as its base, and changes nothing else. The `initialization` of `bin/test` installs it: it makes the layer a base of `Startup`, so zope.testrunner sets it up before `Startup` and tears it down after. The output shows it as `Set up zoe.plone.testing.ZoeStorage` or `Set up zoe.plone.testing.ZoeServe`.

- `just plone zoe suites`: the base is a `zoe.Storage` in a new directory.
- `just plone zeoclient suites`: the base is a `ZEO.ClientStorage` of `zoe serve`. The recipe starts the server on a new store, `target/plone/zeoclient/var/suites`, on `127.0.0.1` and a free port, and gives its address to the layer in `ZOE_PLONE_ZEO_ADDRESS`. The server gets no `ZOE_*` variable of the caller, and writes its log to `target/plone/zeoclient/var/log/zoe-serve-suites.log`. At the end, also when `bin/test` fails, the recipe stops it with SIGTERM.
- `just plone filestorage suites`: the stock storages of plone.testing, without the layer. It is the baseline: a failure that also occurs here does not come from ZOE.

No file of the repository holds a password. `ZOE_PLONE_ADMIN` gives the admin user of the instances as `user:password`. Without it, `just plone` writes a random password once to `target/plone/admin`, which only the user can read, and prints that path. The password never goes on a command line or into a file of the build: buildout gets only the user name, with an empty password, so zope2instance writes no `inituser` file. Before the instance starts, `set_admin.py` runs in it and gives that user the Manager role and the password. `set_admin.py`, `create_site.py` and `read_site.py` read the admin user from `ZOE_PLONE_ADMIN`, or else from the file that `ZOE_PLONE_ADMIN_FILE` names.

`versions.cfg` pins the Plone 6.1 release, and `requirements.txt` gives zc.buildout and its tools at the versions of that release. The build goes to `target/plone`: the scenarios share the eggs and the downloads, and each scenario has its own directory for its scripts, parts and data. `just plone` builds the `zoedb` wheel, installs it into `target/plone/zoedb` and links it as a develop egg, so each build takes the current code.

`templates/zope.conf.in` carries the `<zoe>` stanza. plone.recipe.zope2instance cannot write it, so `zoe.cfg` renders the template with collective.recipe.template into the instance. The instances run on CPython 3.13, the newest version that Plone 6.1 supports.

The first build needs the network. A later build of the same scenario does not.
